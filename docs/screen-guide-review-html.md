> **이 문서가 답하는 것**: 화면의 이 숫자·이 박스·이 문장이 **어디서 왔는가**. 발표 중 화면
> 옆에 띄워 두고 쓴다.
>
> **왜 동작하는지**는 [architecture/pipeline-walkthrough.md](architecture/pipeline-walkthrough.md) 를 본다.
> **실제 숫자**는 [parsing-output-report.md](parsing-output-report.md).

> 작성 2026-08-05.

## 0. 이 화면은 지금 정확한가

**세 층으로 나눠서 봐야 한다.**

### (a) 데이터에서 계산된 숫자 — **전부 정확** ✅

`out/json` · `out/extracted` 를 읽어 그 자리에서 계산하는 값들. `tools/verify_numbers.py` 로
독립 재집계해 대조했고 전부 일치했다.

| 화면 위치 | 대조 결과 |
|---|---|
| 파일별 요약 표 (영역·라인·미배정·found/not_found·미표시) | 5행 전부 일치 |
| 페이지 머리줄 (route·status·canvas·총 n줄·triage) | 7페이지 전부 일치 |
| 커버리지 pill 4개 | 7페이지 전부 일치 |
| ① 최종 파싱 결과 | `llm_view.build_page_view` 를 직접 호출 → `out/llm_view/*.json` 과 **글자 그대로 동일** |
| ② STAGE_3 표 | `out/extracted` 와 일치 |
| ③ 대조 패널의 정본·후보 텍스트 | 일치 |
| ④ 감사용 증거층 (출처 태그·신뢰도) | 일치 |
| ⑤ 판단 로그 | `out/json` 의 `notes[]` 원문 그대로 |

### (b) 코드에 박아 넣은 설명 문장 — **2건 틀림** ❌

데이터가 아니라 사람이 쓴 문장이라 실측이 바뀌어도 자동으로 안 고쳐진다.
**둘 다 화면 위쪽 개요 영역에 있다.**

| 화면 문장 | 실제 |
|---|---|
| "전체 **21줄 중 20줄**은 OCR 이 아예 못 읽어 VLM 이 새로 건진 문구… OCR 출처는 1줄뿐입니다" | **25줄 중 24줄.** OCR 1줄이라는 결론은 맞고 총계만 낡음. `review.html`·`review_parsing.html` 둘 다 |
| "STAGE_3 **5그룹** 분할 호출… 문서당 **5회**" | **상세페이지는 4그룹 46필드.** 올원e 가 실제로 4그룹으로 돌았다. 5그룹 57필드는 이벤트페이지만 |

### (c) 관계 딱지 — **177건 중 7건이 틀린 라벨** ❌

`정본과 불일치 — 원본 확인 필요` / `뒷부분 잘림` 딱지가 ①과 ③에 붙는데, 이게 **라인 정렬이
끝나기 전 순서로 계산**된다. 표의 `라벨|값` 행이 뒤집힌 상태로 비교되면서 오탐이 난다.

```
뒷부분 잘림 → 실제는 앞 항목명 생략   2건  (올원e r006 가입기간, r007 가입금액)
정본과 불일치 → 실제는 표기 차이       4건  (001 의 ①②③④ 목록 항목)
정본과 불일치 → 실제는 앞 항목명 생략   1건  (올원e r010 우대금리)
```

**그래서 ③ 대조 패널의 "확인 필요" 개수가 부풀어 있고**, 위험한 것부터 정렬하는 로직 때문에
오탐이 목록 맨 위에 올라온다. 001 의 "불일치 9건"은 **실제 5건**.
자세한 원인은 [walkthrough §9-②](architecture/pipeline-walkthrough.md).

### 중요한 구분 — 화면은 판정하지 않는다

발표대본에는 002 `인생 대박적금이 온대` 건을 **"후보(온다!)가 맞음"** 이라고 써 놨는데, 원본
PNG 를 크롭해 보니 **원본이 "온대!"** 다. 정본이 맞고 후보가 틀렸다.

**그런데 화면은 틀리지 않았다.** 화면은 `정본과 불일치 — 원본 확인 필요` 라고만 하고 어느 쪽이
맞다고 주장하지 않는다. 설계대로 동작한 것이고, **틀린 건 대본의 주석**이다.
**화면은 "확인하라"고만 한다** — 이 구분을 잡아 두면 질문에 흔들리지 않는다.

**정리: 화면의 숫자는 신뢰해도 된다. 위쪽 개요의 설명 문장 2곳과 관계 딱지 7건이 손볼 대상이다.**

## 1. 화면 전체 구조

```
NH 광고심의 파싱 결과 리뷰                              ← ①  제목
├ 이 화면은 무엇인가 (고정, 안 접힘)
│  ├ (파싱 전용판만) 노란 범위 배너                      ← ②
│  ├ 소개 문단 — "위반 판정은 하지 않는다"                ← ③
│  ├ 처리 단계 SVG 도식 — 6레인 + 주체 범례               ← ④
│  ├ [토글] 단계별 설명 (글로 보기)                       ← ⑤
│  ├ "이 배치가 원칙입니다" 문단                          ← ⑥
│  ├ 산출물 3개 박스                                     ← ⑦
│  ├ "이 화면 보는 법" 문단                               ← ⑧
│  └ [토글] 용어 사전                                     ← ⑨
├ 파일별 요약 표                                          ← ⑩
└ 문서 5개 블록 (각각)
   ├ 문서 머리줄 — 파일명 · 분류 · 파일타입                ← ⑪
   └ 페이지별 (7개)
      ├ 페이지 머리줄 — route·status·canvas·총n줄·triage  ← ⑫
      ├ 커버리지 pill 4개                                  ← ⑬
      ├ 왼쪽: 미리보기 JPG                                 ← ⑭
      ├ 왼쪽: 영역 라벨 오버레이 (체크박스로 on/off)        ← ⑮
      ├ 왼쪽: STAGE_3 근거 hover 하이라이트                 ← ⑯
      └ 오른쪽 토글
         ① 최종 파싱 결과 (LLM 에 넘기는 형태)              ← ⑰
         ② STAGE_3 스키마 추출 결과                        ← ⑱  (파싱 전용판엔 없음)
         ③ OCR 정본 ↔ VLM 통독 후보 대조                   ← ⑲
         ④ 감사용 원본 증거층 — 한 줄씩 쪼갠 그대로          ← ⑳
         ⑤ 파이프라인 판단 로그                            ← ㉑
```

**첫 번째로 잡아야 할 구분**: **⑨까지는 전부 "코드에 박아넣은 설명문"이고, ⑩부터가 실제
데이터다.** 그래서 §0-(b) 의 오류 2건이 전부 위쪽에 있다.

**두 판의 차이**: `review_parsing.html` 은 `out/extracted` 를 **아예 안 읽는다.** 그래서
⑱(② STAGE_3 표)과 ⑯(근거 하이라이트)이 사라지고, ④ 도식의 5번 레인이 흐려지며
"↓ 여기부터는 오늘 범위 밖" 라벨이 붙는다. 토글 번호(①③④⑤)는 전체판과 맞춰 두었다 —
"②가 빠져 있는데 그게 스키마 추출입니다"라고 말하면 된다.

## 3. 커버리지 pill 4개 — 정확히 무엇을 세나

```
[영역 50개]  [라인 74줄]  [미배정 1줄 · VLM 회수 1 · OCR 0]  [저신뢰(<0.8) 1줄]
```

| pill | 정의 | 높은 게 좋은가 |
|---|---|---|
| **영역 n개** | `regions` 개수. **글자가 안 붙은 빈 검출 박스도 센다** | **품질 아님.** 화면을 몇 덩어리로 검출했나일 뿐 |
| **라인 n줄** | 영역에 붙은 줄 + 미배정 줄 | ↑ 많을수록 좋음 (잡은 글자 조각 총수) |
| **미배정 n줄** | 어느 영역에도 안 붙은 낱줄. 괄호에 출처별로 갈라 표시 | **총계는 의미 없음.** 괄호의 **OCR 숫자만** 낮을수록 좋음 |
| **저신뢰 n줄** | 영역 안 라인 중 OCR `confidence < 0.8` | ↓ 낮을수록 좋지만 내용을 봐야 함 |

**미배정을 왜 출처별로 가르나.** 그냥 "미배정 13줄"로 보이면 "13줄을 못 붙였다 = 결함"으로
읽히는데 실측은 정반대다. 5문서 전체 **25줄 중 24줄이 `vlm_sweep`** — OCR 이 **아예 못 읽어서**
통짜 스윕이 새로 건져온 문구다. 그 라인은 좌표가 밴드 근사값이라 **일부러 영역에 안 붙인다**
(좌표를 못 믿는 걸 붙이면 근거 지목이 거짓이 된다). 텍스트는 다음 단계로 그대로 전달된다.
**진짜 결함 신호는 OCR 쪽 숫자**이고 5문서 전체에서 **1줄**이다 — 002 의 `0ㅇ`(신뢰도 0.17, 노이즈).

**저신뢰가 무엇인지 실제로 보면** — 002 의 6줄:

```
p1_r000  conf 0.00  ''      ← 인식 결과가 빈 검출
p1_r004  conf 0.00  ''
p1_r013  conf 0.69  '*'     ← 장식 별표
p1_r013  conf 0.45  '*'
p1_r013  conf 0.37  '*'
p1_r025  conf 0.00  ''
```

**별표 3개 + 빈 검출 3개.** 실질 손실이 없다. 001 의 20줄에는 진짜 오독(`생학해대`,
`오의요도과기`)이 섞여 있고 그게 ⑬ 재판독 대상이 된다.

## 4. 함정 4개 — 질문이 나오면 여기서 막힌다

### 함정 ① ①과 ④는 같은 데이터인데 왜 다르게 보이나

```
④ 증거층 (원자료)              ① 최종 파싱 결과 (정제본)
  O 0.99 상품명                  p1_r004  본문
  O 0.99 NH올원e적금                상품명 NH올원e적금
  ↑ 박스마다 한 줄               ↑ 같은 행 조각을 공백으로 이어붙임
```

①은 `_rows_from_lines` 가 **세로로 50% 이상 겹치는 이웃 라인을 한 행으로 합친다.** OCR 은 한
시각적 줄을 여러 박스로 쪼개기 때문(`1천원 이상` | `30만원` | `이하(원단위)` 가 같은 y 에 x 만
다르게). 그래서 **④의 줄 수 > ①의 줄 수**가 정상이다.

### 함정 ② "후보 부착"보다 화면에 적게 나오는 이유

숫자가 세 군데에서 다르다.

```
out/json 에 부착된 영역 후보   177개    ← 저장
① 에 나란히 표시되는 것        124개    ← 정본과 '다를 때만'
③ 에 모아지는 것              그보다 적음  ← 관계가 same 이고 문자열도 완전 같으면 제외
```

같은 것을 굳이 보여줄 이유가 없어 단계마다 걸러낸다.
**"부착 = 저장" / "표시 = 다를 때만"** — 이 구분을 잡아 두면 된다.

문서별 부착 → 표시: 올원e 35→27 · 001 56→35 · 002 41→25 · 003 45→37.

### 함정 ③ 왼쪽 영역 번호와 오른쪽 번호가 달라 보이는 경우

원인이 **두 가지**이고 **둘 다 이미 고쳐져 있다.**

1. **빈 박스가 실제 영역 이름을 덮었던 것** — PP-StructureV3 가 거의 같은 자리에 레이아웃
   박스를 두 번 낸다. 올원e `r017`[113,2949,1055,3051] ↔ `r019`[113,2950,1056,3050] **1px 차이**.
   우리 중복 제거는 좌표 완전일치만 걸러서 둘 다 남고 글자는 한쪽에만 붙는다. 라벨이 같은
   자리에 겹쳐 그려져 **빈 껍데기 이름이 실제 영역 이름을 덮었다** → 빈 박스를 **먼저·흐리게**
   그려서 해결.
2. **둘 다 실제 영역인데 왼쪽 위 모서리가 같았던 것** — 올원e `r018`[129,3097,1070,3139 · 각주]과
   `r020`[130,3097,1068,3197 · 본문]. 레이아웃 검출이 `r020` 사각형을 실제 글자(y=3158~)보다
   위(y=3097)까지 넓게 잡아 모서리가 겹쳤다 → 겹치면 **뒤엣것을 24px 아래로 밀어낸다.**

**핵심: 데이터는 틀리지 않았다.** 텍스트 배정은 정확했고 **라벨이 화면에서 안 보였을 뿐**이다.

**빈 박스는 몇 개인가** — 225개 중 **24개(10.7%)**. 글자 손실은 없고 박스만 남는다.
근본 해결(겹침 비율로 제거)은 재파싱이 필요해 보류 중.

### 함정 ④ 영역 박스가 실제 글자보다 넓은 경우

003 미리보기를 보면 `지원금 10만원 / (선착순 1,000팀)` 영역 박스가 아래 페이지 꼬리표
`내지1` 까지 삼키고 있다. 낱줄 귀속이 세로로 가까운 같은 칼럼 낱줄을 붙이면서 **박스가 커진**
결과다([walkthrough §4.3](architecture/pipeline-walkthrough.md)).

**이게 세 현상의 공통 원인이다**: (1) 영역 bbox 가 글자보다 넓음(200개 중 10개가 상단 20px+
초과), (2) `내지1`·`내지2`·`표지` 꼬리표가 본문 영역에 붙음, (3) 그 탓에 003 `p1_r011` 에
**잘림 경보가 잘못 뜸**(VLM 이 `내지1` 을 안 읽은 게 "뒷부분 25% 소실"로 잡힘).

읽기순서에는 영향이 없다 — 정렬은 bbox 가 아니라 **라인 좌표**로 하기 때문. hover 하이라이트가
실제 글자보다 크게 잡히는 것만 남은 한계다.

## 6. 화면을 다시 만드는 법

```bash
uv run python tools/make_review.py                                          # 전체판 → out/review.html
uv run python tools/make_review.py --parsing-only --out out/review_parsing.html   # 파싱 전용
uv run python tools/make_review.py --only 003                               # 한 문서만
```

`out/json` 만 있으면 만들어진다. `out/extracted` 가 없는 문서(004 대출성)는 ② 블록이 조용히
생략된다. **모델 호출 0회**이므로 화면만 고칠 때 재파싱이 필요 없다.
