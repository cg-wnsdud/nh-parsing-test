## 1. B3 — 잘못된 "잘림 경보"가 뜨던 문제 ⭐ 유일하게 판정을 바꾼 항목

### 문제

파이프라인은 같은 글자를 **두 번** 읽습니다.

- **정본(正本)**: OCR 이 읽은 것. 이게 기준값입니다.
- **후보**: VLM(이미지를 읽는 AI)이 다시 읽은 것. 참고용입니다.

둘을 비교해서 **"딱지"** 를 붙입니다. 딱지는 다섯 종류입니다:

| 딱지 | 뜻 | 심각도 |
|---|---|---|
| `same` | 표기만 다름 | 문제 없음 |
| `head_drop` | 후보가 **앞의 항목명만 뺐음**, 값은 온전 | 문제 없음 |
| `tail_cut` | 후보의 **뒷부분이 잘렸음** | ⚠️ 위험 |
| `expanded` | 후보가 더 많이 읽음 | 참고 |
| `diverged` | 서로 다름 | ⚠️ 사람이 확인 |

그런데 이 딱지를 **글자 줄을 제대로 정리하기 전에** 붙이고 있었습니다.

표 형태 영역이 문제였습니다. 올원e적금의 실제 사례:

```
원본 화면에 보이는 것:      가입기간   |   12 개월
                          (라벨)        (값)

두 칸의 실제 좌표:
  '가입기간'  bbox=[ 69, 1218, 241, 1272]   ← 위쪽 좌표 1218
  '12 개월'   bbox=[408, 1216, 562, 1275]   ← 위쪽 좌표 1216  (2px 위)
```

**표 한 줄의 두 칸이 2px 어긋나 있습니다.** 인쇄물에선 정상입니다. 그런데 코드가 처음에
줄을 "위에서 아래로" 단순 정렬하면 **값이 라벨보다 앞으로 옵니다**:

```
정리 전 정본 :  "12 개월 가입기간"     ← 순서가 뒤집힘
후보         :  "12 개월"

  → 코드가 보기엔 뒤쪽 '가입기간' 이 사라진 것 → tail_cut "뒷부분 잘림"  ❌ 틀린 딱지
```

정리를 마치면 순서가 바로잡힙니다:

```
정리 후 정본 :  "가입기간 12 개월"     ← 화면에 보이는 대로
후보         :  "12 개월"

  → 앞쪽 '가입기간' 만 빠진 것 → head_drop "앞 항목명 생략"      ✅ 맞는 답
```

**왜 이게 실무 문제였나.** 검수 화면은 "확인 필요" 목록을 **위험한 것부터** 정렬합니다.
`tail_cut`(잘림)은 위험, `head_drop`(항목명 생략)은 무해합니다. 그래서 **가짜 잘림 경보가
검수자가 가장 먼저 보는 자리에 올라오고 있었습니다.**

### 무엇을 바꿨나

딱지 붙이는 계산을 **줄 정리가 끝난 뒤로 옮겼습니다.** 새 함수
`_score_reading_candidates` 하나를 만들어 마지막에 부릅니다.

옮기면서 알게 된 게 하나 더 있습니다 — 줄 정리 말고도 **정본을 바꾸는 단계가 하나 더**
뒤에 있었습니다. 같은 줄을 겹쳐 검출한 "유령 조각"을 지우는 단계입니다. 그것까지 끝난
뒤에 재야 진짜 최종 정본입니다.

### 결과

| | 전 (8/4) | 후 (8/6) |
|---|---|---|
| 저장된 딱지 vs 다시 계산한 딱지 **불일치** | **18건** | **0건** |
| `tail_cut` (위험 딱지) | 8건 | **6건** |
| `head_drop` (무해 딱지) | 5건 | **8건** |

가짜 잘림 경보가 사라지고 무해 판정으로 바뀌었습니다. **글자 자체는 하나도 안 바뀝니다** —
딱지(라벨)만 바뀝니다.

> 참고: 순서 문제만 따로 재면 **11건**입니다(라인 2개 이상인 후보 99건 중).
> 나머지 7건은 오늘 오전에 커밋한 다른 수정(숫자 게이트) 몫이라 원인이 다릅니다.
> `verify_numbers.py --section relation` 이 이 셋을 원인별로 갈라서 보여줍니다.

## 2. B4a — "파일명으로 정했다"가 세 가지 다른 상황을 뭉치던 문제

### 문제

광고물이 예금성인지 대출성인지 정할 때 **두 근거**를 씁니다:

- **파일명 힌트**: `NH농협은행-2026_003-예금성.pdf` → "예금성"
- **VLM 관측**: 이미지를 보고 판단

결과를 `category_source` 에 기록하는데, `"filename"`(파일명으로 정함) 하나가 **완전히 다른
세 상황**을 뭉치고 있었습니다:

| 실제 상황 | 신뢰도 | 옛 기록 |
|---|---|---|
| VLM 이 보고 **"금융상품 광고가 아니다"라고 반대**했는데 파일명이 이김 | 근거 있음, 다만 충돌 | `filename` |
| VLM 호출이 **실패**(서버 죽음)해서 파일명밖에 없음 | 근거 없음 | `filename` |
| HWP 라서 VLM 을 **애초에 안 부름**(이미지가 없음) | 물어본 적 없음 | `filename` |

**003 이 첫 번째 경우입니다.** VLM 이 확신도 0.9 로 이렇게 답했습니다:

> "특정 금융상품(예금/대출)의 가입 유도보다는 **'올원모임' 서비스 이용 활성화를 위한
> 경품 증정 이벤트** 내용을 담고 있습니다."

그런데 산출물에는 이 문장만 남고 "VLM 이 반대했다"는 사실이 안 남아서, **VLM 도 동의한
것처럼 보였습니다.** 이게 중요한 이유는 이 판정으로 **어떤 심의 스키마를 쓸지가
결정되기 때문**입니다(예금성 팩 46개 필드 vs 다른 팩).

### 무엇을 바꿨나

세 상황을 각각 다른 값으로 적습니다. 그리고 VLM 이 반대한 경우 **VLM 이 뭐라고
답했는지와 확신도를 사유에 함께** 적습니다.

### 결과

재실행하니 5문서가 네 가지 값으로 갈렸습니다:

| 문서 | 값 | 읽는 법 |
|---|---|---|
| 올원e · 001 · 002 | `filename_and_vlm` | 파일명과 VLM 이 **합의** |
| **003** | **`filename_vlm_abstained`** | **VLM 이 반대했으나 파일명 채택** ← 검수자가 봐야 함 |
| 004 (HWP) | `filename_no_vlm` | VLM 을 **안 물어봄** |

**판정 자체는 안 바꿨습니다** — 5문서 전부 상품군 결과가 동일합니다. 값을 잘게 쪼갠 것뿐입니다.

## 3. B4c — 글자를 "그림처럼 그려 넣은" 페이지를 못 알아채던 문제

### 문제

PDF 는 페이지마다 셋 중 하나로 판정합니다:

| 판정 | 뜻 | 처리 |
|---|---|---|
| `structured` | PDF 안에 글자 데이터가 정상적으로 들어 있음 | **OCR 을 건너뜀** (빠르고 정확) |
| `scan_like` | 스캔 이미지라 글자 데이터가 없음 | OCR 실행 |
| `hybrid` | 글자는 있는데 이미지 비중이 큼 | 둘 다 실행 |

판정 기준 중 하나가 "이미지가 페이지의 몇 %를 덮나"인데, 이걸 **`IMAGE` 라는 종류의
개체만** 세고 있었습니다.

**003 3페이지가 이 사각지대에 있었습니다.** 이 페이지 상단 헤더는 글자를 글자로 넣지 않고
**윤곽선 도형(`PATH`)으로 그려** 놨습니다. 그러면:

- PDF 안의 글자 데이터에도 **없고** (글자가 아니라 도형이니까)
- 이미지 면적 계산에도 **안 잡힙니다** (`IMAGE` 가 아니니까 0%)

→ `structured` 로 판정 → **OCR 을 건너뜀** → 그 글자들이 통째로 사라질 뻔했습니다.

원본을 잘라 좌표까지 대조해 확인했습니다. `PATH` 개체 11개 중 **8개가 낱말 크기**였고
화면의 글자와 위치가 정확히 일치했습니다:

```
[100,  91, 147, 107]  '10/20'          [155,  90, 240, 108]  '인스타그램'
[ 98, 119, 216, 150]  '올원모임'        [227, 120, 345, 151]  '소문내기'
[359, 120, 448, 151]  '이벤트'          [457, 120, 513, 150]  '멘션'
[1776, 79,1910, 101]  'Last Updated'   [1825,114,1911, 128]  '2025.10.15'
```

나머지 3개만 배경·패널·주황띠였습니다. 실제로 PDF 글자 데이터에는 이 헤더가 **한 글자도
안 들어왔고**(첫 글자가 y=190 부터 시작), 다른 단계(전체 화면 훑기)가 **우연히** 3줄을
건졌습니다.

그런데 판정 근거를 적는 `reasons` 가 **빈 배열**이라 "확인할 게 없다"로 읽혔습니다.

### 무엇을 바꿨나

도형(`PATH`) 개수와 면적도 세어서 기록하고, **`structured` 판정일 때만** 경고 한 줄을
남깁니다(`scan_like`·`hybrid` 는 어차피 OCR 이 도니 위험이 없습니다).

**★ 판정은 안 바꿨습니다.** "글자 도형"과 "장식 도형(테두리·구분선)"을 개수나 면적으로
가를 방법이 지금 표본에는 없습니다. 여기서 기준을 만들면 그건 **샘플 하나에 맞춘 규칙**
입니다. 그래서 세어서 남기기만 합니다.

### 결과

003 3페이지의 `reasons` 가 더 이상 비어 있지 않습니다:

```
[주의] 벡터 도형 11개(면적비 1.71) — 글자를 벡터로 그렸으면 텍스트 레이어에도
이미지 면적비에도 안 잡혀 OCR 생략 시 유실된다 (실측 003 p3: 헤더 8낱말).
판정은 유지 — 스윕 회수 결과를 확인할 것
```

`scan_like` 인 3페이지에는 경고가 안 붙습니다(설계대로).

## 4. B6 — 판단 근거가 그냥 버려지던 문제

### 문제

영역의 **역할**(제목/본문/유의사항/각주/버튼/고지문구/이미지 등 9종)은 4단계로 정해집니다:

```
1단계  레이아웃 엔진이 준 라벨(text, doc_title 등)을 role 로 매핑
2단계  코드 규칙 4개가 다듬음         → '※유의사항' 머리말이면 유의사항, 하단 20%면 유의사항 …
3단계  VLM 이 최종 판정               → role 을 통째로 덮어씀
```

문제는 **3단계가 2단계 결과를 흔적 없이 덮어쓴다**는 것이었습니다. 그래서
"규칙과 VLM 이 어디서 얼마나 갈리는지"를 **잴 방법이 없었습니다.**

또 하나, 레이아웃 엔진은 블록마다 **확신도(score)** 를 주는데 그 값이 어디에도 안 남았습니다.

### 무엇을 바꿨나

두 값을 **저장만** 합니다. 판정에는 안 씁니다.

- `role_rule` — 규칙(2단계)이 내린 판정. VLM 이 덮기 **전** 값
- `layout_score` — 레이아웃 엔진의 확신도

`layout_score` 는 처음에 넣었더니 **225개 전부 비어 있었습니다.** 서버 응답을 직접 까
보니 원인이 예상과 달랐습니다 — 서버가 레이아웃을 **두 형태로** 돌려주는데 **확신도가
한쪽에만** 있었습니다:

```
parsing_res_list  ← 우리가 쓰는 목록.  글자 내용·읽기순서 있음, 확신도 없음
layout_det_res    ← 중복이라 버리던 목록.  확신도 있음
```

그래서 두 목록을 **좌표로 이어 붙여** 확신도를 옮겨오게 했습니다.

### 결과 — 이게 오늘의 가장 큰 수확입니다

**규칙과 VLM 이 199건 중 95건에서 갈립니다.** 어디서 갈리는지가 처음 보였습니다:

| 규칙 판정 → VLM 판정 | 건수 | 읽는 법 |
|---|--:|---|
| 본문 → 유의사항 | 26 | 규칙은 `※유의사항` 머리말·하단20% 로만 잡음. VLM 이 훨씬 많이 찾음 |
| 본문 → 제목 | 22 | **규칙에 제목 판정이 아예 없음** |
| 본문 → 이미지 | 13 | 규칙은 그림을 못 가름 |
| **유의사항 → 제목** | **10** | **⚠️ 하단 20% 규칙이 제목을 유의사항으로 오판** |
| 본문 → 각주 | 6 | |
| 나머지 11종 | 18 | |

> ⚠️ **이 숫자를 기존 문서의 "역할 판정 97.3% 일치"와 섞으면 안 됩니다.**
> - **97.3%** = VLM 을 **두 번 돌렸을 때** 같은 답이 나오는 비율 (재현성)
> - **52.3%** = **규칙과 VLM** 이라는 서로 다른 판정자가 같은 답을 내는 비율 (일치도)
>
> 규칙은 4개짜리 임시 폴백이라 낮은 게 정상입니다. 값은 숫자가 아니라 **"어디서 갈리나"** 에 있습니다.

그리고 **가설 하나가 기각됐습니다.** "레이아웃 엔진이 헷갈린 자리에서 판정도 갈릴 것"이라고
예상했는데, 실측은 반대였습니다:

```
layout_score 평균 —  일치한 것 0.576 (104건)   vs   갈린 것 0.626 (93건)
```

갈린 쪽이 오히려 확신도가 **높습니다.** 이 방향은 더 파지 않는 게 맞습니다.

## 5. B5 — 절대 발동할 수 없던 지시문

### 문제

STAGE_3(필드 뽑기) 프롬프트의 규칙 8이 이렇게 시작했습니다:

> "**섹션 제목에 "예시·목업 화면"이라고 붙은 곳은** 앱 화면 목업입니다. 거기 적힌 금액은…"

그런데 "섹션"은 2026-08-03 에 파이프라인에서 제거됐습니다. 즉 **그 표시가 나올 경로가
원리적으로 없습니다.** 확인해 보니 더 죽어 있었습니다 — 목업 표시용 플래그
(`is_illustrative`)가 **코드 어디에서도 켜지지 않습니다.** 읽는 곳 3군데가 전부 항상
거짓입니다.

**죽은 지시문은 조용합니다.** 규칙이 "…라고 표시된 곳은" 이라고 말하는데 그 표시가 안
나오면, AI 는 규칙 전체를 건너뛰고 **우리는 규칙이 도는 줄 압니다.**

### 무엇을 바꿨나

**불가능한 전제절만 빼고 지시 내용은 유지했습니다.** 견본 여부를 *주변 문구로 판단*하라고
바꿨습니다(메뉴 이름·버튼 글자·사람 이름이 함께 나오면 견본).

목업 격리 로직을 되살리지는 **않았습니다.** 지금 STAGE_3 가 내용으로 잘 걸러내고 있고
(001 앱 화면의 `100,000원`·`NH0000통장` 이 필드가 아니라 "심의무관"으로 감), 코드 게이트를
넣으면 오판이 **진짜 심의 대상을 조용히 빼버릴** 위험이 있습니다.

### 결과

프롬프트가 실제로 화면에 찍히는 것만 참조하는지 검사하는 테스트를 추가했습니다.
이 테스트는 "섹션"이라는 단어가 프롬프트에 다시 들어오면 실패합니다.

## 6. B4b · B7 — 조용히 실패하던 자리들

파이프라인의 원칙 중 하나가 **"조용한 실패 금지"** 입니다. 오늘 그 원칙이 안 지켜지던
자리 세 곳을 찾았습니다.

### 6-1. 역할 판정이 일부만 응답해도 기록이 없었다 (B4b)

VLM 에게 영역 50개의 역할을 물으면 45개만 답하고 5개를 빠뜨릴 수 있습니다. 코드는 이
경우를 **예외로 취급하지 않아서**(정상 응답이니까) 나머지 5개는 조용히 규칙 판정값을
유지하고 아무 기록도 안 남겼습니다.

→ 몇 개 중 몇 개가 답변됐는지 세어서 기록합니다. 빈 검출 박스(글자 없는 껍데기, 225개 중
24개)는 애초에 안 물어보므로 분모에서 뺍니다.

### 6-2. 밴드 판독이 0건을 돌려줘도 이유가 안 남았다 (B7) ⭐ 오늘 실제로 터짐

한 화면 조각의 영역들을 VLM 에게 한꺼번에 읽히는 단계가 있습니다. 오늘 재파싱에서
**003 2페이지가 영역 22개 중 0개**만 판독됐습니다. 예외는 없었습니다. 직전 실행은 22/22 였습니다.

원인을 못 가린 이유는 **응답을 버리는 자리가 셋인데 전부 조용했기** 때문입니다:
모르는 영역 ID / 빈 텍스트 / 형식 파손.

→ 넷(응답에 아예 없음 포함)을 각각 세어서 기록합니다. 버리는 규칙 자체는 그대로 둡니다.

같은 페이지를 다시 파싱하니 22/22 로 정상이었습니다 — **간헐적 서버측 결함**입니다.

### 6-3. 러너가 "전량 실패"를 "완료"로 찍고 있었다 ⭐ 오늘 실제로 당함

오늘 첫 재파싱에서 **VLM 호출 56회가 전부 실패**했는데 러너는 **`exit 0` 에 "완료."** 를
찍었습니다. 원인은 사내 게이트웨이가 모델 이름을 바꿔서였습니다
(`gemma-4-26b-…` → **`spark-gemma-4-26b-…`**).

겉으로 보이는 것이 전부 정상 같았습니다:

| 보이던 것 | 실제 |
|---|---|
| `VLM호출=56` | 실패한 호출도 카운터에 잡힘 |
| `452초` | 추론이 아니라 **3회 재시도 + 대기시간** |
| `영역 225개` | OCR 은 멀쩡히 돌았음. 죽은 건 VLM 단계뿐 |
| 파일별 시간표 정상 | — |

유일한 단서가 **라인 수가 509 → 485 로 24줄 줄어든 것**뿐이었습니다.

→ 두 가지 검사를 넣었습니다:

- **약한 신호**: 실패 메시지 개수를 세어 표에 열로 표시
- **강한 신호**: *산출물 자체를 봄* — 화면이 있고 글자도 붙었는데 판독 후보가 0건이면
  그 페이지의 VLM 경로는 죽은 것. 이 경우 **종료코드 1** 로 올립니다

강한 신호를 쓰는 이유는 **에러 메시지 형식이 바뀌어도 살아남기** 때문입니다.
그리고 이 가드를 넣자마자 위 6-2 의 결함을 잡아냈습니다.

> ⚠️ **팀 공유 필요**: 모델 이름이 바뀌었으므로 **다른 분들 `.env` 도 전부 깨져 있습니다.**
> 현재 이름 확인: `GEMMA_URL` 의 `/chat/completions` 를 `/models` 로 바꿔 GET.

## 7. 도구 개선 — 파일별 소요시간

팀장님 요청 건입니다. `tools/run_nhdata.py` 가 파일별 표를 찍고 `out/_timing.json` 에도

## 8. 오늘 알게 된 것 — 코드 변경이 아닌 사실들

### 8-1. STAGE_3 필드 회수는 실행마다 흔들린다

**같은 코드·같은 입력으로 42/44 ↔ 43/44 가 나옵니다.** 오늘 직접 확인했습니다.

원인은 "전수수집 배열"입니다. 예를 들어 `prize_mentions` 는 경품 관련 문구를 **전부**
모으라는 필드인데, 실행에 따라 3개 중 2개만 모읍니다. 빠진 값은 코드 검산 장치
(`unused_figures`, 미실린 수치)가 잡아냅니다 — 안전망은 작동합니다.

> **"43/44" 를 고정값처럼 대외 자료에 못 박으면 안 됩니다.** "42~43/44" 로 쓰거나,
> 복수 실행 결과를 함께 적어야 합니다.

### 8-2. 003 광고 자체에 불일치가 있다 (심의 지적거리)

`1,000명` 이 왜 안 잡혔는지 원본을 잘라 보다가 찾았습니다:

| 위치 | 원본 문구 | 조건 |
|---|---|---|
| p1_r003 | "추첨을 통해 총 **1,000명** / 모임지원금 10만원 지급!" | **추첨** |
| p1_r011 | "지원금 10만원 (선착순 **1,000팀**)" | **선착순** |

**같은 광고가 한 곳에선 추첨, 다른 곳에선 선착순이라고 씁니다.** 추첨과 선착순은 소비자
입장에서 조건이 전혀 다릅니다. OCR 오류가 아니라 광고 자체의 문제이고, 파싱은 두 문구를
정확히 잡았습니다.

이건 **"원본 이미지로 대조하라"는 규칙이 또 한 번 값을 한 사례**입니다. JSON 만 봤으면
"파싱이 놓쳤다"로 끝났을 겁니다.
