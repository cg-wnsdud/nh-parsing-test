## 1. 30초 요약

```
[트랙 A]  규정문서(법령·준수사항)  →  우리 파싱  →  _hrc.jsonl  →  농협 KL 이 벡터DB 적재
          ★ 검색당하는 쪽 = 지식.  KL 규격을 지켜야 하는 유일한 지점

[트랙 B]  광고물(심의 대상)  →  우리 파싱  →  스키마 추출(필드 값 + 근거 좌표)
          ★ 검색하는 쪽 = 질문.  KL 에 적재하지 않는다 (규격에 좌표 칸이 없다)
                    ↓
          이 값들로 벡터DB(트랙 A 결과)와 RDB 를 조회해서 심의 결과를 만든다
                    ↑
          ★ 이 단계는 아직 아무도 만들지 않았다 — RAG/RDB 담당자와 여기서 만난다
```

**한 줄로**: 규정문서는 사전에 넣는 내용이고, 광고물 스키마 결과는 그 사전을 찾을 때 쓰는
검색어다. 둘이 같은 형식일 이유가 없고 실제로 다르다.

## 2. 배경 — 우리는 무엇을 만들고 있나

NH농협은행 준법감시부는 은행이 내보내는 광고물이 금융 규정을 지켰는지 **사전·사후 심의**한다.
사람이 체크리스트를 들고 광고 이미지를 눈으로 대조하는 일이다. 이 PoC 는 그 일을 돕는다.

**우리(파싱·스키마 트랙)가 맡은 것은 "광고물에서 심의에 필요한 값을 뽑아내는 것"까지다.**
판정은 하지 않는다 — 판정에는 규정 조문이 필요하고, 그건 RAG 로 찾아와야 한다.

### 왜 이렇게 복잡한가 — 입력이 이미지다

광고물이 워드 문서가 아니다. **세로로 8,000픽셀 넘는 상세페이지 이미지, SNS 카드 이미지,
스캔된 PDF** 다. 글자를 도형으로 그려 넣은 것도 있다. 그래서:

- 이미지에서 글자를 읽어야 한다 (OCR)
- 어디까지가 "한 덩어리"인지 나눠야 한다 (레이아웃 영역 검출)
- OCR 이 놓친 것·틀리게 읽은 것을 다시 확인해야 한다 (VLM = 이미지를 보고 답하는 AI)

실측: 문서당 평균 **162초**, VLM 호출 **11.9회**, 처리 시간의 **98%가 AI 대기**.

### 배포 방식이 바뀐 이력 (알아 두면 문서가 이해된다)

| 시점 | 전제 |
|---|---|
| 협의 전 | 우리가 장비(DGX Spark 등)에 서비스를 올려 납품 |
| **2026-08-19 회의 이후** | **농협 폐쇄망 안, 농협 플랫폼(DAP)의 문서처리 파이프라인에 "커스텀 파서"로 꽂는다.** 농협도 이런 협업이 처음이라 "문서로 확정하기보다 프로토타입을 완성해 가서 부딪혀 보고 현장에서 조율" 하기로 결론 |

농협 규격 전체 해설은 [농협KL연동_개발가능성_설명_2026-08-18.md](농협KL연동_개발가능성_설명_2026-08-18.md) 에 있다.

## 3. 큰 그림 — 트랙이 둘이다

**이 표를 놓치면 문서 전체가 헷갈린다.**

| | **트랙 A — 규정문서** | **트랙 B — 광고물** |
|---|---|---|
| 무엇 | 법령·심의사례·은행연합회 준수사항 | 심의 대상 광고물 |
| 예 | `(2023년)예금성상품 광고시 준수사항_은행연합회.hwp` | `1. 대출성상품.pdf` |
| 목적 | **검색당하는 쪽 = 지식** | **검색하는 쪽 = 질문** |
| 우리 스키마를 쓰나 | **안 씀** | **씀** (예금성 62필드 / 대출성 69필드) |
| 산출물 | `RagChunk` 목록 — 제목 + 텍스트 덩어리 | 필드가 채워진 JSON (최상위 21키) |
| 좌표가 필요한가 | 아니오 | **예 — 본질** ("이 지적의 근거가 원본 어디인지" 표시) |
| KL 에 적재하나 | **한다** (`_hrc.jsonl` 규격) | **안 한다** |
| 최종 저장 위치 | 농협 벡터DB (KL 이 넣는다) | 관계형 DB (PostgreSQL) — **우리가 제안할 사항** |

### 왜 광고물은 KL 에 안 넣는가

농협 KL 의 출력 규격이 허용하는 `item` 은 **`text` / `table` / `image` / `h1`~`h4`** 뿐이고,
부가정보를 담을 곳은 `cust_meta` (문자열 key-value, item 당 15칸)다.
좌표·역할·신뢰도를 담을 **전용 필드가 없다**.

우리 광고물 산출물은 영역마다 이런 것을 갖고 있다 (실제 값, [`out_new/json/1. 대출성상품.json`]):

```json
{ "region_id": "p1_r000",
  "bbox": [66, 35, 345, 118],        ← 좌표
  "role": "제목", "role_confidence": 0.9, "role_source": "vlm",
  "lines": [{"text": "금융의모든순간", "bbox": [69,44,308,96],
             "confidence": 0.99996, "source": "ocr"}],
  "vlm_reading": "금융의 모든 순간*", "vlm_reading_score": 1.0 }
```

광고물을 KL 규격으로 바꾸면 **위 정보 대부분을 버려야 한다.** 그런데 심의는 그게 본질이다.
그리고 광고 입력물 자체를 검색 인덱스에 쌓을 이유도 없다 — 검색해야 하는 건 규정이다.

> **정리**: 광고물은 파싱·스키마 추출까지 하고 **결과를 질의어로 써서** 트랙 A 가 쌓아 둔
> 벡터DB 와 RDB 를 조회한다. 그게 §7 이다.

### 4-3. ★ 왜 농협 기본 파서가 아니라 우리 커스텀 파서인가 — 실측 근거 2건

이게 **우리가 이 자리에 있는 이유**다. 둘 다 실제로 측정한 사례다.

**① 규정의 실질 기준이 이미지 안에 있다**

`(2023년)예금성상품 광고시 준수사항` HWP 에는 **금리 표기 사례 스크린샷 10장**이 들어 있다.
"최고금리를 이렇게 쓰면 안 된다"는 판단 기준이 **그림 안에** 있다. 일반 파서는 이미지 안
글자를 못 읽으니 이 지식이 인덱스에 안 들어간다.

우리는 VLM 으로 캡션(전사 + 설명)을 만들어 텍스트로 넣는다. 실측 9개 (1개는 장식 이미지로
크기 필터에 걸려 제외):

```
[이미지 사례 img10] 특정 금리(연 4.00%)를 강조하여 보여주는 사례로, 연보라색
하이라이트를 통해 금리 정보를 시각적으로 부각하고 있습니다.
이미지 내 텍스트: # 님의 만기예상금액 그대로 가입하기 / 1,000,000원 을 / 1년 동안
보관하면 / 1,040,109원을 받아요 / 연 4.00% 예상이자 40,109원(세전)
```

**② 사내 파서가 스캔 페이지를 조용히 건너뛴다**

`(2025년)대출성 상품 광고시 준수사항` PDF 는 **6쪽 중 3쪽이 스캔형**이다. 사내 파서는 OCR 이
없어 그 페이지를 **아무 경고 없이 건너뛴다**(`page.parse_status == "skipped"`).
2026-08-12 측정 당시 **규정 원문 한 쪽이 RAG 인덱스에 통째로 없었다.**

우리는 그 페이지만 렌더해서 OCR 로 되살린다. 이번 실행 로그:

```
note: 3쪽 OCR 복원 완료 (라인 34개, 283자)
```

근거 주석: [`rag_ingest.py`](../src/nh_parsing/rag_ingest.py) 모듈 상단.

### 4-4. `_hrc.jsonl` 이 실제로 어떻게 생겼나

우리가 만든 실제 출력이다. **`cust_meta` 를 읽는 법이 §4-5 다.**

```jsonl
{"item": "h2", "value": "1. 준수사항"}

{"item": "text", "value": "예금성 상품 광고시 준수사항 (세부기준)", "page": 0,
 "cust_meta": [{"name":"cust_attr1","value":"table"},
               {"name":"cust_attr2","value":"(2023년)…_c000"},
               {"name":"cust_attr4","value":"digital"},
               {"name":"cust_sattr1","value":"(2023년)예금성상품 광고시 준수사항_은행연합회"},
               {"name":"cust_sattr2","value":"예금성"}]}

{"item": "text", "value": "[이미지 사례 img10] 특정 금리(연 4.00%)를 강조하여…", "page": 0,
 "cust_meta": [{"name":"cust_attr1","value":"image_caption"},
               {"name":"cust_attr3","value":"img10"}, …]}

{"item": "image", "value": "img10.png",
 "type_property": {"title":"", "width":0, "height":0, "ratio":""}, "page": 0, "cust_meta": […]}
```

`_hrc.json` (문서 정보):

```json
{"name": "(2025년)대출성 상품 광고시 준수사항_은행연합회.pdf",
 "file_type": "pdf", "size": 528132, "parsed_status": "S",
 "page_info": [{"page":1,"width":595.0,"height":841.0}, … 6쪽]}
```

### 4-5. `cust_meta` 설계 — 왜 이렇게 나눴나

**`attr` 과 `sattr` 은 성질이 다르다.** 농협 규격서 표 원문:

| 키 | 규격서 설명 |
|---|---|
| `cust_attr1~10` | **(조회only)** Custom 파서 또는 Post 파서를 통해 추출하는 메타 |
| `cust_sattr1~5` | **(검색,조회)** … **임베딩시 포함** |

→ **`sattr` 에 넣은 값은 벡터에 섞인다.** 좌표나 ID 를 여기 넣으면 검색 품질이 떨어진다.
그래서 이렇게 갈랐다:

| 칸 | 값 | 왜 |
|---|---|---|
| `cust_attr1` | 원래 청크 종류 (`text`/`table`/`image_caption`/`ocr_page`/`image_asset`) | 조회 시 "이게 이미지에서 뽑은 텍스트인지 원문인지" 구분 |
| `cust_attr2` | `chunk_id` | 우리 산출물과 대조 (감사 추적) |
| `cust_attr3` | `asset_id` | 캡션의 원본 이미지 추적 |
| `cust_attr4` | `digital` \| **`ocr`** | **정본 신뢰도.** `ocr` 은 스캔 복원 = 판독이라 틀릴 수 있다 |
| `cust_sattr1` | 출처 문서명 | "2023년 예금성 준수사항" 같은 질의에 걸려야 함 |
| `cust_sattr2` | 상품군 (`예금성`/`대출성`) | 검색 필터. **파일명으로만 결정**하고 본문 판단은 하지 않는다 |
| `cust_sattr3` | 조항 제목 | 검색어이자 출처 표시 |

**`cust_attr5`·`cust_sattr4~5` 는 비워 뒀다.** `cust_sattr4~5` 는 §7 의 **연결 키(`checklist_ref`)**
자리로 예약해 둔 것이다.

> **왜 5칸까지만 쓰나**: 규격서 본문(`readme.md:174`)은 attr 를 **5개**로, 표(`:215~229`)는
> **10개**로 적었다. 이름도 본문은 `cust_arrt`(오타), 정의 예시는 `cust_mata`(오타), 실제
> jsonl 예시만 `cust_meta`+`cust_attr1` 로 정상이다. **적은 쪽에 맞춰 5칸 안에서만 쓴다** —
> 6~10 이 실제로 저장되는지 확인되지 않았다. 현장 확인 항목이다.

### 4-6. 규격서와 우리 청크가 어긋나서 **우리가 판단한 것 3건**

억지로 맞추지 않고 근거를 남겼다. 코드 주석에도 같은 내용이 있다.

| # | 어긋남 | 우리 선택 | 왜 |
|---|---|---|---|
| 1 | KL 의 `table` item 은 `value` 가 **HTML `<table>`** 이어야 한다. 그런데 우리 `table` 청크의 text 는 **평문**이다 (실측: `"Ⅰ. 목적"`, `"Ⅲ. 일반원칙"` — HWP 가 제목을 표 안에 넣은 문서) | **`text` item 으로 낸다** + `cust_attr1="table"` | 평문을 `<table>` 로 감싸면 표가 아닌 것을 표로 신고하는 것 |
| 2 | `image` item 의 `value` 는 파일명이고 캡션을 담을 곳이 `type_property.title` 뿐인데, **title 이 임베딩 대상인지 규격에 없다** | 캡션은 **`text` item**, 이미지 파일은 별도 `image` item + `_img.zip` | 규격서 "VectorDB 활용 예"에서 본문으로 임베딩되는 것은 `TEXT` 의 `value` 다. **캡션이 검색에 걸려야 §4-3① 의 의미가 산다** |
| 3 | `image` 의 `width`/`height` 단위가 규격서는 **"mm"**, 정답 샘플은 `1102×557`(A4 폭 210mm 초과 = **픽셀**). `ratio` 는 "페이지 크기 대비"인데 규정문서는 페이지 크기를 모른다 | `width=0, height=0, ratio=""` 로 두고 **현장 확인 항목으로 올린다** | 모르는 값을 지어내지 않는다 |

`page` 는 전부 **0** 이다. 규격서가 "페이지 번호를 알 수 없는 경우에는 0" 을 허용하고,
농협 정답 샘플(`out_sample_hrc.jsonl`)도 **141줄 전부 page=0** 이었다.

규격 준수는 테스트로 못박아 뒀다 — [`tests/test_kl_export.py`](../tests/test_kl_export.py) 14개.

**지표를 읽는 규율 (중요)**: 파싱 결과는 **두 층**이다.
- **결정론 층** (`source ∈ {ocr, digital}`) — 같은 코드·같은 입력이면 **항상 동일**. 단일 수치로 제시 가능

→ 개선을 주장할 때는 결정론 층 수치로만. 이건 §8-3 의 **재처리 정책**과 직결된다.

### 5-3. 최종 산출물 구조 — 최상위 21키, 4층

실제 파일: `out/extracted/<문서>.json` / `out_proto/extracted/<문서>.json`

```
① 식별      document · doc_id · product_group · ad_type · schema_id · schema_version
② 추출값    fields · observations · events · unmapped · group_analysis
③ 코드검산  review_gaps · input_gap · evidence_unbacked · unused_figures
           status_corrections · events_pruned · observations_pruned · errors
④ 집계      coverage(17지표) · elapsed_s
```

**필드 한 칸의 모양** — 값이 있을 때:

```json
"product_name": {
  "value": "NH메디칼론",
  "evidence": ["p1_r001"],      ← ★ 근거를 "영역 ID" 로 가리킨다 (§7-2)
  "status": "found",
  "note": "",
  "group": "L1_상품기본",
  "evidence_score": 1.0,        ← 코드가 사후에 붙임
  "evidence_backed": true
}
```

`{value, evidence, status, note}` 는 **VLM 이 낸 것**, `{group, evidence_score,
evidence_backed}` 는 **코드가 사후에 검산해 붙인 것**이다.

**값이 없을 때 — 여기가 §8-2 의 핵심이다:**

```json
"contract_period": {
  "value": "", "evidence": [], "status": "not_found",
  "absence": {
    "kind": "해당없음",              ← ★ 3분류
    "obligation": "필수",
    "rule": "subtype_not_in",
    "detail": ["입출금(통장·MMDA)"]
  }
}
```

**`absence.kind` 3분류가 이 프로젝트의 핵심 개념이다:**

| kind | 뜻 | 심의에서 |
|---|---|---|
| **해당없음** | 이 상품 유형에는 애초에 필요 없는 항목 (예: 입출금 통장에 "계약기간") | 문제 없음 |
| **미표시** | 표시해야 하는데 광고에 없다 | **지적 대상** |
| **판정제외** | 근거가 없어 판정하지 않는다 | 사람이 봐야 함 |

`1. 대출성상품` 실측: 판정제외 1 · 해당없음 12 · 미표시 3.

**`observations`** — 금지·주의 표현 **의심 후보**다. `field_key` 를 키로 하는 dict 이고 각
값이 배열이다. **판정이 아니다.** 하류가 이걸 위반으로 굳히면 허위 지적이 된다 (§8-4).

**`unmapped`** — 어느 필드에도 안 맞은 문구. 유실 방지 안전망이다.

**`coverage`** — 17지표. 골드(정답) 없이도 재는 자기진단이다:

```
regions_total 34 · regions_cited 22 · region_coverage 0.647
fields_found 36 · fields_not_found 16 · fields_uncertain 1
absence_missing 3 · absence_not_applicable 12 · absence_out_of_scope 1
input_gap_regions 0 · unmapped_total 14 · evidence_unbacked_count 0 · …
```

### 6-4. 필드에 `kind` 가 있고 그게 처리 정책을 정한다

| kind | 뜻 | 처리 |
|---|---|---|
| `numeric` | 금리·금액 등 수치 | 값 검산 |
| `template` | 정형 고지문구 | 문구 대조 |
| **`verbatim`** | **광고 표현 원문** | **판정 금지 · 원문 그대로 보존** |
| `enum` | 정해진 값 중 하나 | 목록 대조 |
| `collection` | 전부 모아야 하는 것 (금리 언급 전수 등) | 누락 검사 |

**`verbatim` 을 다듬으면 안 되는 이유가 실측으로 있다** (§8-5): 003 문서에서 `1,000명` 과
`1,000팀` 표기 불일치가 정규화 과정에 합쳐지며 **심의 대상이 소멸한 전례**가 있다.

### 6-8. 실행해 보고서야 드러난 결함 3종 (수정 완료)

## 7. 둘이 어디서 만나나 — 아직 아무도 안 만든 부분

```
[트랙 B 결과]  광고물 fields
   product_name = "NH메디칼론"
   fee_and_cost = "●수입인지대금: 대출금액 5천만원 이하 비과세…"
   interest_rate_range = (미표시)     ← absence.kind = "미표시"
        │
        ├──▶ 벡터DB 조회 (트랙 A 가 쌓아 둔 규정 청크)
        │      "이 광고에 걸리는 규정 조문이 무엇인가"
        │
        └──▶ RDB 조회
               "이 상품 유형에 필수인 표시의무가 무엇인가"
               "과거 유사 광고에서 어떤 지적이 있었나"
                      ↓
              심의 결과 생성  ← ★ 여기가 RAG/RDB 담당자 영역
```

### 7-1. 우리가 넘기는 것 · 담당자가 만들 것

| | 우리(파싱·스키마) | 담당자(RAG·RDB) |
|---|---|---|
| 규정문서 | `_hrc.jsonl` 을 KL 에 넣는다 | KL 검색 API 로 조회 |
| 광고물 | `out/extracted/*.json` (21키) | RDB 에 적재 + 질의어로 사용 |
| 판정 | **하지 않는다** | **여기서 한다** |

### 7-2. ★ 연결 키 제안 — `checklist_ref`

**문제**: 광고물 fields 로 벡터DB 를 검색해 규정 청크를 받아도, **그 청크가 어느 체크리스트
항목인지 모르면 심의 판정이 안 된다.**

**우리가 이미 갖고 있는 것**: 스키마 필드마다 `checklist_ref` 가 붙어 있고, 정본 97항목과
대조해 **유령 참조 0건**으로 검증됐다 (§6-5).

**제안**: 규정문서를 KL 에 적재할 때 **`cust_sattr` 에 `checklist_ref` 를 심는다.**

```
[규정문서 청크 → _hrc.jsonl]
   cust_sattr1 = "(2023년)예금성상품 광고시 준수사항_은행연합회"   (출처)
   cust_sattr2 = "예금성"                                        (상품군 필터)
   cust_sattr3 = "가. 최고금리를 표시하는 경우…"                  (조항 제목)
   cust_sattr4 = "DEP-INC-06"        ← ★ 예약해 둔 자리
   cust_attr2  = chunk_id

[광고물 fields]
   interest_rate_range.checklist_ref = ["DEP-INC-06"]
        │
        └─▶ 같은 값으로 KL 을 조회 → 해당 조문 청크가 나온다
            → 심의 결과에 근거 조문을 붙일 수 있다
```

근거: `cust_sattr*` 은 규격서에 **"(검색,조회) … 임베딩시 포함"** 으로 명시돼 있다.
[`kl_export.py`](../src/nh_parsing/kl_export.py) 에 `cust_sattr4~5` 를 **비워 둔 채 예약**해
놓았다.

> **⚠ 아직 안 되는 것**: 규정문서 청크 → 체크리스트 항목 매핑이 **자동으로 되지 않는다.**
> `RagChunk` 에는 `checklist_ref` 가 없다. 이걸 채우는 방법(사람이 붙이나, 규칙으로 뽑나,
> VLM 이 판단하나)이 **합의 대상**이다.

## 8. 넘기기 전에 합의할 것 6건

이게 회의의 실질이다. 각 항목에 **왜 위험한지의 실측 근거**를 달았다.

### 8-1. 🔴 연결 키 — `region_id` 는 재처리하면 깨진다

`evidence: ["p1_r062"]` 의 `region_id` 는 **파싱 실행마다 달라질 수 있다.**
2026-08-16 실행에서 파싱 방식을 바꾸자 영역이 **1,905 → 2,463개**로 변했다. 그러면 예전에
저장한 `p1_r062` 가 다른 영역을 가리킨다.

**필요한 것**: `region_id` 를 **처리 버전과 묶어서** 저장해야 한다
(예: `parser_version` + `doc_id` + `region_id` 를 복합 키로).

### 8-2. 🔴 값이 없을 때의 DB 표현 — `null` 하나로 뭉치면 안 된다

`null` 로 뭉치면 **"미표시"(지적 대상)와 "해당없음"(문제 없음)이 같아진다.**
우리가 `absence.kind` 3분류를 만든 이유가 이것이다 (§5-3).

`1. 대출성상품` 실측: **판정제외 1 · 해당없음 12 · 미표시 3**. 만약 이 16개를 다 `null` 로
저장하면 **"미표시 3건"이라는 지적이 사라진다.**

**필요한 것**: `status` 와 `absence.kind` 를 **별도 컬럼으로** 보존.

### 8-3. 🔴 재처리 정책 — VLM 층은 실행마다 흔들린다

"같은 입력 → 같은 출력"(멱등)을 전제한 설계는 깨진다. 5문서 2회 실행 실측: 문장회수
**234 vs 233**, 후보로만 회수된 건수 13→12→9.

**결정론 층**(`source ∈ {ocr, digital}`)은 항상 동일하고, **비결정 층**(`vlm_sweep`,
`vlm_reading`)이 흔들린다.

**필요한 것**: 재처리 시 (가) 기존 결과를 덮을지 버전으로 쌓을지, (나) 심의 결과가 이미
나온 문서를 재처리해도 되는지.

### 8-4. 🟡 `observations` 는 판정이 아니다 — "의심 후보"다

하류가 이걸 위반으로 굳히면 **허위 지적**이 된다. 첫 실행에서 관측 49건 중 **41건(84%)이
유령**이었고 제거해서 18건만 남긴 이력이 있다 (§6-8 ②).

**필요한 것**: DB 에서도 "의심 후보" 성격이 유지되어야 하고, 화면에 위반으로 표시하기 전에
사람 확인 단계가 있어야 한다.

### 8-5. 🟡 `verbatim` 필드는 다듬지 말 것

DB 저장 시 **공백 정규화·트림·유니코드 정규화를 하면 심의 대상이 사라진다.**
003 문서에서 `1,000명`/`1,000팀` 표기 불일치가 정규화로 합쳐지며 소멸한 전례가 있다.

**필요한 것**: `kind == "verbatim"` 필드는 **원문 바이트 그대로** 저장.

### 8-6. 🔴 규정문서 청크의 `checklist_ref` 를 누가 어떻게 채우나

§7-2 의 자리는 예약해 뒀지만 **값을 채우는 방법이 없다.** 세 갈래:

| 안 | 방법 | 비용 / 위험 |
|---|---|---|
| 가 | 사람이 규정 청크마다 체크리스트 항목을 붙인다 | 정확하지만 규정문서 12건 × 청크 수십 개 |
| 나 | 규칙으로 뽑는다 (조항 번호 `§16① 5 나` ↔ 정본의 `근거규정` 열 매칭) | **정본에 `근거규정` 열이 실재한다** → 가능성 있음. 다만 표기 불일치 위험 |
| 다 | VLM 이 판단한다 | 비결정 층이 되어 §8-3 문제가 규정 쪽까지 번진다 |

**추천은 (나) → (가) 보정** 이다. 정본 체크리스트에 `근거규정` 열이 있어(`기준 §16① 1`)
규정문서 본문의 조항 번호와 맞출 근거가 실재한다.

### 그 밖에 확인이 필요한 것

| 항목 | 상태 |
|---|---|
| **KL 검색(조회) API 규격** | 받은 자료 17개에는 **적재(쓰기) 규격만** 있고 검색 규격이 없다. 조회를 못 하면 심의 경로를 만들 수 없다 → **농협에 요청 필요** |
| `cust_attr6~10` 이 실제로 저장되나 | 규격서 본문 5개 / 표 10개로 불일치. 현장 시험 |
| jsonl item 이 곧 청크 단위인가, KL `chunker` 가 다시 자르나 | 규격서에 단서가 상충 |
| 카드상품 스키마 | 샘플 89건 중 20건(22%)이 카드인데 스키마가 없다 |

## 9. 앞으로 농협 틀 안에서 어떻게 구현할 것인가

### 9-1. 최종 구조

```
┌─────────────────────────────────────────────────────────────────┐
│ 농협 폐쇄망                                                       │
│                                                                 │
│  DAP / GenAI Knowledge Lake (KL)                                │
│    └─ Custom 파서 슬롯                                           │
│         [진입점 껍데기]  ← 우리가 만든다. 얇다                     │
│           POST /parsing → 202 + 번호표                           │
│           GET /parsing/result/{번호표} → zip                     │
│                  │ HTTP 요청                                     │
│                  ▼                                              │
│         [에이전트 서비스]  ← 우리 파이프라인 본체                  │
│           파싱 · 스키마 추출 · KL 형식 변환                        │
│                  │                                              │
│                  ├──▶ PP-StructureV3 (레이아웃·OCR)              │
│                  └──▶ Gemma 4 26B (VLM)                         │
│                                                                 │
│  PostgreSQL  ← 광고물 파싱·추출 결과, 심의 이력                    │
│  프론트엔드(WAS)  ← 컨테이너 이미지로 제공                          │
└─────────────────────────────────────────────────────────────────┘
```

**진입점과 에이전트 서비스를 나누는 이유**(회의 결정사항이기도 하다):

| | 같은 컨테이너에서 직접 호출 | **별도 에이전트 서비스에 HTTP** |
|---|---|---|
| KL 컨테이너에 필요한 라이브러리 | pypdfium2 + 사내파서 + JVM + Pillow… 전부 | **`requests` 하나** |
| 농협 베이스 이미지에 있나 | pypdfium2·jpype1 **없음 → 반입 필요** | requests 2.34.2 **이미 있음** |
| Python 3.11 제약 | 우리 코드 전부가 3.11 에서 돌아야 함 | **진입점만.** 에이전트는 3.13+자바 자유 |

→ **별도 서비스 방식이 압도적으로 유리하다.** 사내 HWP 파서가 Python 3.13 + 자바를
요구하는데 농협 환경은 3.11 기준이라, 이 분리로 그 충돌이 자동으로 풀린다.

### 9-2. 남은 단계

| # | 작업 | 상태 |
|---|---|---|
| 1 | 브랜치·문서 정리 | ✅ 완료 (`f17aaf3`) |
| 2 | `prototype/` 폴더 + 케이스 복사 | ✅ 완료 |

| **5** | **RAG/RDB 담당자 설명 (이 문서)** | ✅ 완료 |
| 6 | `kl_parser/` 진입점 껍데기 + 농협 예제 결함 2건 수정 | ⬜ |
| 7 | 로컬 왕복 시험 (POST → 폴링 → zip → 규격 검사) | ⬜ |
| 8 | Python 3.11 호환 검증 (사내 HWP 파서 포함) | ⬜ |

**⚠ 농협 예제 코드 결함 2건** (6번에서 반드시 고칠 것):
1. `TIMEOUT = os.getenv("TIMEOUT", 600)` → 환경변수를 설정하면 **문자열**이 되어
   `timeout + 10` 이 TypeError. **우리 문서 최대가 590초라 타임아웃을 늘리려는 순간 죽는다.**
2. `except` 블록이 미할당 `work_dir` 을 참조할 수 있다.

### 9-3. 시간 규격은 여유가 있다

| 제약 | 값 | 우리 최대 590초와 |
|---|---|---|
| KL 폴링 기본 timeout | **3시간** (10,800초) | 18배 여유 |
| 농협 예제 subprocess `TIMEOUT` 기본 | 600초 | 마진 10초 → 조정 필요 |
| gunicorn `timeout` | 180초 | **무관** (비동기라 진입점은 202 를 즉시 반환) |

### 9-4. 모델 교체 준비 상태

폐쇄망 안에서 OCR/VLM 을 무엇으로 쓸지가 아직 미정이다. 우리 코드는 **환경변수만 바꾸면
교체된다** ([`config.py`](../src/nh_parsing/config.py)): `PADDLEX_URL`, `GEMMA_URL`,
`GEMMA_MODEL` 전부 `os.environ.get`.

단 성질이 다르다:

| | 코드 변경량 | 대체 모델 요건 |
|---|---|---|
| **VLM** (Gemma) | 거의 없음 (URL·모델명) | OpenAI 호환 + **이미지 입력** + **strict json_schema**(구조화 출력). 품질 재측정 필수 |
| **OCR** (PaddleX) | 어댑터 한 파일(187줄) | **레이아웃 블록 + 읽기순서**를 줘야 한다. 글자 줄만 주면 **영역·역할·카드분할이 사라진다** = 재설계 |

## 11. 용어 사전

| 용어 | 뜻 |
|---|---|
| **DAP** | 농협 AI/데이터 플랫폼 |
| **KL / 날리지 레이크** | GenAI Knowledge Lake. DAP 안의 사내 문서검색(RAG) 제품 |
| **커스텀 파서** | KL 문서처리 파이프라인의 "읽기" 슬롯에 꽂는 부품. 우리 자리 |
| **RAG** | 검색으로 보강한 생성. 문서를 미리 저장해 두고 질문에 관련 조각을 찾아 LLM 에 붙여 주는 방식 |
| **임베딩 / 벡터DB** | 글자를 숫자 배열로 바꾸는 것 / 그 배열을 저장하고 "가까운 것"을 찾아 주는 DB |
| **jsonl** | JSON Lines. 한 줄에 완결된 JSON 하나 |
| **`_hrc`** | hierarchization(계층화·구조화). KL 출력 파일명 규칙 |
| **VLM** | Vision Language Model. 이미지를 보고 글로 답하는 AI. 우리는 Gemma 4 26B |
| **PP-StructureV3** | 우리가 쓰는 레이아웃 검출 + OCR 모델 |
| **영역 (Region)** | 우리 파싱 산출물의 단위. 레이아웃 블록에서 나오고 좌표·역할·판독후보가 붙는다 |
| **`region_id`** | 영역 식별자 (`p1_r062` = 1쪽 62번째 영역). 스키마의 `evidence` 가 이걸 가리킨다 |
| **`parse_route`** | `digital`(텍스트 레이어 신뢰) / `ocr`(스캔형) / `hybrid`(둘 병행) |
| **`absence.kind`** | 값이 없는 이유 3분류: 해당없음 / 미표시 / 판정제외 |
| **`verbatim`** | 광고 표현 원문. 판정 금지·다듬기 금지 필드 종류 |
| **`checklist_ref`** | 스키마 필드가 가리키는 체크리스트 항목 ID (`DEP-INC-06`) |
| **골드 (gold)** | 사람이 만든 정답지. `gold/*.yaml` |
| **결정론 층 / 비결정 층** | 같은 입력이면 항상 같은 결과가 나오는 부분 / 실행마다 달라지는 VLM 부분 |
| **strict json_schema** | 모델 응답이 정해진 JSON 구조를 벗어나지 못하게 강제하는 기능 |
