## 2. (완료됨) 구조 변경 — 아래는 착수 전 기록

### 배경

`triage_page()`가 PDF 페이지를 `structured`(순수 디지털 텍스트) / `hybrid`(디지털+OCR
병행) / `scan_like`(전면 OCR) 3갈래로 나눈다. **`structured` 판정이면 StructureV3(레이아웃
검출 모델)를 아예 안 부르고**, 코드가 세로 간격만 보고 영역을 만든다(`_pseudo_regions`,
`pipeline.py`). 가로 인식이 없어 좌우 2단 페이지가 한 영역으로 뭉칠 수 있다(실측: 28쪽 중
2쪽 — `7. 대출성상품 p1`, `6. 대출성상품 p1`).

처음엔 "2쪽뿐이니 구조 변경은 과잉"이라 판단했는데, 사용자가 반박: **StructureV3는 GPU라
빠른데 왜 구조(레이아웃)는 안 받고 아예 건너뛰냐, 구조는 받고 거기에 정확한 디지털
텍스트를 끼워넣으면 안 되냐.**

실측으로 확인한 결과 이 반박이 맞다:
- StructureV3 단일 타일 호출 실측: **3.67초, GPU, 레이아웃 블록 72개 반환**
  (`1. 대출성상품.pdf` p1, 캔버스 1654×2339, 타일 1개 기준)
- VLM(Gemma) 비용은 **라우팅과 무관하게 이미 전부 지불 중**이다 — 카드분할·역할판정·
  밴드재판독·분류(`_apply_vlm_judgments`)는 모든 route에서 항상 돈다. `structured`가
  아끼는 건 **StructureV3 호출 하나(3.67초)뿐**이고, 그 대가로 영역 품질 전체를 잃고 있었다.
- 오늘 고친 A(가로공백 분리)·B(겹침비율 배정)·J(디지털·OCR 비대칭 포함비율 병합)가
  정확히 "구조는 OCR, 값은 디지털" 조합을 안전하게 만드는 전제조건이다. 예전엔 이 조합이
  라벨+값 중복(J로 해결) 같은 부작용을 냈을 텐데 지금은 아니다.

### 하려는 것

`hybrid`가 이미 하는 방식(`_ocr_canvas_to_page(canvas, page_no, extra_digital=digital,
route="hybrid")` — 디지털 텍스트 추출 + StructureV3 호출 + `_merge_digital_ocr`로 병합,
디지털이 항상 우선)을 **`structured` 판정에도 그대로 적용**한다. 3갈래 판정(structured/
hybrid/scan_like)은 진단·기록용으로 남기되, **"OCR을 부르느냐 마느냐"의 분기만 없앤다.**

`pipeline.py`의 이 블록이 대상이다:
```python
if verdict.verdict == "structured":
    lines = extract_digital_lines(pdf_page, canvas.px_per_pt)
    cov = ink_coverage(canvas.image, [l.bbox for l in lines if l.bbox])
    if cov < SETTINGS.min_ink_coverage:
        verdict.verdict = "hybrid"
        ...
        page = _ocr_canvas_to_page(canvas, page_no, extra_digital=lines, route="hybrid")
    else:
        page = _assemble_page(canvas, lines, blocks=[], route="digital", page_no=page_no)  # ← 이 else 분기를 없애는 게 목표
elif verdict.verdict == "hybrid":
    ...
```

### 해야 할 일 (순서)

1. `structured` 분기도 `_ocr_canvas_to_page(..., extra_digital=lines, route=?)`를 타게
   변경. `route` 라벨을 그대로 "digital"로 유지할지, "hybrid"로 통일할지는 review.html의
   `route=` 표시·필터링에 영향을 주므로 확인 후 결정.
2. `ink_coverage` 기반 강제 hybrid 전환 로직(H, 4efb092)은 이제 항상 OCR을 부르므로
   불필요해질 수 있음 — 다만 `verdict.reasons`에 남기는 진단 정보(잉크 커버리지 수치)는
   유용하니 로직만 정리하고 기록은 유지하는 방향 검토.
3. **digital 경로 29쪽 전부 실제 재실행** (모델 호출 필요, 스킵 불가):
   - 컬럼 혼입 의심 2쪽(`7. 대출성상품`, `6. 대출성상품`)이 실제로 해결되는지
   - 나머지 27쪽에 회귀(중복·유실·비용 폭증)가 없는지
   - 총 소요시간 실측 (29 × 3.67초 ≈ 1분 47초는 순차 GPU 추정치일 뿐, 실측 필요)
4. 테스트 추가 후 커밋. `pipeline.py`의 `_process_pdf` 분기 로직을 테스트하는 파일이
   마땅치 않으므로 신규 작성 필요.
5. **`docs/parsing-review.html`, `tools/make_review.py`의 파이프라인 설명문 갱신** —
   "structured면 OCR 생략"이라는 설명이 이번에 사실과 달라진다. §3(아래) 참조.

## 5. 알아둘 것 — 이번 세션에서 확인된 사실·원칙

- **document-processor**는 광고 파싱 본선에 안 쓰인다(`pipeline.py`가 pypdfium2만 씀).
  HWP 트랙과 RAG 트랙에서만 쓴다. "사내 표준이라 반드시 써야 한다"는 근거는 없다 —
  성능이 나으면 바꿀 수 있다(사용자 명시).
- **kordoc**: npm 패키지, ML 의존성 없는 결정론적 파서(OCR만 옵션으로 PP-OCRv5 사용).
  자동 판정(`needsOcr`)이 우리와 같은 사각(뽑힌 글자 수만 봄)을 가진다 — 그대로 갖다 써도
  H 결함은 안 고쳐진다. `--ocr-force`는 완전 복구하지만 전면 OCR과 같은 비용.
  이미 `tools/run_schema_source.py`에 HWP 파싱 실패 시 폴백으로 들어가 있다(신규 도입 아님).
- **VLM 스윕은 라우팅과 무관하게 항상 돈다** — digital 경로에서도 로고·구호(`금융의 모든
  순간`, `NH농협금융`) 같은 이미지 속 문구를 회수하지만, 좌표가 근사치라 영역 단위 근거
  지목은 안 된다.
- **사용자 표준 원칙**: 파싱 결과 집계·판정 전에 반드시 원본 이미지로 최소 표본을 직접
  대조할 것 (JSON/좌표 휴리스틱만으로 결론 내지 말 것 — 과거 여러 번 재확인 후 숫자가
  크게 바뀐 전례 있음).
- **89개 전체 재실행은 사용자가 원치 않는다** — 항상 실제로 영향받는 파일만 모델 호출
  0회 코드 계산으로 골라서 재실행할 것 (`rerun_set.json` 같은 방식). 다만 §3의 "89개 전체
  재검증"은 여러 수정이 누적된 최종 확인 목적이라 예외.
- **세션 임시 폴더(scratchpad)는 새 채팅에서 사라진다** — 오늘 만든 `out_new_before_ABCDE`
  백업(A~E 적용 전 89개 json 스냅샷)은 새 세션에서 접근 불가. 이후 before/after 대조가
  필요하면 git에서 `5f778d1`(A~E 이전 마지막 커밋) 체크아웃 후 재생성해야 한다.
