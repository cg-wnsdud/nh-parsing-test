## 1. 배경과 설계 목표

### 1.1 이 문서가 다루는 범위

광고심의 에이전트의 **가장 앞단** — 입력 파일이 시스템에 들어와서, 후속 엔진(Rule/RAG/Multimodal/LLM Agent)이 소비할 수 있는 구조화된 데이터가 되기까지의 파싱 계층을 설계한다.

- 대상: 기준자료(rag-data) 인제스천 파싱 + 광고물 입력 파싱
- 비대상: 검토 로직(Rule Engine, RAG 검색), UI, 리포트 생성

### 1.2 요구사항에서 오는 제약 (설계 입력)

| 근거 | 제약 |
| --- | --- |
| F-003 (OCR/VLM 텍스트 추출) | 추출 텍스트 + **위치 좌표** + **추출 신뢰도**를 저장. 신뢰도 미달 문구는 "판독 확인 필요" 상태로 구분 |
| F-004 (광고 화면 구조 분석) | 제목/본문/유의사항/각주/버튼/고지문구 **영역 분류** 필요 |
| F-011 (시각적 표시 적정성) | 글자 크기·강조·대비·시인성 분석 → 원본 렌더링 이미지가 반드시 필요 |
| F-013 (광고 화면 근거 매핑) | 문제 문구를 **Bounding Box**로 원본 화면 위에 표시 → 파싱 단계부터 좌표 보존이 필수 |
| 회의록 결정사항 | 지원 문서: PDF, 이미지, HWP/HWPX, PPT, DOCX 우선. 배너보다 **상세페이지 중심** |
| 개발 환경 | **폐쇄망**, NH 내부 GPU/AI 플랫폼. 외부 API 사용 불가 → 모든 모델은 온프렘 서빙 |
| 저장소 명세 | PostgreSQL(메타) + Qdrant(벡터) + OpenSearch(키워드), Python + uv, Docker |

### 1.3 설계 원칙

1. **조용한 실패 금지** — 파싱 불가 페이지/영역은 반드시 상태값(`skipped`, `low_confidence` 등)으로 드러낸다. 사내 파서의 SCAN_LIKE 조용한 스킵을 그대로 노출하지 않는다.
2. **파일 단위가 아닌 페이지·영역 단위 분기** — 같은 PDF 안에서도 텍스트 페이지와 이미지 페이지가 섞인다(실측: NH농협은행-2026_003). 라우팅은 페이지 단위로 결정한다.
3. **좌표 보존** — 모든 추출 텍스트는 원본 렌더 기준 픽셀 bbox를 갖는다. 좌표 없는 텍스트는 검토 근거 매핑(F-013)에 쓸 수 없다.
4. **디지털 텍스트 우선** — 텍스트 레이어가 신뢰 가능하면 OCR보다 항상 우선한다(무손실). OCR/VLM은 디지털 추출이 불가능하거나 불신할 때만 투입한다.
5. **근거 추적성** — 각 텍스트 조각에 출처(`digital | ocr | vlm`)와 신뢰도를 남겨 감사 대응(NFR-004)을 지원한다.

### 2.2 진단에서 나온 시사점

1. **광고물 6개 중 4개(2,3,4,6)는 OCR/VLM 없이는 심의 대상 텍스트를 얻을 수 없다.** 특히 4번(PDF-003)은 텍스트 레이어가 "있는" 파일인데도 준법 검토의 핵심인 **상품 유의사항 전문이 이미지 안에 렌더**되어 있다 → 텍스트 레이어 존재 여부만으로 파일 단위 분기를 하면 유의사항이 통째로 누락된다.
2. **세로 초장신 캔버스가 표준 입력이다** (720×6111, 1122×6429px, 720×6554pt). OCR/VLM 모두 원본 그대로 넣으면 다운샘플링으로 깨알 유의사항이 뭉개진다 → 수평 밴드 타일링이 필수.
3. **파서 라이브러리 선택이 파일 하나로도 갈린다.** PDF-001은 pdfminer 계열이 파싱 자체를 실패한다. 파서별 견고성 차이를 전제로 폴백 체인이 필요하다.
4. **HWP는 두 얼굴이다.** 기준자료 HWP(1번)는 텍스트 인제스천으로 충분하지만, 광고물 HWP(5번)는 텍스트 추출 + **시각 검토용 렌더링**(F-011)이 모두 필요하다.
5. **파일명이 강한 분류 prior다.** `NH농협은행-2026_001-예금성.pdf` 형식으로 상품군이 파일명에 명시된다 → 분류 단계에서 파일명 prior + 내용 관측 결합(이전 프로젝트 검증 패턴).

## 3. 전체 아키텍처 — 이중 트랙 + 페이지 단위 분기

```
                         ┌──────────────────────────────────────────┐
 기준자료 (rag-data)      │  Track A: 기준자료 인제스천                 │
 법령/규제/심의사례        │  document-processor → DocIR               │
 (HWP/HWPX/PDF/DOCX)  ──▶│  → 청킹 + 메타데이터(DR-001)               │
                         │  → Qdrant(벡터) + OpenSearch(키워드)       │
                         └──────────────────────────────────────────┘

                         ┌──────────────────────────────────────────┐
 광고물 입력              │  Track B: 광고물 분석 파싱                  │
 (PDF/PNG/JPG/HWP...) ──▶│                                          │
                         │  [B0] 입력 정규화: 페이지 캔버스 목록 생성    │
                         │  [B1] 페이지 triage:                      │
                         │       텍스트 신뢰 가능? ──yes──▶ 디지털 추출  │
                         │            │no                (좌표 포함)   │
                         │            ▼                              │
                         │  [B2] OCR/VLM 파이프라인                   │
                         │       분류(파일명 prior+VLM)               │
                         │       → 타일링 → 레이아웃/OCR              │
                         │       → VLM 폴백/추출 → 신뢰도 스코어링      │
                         │            │                              │
                         │            ▼                              │
                         │  [B3] 결과 통합: AdPageIR                 │
                         │       (영역 bbox + 텍스트 + 출처 + 신뢰도)   │
                         └──────────────────────────────────────────┘
                                        │
                                        ▼
                          후속 엔진 (Rule / RAG / Multimodal / LLM Agent)
```

핵심 결정: **Track A와 B는 파서를 공유하되 목적이 다르다.**
- Track A의 산출물은 검색 가능한 텍스트 청크(좌표 불필요, 조문 구조 중요).
- Track B의 산출물은 원본 화면 좌표에 앵커된 영역별 텍스트(F-013의 bbox 하이라이트가 소비).

## 4. 라우팅 규칙 (분기표)

### 4.1 1차 라우팅 — 파일 확장자/매직바이트

| 입력 | 초기 경로 |
| --- | --- |
| PNG / JPG / 모바일 캡처 | Track B의 [B2] OCR/VLM 직행 (사내 파서는 이미지 입력 불가) |
| PDF | 페이지 단위 triage로 (4.2) |
| HWP / HWPX | 사내 파서로 텍스트·표 추출. **광고물이면** 추가로 렌더링 경로(6.8) 병행 |
| DOCX / PPT | 사내 파서(DOCX) / PDF 변환 후 PDF 경로(PPT). PoC 샘플 확보 후 상세화 |

### 4.2 PDF 페이지 단위 triage

사내 파서(document-processor)의 probe/triage를 그대로 활용하되, 결과를 명시적으로 소비한다:

| 페이지 판정 | 판정 기준(사내 파서 내장) | 처리 |
| --- | --- | --- |
| STRUCTURED | 정상 문자 비율 ≥ 0.5, 문자수 > 20, U+FFFD 과다 아님 | DocIR 텍스트 + bbox 채택 (`source=digital`) |
| SCAN_LIKE | 전면 이미지(면적비 ≥ 0.95), 한글 깨짐(U+FFFD ≥ 8개 & 30%), PUA 난독 | `render_scan_like_pdf_pages()`(216 DPI, 픽셀→문서좌표 변환기 내장)로 렌더 → [B2] OCR/VLM 투입 |

**필수 안전장치 2가지:**

1. **조용한 스킵 방지** — 사내 파서는 SCAN_LIKE 페이지를 경고 없이 스킵하고 `parse_status="skipped"`만 남긴다. 래퍼에서 모든 페이지의 `parse_status`를 검사해 스킵 페이지를 OCR 큐로 넘기는 것을 **강제**한다(누락 시 파이프라인 실패로 처리).
2. **STRUCTURED 페이지의 이미지 영역 보완** — 실측 4번 파일처럼 텍스트 레이어가 일부 있어도 콘텐츠 대부분이 이미지인 페이지가 있다. STRUCTURED 판정이어도 **페이지 내 이미지 면적비가 임계치(초안: 50%) 이상이면 해당 이미지 영역을 OCR 대상으로 추가**한다(영역 단위 하이브리드). 텍스트 레이어와 OCR 결과는 좌표 겹침으로 중복 제거.

### 4.3 파서 폴백 체인 (파일 열기 실패 대응)

PDF-001처럼 특정 라이브러리가 파싱 자체를 실패하는 파일이 존재한다.

```
사내 파서(pdfium 기반 probe) 실패
  → pypdf로 페이지 수/크기만 확보 후 전체 페이지를 이미지 렌더 → OCR 경로
    → 그것도 실패 시 "판독 불가" 상태로 등록 (F-001 예외 처리와 연결)
```

HWP의 경우: 사내 파서(hwplib 변환) 실패 → kordoc(Node.js, HWP3~5/HWPX 지원)을 2차 폴백 후보로 검증 → 실패 시 "판독 불가". kordoc은 Node 의존성이 추가되므로 실제 실패 사례가 확인된 뒤에만 도입한다.

## 5. Track A — 기준자료(rag-data) 인제스천

1. **파싱**: document-processor `DocIR.from_file()` → 문단/표 구조 확보. HWP 5.0은 내부적으로 hwplib(Java)→HWPX 변환을 거치므로 워커 컨테이너에 **Java 런타임 포함** 필요.
2. **청킹**: 조문/항목 단위 우선(규제 문서는 `Ⅰ. 목적`, `ㅇ`, `-` 계층이 뚜렷). 표는 행 단위 + 표 전체 컨텍스트 병행.
3. **메타데이터(DR-001 스키마)**: 문서명, 조문번호, 시행일, 상품군, 광고유형, 필수/금지/권고, 중요도, 버전. 파싱 단계에서 자동 추출 가능한 것(문서명, 날짜, 섹션 번호)과 기준 관리자가 입력할 것을 구분.
4. **색인**: Qdrant(임베딩) + OpenSearch(키워드/조문번호/금지어) 이중 색인 — 명세서의 Hybrid Search 구조.
5. **내장 이미지(예시 광고 BMP 등)**: 1차 범위에서는 자산으로 저장만 하고 색인하지 않음. 심의사례 이미지의 OCR 태깅은 2차 우선순위(성능 향상 여지가 확인되면).

## 6. Track B — 광고물 분석 파싱 (OCR/VLM 핵심 설계)

### 6.1 입력 정규화 [B0]

모든 광고물을 **"페이지 캔버스" 목록**으로 정규화한다. 캔버스 = 원본 픽셀 좌표계를 가진 단일 이미지 + (있다면) 디지털 텍스트 오버레이.

- PNG/JPG: 원본 그대로 1캔버스. RGBA → 흰 배경 합성 RGB(이전 프로젝트 `rgb_on_white` 재사용).
- PDF: 페이지별 렌더(216~220 DPI). STRUCTURED 페이지는 디지털 텍스트를 같은 좌표계로 투영.
- HWP 광고물: 텍스트는 디지털 정본, 캔버스는 렌더링 경로(6.8)로 생성.
- 세로 스크롤 캔버스(높이 4000px↑)는 분할하지 않고 **원본 좌표계를 유지한 채** 타일 뷰만 생성(6.3).

### 6.2 분류 [B2-1]

- **파일명 prior**: `예금성|대출성|적금|...` 키워드 → 상품군 후보 (실측: NH 파일명 규칙이 이를 보장).
- **VLM 페이지 분류**: 광고유형(상세페이지/안내장/배너/이벤트), 상품군 확인, 회전 판단.
- prior와 관측의 합의/충돌을 `category_source`로 기록(이전 프로젝트 검증 패턴 — 감사 추적성).

### 6.3 타일링 전략 (세로 스크롤 대응) [B2-2]

실측 3대 난제(초장신 캔버스, 장식 타이포·복잡 배경, 깨알 유의사항) 중 첫 번째 대응:

- 트리거: 캔버스 장변 ≥ 4000px 또는 총 화소 ≥ 30MP (이전 프로젝트 임계치에서 출발, 벤치마크로 조정).
- 분할: **수평 밴드**(폭 = 캔버스 폭, 높이 ≈ 1500~2000px), 인접 밴드 간 **오버랩 ≈ 10~15%** — 밴드 경계에서 문장/영역이 잘리는 것을 오버랩 병합으로 복구(이전 프로젝트 `stitch_tile_segments`의 union-find 병합 재사용).
- 좌표 정규화: 타일 내 좌표 → 캔버스 원본 좌표로 즉시 환산. **모든 하위 단계는 원본 좌표계만 사용.**

### 6.4 레이아웃 분석 + OCR [B2-3]

기준선(baseline) 구성 — 이전 프로젝트에서 검증된 조합:

- **PaddleX PP-StructureV3** (HTTP 서빙): 영역(제목/본문/표/이미지) 검출 + OCR(텍스트/신뢰도/폴리곤). 폐쇄망 온프렘 서빙 가능.
- 영역 분류 매핑: PP-Structure의 일반 영역 유형 → F-004의 광고 도메인 영역(제목/본문/유의사항/각주/버튼/고지문구)으로 재분류. 재분류는 규칙(위치·크기·키워드) + VLM 보조로 수행 — 예: 하단부 + 작은 글씨 + "유의사항" 헤더 → 유의사항 영역.
- **깨알 유의사항 대응**: 유의사항 후보 영역은 원본 해상도 크롭으로 **2차 고해상도 OCR** 수행(전체 페이지 OCR과 별도 패스).

### 6.5 VLM의 역할 [B2-4]

VLM(OpenAI 호환 서빙, 예: Gemma 계열/Qwen-VL 계열 — 8절에서 비교)은 4가지 태스크로 한정:

1. **페이지 분류/회전** (6.2)
2. **폴백 ROI**: PP-Structure가 영역을 놓친 페이지(장식 타이포, 복잡 배경)에서 영역 재검출. 좌표만 반환, 텍스트는 OCR/추출 단계가 담당(이전 프로젝트의 "coordinates-only" 원칙 — 환각 억제)
3. **필드 추출**: 크롭 이미지 → 구조화 관측(금리 수치, 우대조건, 심의필 번호, 기간 등). strict json_schema 강제 + pydantic 재검증
4. **judge**: OCR 텍스트 + 추출 관측을 종합해 페이지 최종 구조 확정. "OCR/관측에 있는 값만 사용, 새 값 생성 금지" 프롬프트 원칙 유지

### 6.6 신뢰도와 OCR 스코어링 [B2-5]

- OCR 신뢰도(엔진 자체 점수)를 문구 단위로 저장 → F-003의 "판독 확인 필요" 상태 판정.
- VLM 추출값은 OCR 텍스트와 토큰 교차검증(`ocr_backed` 점수, 이전 프로젝트 `check_field_consistency` 재사용). **비차단 신호** — 값을 버리지 않고 검토 화면에 신뢰도로 노출.
- 금리·수치 필드는 추가로 정규식 검증(`연 X.X%`, `X.X%p` 패턴) — 광고심의에서 수치 오추출은 치명적이므로 이중 검증.

### 6.7 좌표계 통일

- 정본 좌표계: **원본 캔버스 픽셀** (PNG는 원본 픽셀, PDF는 렌더 DPI 기준 픽셀 + DPI 기록).
- 저장 시 `(canvas_w, canvas_h, dpi, page_no)`를 함께 기록해 UI가 어떤 배율에서도 bbox를 복원 가능하게 함.
- PDF 디지털 텍스트의 pt 좌표는 렌더 픽셀로 환산해 통일(사내 파서의 `pixel_bbox_to_doc_bbox` 역방향).

### 6.8 HWP 광고물의 이중 표현 (미해결 갭 → 옵션 비교)

HWP 광고물은 텍스트는 완벽하게 뽑히지만 F-011(크기/강조/시인성)·F-013(bbox)에 필요한 **렌더 이미지와 좌표**가 없다. 옵션:

| 옵션 | 방법 | 장점 | 단점 |
| --- | --- | --- | --- |
| R1 | LibreOffice(hwp 필터) headless로 HWP→PDF → PDF 경로 재사용 | 파이프라인 단일화 | hwp 필터 품질 검증 필요(레이아웃 뒤틀림 가능) |
| R2 | 사내 파서 HWPX→HTML 렌더 → headless 브라우저 스크린샷 | 사내 파서 재사용 | float/절대배치 미반영(사내 파서 문서화된 한계) |
| R3 | HWP 내장 PrvImage(미리보기) 사용 | 즉시 가능 | 저해상도, 1페이지뿐 — 검토용 부적합, 데모용만 |
| R4 | 텍스트 정본 + 렌더 없이 텍스트 검토만 수행 | 갭 없음 | F-011/F-013을 HWP에 한해 포기 |

**권고**: 프로토타입에서 R1 품질을 실측(HWP-004로 원본 대비 비교) 후 R1/R2 결정. R3은 데모 임시용.

## 7. 출력 스키마 — AdPageIR (초안)

Track B 산출물. 후속 엔진과 UI(F-013)가 소비하는 계약.

```
AdDocument
├─ doc_id, source_file, file_type, product_group(분류), ad_type(분류)
├─ category_source: filename | vlm | filename_and_vlm | vlm_overrode_filename
├─ pages: [AdPage]
│   ├─ page_no, canvas_w, canvas_h, dpi
│   ├─ parse_route: digital | ocr | hybrid      ← 페이지가 어느 경로로 처리됐나
│   ├─ parse_status: ok | partial | unreadable  ← 조용한 실패 금지
│   ├─ regions: [AdRegion]
│   │   ├─ region_id, bbox(원본 픽셀), role(제목|본문|유의사항|각주|버튼|고지문구|이미지|표)
│   │   ├─ role_confidence
│   │   ├─ lines: [ {text, bbox, confidence, source: digital|ocr|vlm} ]
│   │   └─ style_hints: {font_size_px 추정, bold 여부, 대비 추정}   ← F-011용
│   └─ extracted_fields: [ {key(금리|우대조건|심의필번호|기간|...), value, bbox, ocr_backed, confidence} ]
└─ assets: 페이지 렌더 PNG, 영역 크롭 (콘텐츠 주소 기반 저장)
```

- 명세서 8.1(광고물 기본정보)·8.2(검토 결과)와 매핑: `AdRegion.lines`가 검토 결과의 `target_text` + 좌표 출처가 되고, `extracted_fields`가 Rule Engine(금리 비교 등)의 입력이 된다.
- 저장: PostgreSQL(메타/결과) + 아티팩트 저장소(렌더/크롭 — PoC는 파일시스템 or DB BLOB, 이전 프로젝트의 콘텐츠 주소 방식 차용).

## 8. OCR/VLM 엔진 — 기준선과 대안 비교 계획

### 8.1 기준선 (이전 프로젝트 검증 조합)

| 역할 | 엔진 | 근거 |
| --- | --- | --- |
| 레이아웃 + OCR | PaddleX PP-StructureV3 (온프렘 HTTP) | 이전 프로젝트 실전 검증, 한글 OCR 품질 양호, 좌표/신뢰도 제공 |
| 분류/폴백ROI/추출/judge | OpenAI 호환 VLM (vLLM 서빙) | strict json_schema 강제 가능, 폐쇄망 GPU 서빙 |

### 8.2 비교 대상 대안

| 대안 | 가설 | 확인 포인트 |
| --- | --- | --- |
| VLM 단독 파싱 (OCR 생략) | 최신 VLM은 레이아웃+텍스트를 한 번에 읽을 수 있다 | 깨알 유의사항 재현율, bbox 정확도(VLM bbox는 일반적으로 부정확), 비용/지연 |
| 최신 PaddleOCR (PP-OCRv5/신규 구조 모델) | StructureV3 대비 한글 인식률 개선 여부 | 장식 타이포·복잡 배경 케이스 |
| 국산 상용 파서 (예: Upstage Document Parse 등) | 관리형 품질 | **폐쇄망 온프렘 라이선스 가능 여부가 선결** — 불가 시 탈락 |
| kordoc | HWP 폴백 | 사내 파서 실패 HWP에서만 평가 |

### 8.3 벤치마크 설계 (프로토타입 단계에서 실행)

- **데이터**: nh-data 6개 + 농협 제공 예정 샘플. 각 파일에 대해 정답지 작성: ① 전체 문구 전사, ② 유의사항 문구 목록, ③ 핵심 필드(금리, 심의필 번호, 기간, 우대조건), ④ 영역 bbox(주요 영역 10~20개).
- **지표**:
  - 문자 정확도(CER) — 전체 및 **유의사항 영역 한정**(가장 중요)
  - 필수 필드 재현율/정밀도 (금리 수치는 완전 일치 기준)
  - 영역 검출 IoU ≥ 0.5 비율
  - 페이지당 처리 시간/자원
- **합격선**: 명세서 수용 기준(필수 문구 검토 정확도 80%)을 역산 — 파싱 단계에서 유의사항 문구 재현율 90%+ 목표(파싱 손실이 검토 정확도의 상한을 결정하므로).

nh-data 6개 전부 AdPageIR 생성 성공 (구현: `src/nh_parsing/`, 결과: `out/`).

| 파일 | 경로 | 결과 |
| --- | --- | --- |
| PDF-001 (이미지 PDF) | scan_like → OCR, 12타일 | 363라인, 유의사항 3영역(75/40/62라인), 심의필 2025-0000, 16.9s |
| PDF-003 (PPT 혼합) | p1·p2 scan_like → OCR, p3 structured → 디지털 | 페이지 단위 분기 실증 — p2에서 이미지 안 유의사항 5영역 확보 |
| PNG 2종 (스크롤 캡처) | OCR + 타일링(4~5밴드) | 유의사항 영역·라인 bbox 정상, 라인당 신뢰도 확보 |
| HWP 2종 | 사내 파서 디지털 추출 | 대출성: 21라인 + 심의필 + 금리 5건. 은행연합회: 70라인(표 포함) |

실측에서 확인된 후속 과제:
1. **장식 폰트 수치 오인식**: PNG-002 헤드라인 "최고 연 7.1%" → OCR이 `최고연71%`(소수점 소실). 같은 파일 하단 fine-print에서는 `최고 7.1%` 정상 인식 → **수치 필드는 6.6의 이중 검증(고해상도 크롭 재확인 or VLM 대조) 필수** 입증.
2. **타일 경계 잘림**: 경계에 걸린 텍스트가 저신뢰 깨진 라인으로 재검출됨 → bbox 겹침(IoU≥0.5) 기반 고신뢰 우선 dedupe 로 해소(`tiling.py`). 잔여 저신뢰 라인은 F-003 "판독 확인 필요" 상태로 유지.
3. **VLM 분류 백엔드 불안정**: LiteLLM 뒤 vLLM 연결 실패(500) 발생 — 파일명 prior 폴백으로 파이프라인 무중단 동작 확인. 재시도 정책 필요.

     가드 추가, 걸리면 원값 유지.
   - **크롭 재확인 API 실패의 조용한 삼킴**: `except Exception: continue` 가
     실패 사유를 notes 에 남기지 않아, 002 '최고연71%'(장식 폰트 소수점 소실
     기존 결함) 교정이 "실행마다 되거나 안 되거나" 하는 게 모델 변동인지 API
     신뢰성 문제인지 구분 불가했음. 실패 시에도 notes 기록하도록 수정 →
     실제 원인이 아래 항목으로 즉시 드러남.
   - **guided-decoding 문자열 종료부 손상**(진짜 근본 원인): gemma-4-26b-NVFP4-MTP
     가 문자열 값을 다 쓰고(`finish_reason=stop`) 닫는 따옴표 직전 불필요한
     역슬래시를 내보내 문자열이 안 닫힌 채 응답이 끊김(`Unterminated string`).
     같은 호출을 반복해도 실패 위치/형태가 미묘하게 다름(서버 비결정성) —
     처음엔 max_tokens 부족으로 오진단했으나 raw 응답 직접 캡처로 반증.
     `gemma_client.chat_json` 에 텍스트 전체에서 **마지막 역슬래시 하나만
     제거 후 재파싱**하는 위치 무관 복구(`_repair_trailing_escape`)를 추가 —
     모든 VLM 호출(분류/영역판정/필드추출/캡션/judge)에 자동 적용. 002
     '최고연71%'→'7.1%' 교정이 이후 4/4 재현 성공, judge 가 중복 병합까지
     자동 처리(우대금리 설명 안의 동일 수치와 겹쳐 촉발)하는 전체 체인 확인.
   - 교훈: 조용한 실패를 없애는 것 자체가 디버깅 도구다 — notes 기록을
     추가하자마자 "왜 가끔 실패하는지"가 한 번의 원문 캡처로 바로 드러남.
15. **미배정 라인 섹션 귀속 + 덤프 구조화** (2026-07-20, 사용자 육안 검수 피드백):
   - 사용자 검수에서 "우대이율 안내/상품유의사항에 속해야 할 내용이 미배정"
     지적 → 좌표 대조 결과 전부 해당 섹션 bbox 안에 있는데 레이아웃 블록
     밖이라 배정을 못 받은 것. `pipeline._absorb_unassigned_into_sections`:
     정밀 bbox(ocr/digital) 미배정 라인의 중심점이 섹션 bbox 안이면 최근접
     영역에 귀속(+영역 bbox 확장). vlm_sweep 라인은 근사 bbox 라 제외 —
     y 추정이 이웃 섹션에 떨어지는 오귀속 실측(올원). 재실행: 001 36줄,
     002 14줄, 003 9줄, 올원 1줄, 연합회 6줄 귀속.
   - `dump_text.py` 재작성: y-평탄화 → **묶음(카드) → 섹션 → 영역** 구조 출력
     (003 좌우 카드가 가로질러 읽히던 문제는 파싱이 아니라 덤프 뷰 문제였음 —
     JSON 에는 group_no 로 카드 구분이 이미 존재).
   - 서빙 결함 복구 검증: 연합회 재실행에서 크롭 재확인 실패 0건(수정 전 10여
     건), '연 3,65%'→'3.65%' 등 교정 정상. 채점: 분류 100%/문장 82%/섹션 84%/
     필드 81% — 필드 하락분(-5)은 귀속과 무관한 실행 간 변동 + 기존 백로그
     (금리/우대금리 키, 크롭 교정값 수식어 소실, 이벤트기간 표기 변형).
     → **필드 추출의 실행 간 변동 자체가 백로그 승격** (동일 입력 재실행 시
     ±5건 흔들림 — 프롬프트 안정화 or 다수결 앙상블 검토).
16. **필드 추출 복수 관측 도입** (2026-07-20, 이전 프로젝트 `_add_observation`
   관측→병합 구조 이식 — 위 백로그 해소):
   - `pipeline._extract_fields_multi`: 전체 1회 + **섹션 단위 N회**(섹션 라인
     + 섹션 bbox 크롭 첨부, 상한 12) 관측 → `field_judge.merge_observations`
     가 (key, 정규화 값) 동일·포함 관계를 병합하고 obs_count(득표) 누적,
     더 완전한(긴) 값이 대표. 누락·절단 변동을 합집합으로 흡수.
   - 검증(올원 2회 연속 실행): 골드 관련 핵심 값 13개가 **두 실행 모두 유지**,
     잔여 차이는 부가 문맥 길이 수준. 올원 필드 채점 **10/10 만점** — 상습
     실패 항목('최고 연 3.6%p' 키, '70,200원' 누락) 해소. 비용: 페이지당
     VLM 호출 +7회 수준이나 섹션 크롭이 작아 시간은 회당 ~114s 로 유지.
   - 전체 파이프라인 단계별 시각 가이드 신설: `docs/architecture/pipeline-overview.md`.
   - 평가기: 골드 YAML 인용 보정(내용 무변경), norm 에 백틱·이모지·U+FFFD 제거,
     하이픈은 숫자 사이만 보존(물결 오인식 흡수).

## 부록 B — 사내 파서(document-processor) 제약 상세

- PDF 텍스트/구조: 벤더링된 OpenDataLoader Java CLI(subprocess). pypdfium2는 probe/렌더 전용
- HWP 5.0: jpype1 + hwplib/hwp2hwpx(Java) → HWPX 변환 후 순수 Python 파싱. BinData 이미지 추출됨
- **OCR 없음**: SCAN_LIKE 페이지(전면 이미지, U+FFFD 과다, PUA 난독)는 조용히 스킵(`parse_status="skipped"`, reason `pdf_scan_like`). 전 페이지 스캔이면 빈 DocIR
- 외부 OCR 훅: `pdf/page_images.py::render_scan_like_pdf_pages()` — 파이프라인 미연결, 우리가 연결
- 이미지 입력(PNG/JPG) 최상위 미지원
- 이미지가 asset으로 안 뽑히는 케이스: SCAN_LIKE 스킵 페이지 전체, 벡터 그래픽/패스 텍스트, 인라인 이미지(BI/ID/EI), ODL이 image 노드로 승격 못 한 요소, CMYK/SMask silent drop 가능
- 런타임: Python 3.13+, Java, .NET 8(DOC만)
