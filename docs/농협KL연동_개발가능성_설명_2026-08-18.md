# 농협 KL 연동 — 개발 가능성 설명서

> **이 문서가 답하는 것**
> 1. 농협이 준 자료가 결국 무슨 얘기인가 (플랫폼 구조부터)
> 2. 우리가 만든 파이프라인의 입출력과 농협 규격이 **어디서 어떻게 맞물리는가**
> 3. "개발 가능하다"의 근거가 무엇인가 — 항목별로
> 4. 그걸 **지금 당장 확인할 수 있는가**
> 5. 미확정 1순위(폐쇄망 안 OCR·VLM)가 정확히 무슨 문제인가, **교체가 가능한가**
>
> 작성 2026-08-18. 숫자와 코드 위치는 전부 실측이며 근거를 적었다.
> 이 문서와 코드가 어긋나면 **코드를 믿을 것.**

---

## 0. 이 문서를 읽는 법

§1 을 먼저 읽으면 나머지가 다 그 그림의 세부가 된다. §5~§7 이 "왜 가능한가"의 본문이고,
§8 이 "지금 확인 가능한가"의 답이다. §9 가 회의에서 가장 중요한 미확정 항목이다.

## 1. 전체 그림 — 한 장

```
┌─────────────────────────────────────────────────────────────────────┐
│  농협 내부망 (폐쇄망 = 인터넷 없음)                                    │
│                                                                     │
│   DAP  (농협 AI/데이터 플랫폼)                                        │
│    │                                                                │
│    └─ GenAI Knowledge Lake  ( = "KL" = "날리지 레이크" )              │
│        사내 문서검색(RAG) 시스템                                      │
│                                                                     │
│        문서등록 ─▶ [ 읽기 ] ─▶ [ 자르기 ] ─▶ [ 숫자화 ] ─▶ [ 저장 ]   │
│                      ↑          (청킹)      (임베딩)     (벡터DB)    │
│                      │                                              │
│              ★ 이 자리가 비어 있다 ★                                 │
│                "Custom 파서" 슬롯                                    │
│                                                                     │
│        받은 자료 17개 = 이 슬롯에 꽂을 부품의 규격서 + 빈 껍데기        │
└─────────────────────────────────────────────────────────────────────┘
```

**농협이 요구하는 것은 딱 두 가지다.**

1. 이 슬롯에 맞는 **입출력 규격**을 지켜라 (`POST /parsing` 으로 받고, `_hrc.jsonl` 을 zip 으로 돌려줘라)
2. **벡터 적재는 KL 이 한다** — 우리는 "읽기"까지만

**농협이 요구하지 않는 것**: 어떻게 읽을지. 자료 17개에 파싱 방법에 대한 요구는 **한 줄도 없다.**
그래서 우리 파싱 알맹이는 손대지 않는다.

### 1-1. 우리 트랙이 둘로 갈린다

| 트랙 | 무엇 | 목적 | KL 로 가나 |
|---|---|---|---|
| **규정문서** | 법령·심의사례·은행연합회 준수사항 (HWP/PDF) | 검색해서 심의 근거로 쓴다 | **예 — 여기만** |
| **광고물** | 심의 대상 광고물 (PDF/PNG/HWP) | "이 지적의 근거가 원본 어디인지" 화면 표시 | **아니오** (§4-3 이유) |

이 구분을 놓치면 문서 전체가 헷갈린다. **KL 규격은 규정문서 트랙의 얘기다.**

## 2. 농협 플랫폼 구조 — 자료에서 확인된 것

### 2-1. 계층

```
DAP                          플랫폼 전체 이름
 └─ GenAI Knowledge Lake     RAG 제품 (약칭 KL)
     └─ 문서 인제스천 파이프라인
         └─ 도구 슬롯 4종:  preparser → parser → chunker → postparser
                              ↑
                        우리가 채우는 자리
```

이건 해석이 아니라 자료에 **필드로 박혀 있다** — `readme.md:37` 의 `parser_info`:

```json
{
  "tool_type":   "도구 타입 - parser, chunker, preparser, postparser",
  "exe_type":    "파서 실행 타입 - default, source, api",
  "custom_type": "parser: md/uh/hr, chunker/preparser/postparser: default",
  "pre_parser_id": "Pre 파서 ID",
  "post_parser_id": "Post 파서 ID",
  "is_ocr": "OCR 여부",
  "prop": "OCR/LLM 제공자 정보(SUPPLIER:upstage/...., URL, API KEY)",
  "masking_info": "개인정보 마스킹 정보"
}
```

| 필드 | 읽어야 할 것 |
|---|---|
| `tool_type` 4종 | 문서 처리가 **4단계 플러그인 구조**다. 파서는 그중 한 칸 |
| `pre/post_parser_id` | 파서 앞뒤로 도구를 **체인**으로 붙일 수 있다 |
| `exe_type` 3종 | 파서를 주는 방법이 3가지 — 기본제공 / **소스코드 제공** / **API 연계**. 우리가 받은 건 API 연계 예제(폴더명 `..._example_api`) |
| `is_ocr` + `prop` | **KL 이 OCR/LLM 제공자를 자기가 알고, URL·키를 파서에게 넘겨준다.** 예시로 `upstage` — §9 의 핵심 단서 |
| `masking_info` | 개인정보 마스킹이 플랫폼 관심사로 들어와 있다 |

`custom_type` 의 `hr` = **hierarchization(계층화·구조화)** 으로 보인다.
근거: 출력 파일명 `_hrc.jsonl`, readme 예제 작업폴더 `/work/parser/hr`, readme 제목 "Parsing + 구조화".
`md`·`uh` 는 **자료에 설명이 없어 모른다.**

## 3. 우리 파이프라인의 실제 입출력

### 3-1. 입력

```python
process_file(source: Path, preview_dir) -> AdDocument
```

**파일 경로 하나**를 받는다. 지원 형식: PDF, PNG/JPG, HWP, HWPX.
파일 확장자로 경로를 가르고(`pipeline.py:33`), 파일명을 분류의 사전 근거로도 쓴다.

### 3-2. 출력 — 광고물 트랙 (`out_new/json/*.json`)

실제 산출물에서 그대로 꺼낸 것이다(`out_new/json/1. 대출성상품.json`):

```json
{
  "doc_id": "...", "source_file": "...", "file_type": "pdf",
  "product_group": "대출성", "ad_type": "상세페이지",
  "category_source": "filename_and_vlm", "classification_confidence": 0.9,
  "pages": [
    {
      "page_no": 1, "canvas_w": 2000, "canvas_h": 18206, "dpi": 200,
      "parse_route": "hybrid", "parse_status": "ok", "triage": {...},
      "regions": [
        {
          "region_id": "p1_r000",
          "bbox": [66, 35, 345, 118],
          "label": "header",
          "layout_score": 0.8158,
          "role": "제목",
          "role_confidence": 0.9,
          "role_source": "vlm",
          "role_rule": "고지문구",
          "card_no": null,
          "is_illustrative": false,
          "lines": [
            { "text": "금융의모든순간",
              "bbox": [69, 44, 308, 96],
              "confidence": 0.99996,
              "source": "ocr",
              "vlm_reading": null }
          ],
          "vlm_reading": "금융의 모든 순간*",
          "vlm_reading_score": 1.0,
          "vlm_reading_coverage": 1.0,
          "vlm_reading_relation": "same"
        }
      ],
      "unassigned_lines": [...], "notes": [...]
    }
  ],
  "notes": [...]
}
```

**구조를 말로 옮기면**: 문서 → 페이지 → **영역(Region)** → **줄(Line)**.
영역마다 좌표·레이아웃 라벨·역할·역할신뢰도·역할판정출처·VLM 통독 후보가 붙고,
줄마다 좌표·OCR 신뢰도·출처(`ocr`/`digital`/`vlm_sweep`)가 붙는다.

### 3-3. 출력 — 스키마 추출 트랙 (`out/extracted/*.json`)

```json
{
  "doc_id": "NH농협은행-2026_001-예금성",
  "product_group": "예금성", "ad_type": "이벤트페이지",
  "schema_id": "예금성", "schema_version": "v1",
  "fields": {
    "product_name": {
      "value": "NH올원TEENZ통장",
      "evidence": ["p1_r062"],        ← ★ 영역 ID로 근거를 가리킨다
      "status": "found",
      "group": "G1_상품기본",
      "evidence_score": 1.0, "evidence_backed": true
    },
    "contract_period": {
      "value": "", "evidence": [], "status": "not_found",
      "absence": {                    ← ★ 왜 없는지까지 구분
        "kind": "해당없음", "obligation": "필수",
        "rule": "subtype_not_in", "detail": ["입출금(통장·MMDA)"]
      }
    }
  },
  "coverage": { "regions_total": 62, "regions_cited": 31, ... }
}
```

**`evidence: ["p1_r062"]` 가 핵심이다.** 스키마 필드가 좌표를 직접 들고 있지 않고 **영역 ID를 가리킨다.**
화면에서 근거를 하이라이트할 때 이 ID로 §3-2 산출물에서 bbox 를 찾아 붙인다.
즉 **파싱 산출물과 추출 결과가 ID로 연결된 2층 구조**다.

### 3-4. 출력 — 규정문서 RAG 트랙 (`rag_ingest.py`)

```python
class RagChunk:
    chunk_id: str
    kind: str          # "text" | "table" | "image_caption"
    heading: str|None   # 청크가 속한 조항/제목 (출처 표시용)
    text: str
    asset_id: str|None  # image_caption 청크의 원본 이미지 키
    notes: list[str]
```

**이 트랙이 KL 로 간다.** 좌표가 없고 "제목 + 본문"뿐인 게 우연이 아니라, 애초에 검색용으로 설계했기 때문이다.

## 4. 농협 KL 이 요구하는 입출력

### 4-1. 입력 — KL 이 우리를 부르는 방식

```
POST /parsing
  Content-Type: multipart/form-data
  src_file = (원본 파일 바이너리)
  option   = (base64 로 인코딩한 JSON 문자열)
             디코딩하면 { "parser_info": {...}, "doc_data": {...} }
```

우리 응답 (즉시, 파싱 시작도 전에):

```json
202  {"result":"OK","body":{"uuid":"12378ba806e44279afdf81e6437210a9","timeout":600}}
```

그 다음 KL 이 반복 질문(폴링):

```
GET /parsing/result/12378ba806e44279afdf81e6437210a9
  → 200 {"status":"PARSING"}                    아직
  → 200 {"status":"ERROR","message":"..."}       실패
  → 200 [zip 바이너리]                           완료
```

### 4-2. 출력 — zip 안에 들어갈 것

| 파일명 | 필수 | 내용 |
|---|---|---|
| `원본파일명_hrc.jsonl` | **필수** | 구조화된 본문 (한 줄에 item 하나) |
| `원본파일명_hrc.json` | 요구됨 | 문서 정보 (페이지 수·크기·파싱상태) |
| `원본파일명_img.zip` | 이미지 있으면 | 뽑아낸 이미지들 (zip 안에 zip) |
| `doc_data.json` | 선택 | 메타를 우리가 바꿨을 때만 |

**파일명 규칙**: 확장자를 떼지 않고 그대로 붙인다. `sample.hwp` → `sample.hwp_hrc.jsonl`

### 4-3. `_hrc.jsonl` 의 item — **item 하나에 허용되는 필드 전부**

```json
{"item":"text",  "value":"문장", "page":1,
                 "cust_meta":[{"name":"cust_attr1","value":"문자열"}]}
{"item":"table", "value":"<table><tr><td>...</td></tr></table>",
                 "type_property":{"title":"표 제목"}, "page":2}
{"item":"image", "value":"BIN0001.jpg",
                 "type_property":{"title":"", "width":70, "height":100, "ratio":"11%"}, "page":2}
{"item":"h1"|"h2"|"h3"|"h4", "value":"제목"}
```

이게 **전부**다. 그리고 우리 것과 하나씩 맞춰 보면:

| 우리가 가진 것 (§3-2) | KL item 의 대응 필드 |
|---|---|
| `text: "금융의모든순간"` | ✔ `value` |
| `page_no` | ✔ `page` |
| `bbox: [66,35,345,118]` | **없음** |
| `role: "제목"` | **없음** (h1~h4 는 문서 목차 계층이지 광고물 역할이 아니다) |
| `role_confidence: 0.9` | **없음** |
| `confidence: 0.99996` (OCR 신뢰도) | **없음** |
| `vlm_reading: "금융의 모든 순간*"` (판독 후보) | **없음** |
| `source: "ocr"/"digital"/"vlm_sweep"` | **없음** |

`cust_meta` 에 밀어 넣을 수 있느냐 — **양이 안 맞는다.**
`cust_meta` 는 **문자열 15칸**(`cust_attr1~10` + `cust_sattr1~5`)이고,
문서 하나에 영역이 62~91개, 영역당 필드가 10개 넘는다.

> ### 여기서 반드시 짚을 것
>
> **"우리가 좌표를 모른다"가 아니다. KL 서류 양식에 그걸 적을 칸이 없다는 뜻이다.**
> 우리는 §3-2 처럼 다 갖고 있다.
>
> 그리고 그게 문제가 안 되는 이유: **좌표가 필요한 산출물은 KL 로 보내지 않는다.**
> KL 은 검색 인덱스이고, 광고물 심의 근거는 검색 인덱스에 들어갈 물건이 아니다.
> 광고물은 우리 앱 DB(PostgreSQL)로 간다.

### 4-4. `_hrc.json` (문서 정보)

실제 샘플:

```json
{"name": "sample.hwp", "source": "/HYB008/.../sample.hwp", "file_type": "hwp",
 "size": 260, "title": "인사관리 규정", "subject": "본문", "updated": "",
 "parsed_status": "S",
 "page_info": [{"page":1,"width":21.0,"height":29.7}, ... 17개]}
```

`21.0 × 29.7` = A4 를 **cm** 로 적은 것. readme 의 PDF 예시는 `595.3 × 841.9` = 같은 A4 를 **pt** 로 적었다.
**단위 규정이 없다.** `parsed_status: "S"` 는 성공으로 보이지만 값 목록이 자료에 없다.

### 4-5. 규격서와 실제 샘플의 불일치 4건 — 곧이곧대로 따르면 안 되는 지점

| 항목 | readme.md 는 | 실제 out_sample 은 |
|---|---|---|
| item 유형 | text/table/image/h1~h4 **7종** | 첫 줄이 `{"item":"break","value":"","page":0}` — **8번째 유형** |
| image `value` | "이미지 **파일명**" | **절대경로** `/HYB008/datasets/.../BIN0001.jpg` |
| image 크기 단위 | "**mm** 기준" | `1102 × 557` — A4 폭이 210mm 인데 1102 → **픽셀로 보임** |
| cust_meta 개수 | 표에는 `cust_attr` **1~10** | 본문 예시엔 `cust_arrt1~5` (오타 + 개수 불일치) |

`page` 는 141줄 **전부 0**. readme 가 "모르면 0" 을 허용하고 HWP 는 페이지가 확정되지 않아 그렇다.
**우리 HWP 트랙도 같은 상황이다** — 즉 이 부분은 우리에게 유리하다.

## 5. 둘이 만나는 지점 — 단계별 흐름

이게 "가능하다"의 실체다. **8단계이고, 우리가 새로 쓰는 건 ④와 ⑥뿐이다.**

```
① KL 이 부른다
     POST /parsing  (src_file=규정문서.hwp, option=base64)
     └─ 농협 예제 main.py 가 이미 구현.  우리 작업: 없음

② 우리가 즉시 202 를 답한다 + 파일을 작업폴더에 저장
     {"result":"OK","body":{"uuid":"...","timeout":...}}
     └─ 농협 예제 main.py 가 이미 구현.  우리 작업: timeout 값만 우리 실측으로 조정

③ 뒤에서 별도 프로세스가 parsing_service.parse() 를 호출한다
     └─ 농협 예제 main.py 가 이미 구현.  우리 작업: 없음

④ parse() 안에서 우리 파이프라인을 부른다              ★ 우리가 쓴다 (얇다)
     방식 A: 같은 컨테이너 안에서 함수 직접 호출
     방식 B: 별도 에이전트 서비스에 HTTP 요청
             ← 회의 결정문("실제 문서 처리는 별도 에이전트 서비스")이 B

⑤ 우리 파이프라인이 돈다 (알맹이 — 손대지 않는다)
     ingest_rag_file(경로) → RagDocument{chunks[RagChunk]}
     └─ 우리 작업: 없음.  이미 동작하는 코드

⑥ RagChunk[] → _hrc.jsonl 로 직렬화                    ★ 우리가 쓴다 (신규)
     + _hrc.json (문서정보) + _img.zip (이미지)
     └─ 매핑은 §5-1.  거의 1:1

⑦ 작업폴더에 파일을 놓고 상태를 DONE 으로 바꾼다
     └─ 농협 예제 parsing_service.write_parse_status() 가 이미 구현

⑧ KL 이 폴링해서 가져간다 → zip 으로 묶어 반환 → 작업폴더 삭제
     └─ 농협 예제 main.py 가 이미 구현.  우리 작업: 없음
```

### 5-1. ⑥의 매핑 — 실제로 거의 1:1 이다

```
RagChunk.kind == "text"           →  {"item":"text",  "value": chunk.text, "page": n}
RagChunk.kind == "table"          →  {"item":"table", "value":"<table>…",
                                       "type_property":{"title":""}, "page": n}
RagChunk.heading (조항/조 제목)     →  {"item":"h1"|"h2"|…, "value": heading}
RagChunk.kind == "image_caption"  →  ★ 판단 필요 (아래)
내장 이미지 파일                    →  {"item":"image","value":"BIN0001.jpg",
                                       "type_property":{"title":"","width":…,"height":…,"ratio":"…"}}
                                     + 실제 파일은 _img.zip 에
```

**`image_caption` 만 결정이 필요하다.** KL 의 `image` item 은 `value` 가 파일명이고
캡션 텍스트를 담을 곳이 `type_property.title` 뿐인데, 우리 캡션은 "전사 + 설명" 문단이라 title 에 맞지 않고
무엇보다 **title 이 임베딩 대상인지 확실하지 않다.**

→ **`text` item 으로 넣는 것이 맞다.**
근거: readme 의 "VectorDB 활용 예"에서 본문으로 임베딩되는 건 `TEXT` 타입의 `value` 다.
이미지 자체는 `image` item + `_img.zip` 으로 보내고, 캡션은 **text item 으로 그 뒤에 붙이면** 검색에 걸린다.

**이게 우리 커스텀 파서의 존재 이유 그 자체다.** KL 기본 파서는 이미지 안 글자를 못 읽는데:

- 은행연합회 예금성 준수사항 HWP: **금리 표기 사례 스크린샷 10장** 안에 실질 심의 기준이 있다
  (`rag_ingest.py` 모듈 주석, 2026-07-18 실측)
- 대출성 준수사항 PDF: **6쪽 중 3쪽이 스캔 페이지라 사내 파서가 조용히 건너뛰어, 규정 원문 한 쪽이
  RAG 인덱스에 없었다** (2026-08-12 실측)

우리는 전자를 VLM 캡션으로 텍스트화하고, 후자를 렌더해서 OCR 로 되살린다.

## 9. 미확정 1순위 — 폐쇄망 안에서 OCR·VLM 을 무엇으로 쓰는가

지난 설명에서 "③군 1순위" 라고 줄여 쓴 게 이것이다. **회의에서 가장 중요한 항목이다.**

### 9-1. 문제가 정확히 무엇인가

우리 파이프라인은 **AI 모델을 직접 돌리지 않는다. 두 서버에 HTTP 로 물어본다.**

```
paddlex_client.py:87   →  PADDLEX_URL  =  https://pika.ihopper.co.kr/paddlex/layout-parsing
                          (PP-StructureV3 — 레이아웃·영역 검출 + OCR)

gemma_client.py:102    →  GEMMA_URL    =  https://pika.ihopper.co.kr/llm/v1/chat/completions
                          GEMMA_MODEL  =  spark-gemma-4-26b-NVFP4-MTP
                          (Gemma 4 26B — VLM 판독·역할판정·분류·스키마추출)
```

`pika.ihopper.co.kr` 은 **우리 사내 클러스터**다. 농협 폐쇄망 안에서는 **접속이 안 된다.**

> **이 두 개가 폐쇄망 안에 없으면, 껍데기를 완벽히 만들어도 파싱 결과가 0건 나온다.**

얼마나 의존하는지 숫자로:

| | 값 |
|---|---|
| VLM 호출 | 문서당 **11.9회** (89건 1,057회) |
| VLM 대기가 전체 처리시간에서 | **98%** |
| VLM 을 쓰는 단계 | 실측 5단계 — `band_read`(밴드 통독), `lowconf_line_reread`(저신뢰 재판독), `region_roles`(역할 판정), `missing_text_sweep`(누락 스윕), `ad_classification`(분류) + 카드분할·스키마추출·이미지캡션 |
| VLM 호출 지점 | 코드상 **9곳** (`vlm_direct.py` 4, `cards.py`·`extract.py`·`extract_models.py`·`rag_ingest.py`·`vlm_judge.py` 각 1) |
| OCR 호출 지점 | **2곳** (`pipeline.py:155`, `rag_ingest.py:177`) |

### 9-2. 선택지 셋

| 안 | 내용 | 영향 |
|---|---|---|
| **가** | 농협이 폐쇄망 안에 PP-StructureV3 + Gemma 4 26B 를 올려 준다 | **파싱 품질 그대로.** 26B 모델이라 GPU 자원 필요 → 농협 확인 |
| **나** | 농협 DAP 가 제공하는 OCR/LLM 을 쓴다 | 규격상 가능(§2-1 의 `prop` 필드가 공급자 URL·키를 주입하는 구조, 예시 `upstage`). **단 파싱 지표 전부 재측정** |
| **다** | 우리 장비(DGX Spark 등)를 반입한다 | 우리 메일의 "장비 반입 절차" 문의가 이것 |

### 9-3. "바로 교체 가능한가" — 코드를 읽고 답한다

**질문을 두 개로 나눠야 한다.** ① 코드를 갈아끼우는 게 쉬운가, ② 갈아끼운 게 같은 일을 해 주는가.

#### OCR(PaddleX) 교체 — 코드는 한 파일, **기능 요건이 까다롭다**

접점은 `paddlex_client.py` **한 파일(187줄)** 이고 호출은 2곳뿐이다. 어댑터를 새로 쓰면 된다.
**문제는 우리가 이 서버에서 받아 쓰는 것이 "글자"만이 아니라는 점이다:**

```python
# 응답에서 실제로 꺼내 쓰는 것 (paddlex_client.py:102~139)
pruned["overall_ocr_res"]["rec_texts"|"rec_scores"|"rec_boxes"|"rec_polys"]
    → OCR 라인 (글자 + 좌표 + 신뢰도)          ← 대부분의 OCR API 가 준다

pruned["parsing_res_list"][].{block_bbox, block_label, block_content}
    → ★ 레이아웃 블록 (좌표 + 라벨 + 읽기순서 + 블록 본문)
      ← 이걸 주는 서비스는 흔하지 않다

pruned["layout_det_res"]["boxes"][].{coordinate, label, score}
    → 검출 확신도 (진단용, 없어도 됨)
```

**`parsing_res_list` 가 우리 파이프라인의 뼈대다.** 우리 "영역(Region)" 개념이 여기서 나오고,
그 위에 역할 판정·카드 분할·스키마 근거(`evidence: ["p1_r062"]`)가 전부 올라가 있다.

→ 만약 대체 OCR 이 **글자 줄만** 주고 레이아웃 블록을 안 주면,
**영역·역할·카드분할이 통째로 사라진다** = 파이프라인의 핵심이 없어진다.

**판정**: 코드 교체는 한 파일. 하지만 **"레이아웃 블록 + 읽기순서를 주는 OCR"** 이라는 조건을
만족하는 대체품이어야 한다. 조건을 못 맞추면 교체가 아니라 재설계다.

#### VLM(Gemma) 교체 — **거의 설정만 바꾸면 된다** (단, 요건 3개)

우리 VLM 호출은 **OpenAI 호환 표준 인터페이스**다(`gemma_client.py:90~101`):

```python
payload = {
    "model": SETTINGS.gemma_model,
    "temperature": 0,
    "max_tokens": max_tokens,
    "messages": [{"role": "user", "content": content_parts}],   # 텍스트 + 이미지 파트
    "response_format": {
        "type": "json_schema",
        "json_schema": {"name": schema_name, "strict": True, "schema": schema},
    },
}
```

→ **URL 과 모델명만 바꾸면 코드 수정이 거의 없다.** 단 대체 모델이 세 가지를 만족해야 한다:

| 요건 | 왜 필요한가 |
|---|---|
| ① OpenAI 호환 `/v1/chat/completions` | 위 payload 를 그대로 받아야 함 |
| ② **이미지 입력(vision) 지원** | 우리는 이미지를 넣고 판독을 시킨다 — 텍스트 전용 LLM 은 못 씀 |
| ③ **strict json_schema (guided decoding) 지원** | 코드 주석: *"LiteLLM→vLLM 경로에서 실제로 강제되는 유일한 구조화 출력 모드"*. 이게 없으면 응답이 JSON 형식을 안 지켜 파싱이 깨진다 |

③이 특히 중요하다. 우리는 이미 이 부분에서 결함을 두 번 겪었다
(strict schema 에서 배열이 빈 채 오던 퇴행, 닫는 따옴표 앞 역슬래시 오발행). 모델이 바뀌면 **재검증이 필요하다.**

**판정**: 코드 관점에서는 **URL·모델명 교체 수준**. 기능 요건 3개를 만족하는 모델이어야 하고,
**품질은 반드시 재측정**해야 한다(판독 품질이 파이프라인 산출물의 절반을 만든다).

#### 정리

| | 코드 변경량 | 기능 요건 | 품질 영향 |
|---|---|---|---|
| **OCR** | 한 파일(187줄) 어댑터 재작성 | **까다롭다** — 레이아웃 블록 + 읽기순서 필수 | 없으면 파이프라인 재설계 |
| **VLM** | 거의 없음 (URL·모델명) | OpenAI호환 + vision + strict schema | **재측정 필수** |

**회의 발언용**:
> *"우리 파이프라인은 레이아웃 검출과 VLM 판독을 별도 모델 서버에 HTTP 로 요청하는 구조입니다.
> VLM 은 표준 인터페이스라 교체 자체는 설정 수준이지만, 이미지 입력과 구조화 출력을 지원하는
> 모델이어야 하고 품질은 다시 측정해야 합니다.
> OCR 은 단순 글자 인식이 아니라 레이아웃 영역과 읽기순서까지 받아 쓰고 있어서, 그걸 주지 않는
> 서비스로 바꾸면 우리 파이프라인의 핵심인 영역·역할 구조가 사라집니다.
> 그래서 폐쇄망 안에서 이 두 모델을 어떻게 확보하느냐가 먼저 정해져야 합니다."*

## 10. 조건부 1건 — HWP + Python 3.11

| 사실 | 근거 |
|---|---|
| 우리는 HWP·HWPX 를 사내 파서(`document-processor`)로 읽는다 | 코드 |
| 그 파서가 **Python 3.13 이상**을 요구한다 | 설치본 메타데이터 `Requires-Python: >=3.13` |
| 그 파서는 내부적으로 **자바**를 쓴다 | JAR 6개(hwplib 1.1.10, hwpxlib 1.0.8, opendataloader-pdf-cli 2.2.1 등) + `jpype1` |
| 농협 환경은 **3.11** 기준 | 회의 결정사항 |

**우리 파싱 코드 자체는 3.11 에서 문제없어 보인다** — 3.12+ 전용 문법·기능을 하나도 안 쓴다
(match문 0, PEP695 0, `Path.walk` 0, `itertools.batched` 0, `typing.override` 0, `tomllib` 0 — 전수 grep).
**걸리는 건 사내 파서 하나다.**

해결 경로:

| 안 | 내용 | 비용 |
|---|---|---|
| **A** | 3.11 은 **KL 진입점 껍데기에만** 적용, 실제 처리하는 에이전트 서비스는 별도 이미지(3.13 + JRE) | **가장 자연스럽다** — 회의 결정문("실제 문서 처리는 별도 에이전트 서비스") 그대로. 농협에 적용 범위만 확인 |
| **B** | 사내 파서를 3.11 에서 돌게 내린다 | **반나절이면 사실 확인 끝.** 선언만 3.13 이고 실제로 도는 경우가 흔하다 |
| **C** | HWP 를 다른 방법으로 읽는다 | 큼 (최후) |

## 11. 회의 답변 스크립트

지난 설명의 "④-Q1" 이 이것이다. 그대로 말할 수 있게 풀어 썼다.

**Q. 그래서 개발 가능합니까?**
> 커스텀 파서로 붙이는 것 자체는 가능합니다. 규격이 명확하고, 농협이 준 예제가 통신 부분을 이미
> 구현해 놨습니다. 우리가 새로 만들 것은 우리 파이프라인을 부르는 코드와, 결과를 농협 형식으로
> 바꿔 쓰는 코드 두 개입니다.
> 다만 폐쇄망 안에서 OCR·VLM 모델을 어떻게 확보할지가 정해져야 실제로 돌려볼 수 있습니다.
> 우리 파이프라인은 그 두 모델을 외부 서버로 호출하는 구조이기 때문입니다.

**Q. 얼마나 걸립니까?**
> 껍데기는 규격이 명확해서 오래 걸리지 않습니다. 일정을 좌우하는 건 두 가지입니다 —
> 사내 HWP 파서의 3.11 호환 확인(반나절이면 답이 나옵니다), 그리고 모델 확보 방식 결정입니다.
> *(구체 기간은 이 두 개 종속으로 두는 것이 안전하다.)*

**Q. 파이썬 3.11 로 됩니까?**
> 우리 파싱 코드는 문제없습니다. 사내 HWP 파서 하나가 3.13 과 자바를 요구하는데,
> 회의 결정대로 "실제 처리는 별도 에이전트 서비스"로 두면 3.11 제약은 진입점에만 적용되어
> 해결됩니다. 그게 아니면 파서를 3.11 로 내리는 방법을 검증하겠습니다.

**Q. 반입할 라이브러리가 많습니까?**
> 적습니다. 농협 베이스 이미지의 284개를 전수 대조했고, 이미지·PDF 처리 기준으로는 pypdfium2
> 하나입니다. HWP 까지 포함하면 자바 실행환경이 추가됩니다. 목록은 3.11 검증이 끝나는 대로
> 전달하겠습니다.

**Q. 벡터DB 적재는요?**
> 우리가 하지 않습니다. 구조화된 결과물만 내놓고, 자르기·임베딩·적재는 KL 파이프라인이 합니다.
> 회의 결정사항 그대로입니다.

**Q. 지금까지 만든 파싱은 버리는 겁니까?**
> 아닙니다. 파싱 알맹이는 그대로 씁니다. 농협 자료에 "어떻게 파싱하라"는 요구는 없고 입출력
> 규격만 있습니다. 껍데기 하나를 추가하는 일입니다.
> *(숫자를 원하면: 89건 전수 검증, 영역 검출 2,463개, 텍스트 유실 0 — 3회 실행에서 정본 글자수 59,949 동일)*

**Q. 농협 예제 코드 그대로 쓰면 됩니까?**
> 거의 그대로 쓸 수 있지만 결함 두 개를 찾았습니다. 특히 타임아웃 설정값을 환경변수로 주면
> 오류로 죽는 버그가 있어서, 우리 문서가 최대 590초라 타임아웃을 늘리려는 순간 물립니다.
> 고쳐서 쓰겠습니다.

**Q. 광고물도 이 경로로 들어갑니까?**
> 그 부분은 우리가 제안해야 할 사항입니다. 농협 형식에는 좌표를 담을 칸이 없는데, 광고심의는
> "이 지적의 근거가 원본 어디인지"를 화면에 표시해야 해서 좌표가 본질입니다.
> 그래서 규정문서는 KL 로 보내고, 광고물은 우리 앱이 직접 처리하는 쪽으로 설계하려 합니다.

## 12. 용어 사전

|---|---|

| **RAG** | 검색으로 보강한 생성. 문서를 미리 저장해 두고 질문에 관련 조각을 찾아 LLM 에 붙여 주는 방식 |
| **청킹** | 문서를 검색 단위로 자르는 것 |
| **임베딩** | 글자를 숫자 배열(벡터)로 바꾸는 것 |
| **벡터DB** | 그 숫자 배열을 저장하고 "가까운 것"을 찾아 주는 데이터베이스 |
| **jsonl** | JSON Lines. 한 줄에 완결된 JSON 하나. 줄 수만큼 데이터가 있다 |
| **`_hrc`** | hierarchization(계층화·구조화)의 줄임으로 보임. KL 출력 파일명 규칙 |
| **폴링(polling)** | "다 됐어?" 를 반복해서 묻는 방식 |
| **202** | HTTP 상태 코드. "접수했다, 아직 처리 중" |
| **multipart/form-data** | 파일과 텍스트를 한 HTTP 요청에 섞어 보내는 방식. 웹에서 파일 첨부와 같은 것 |
| **base64** | 아무 데이터든 영문·숫자·`+/=` 만으로 표현하는 변환. 전송 중 깨지지 않게 쓴다 |
| **`.sh`** | 셸 스크립트. 터미널에 칠 명령들을 파일에 순서대로 적어 둔 것 |
| **`.whl` (휠)** | 파이썬 패키지를 미리 만들어 압축해 둔 설치 파일. 실체는 zip. 이름에 파이썬 버전·OS 가 박힌다 |
| **pip / PyPI** | 패키지 설치 도구 / 패키지가 올라가 있는 인터넷 저장소 |
| **PYTHONPATH** | 파이썬이 패키지를 찾을 때 뒤지는 폴더 목록 |
| **폐쇄망** | 인터넷과 물리적으로 끊긴 내부망. `pip install` 이 안 된다 |
| **컨테이너 이미지** | 프로그램 + 라이브러리 + 설정을 한 덩어리로 굳혀 놓은 것 |
| **베이스 이미지** | 이미지를 만들 때의 출발점. "우분투 + 파이썬 3.11 + 라이브러리 284개"까지 깔린 상태 |
| **FastAPI / uvicorn / gunicorn** | 요청→함수 규칙을 쓰는 도구 / 실제로 포트를 열고 요청을 받는 서버 / 그 서버를 여러 개 띄워 관리하는 관리자 |
| **PP-StructureV3** | 우리가 쓰는 레이아웃 검출 + OCR 모델 (PaddleX 서버로 호출) |
| **VLM** | Vision Language Model. 이미지를 보고 글로 답하는 모델. 우리는 Gemma 4 26B 를 쓴다 |
| **guided decoding / strict json_schema** | 모델 응답이 정해진 JSON 구조를 벗어나지 못하게 강제하는 기능 |
| **영역(Region)** | 우리 IR 의 단위. 레이아웃 블록에서 나오고, 역할·좌표·판독후보가 붙는다 |
| **`evidence: ["p1_r062"]`** | 스키마 추출 결과가 근거를 가리키는 방식. 영역 ID 이고, 이걸로 좌표를 되찾는다 |
