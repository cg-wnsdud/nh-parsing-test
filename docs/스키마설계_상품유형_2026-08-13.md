# 상품유형 스키마 설계 — 정본 확정 계층

> **이 문서가 답하는 것**: 파싱 파이프라인의 마지막 단계에 왜 스키마가 필요하고, 예금성·대출성
> 두 스키마를 어떤 구조로 짰는가.
>
> 작성 2026-08-13. 근거는 전부 실제 자료·실제 산출물이며 위치를 적었다.
> 필드 표는 스키마 파일에서 생성한 것이다(손으로 옮기지 않았다).

---

## 1. 이 계층은 심의 판정을 하지 않는다

기존 스키마는 심의 체크리스트 항목에 1:1 대응하는 구조였다. 그래서 "심의를 준비하는 것"처럼
보였지만, 이 계층이 실제로 해야 하는 일은 셋이다.

| | 목적 | 왜 스키마가 필요한가 |
|---|---|---|
| **A** | **정본 확정** — OCR본과 VLM본이 갈릴 때 무슨 근거로 어느 쪽을 채택할지 | 필드의 성격이 판정 정책을 결정한다 (§3) |
| **B** | **전량 전달** — 입력의 모든 텍스트를 빠짐없이 RAG/DB 엔진으로 | 필드가 있어야 "어디에도 안 실린 텍스트"를 셀 수 있다 (§6) |
| **C** | **표현 보존** — 광고 문구도 원문 그대로 같이 넘어감 | 다듬으면 심의 대상 자체가 사라진다 (§3) |

산출물은 "심의 결과"가 아니라 **확정된 최종 파싱 결과 + 그 확정 근거**다.

**왜 이 자리인가.** [truncation.py:38](../src/nh_parsing/truncation.py#L38)이 `diverged` 를
*"서로 다른 내용 — 어느 쪽이 맞는지 여기서 못 정함"* 으로 명시해 두었다. 5문서 225영역 중
실제로 갈린 것이 38건(`diverged` 21 · `head_drop` 8 · `tail_cut` 5 · `expanded` 4)이고,
**그 21건을 정하는 자리가 없었다.** 이 스키마가 그 자리다.

## 3. 핵심 설계 — 필드의 `kind` 가 판정 정책을 결정한다

OCR과 VLM은 **실패 방식이 다르다.** 그래서 교차검증이 성립하지만, 어느 쪽을 믿을지는
필드 성격마다 다르다. 5문서 실측에서 나온 충돌 30건을 분류해 정책을 뽑았다.

| `kind` | 예 | OCR 실패 | VLM 실패 | 판정 정책 |
|---|---|---|---|---|
| `numeric` | 금리·기간·한도·요율 | 소수점·단위 소실<br>`최고연71%` ← `7.1%` | 숫자를 바꿔 씀<br>`추첨15` → `추첨 10명` | 숫자 정합성이 심판 |
| `template` | 심의필·예금자보호·설명권리 | 글자 오독 | 뒤 잘림 | 정형 문구 근접도 |
| `verbatim` | 헤드라인·광고카피·표현 | 장식 폰트 실패 | 예쁘게 다듬음 | **판정 안 함 — 양쪽 보존** |
| `enum` | 세부유형·고정변동 여부 | — | — | 판독 무관하게 문구에서 추론 |
| `collection` | `rate_mentions`·`figure_mentions` | — | — | 합치지 않고 전수 수집 |

### `verbatim` 이 왜 "판정 안 함" 인가

실측: 003 광고는 헤드라인에 `총 1,000명`, 경품박스에 `(선착순 1,000팀)` 이라고 **서로 다르게**
적혀 있었는데, 추출이 이걸 하나로 합쳐 **표기 불일치 자체가 사라진** 적이 있다. 그 불일치가
심의가 잡아야 할 대상인데도. `verbatim` 은 정본이 곧 원문이라, 다듬는 순간 목적 C가 깨진다.

### `numeric` 의 판정 우선순위 (실측 근거 순)

```
1. 양쪽 일치                    → 확정
2. 한쪽만 유효 수치 형태          → 그쪽    (OCR '최고 [요'  vs  VLM '최고 연 7.1%')
3. 문서 내 정합성                → 맞는 쪽  (올원e ①0.1+②0.2+③0.2 = 최고 0.5%p ✓)
4. 알려진 실패 패턴              → 회수     (OCR 이 원문자를 숫자로 붙임: '1O.1%p' ← '① 0.1%p')
5. 관계 딱지                    → tail_cut 이면 정본(OCR) 채택
6. 그래도 못 정하면              → 양쪽보존 + 사람 검수   ← 억지로 정하지 않는다
```

**표기 규약을 하드 판정 근거로 쓰지 않는 이유.** 처음엔 규정의 표기 규약(`연`·`세전`·`%p`)을
심판으로 쓸 생각이었는데, 준수사항·가이드라인 네 문서를 전수 검색한 결과 **명문 규정이 없다** —
`소수점`·`환산`·`기준일` 0건, `%p` 는 예시 이미지 1건뿐이고, 관측된 소수점 자리수도
제각각(`4.75` / `5.463` / `5.8`)이다. 규약을 규칙으로 승격하면 과적합이다. 따라서 표기 규약은
**약한 신호**로만 쓰고 강한 판정은 숫자 정합성에 둔다.

## 4. 결정적 분기 — 판독 충돌과 광고 자체의 오류는 다르다

004 대출성 광고(`공무원을 위한 신용대출`)를 검산했다. 이 광고는 **심의사례에 실제로 등장하는
바로 그 광고**이고, 지적된 결함이 파일에 그대로 남아 있다.

```
광고 표기: 최저 연 4.45% ~ 최대 연 5.45%
광고 표기: 기준금리 3.10% + 가산금리 2.30% - 우대금리 1.00%p

  기준+가산       = 5.40  vs 최대 표기 5.45   →  불일치
  기준+가산-우대  = 4.40  vs 최저 표기 4.45   →  불일치
  역산: 5.45-2.30 = 3.15  /  4.45-2.30+1.00 = 3.15   →  양쪽에서 같은 답

  우대금리 조건별 합 0.2+0.3+0.2+0.1+0.2 = 1.00%p  vs 표기 1.0%p  →  일치
```

심의사례의 지적과 정확히 일치한다 — `대출금리 산출기준 계산 오류`,
수정후 `기준금리(3.15%)`. 그런데 **004는 HWP 디지털 텍스트라 판독 충돌이 아니다.**
판독은 하나뿐이고, 틀린 건 광고 자체다.

그래서 두 개념을 갈라야 한다:

| 구분 | 정체 | 우리가 할 일 |
|---|---|---|
| `reading_conflict` | OCR ≠ VLM | **정해야 함** — §3 우선순위로 판정, 근거 기록 |
| `arithmetic_mismatch` | 확정 텍스트 안에서 숫자가 안 맞음 | **고치면 안 됨** — 신호만 남기고 원문 보존 |

**이 구분을 놓치면 두 방향으로 다 틀린다.** 판독 충돌을 안 정하면 없던 불일치를 만들어
허위 지적을 유발하고(OCR `1O.1%p`), 광고 자체의 오류를 "고쳐주면" 진짜 지적사항이
사라진다(004 `3.10%`).

이 때문에 대출성 스키마는 **기준금리·가산금리·우대금리·최저금리·최고금리를 각각 분리**한다.
합·차 검산이 가능한 형태로 넘기는 것까지가 우리 일이고, 검산해서 위반이라고 판정하는 건
심의 엔진의 일이다. 검산 관계를 선언한 필드는 표에서 ⚖ 로 표시했다.

## 5. 파일 구성

```
src/nh_parsing/schemas/
├── _common.json      31필드 · 5그룹   예금성·대출성 공통
├── 예금성.json        31필드 · 4그룹   includes: _common  →  합 62필드 · 9그룹
├── 대출성.json        38필드 · 5그룹   includes: _common  →  합 69필드 · 10그룹
└── _overlay_이벤트.json  11필드        (이번 범위 밖 — 광고유형 축)
```

공통부를 분리한 근거: 두 체크리스트를 대조하니 은행명·심의필·약관필독·설명권리·수수료·
통계출처·수상인증·제휴서비스·추천보증·전자적전송매체·공동광고가 **DEP-*/LOAN-* 양쪽에
같은 문구로 존재한다.** 갈리는 건 금리 축과 상품 고유 조건뿐이다.

**갈라지는 지점이 곧 두 상품군의 차이다:**

| | 예금성 | 대출성 |
|---|---|---|
| 금리 구조 | 기본금리 **+** 우대금리 = 최고금리 | 기준금리 **+** 가산금리 **−** 우대금리 |
| 강조 금지 대상 | 최고금리 | 최저금리 |
| 병기 의무 대상 | 기본금리 | 최고금리 (**광고면적 무관** — 예금성엔 없는 한정구) |
| 전용 항목 | 우대조건별 구분 표기, 추첨 당첨확률, 만기 수취이자 예시 | 신속성 과장 지양, 플랫폼 금리 최신화, 부대비용·중도상환 |
| 적용제외 | 입출금이자유로운예금, 외화예적금 | 예적금담보대출 |

## 6. 전량 보존을 구조로 강제한다

목적 B는 "빠짐없이"인데, 이건 프롬프트로 부탁할 일이 아니라 **셀 수 있게 만들어야** 한다.
3층으로 받는다.

```
① 구조화 필드        스키마 필드 (검산 가능한 형태)
② 전수 수집 배열      figure_mentions · rate_mentions · other_notices · non_ad_text
③ unmapped          어느 필드에도 안 맞은 문구 (기존, 모든 호출그룹 필수)
                     ↓
   coverage_audit    모든 region_id 가 ①②③ 중 최소 한 곳에 등장했는지 코드 검산
```

`non_ad_text` 를 새로 넣은 이유가 있다. 실측에서 OCR이 `표지`·`내지1`·`내지2`·`이벤트 시안`
같은 **인쇄·제작용 라벨**을 주웠다. 이건 광고 내용이 아니라 심의 대상 문구로 올라가면
오탐이 되는데, 그냥 버리면 유실이다. 지우지 않고 따로 모은다.

## 8. 체크리스트 커버리지 (코드 집계)

NH 준법감시부 체크리스트를 스키마가 실제로 얼마나 가리키는지 코드로 셌다.

| 상품군 | 체크리스트 항목 | 커버 | 미커버 |
|---|---|---|---|
| 예금성 | 37 | **36** | 1 (`DEP-PLUS-01`) |
| 대출성 | 36 | **35** | 1 (`LOAN-PLUS-01`) |

미커버 2건은 둘 다 `그 외 사유` 항목이고 근거가 `심의의견에 별도로 작성` 이다 — 규칙이 아니라
운영용 예비 항목이므로 필드로 만들 대상이 아니다. 구조적으로는 `other_notices` +
`unmapped` 가 같은 역할을 한다.

무효 참조 0건 — 모든 `checklist_ref` 가 실재하는 항목ID를 가리킨다.

## 10. 확인 필요 — 근거가 약한 것을 숨기지 않는다

| # | 항목 | 왜 확인이 필요한가 |
|---|---|---|
| 1 | **대출 세부유형 enum** | NH 체크리스트와 준수사항에는 대출 세부유형 분류축이 **없다.** 지금 목록은 실데이터 광고명과 004 본문에서 관측한 잠정 분류이므로 `status: 확인필요` 로 표시해 뒀다. 준법감시부 확인 필요 |
| 2 | **`DEP-FMT-01` / `LOAN-FMT-01` (글자 색깔·크기 균형)** | 텍스트만으로 판정 불가. 관측 필드(`obs_*_only_emphasis`)로 "기본금리가 아예 없거나 멀리 떨어져 있음" 만 잡는다. 실제 심의사례엔 `유의사항 글자크기 7pt → 10pt` 같은 지적이 있는데 **우리는 pt 를 모른다.** 가이드라인은 오히려 수치 기준을 없애고 포괄 규정으로 바꿨다고 명시 |
| 3 | **예금자보호 한도** | 자료 간 충돌(5천만원 vs 1억원)이 남아 있다. 스키마는 값을 고정하지 않고 광고에 적힌 숫자를 그대로 담게 했다 — 현행 규정 일치 여부는 심의 엔진이 판정 |
| 4 | **`rate_annual_marker` / `rate_tax_basis` 의 enum 판정** | "일부에만 붙어 있으면 표기없음" 규칙은 우리가 정한 것이다(`basis: derived`). 실제 심의가 어떻게 보는지 확인 필요 |
| 5 | **근거 자료 자체의 파싱 결함** | 대출성 준수사항 **3쪽 전체가 파싱에서 누락**됐다(`pdf_scan_like`). 소실된 것이 `2. 예시` 절 전부라 금리 병기 예시 6건이 통째로 빠진다. 가이드라인 16쪽 2단 표는 셀 순서가 뒤섞여 **유형이 뒤바뀐 결합**이 만들어진다. 근거대장을 이 JSON 으로 갱신할 때 반드시 원본 대조 필요 |
| 6 | **이벤트 오버레이** | 이번 범위 밖(광고유형 축)이라 손대지 않았다. `kind` 미부착 상태이므로 다음 차례에 정합 |

## 11. 구현 중 드러난 조용한 실패 경로 (중요)

스키마 파일만 고치고 테스트를 돌렸더니 2건이 깨졌다. 원인을 파보니 **스키마 변경만으로는
안 되는 결함**이었다 — 기록해 둘 가치가 있다.

세부유형 용어를 `입출금(통장·MMDA)` → `입출식` 으로 바꿨을 때 이런 경로가 열렸다:

```
값:   "입출금(통장·MMDA)"        (구 용어, 신 스키마 enum 에 없음)
조건: subtype_not_in: ["입출식"]

  "입출금(통장·MMDA)" in ["입출식"]  →  False
  not_in 조건 → True → 조건 통과
  → 필드가 '필수·전 광고' 로 평가
  → 없던 '미표시' 지적이 생성된다
```

조건 문법이 **부정형**(`subtype_not_in`)을 쓰기 때문에, 스키마가 모르는 문자열이 들어오면
"목록에 없음" 이 참이 되어 조건이 그냥 통과한다. 값이 깨진 게 아니라 **어휘가 바뀐 것만으로도
허위 지적이 생긴다.** 기존 코드에는 `판단불가` 가드는 있었지만 "선언된 enum 에 없는 값"
가드는 없었다.

**고친 방법**: 스키마가 분류축 필드와 유효값을 스스로 선언하고(`subtypes.field_key` /
`values`), `applicability._read_subtypes()` 가 그걸 읽어 검증한다. 선언에 없는 값이면
유형을 모르는 것으로 취급해 `확인필요` 로 보낸다 — 해당없음도 미표시도 아니다.

회귀 테스트 2개를 고정했다: `test_스키마가_모르는_유형값은_확인필요로_간다`,
`test_복수유형_광고는_한쪽만_맞아도_대상이다`.

**부수 발견**: `deposit_kind`·`contact_info` 가 `권장` 등급이었는데, `권장` 은 판정 대상이라
**표기가 없을 때마다 '미표시' 가 생긴다.** 두 항목은 체크리스트·조문 근거가 없는 관측
항목이므로 `수집`(판정 제외)으로 내렸다. 근거 없는 항목에 판정 등급을 주면 지적사항이
부풀려진다.

| [applicability.py](../src/nh_parsing/applicability.py) | 배열 세부유형 + enum 검증 (§11) |
| [reclassify_absences.py](../tools/reclassify_absences.py) | 출력 키 변경 반영 (`product_subtype` → `product_subtypes`) |

**남았다**

| # | 대상 | 내용 |
|---|---|---|
| 1 | `schema_pack.response_schema()` | 응답 envelope 에 `reading_choice` 추가 (enum 5종). **판정 근거·신뢰도는 LLM 이 아니라 코드가 붙인다** — 이 저장소 원칙(판단은 VLM, 검산은 코드) |
| 2 | 신규 `adjudicate.py` | §3 우선순위를 코드로. `arithmetic_mismatch` 는 고치지 않고 신호만 (§4) |
