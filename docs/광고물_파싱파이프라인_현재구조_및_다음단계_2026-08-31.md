# NH 광고물 파싱 파이프라인: 현재 구조, 산출물, 다음 단계

> 최초 작성: 2026-08-31 / 최신 반영: 2026-09-04
> 기준 브랜치: `codex/region-reader-judge-pipeline`
> 대상 독자: 이 프로젝트를 처음 보는 기획·심의·개발 담당자
> 범위: 현재 광고물 파서의 실제 코드와 JSON 계약(P1 `evidence-v6`, P2 `ad-review-input-v6`, 영역 중심 P3 후보 `ad-review-region-input-v1`) 기준. 이 브랜치의 일부 변경은 아직 커밋 전이므로 `main`의 과거 결과와 혼동하지 않는다.

## 1. 먼저 한 문장으로

이 파이프라인은 **광고 이미지에서 글자를 읽어, “어떤 문구가 어느 페이지의 어디에 있었는지”와 “농협 광고 템플릿의 어느 항목과 연결되는지”를 근거와 함께 넘기는 파서**다.

파서가 하지 않는 일도 분명하다.

- 파서는 “위반”을 확정하지 않는다.
- OCR과 VLM의 읽기가 다르다고 VLM 문구로 원문을 자동 교체하지 않는다.
- 템플릿 항목을 찾지 못했다고 곧바로 “미준수”라고 결론 내리지 않는다.

그 판단은 다음 심의 단계가 규정, 상품 조건, 사람 검수 결과를 함께 보고 한다. 파서는 그 판단에 필요한 **광고물 근거 원장**을 만든다.

## 2. 전체 그림

```text
광고 PDF / PNG / JPG / HWP
        │
        ▼
① 입력 판별 · 렌더 · 타일 분할
        │
        ▼
② PaddleX StructureV3: 레이아웃 블록 + OCR 줄 + 좌표
        │
        ▼
③ 좌표 복원 · 중복 제거 · 디지털 PDF 텍스트 병합
        │
        ▼
④ 블록에 줄을 배정해 영역(region) 확정
        │
        ▼
⑤ 다상품 카드 / 공통영역 경계
        │
        ▼
⑥ 영역에 못 붙은 줄 좌표 귀속 · 레이아웃 미검출 진단
        │
        ├───────────────► ⑦ 누락 문구 탐색 후보(별도 보관)
        │
        ▼
⑧ 읽기 순서 확정 (영역 안 + 영역끼리)  ──► line_ref 줄번호가 여기서 고정된다
        │
        ▼
⑨ 영역 Reader / 불일치 시 Judge  ──► 관측값만 기록, 정본은 유지
        │
        ▼
⑩ 상품군·광고유형 분류 → 농협 제공 광고 템플릿 선택
   (다상품 카드면 card_no별로 독립 선택)
        │
        ▼
⑪ 온전한 영역 문맥에서 템플릿 라벨과 줄 범위 연결
        │
        ├──────────────────────┬──────────────────────────────┐
        ▼                      ▼                              ▼
P1/evidence-v6        P2/ad-review-input-v6       P3/ad-review-region-input-v1 후보
근거 원장·감사용       라벨별 심의 입력             영역 전문 1회 + 0..N 라벨 범위 + 표
```

세 산출물은 서로 다른 OCR 결과를 만드는 것이 아니다. 동일한 P1 근거를 심의가 어떤 단위로 읽을지에 따라 두 가지 투영(P2/P3)으로 제공한다. 현재 P2는 기존 호환용이고, P3는 영역 문맥 보존 효과를 비교하기 위한 후보 계약이다.

| 파일 | 주 사용자 | 목적 |
|---|---|---|
| `json/<문서>.json` | 검수 화면, 운영 감사, 오류 재조사, RDB 저장 | 원문 줄·좌표·영역·VLM 관측을 잃지 않는 근거 원장 |
| `review_input/<문서>.json` | RAG/규정 조회/심의 엔진 | 템플릿에 배정된 문구와 그 밖의 광고 문구를 바로 소비할 수 있는 업무용 투영 |
| `review_region_input/<문서>.json` | 영역 문맥 기반 심의 실험 | 영역 전문은 한 번만 싣고 같은 영역에 0개·1개·여러 라벨 줄 범위를 연결하는 P3 후보 |

`review_input`의 모든 값은 `evidence`의 줄(`line_ref`)을 다시 가리킨다. 따라서 심의 엔진이 의심스러운 결론을 내리면 언제든 `evidence`와 원본 이미지의 bbox로 되돌아갈 수 있다.

## 3. 먼저 알아둘 용어

| 용어 | 쉬운 설명 | 이 파이프라인에서의 의미 |
|---|---|---|
| OCR | 이미지 속 글자를 문자열로 읽는 기술 | PaddleX가 광고 이미지에서 줄 단위 텍스트와 좌표를 만든다. |
| StructureV3 | 페이지의 배치를 찾는 PaddleX 모델 | 제목·본문·표·이미지 같은 **사각형 영역**과 OCR 결과를 찾는다. 이 영역은 최종 의미 판단이 아니라 화면상의 경계다. |
| 타일(tile) | 긴 페이지를 OCR에 보내려고 자른 조각 | 자를 위치는 글자 밀도가 정하고 조각 높이 상한은 1600px이다. 좌표는 뒤에서 페이지 전체 좌표로 되돌린다. |
| 레이아웃 블록 | StructureV3가 타일에서 찾은 사각형 원본 | 아직 줄이 배정되지 않은 상태다. 여기에 줄을 붙이면 영역(region)이 된다. |
| 영역(region) | 화면에서 StructureV3가 잡은 하나의 사각형 | `region_id`, `bbox`, 레이아웃 라벨, 그 안의 OCR 줄을 가진다. 경계는 StructureV3가 만들고, 어느 줄이 그 안에 들어가는지는 파서가 좌표로 정한다. |
| bbox | 사각형 위치 | `[왼쪽 x, 위 y, 오른쪽 x, 아래 y]` 픽셀 좌표. 문구가 원본의 어디에 있는지 보여 준다. |
| 디지털 텍스트 | PDF 안에 이미 들어 있는 문자 레이어 | 이미지 OCR보다 우선할 수 있는 텍스트 출처다. 그림으로 만든 글자는 여기 없을 수 있다. |
| 파서 기본 텍스트(parser primary text) | 현재 파서가 기본값으로 보존하는 원문 텍스트 | 각 `lines[].parser_text`와 이를 합친 영역 문자열이다. OCR만 뜻하지 않으며 `text_source`가 `ocr`인지 `digital`인지 함께 밝힌다. 법적 정답이나 사람 검수 완료본이라는 뜻은 아니다. |
| VLM | 이미지를 보고 질문에 답하는 Vision Language Model | 이미지 crop을 보고 독립적으로 문구를 읽거나, 후보 두 개를 비교한다. |
| VLM 영역 판독 | 영역 이미지를 파서 기본 텍스트와 독립적으로 읽는 VLM | OCR·디지털 PDF 텍스트를 교체하는 모델이 아니라, 파서 기본 텍스트를 점검하기 위한 두 번째 판독이다. |
| VLM Judge | 파서 기본 텍스트와 VLM 영역 판독이 다를 때만 둘을 비교하는 VLM | 어느 후보가 화면에 더 가까워 보이는지 의견을 남긴다. 아직 자동 수정 권한은 없다. |
| shadow(섀도우) | 실제로 실행·기록하지만 운영 기준값은 바꾸지 않는 시험 방식 | VLM이 틀려도 `parser_primary_text`는 유지한다. 성능·오염률을 측정한 뒤에만 정책 변경을 검토한다. |
| 카드(card) | 한 페이지에 나란히 있는 여러 상품/이벤트의 공간 묶음 | `card_no=1,2,...`는 같은 카드 안 문구가 섞이지 않도록 돕는다. `0`은 공통 제목·공통 고지처럼 공유 영역, `null`은 공간상 확정하지 못한 영역이다. 상품 의미를 확정하는 라벨은 아니다. |
| 템플릿 | 농협이 제공한 “광고에 어떤 항목을 표시해야 하는지” 목록 | 예: 회사명, 상품명, 금리, 대출한도, 유의사항. 규정 위반 판정 규칙 그 자체가 아니다. |
| 템플릿 라벨 | 광고 문구가 템플릿의 어느 항목과 관련되는지 붙이는 이름 | P2 `labelled_ad_copy[].label` 또는 P3 `regions[].labels[].label`이다. 위치를 찾았다는 뜻이지, 필수조건 충족·위반 결론은 아니다. |
| 회수 후보(recovery candidate) | StructureV3/OCR가 놓쳤을 수 있어 페이지 전체를 훑어 찾은 문구 후보 | 정본·템플릿 값에 자동 합치지 않고 `unverified_recovery_candidates`로 별도 보관한다. |

## 4. 파싱 단계별 설명

### 0) 호출 진입점과 입력

광고물 처리의 공통 진입점은 `src/nh_parsing/pipeline.py`의 `process_file()`이다. CLI는 `tools/run_ad_label.py`, 농협 KL 연동은 `kl_parser/app_custom_parser/service/parsing_service.py`가 이 공통 경로를 호출한다.

입력으로 PDF, PNG/JPG 계열 이미지, HWP를 받는다. 지원하지 않는 확장자는 파싱 불가 상태와 사유를 남긴다.

### 1) 입력 판별, 렌더, 타일 분할

PDF는 먼저 페이지가 다음 중 어디에 가까운지 살핀다.

- `structured`: PDF 문자 레이어가 비교적 정상인 문서
- `scan_like`: 스캔 이미지처럼 문자 레이어를 신뢰하기 어려운 문서
- `hybrid`: 문자 레이어와 이미지 기반 텍스트가 함께 있는 문서

**이 3갈래는 진단 기록이고, 실제 처리 경로는 두 갈래다.** `structured`와 `hybrid`는 같은 처리로 합쳐진다 — 둘 다 StructureV3를 부르고 디지털 텍스트를 우선해 병합한다. 그래서 페이지의 `parse_route`에는 `hybrid`(두 출처를 병합했다) 또는 `ocr`(스캔형·이미지 입력)만 남고, 3갈래 판정 자체는 파싱 중간 산출물의 `page.triage`에 사유와 함께 보관된다.

예전에는 `structured`면 "디지털 텍스트가 이미 있으니 무거운 모델을 또 부를 것 없다"며 StructureV3를 건너뛰었다. 실측해 보니 그 절약은 StructureV3 호출 하나(단일 타일 3.67초, GPU)뿐인데 — VLM 호출은 경로와 무관하게 이미 전부 지불하고 있다 — 그 대가로 가로 인식을 통째로 잃고 있었다. 블록이 없으면 4)의 폴백을 타는데 그것은 세로 간격만 보므로 좌우 2단 페이지가 한 덩어리로 뭉친다(실측 2026-08-14, `6. 대출성상품.pdf` p1: 라벨 5줄이 한 영역 27줄로 뭉쳤다).

`structured`에서는 라우팅을 가르지 않는 대신 **문자 레이어가 화면의 글자를 얼마나 설명하는지**를 재서 근거에 남긴다(글자 획 픽셀 중 문자 레이어가 덮은 비율). 30% 미만이면 "글자를 도형·그림으로 그린 페이지라 디지털 텍스트만으로는 화면을 설명하지 못한다"는 경고가 붙는다. 판정을 바꾸지는 않고, 산출물 신뢰도를 읽는 재료로만 쓴다.

렌더는 PDF를 이미지 캔버스에 그린 뒤 흰 배경 RGB로 정규화한다. 스캔형·혼합형은 내장 래스터의 원본 해상도로 렌더해 **업스케일을 금지한다** — 없는 해상도를 늘려도 글자는 살아나지 않고 타일 수만 늘어난다.

긴 페이지는 타일로 나눈다. 규칙은 세 개다.

| 기준 | 값 | 왜 |
|---|---|---|
| 자를지 말지 | 캔버스 높이 4000px 초과 | 그 아래는 한 장으로 보낸다 |
| 어디서 자를지 | **글자 밀도(에지 프로파일)가 정한다** | 산술로 1600px마다 자르면 조각마다 담기는 글자량이 2.3~3.4배까지 차이 나고 컷이 글자 한가운데를 지난다 |
| 조각 높이 상한 | 1600px — 넘으면 조각 수를 늘린다 | 조각이 길면 레이아웃 검출이 블록을 거칠게 묶는다. 실측(2026-07-28) 상한 없이 돌렸을 때 002의 블록이 84→62로 줄고 '최고연 7.1%'를 담던 작은 영역이 큰 영역에 흡수됐다. 상한을 걸면 조각은 15→24장으로 늘지만 블록은 332→360으로 세밀해지고 골드 회수도 138→139로 손실 없이 올라간다 |

조각 사이에는 200px 오버랩을 둔다. 경계에 걸친 내용이 양쪽 어디에서도 안 읽히는 일을 막는 안전장치다. 실측 타일 수(out_0903_step12_rerun): `16. 대출성상품`(1654×2339) 1장, `001-예금성`(720×6554) 7장, `002-예금성`(720×6111) 8장, `올원e적금`(1122×6429) 9장, `8. 카드상품`(11812×11812) 17장.

### 2) StructureV3와 OCR: 화면을 블록과 줄로 분해

각 타일을 PaddleX PP-StructureV3에 보낸다. 여기서 얻는 것은 크게 두 가지다.

- **레이아웃 블록**: text, table, image 등 화면의 사각형과 검출 확신도
- **OCR 줄**: 실제로 읽힌 글자, 줄 bbox, OCR 신뢰도

PaddleX는 같은 화면을 두 목록으로 준다. 읽기순서와 본문이 담긴 `parsing_res_list`를 정본으로 쓰고 `layout_det_res` 쪽은 중복으로 버린다. 다만 **검출 확신도(`score`)는 `layout_det_res`에만 있어서** 좌표로 짝지어 이어 붙인다 — 안 붙이면 확신도가 통째로 사라진다. 이 값은 판정에 쓰지 않고 진단과 라벨링 프롬프트의 참고 신호로만 보관한다(산출물의 `layout.score`).

`table_res_list`의 HTML·셀 격자는 광고 파이프라인에서 쓰지 않는다. StructureV3에서는 "여기가 표다"라는 경계만 받는다.

실측 라벨 분포(`16. 대출성상품` p1, 영역 33개): text 20, paragraph_title 4, table 2, vision_footnote 2, header 2, doc_title 1, figure_title 1, footer 1.

중요한 구분은 StructureV3의 `text`/`table`이 화면 배치 모델의 분류라는 점이다. 이것은 아직 “이 문구가 상품명인지, 유의사항인지”를 뜻하지 않는다. 그 업무 의미는 뒤의 템플릿 라벨링 단계에서 붙인다.

### 3) 좌표 복원, 중복 제거, PDF 텍스트 병합

타일 안에서 얻은 좌표는 페이지 전체 좌표로 되돌린다. 줄 bbox뿐 아니라 **블록 bbox와 표 셀 좌표도 같은 만큼 내린다** — 안 내리면 셀이 타일 좌표에 남아 페이지 위쪽 엉뚱한 자리를 가리킨다.

오버랩 구간에서 같은 글자가 두 번 읽히면 중복을 제거한다. 판정은 **텍스트가 같은지 보지 않고 위치 겹침만** 본다. 타일 경계에서 잘린 글자는 같은 자리에 '깨진 텍스트 + 낮은 신뢰도'로 다시 검출되기 때문이다(실측: '수 있는 권리가 있습니다.' 0.99 vs '7리콘극' 0.6). IoU 0.5 이상이거나 포함비 0.7 이상이면 중복으로 보고 **신뢰도가 높은 쪽만** 남긴다. 포함비까지 보는 이유는 큰 줄 안에 들어앉은 부분 조각도 걸러야 하기 때문이다.

디지털 PDF에서는 PDF 문자 레이어와 OCR이 겹치는 경우가 많다. 이때 디지털 텍스트와 겹친 OCR은 제거해, 안정적인 PDF 문자 레이어를 기본 텍스트 출처로 쓴다.

줄 단위 출처는 `text_source`에 `digital` 또는 `ocr` **둘 중 하나로만** 남는다. `hybrid`는 줄의 값이 아니라 **페이지의 `parse_route` 값**이다(두 출처를 병합한 경로라는 뜻). 실측(out_0903_step12_rerun): `16. 대출성상품`은 digital 106줄 + ocr 14줄, `8. 카드상품`은 digital 57줄 + ocr 14줄, 이미지로 들어온 3건은 전부 ocr이다.

### 4) 블록에 줄을 배정해 영역(region)을 확정

여기가 실제로 “영역을 나누는” 자리다. 영역의 **경계는 StructureV3가 만들고**, 어느 줄이 그 안에 들어가는지는 **파서가 좌표로 정한다.**

판정 기준은 **줄 자기 면적 대비 겹침 비율이 0.5 이상**인 영역이다.

- 중심점이 아니라 겹침 면적으로 잰다. 표 칸이 한 줄로 합쳐진 경우 중심점이 어느 칸에 찍히느냐에 따라 통짜 줄 전체가 엉뚱한 영역에 붙는다(실측 `올원e적금` p1_r006: 오른쪽 칸 '가입금액100만원이상'이 왼쪽 영역에 붙었다). 겹침 비율로 재면 “이 줄의 대부분을 담은 영역”이 이긴다.
- 겹침 비율이 같으면(중첩된 두 영역이 줄을 둘 다 완전히 품을 때) **더 작은, 더 구체적인 영역**이 이긴다. 결과가 블록 목록 순서에 흔들리지 않게 하는 장치이며, 6)의 귀속 규칙과 같은 원칙이다.
- 0.5에 못 미치면 어느 영역에도 넣지 않고 `unassigned_lines`로 보류한다. **버리지 않는다.**

영역 안의 줄은 일단 좌표순(위→아래, 왼쪽→오른쪽)으로 세워 둔다. 최종 읽기 순서는 8)에서 확정한다.

**레이아웃 블록이 아예 0개면 폴백을 탄다.** 줄의 수직 간격이 `1.5 × 줄높이 중앙값` 이내면 한 문단으로 묶는 방식이다. 세로 간격만 보므로 좌우 2단 페이지가 통째로 뭉치는 한계가 있다 — 1)에서 `structured` PDF에도 StructureV3를 부르는 이유가 바로 이 폴백을 피하려는 것이다.

실측 영역 수(out_0903_step12_rerun, 모두 1쪽 문서): `16. 대출성상품` 33개, `8. 카드상품` 45개, `001-예금성` 76개, `002-예금성` 53개, `올원e적금` 50개. 영역당 줄 수는 **중앙값이 1줄이고 최대가 56줄**(`16. 대출성상품` p1_r019 요율표)이다. 즉 **영역 하나가 항목 하나라는 뜻이 아니다.** 그렇다고 긴 영역을 20줄씩 자르면 뒤 조각에서 표 머리·앞 문장이 사라져 의미가 바뀐다. 현재는 영역 내부를 자르지 않고, 한 영역에 여러 라벨 범위를 허용한다.

### 5) 여러 상품·이벤트가 한 페이지에 있을 때 카드 경계 보존

한 페이지에 `EVENT 1`과 `EVENT 2`, 또는 두 상품 카드가 나란히 있으면 y좌표만으로 정렬할 때 두 카드의 문장이 교차할 수 있다. 그래서 카드 경계를 먼저 잡아 두고, 뒤의 읽기 순서와 라벨링이 그 경계를 넘지 않게 한다.

판단 주체는 VLM이지만 **VLM을 부르기 전에 결정론 단계가 있다.** 세 층으로 되어 있다.

1. **라우팅 게이트 — 여기서 걸리면 VLM 호출 자체를 하지 않는다.** 세로 스크롤(높이/폭 ≥ 2)은 카드 후보가 아니다. 모바일 상품페이지는 박스형 섹션이 있어도 카드가 아니기 때문이다. 한 덩어리 텍스트 슬라이드(단일 패널)도 글자밀도로 걸러 낸다. 다만 전체 밀도가 1로 나와도 곧장 제외하지 않고 부분 구간의 분리 신호를 한 번 더 본다 — 실측 `2. 카드상품.pdf`: 두 카드를 비교하는 페이지인데 상단 공통 헤더가 전체 높이에 걸쳐 있어 깨끗한 자리가 없었고, VLM이 판단할 기회 자체가 막혀 있었다.
2. **밀도 관측을 증거로 실어 1회만 묻는다.** 결정론적인 글자밀도 관측을 프롬프트에 넣어 답을 고정하는 쪽을 택했다. 같은 질문을 여러 번 반복하는 것은 새 정보를 주지 않기 때문이다. 밀도 근거를 만들 수 없을 때(캔버스 없음 등)에만 예전처럼 복수 관측으로 흔들림을 흡수한다.
3. **복수 관측일 때는 카드 번호를 직접 투표하지 않는다.** 번호 순열이 실행마다 다르므로(어떤 실행의 1번이 다른 실행의 2번일 수 있다) “두 영역이 같은 카드로 묶인 횟수”를 투표해 과반이면 한 카드로 합친다. 최종 번호는 시각 순서(위→아래, 좌→우)로 다시 부여한다. 과반이 스크롤로 답하면 카드 없음으로 둔다.

밀도가 센 개수와 VLM이 답한 개수가 다르면 **VLM 판단을 채택하되 불일치를 노트로 남긴다.** 증거를 보고도 다르게 답했다면 다시 물어도 같은 답이 나오므로, 받아들이고 사람이 볼 수 있게 적어 두는 편이 낫다 — 조용한 불일치를 만들지 않는다.

- `card_no=1,2,...`: 각 상품/이벤트 카드의 공간 묶음
- `card_no=0`: 카드 공통 제목, 공통 심의번호, 공통 하단 고지처럼 공유하는 영역
- `card_no=null`: 좌표상 어느 카드로도 단정하지 않은 영역

이는 “이 카드는 반드시 A 상품”이라고 결정하는 기능이 아니다. 하류 단계가 상품 귀속을 판단할 때 문구 혼입을 막을 최소 공간 정보다.

실측(out_0903_step12_rerun 5문서): 다섯 건 모두 카드 배정이 일어나지 않아 `card_no`가 전부 `null`이다. 산출물만으로는 게이트에서 걸렸는지(스크롤·단일패널) VLM이 카드형이 아니라고 답했는지 구분되지 않는다 — 카드 묶음이 생겼을 때만 노트가 남기 때문이다. 세로로 긴 3건은 종횡비만으로도 스크롤 게이트에 걸리고, `16. 대출성상품`(높이/폭 1.41)과 `8. 카드상품`(1.00)은 밀도 판정으로 넘어간다. 카드 경계가 실제로 갈리는 문서는 003(EVENT 1/2)이나 `2. 카드상품`처럼 가로로 넓은 슬라이드형이다. **`card_no`가 전부 `null`인 산출물은 카드 판정 실패가 아니라 “카드형이 아니다”라는 판정 결과다.**

### 6) 영역에 못 붙은 줄을 좌표만으로 다시 귀속

4)에서 보류된 줄을 한 번 더 영역에 붙인다. **좌표만 보는 결정론 단계이고 VLM과 무관하다.**

- 대상은 `ocr`·`digital` 줄만이다. 7)의 sweep 후보는 근사 밴드 bbox라 제외한다.
- 1순위: 줄 중심점을 품는 영역 — 여럿이면 가장 작은(구체적인) 영역
- 2순위: 품는 영역이 없으면 **같은 칼럼에 있는** 영역(가로 구간이 줄 폭의 절반 이상 겹치는 영역) 중 수직 갭이 `max(300, 캔버스높이 × 0.15)` 이내인 최근접 영역. 가로 게이트가 없으면 좌우로 분할된 패널에서 영역이 패널 경계를 관통한다.
- 둘 다 실패하면 미배정으로 남긴다.

예전에는 VLM이 만든 섹션 bbox를 게이트로 썼는데, 섹션이 실행마다 흔들려 **같은 낱줄이 실행마다 다른 영역에 붙었다**(001 실측 11줄이 영역↔미배정 사이를 오갔다). 그래서 이제 영역만 보고 결정한다.

실측(out_0903_step12_rerun): 이 단계에서 귀속된 줄이 각각 8 / 18 / 58 / 18 / 4줄이고, 최종 미배정은 0 / 0 / 0 / 1 / 0줄이다. `001-예금성`은 58줄(중심점 포함 29 + 근접 29)이 여기서 영역을 얻었다. 숫자가 큰 이유는 StructureV3 블록이 촘촘해 줄이 블록 사이 여백에 걸치는 일이 잦기 때문이며, **미배정이 0이라는 것이 4)의 배정이 완벽했다는 뜻은 아니다.**

이어서 미배정으로 남은 낱줄 중 **응집한 덩어리**가 있으면 진단 노트로 남긴다. 낱줄이 27개라는 숫자만으로는 “레이아웃이 깨진 것”인지 “원래 흩어진 화면”인지 알 수 없기 때문이다. 놓친 덩어리를 유사 영역으로 승격하지는 **않는다** — 승격하면 하류 입력이 함께 흔들리므로, 먼저 재고 재는 게 쓸모 있다는 근거가 쌓인 뒤에 붙인다(실측 2026-07-29: 001 p1의 8줄 덩어리는 앱 목업의 UI 바 — '로그아웃', '김농협님>' — 여서 미배정으로 남는 것이 맞았다).

### 7) 누락 문구 탐색은 보조 후보로만 보관

StructureV3가 아예 영역을 만들지 못한 장식 문구·벡터 텍스트를 찾기 위해 **페이지 전체를 밴드로 나누지 않고 한 번** 추가로 훑는다. 이를 **페이지 sweep**이라고 한다.

이것은 9)의 영역 Reader의 대체물이 아니다. Reader는 StructureV3가 이미 만든 영역만 읽을 수 있으므로, **영역이 아예 없는 자리**를 찾는 일은 sweep만 할 수 있다. 두 단계가 겹치는 것이 아니라 서로 다른 사각지대를 본다.

이 결과는 OCR 줄에 섞지 않는다. bbox가 넓은 밴드 단위라 정확한 영역 귀속을 보장하기 어렵기 때문이다. 따라서 `recovery_candidates` / `unverified_recovery_candidates`에만 넣고, 사람 또는 후속 검증이 채택할 때까지 정본과 템플릿 필드에서는 제외한다.

이 방식은 “새로운 문구를 놓치지 않으려는 탐색”과 “기존 정본을 조용히 오염시키지 않는 보수성”을 함께 지킨다.

실측 후보 수(out_0903_step12_rerun): `16. 대출성상품` 0개, `8. 카드상품` 1개, `001-예금성` 6개, `002-예금성` 2개, `올원e적금` 3개.

### 8) 읽기 순서 확정

지금까지의 줄 순서는 좌표순 나열이고, 여기서 읽기 순서를 확정한다. 두 층을 각각 고친다.

**영역 안의 줄.** 페이지 전역 정렬은 각 줄을 직전 행하고만 비교하므로, 세로로 긴 페이지에서는 같은 시각적 줄의 단어들 사이에 다른 위치의 줄이 끼어들어 행 묶기가 깨진다(001 실측: 단어가 top 좌표순으로만 나열됐다). 영역 하나로 범위를 좁혀 다시 정렬하면 끼어드는 무관한 줄이 없어 올바른 순서가 된다.

**영역끼리의 순서.** 영역 목록은 PaddleX `parsing_res_list` 순서를 그대로 쓰는데, 그 순서는 문장을 거꾸로 놓는 데가 있다(실측 `[예금성상품-적금] 올원e적금.png` p1, 원본 이미지 대조 완료).

```text
원본:  '금융소비자 보호에 관한 법률 제19조제1항에 따른 설명을 받을'  y=5546
       '수 있는 권리가 있습니다.'                                    y=5611
기존:  r044 '수 있는 권리가 있습니다.'      ← 뒷줄이 먼저 실렸다
       r045 '금융소비자 보호에 관한 법률…'
```

**여기서 y로 전부 다시 정렬하지는 않는다.** 전역 재정렬은 2단 문서를 망가뜨린다 — 좌우 칸의 문장이 교차하기 때문이다. 그래서 세로로 겹치는 이웃끼리의 **최소 교환만** 한다.

이 단계의 목표는 사람이 페이지를 읽는 순서에 가까운 텍스트 나열을 만드는 것이지, 특정 상품 디자인에 맞춘 “완벽한 의미 순서”를 억지로 확정하는 것이 아니다.

**이 단계의 위치에는 두 가지 제약이 있다.**

- **카드 배정(5) 뒤여야 한다.** 카드 경계를 지키며 교환해야 하기 때문이다.
- **산출물 단계가 아니라 파싱 단계여야 한다.** `line_ref`의 줄 번호(`p1/p1_r011/L00`의 `L00`)는 이 순서에 번호를 매긴 결과이고, 템플릿 라벨링도 같은 순서로 번호를 매긴다. 산출물 쪽에서 순서를 바꾸면 두 번호가 어긋나 **라벨이 다른 줄에 조용히 붙는다.** 파싱에서 한 번 고쳐 두면 검수 화면과 하류 전부가 같은 순서를 본다.

### 9) 영역 Reader: 같은 StructureV3 영역을 VLM이 독립 판독

현재 시험 파이프라인에서는 StructureV3가 만든 텍스트·표 영역을 대상으로 VLM Reader를 실행한다. Reader 입력은 OCR 문자열이 아니라 **해당 영역의 이미지 crop**이다.

이웃 문구 혼입을 줄이기 위해 crop에서 다음을 적용한다.

- 목표 bbox를 파란 테두리로 표시한다.
- bbox 바깥은 흰색으로 마스킹한다. 단 StructureV3 bbox가 글자 끝을 살짝 자르는 경우가 있어 `REGION_CROP_PADDING_PX=16`만큼의 안전 고리를 남기고, 마스킹은 `REGION_MASK_BLEED_PX=2`만큼 물려 넣는다.
- 목표 영역 안에 다른 StructureV3 텍스트 영역이 완전히 포함되어 있으면 그 하위 영역도 마스킹한다. 어느 영역을 뺐는지는 관측에 함께 기록한다.

표 영역에는 일반 Reader와 별도로 표 Reader를 요청할 수 있다. 표 Reader는 `text`, `rows`, `confidence`, `structure_confidence` 관측을 남긴다. **PaddleX의 HTML/셀 격자는 현재 최종 계약에서 사용하지 않는다.** StructureV3의 “표 영역 bbox”만 경계로 사용하고, 표 내부 행 관계는 VLM 관측으로 따로 둔다.

**어떤 영역을 보낼지는 `REGION_READING_SCOPE`가 정한다.**

- `all`(기본): 줄과 bbox를 가진 **모든** 텍스트·표 영역을 보낸다. 역할 9종이나 예전 밴드 후보와 무관하며, 이것이 이 브랜치의 비교 기준이다.
- `tables`: **표 영역만** 전체 crop으로 읽는다. 일반 본문 Reader 비용 없이 표 `rows` 관측만 시험할 때 사용한다.
- `targeted`: 비용 측정용 보조 모드다. **표 영역**과 **OCR 신뢰도가 임계 미만인 줄을 가진 영역**만 골라 보내고, 선별 사유를 관측에 남긴다.

쪽당 요청 수는 `REGION_READER_MAX_PER_PAGE`로 상한을 걸 수 있고 **기본값 0은 무제한**이다. 즉 기본 설정에서 이 단계를 켜면 영역 수만큼 VLM 호출이 일어난다 — 실측 영역 수가 문서당 33~76개이므로(4) 참조) 비용을 먼저 계산하고 켜야 한다.

`REGION_READING_MODE=shadow`일 때 이 단계가 켜지고, **기본 운영 설정은 `off`**라서 외부 VLM 호출·비용 없이 일반 파싱만 실행한다. `off`로 돌린 산출물에서는 `vlm_region_reading`이 `null`이고 표 관측도 `status=not_run`으로 남는다 — 값이 비어 있는 것이 결함이 아니라 **이 단계를 실행하지 않았다는 정직한 기록**이다.

### 10) Judge: 서로 다르게 읽힌 영역만 비교

OCR 정본과 Reader 텍스트가 글자와 숫자 기준으로 같으면 Judge를 부르지 않는다. 다를 때만 OCR과 Reader를 A/B 후보로 익명화해 Judge에게 같은 crop과 함께 비교시킨다.

Judge 결과는 다음과 같은 상태와 근거로 남긴다.

- `agreed`: OCR 정본과 Reader가 실질적으로 일치
- `judge_selected` 등: Judge가 한 후보를 더 선호
- `uncertain`: 어느 쪽도 안전하게 채택하기 어렵거나 차이가 큼
- `reader_failed` / `judge_failed`: 외부 모델 호출 실패

하지만 shadow 모드에서는 Judge가 VLM 판독을 선호해도 `lines[].parser_text`를 바꾸지 않는다. 즉, **파서 기본 텍스트·VLM 후보·Judge 의견은 함께 보이되 한 값으로 뭉개지지 않는다.** 이것이 세 값이 공존하는 이유다.

### 11) 문서 분류와 광고 템플릿 선택

문서의 텍스트·이미지 문맥으로 상품군, 광고유형, 노출 상품명을 분류한다. 이 결과와 파일명 등을 근거로 농협 제공 템플릿 중 하나를 선택한다. 결정할 수 없으면 VLM 결선 판단을 한 번 보조로 사용하며, 그래도 불확실하면 불확실성을 남긴다.

**분류와 템플릿 선택은 같은 단계가 아니다.** 분류(상품군·광고유형·노출 상품명)는 파싱 함수 안에서 끝나 파싱 중간 산출물(`<out>/parse/`)에 함께 저장되고, 템플릿 선택과 라벨링은 그 뒤 별도 모듈이다. 그래서 `--reuse-parse`로 다시 돌리면 **분류까지 재사용되고 템플릿·라벨링만 다시 실행된다** — 파싱이 문서당 9분이라 라벨링 한 줄을 고쳐 재확인할 때마다 다시 파싱하면 45분이 들기 때문에 만든 경계다. 분류 결과를 다시 뽑고 싶으면 `--reuse-parse` 없이 실행해야 한다.

템플릿은 **12종**이다 — 대출성 3종(상품명 노출 / 미노출 / 대출모집인), 예금성 5종(입출식 / 거치식 / 적립식 / 지수연동예금 / 상품명 미노출), 카드 4종(개인 / 법인 / 미노출 / 장·단기카드대출). 각 템플릿은 “회사명, 상품명, 금리, 대출한도, 유의사항…”처럼 광고에서 점검할 항목을 정의한다. 이는 다음 단계가 무엇을 확인해야 하는지 알려 주는 기준표다.

**근거가 모자라면 억지로 고르지 않고 `판단불가`로 둔다.** 대출성만 봐도 '상품명 노출'은 점검 항목이 12개, '미노출'은 3개다. 틀리게 고르면 점검 항목 9개가 통째로 사라지거나 없던 항목이 쏟아진다. 하나 고르는 것보다 “못 정했다”고 말하는 편이 하류에 정직하다. VLM 결선은 **후보가 있는 판단불가**(예: 예금성 세부유형)에만 부르고, 상품군 자체를 모르는 경우처럼 물어볼 거리가 없으면 그대로 판단불가로 내려보낸다.

### 12) 템플릿 라벨링: 광고 문구와 템플릿 항목 연결

템플릿을 고른 뒤 광고 문구의 줄 범위를 템플릿 항목과 연결한다. 두 신호를 함께 쓴다.

1. **정형 문구 완전 일치**: 템플릿이 지정한 고정 문구와 문자열이 정확히 맞는지 확인
2. **영역 단위 VLM 라벨링**: 제목/본문 같은 9종 범용 역할이 아니라, 선택한 템플릿의 실제 항목명으로 줄 범위를 판단

2026-09-04부터 영역 단위 라벨링의 입력 불변식은 다음과 같다.

- 한 영역은 **처음 줄부터 마지막 줄까지 전문을 한 요청 안에 유지**한다. 과거의 앞 40줄/600자 절단과 20줄 단위 분할은 제거했다.
- VLM 요청 하나에는 효율을 위해 여러 영역이 함께 들어갈 수 있지만, 배치 경계는 **영역 사이에서만** 생긴다. 현재 배치 기준은 최대 12영역, 합계 120줄, 합계 12,000자이며 이 값을 넘는 단일 영역도 자르지 않고 혼자 보낸다.
- 같은 `region_id`를 여러 번 반환할 수 있다. 각 답은 `line_from`~`line_to`와 라벨 하나를 가지므로 한 영역에 0개·1개·여러 라벨을 붙일 수 있다.
- 서로 다른 라벨의 줄 범위가 겹치는 것을 허용한다. 예를 들어 한 문장이 회사명 고지이면서 상품 유의사항의 일부라면 두 라벨이 같은 `line_ref`를 가리킬 수 있다.
- 응답이 영역 일부만 덮으면 덮이지 않은 줄을 “판정 기회를 못 얻은 줄”로 노트에 남긴다. `해당없음`으로 명시한 범위와 호출 무응답을 구분한다.
- `table=있음`인 영역도 표 머리와 모든 행을 포함한 전문으로 항목을 판정한다. 숫자 행만 떼어 낱말로 분류하지 않는다.

이 변경의 직접 원인은 `16. 대출성상품`의 `p1_r019`다. 56줄 요율표를 20줄씩 나누자 표 머리가 없는 L40~L55가 `대출대상`으로 오분류됐다. 영역 전체를 보여 주고 줄 범위만 나누게 해야 “같은 표의 뒤쪽 요율 행”이라는 문맥을 유지할 수 있다.

여기서 `review_targets`는 “이번 템플릿에서 확인할 항목”과 “현재 광고에서 연결된 줄의 `line_ref`”를 묶은 작업 목록이다.

- `located`는 해당 항목의 문구 위치를 찾았다는 뜻이다.
- `not_located`는 파서가 연결된 줄을 찾지 못했다는 뜻이다.
- 둘 다 최종 심의 결론은 아니다. 조건부 필수 여부, 표현 적정성, 숫자 정확성은 다음 단계에서 판정한다.

과거의 제목/본문/각주 등 9종 role은 전체 문서 읽기 보조로는 쓸 수 있지만, 현재 핵심 출력에서는 템플릿 항목 라벨보다 우선하지 않는다. 광고 심의에 필요한 질문이 “이것이 본문인가?”보다 “이 문구가 금리·대출한도·유의사항과 관련되는가?”인 경우가 많기 때문이다.

### 13) P1과 두 심의 투영으로 내보내기

마지막으로 동일한 파싱 결과를 세 계약으로 만든다.

- `P1/evidence-v6`: 세부 근거를 빠뜨리지 않는 원장
- `P2/ad-review-input-v6`: 기존 하류가 순회할 라벨별·미배정 review_text 목록
- `P3/ad-review-region-input-v1` 후보: 영역 전문을 한 번만 싣고 그 아래에 0..N 라벨 범위와 표를 붙인 목록

현재 `run_ad_label.py`와 `run_parsing_batch.py`는 세 파일을 함께 만든다. KL Parser 배포 경로는 아직 P1+P2 호환을 유지하며, P3의 품질 비교가 끝난 뒤 전환 여부를 정한다.

## 5. 최종 산출물 1: P1/evidence-v6 근거 원장

### 무엇을 위한 파일인가

`json/<문서>.json`은 “이 문구를 왜 이렇게 판단했는가?”를 다시 확인하기 위한 원본 근거 파일이다. 화면 검수, 오류 분석, RDB 보관, 후속 엔진의 근거 링크에 사용한다.

### 최상위 구조

```json
{
  "doc_id": "문서 식별자",
  "source_file": "원본 파일명.pdf",
  "file_type": "pdf",
  "classification": {
    "product_group": "대출성",
    "ad_type": "...",
    "product_name_shown": "...",
    "source": "...",
    "confidence": 0.0
  },
  "template": {
    "template_id": "단일 상품일 때만 값",
    "status": "확정 | 판단불가 | card_scoped",
    "selection_mode": "per_card일 때만 존재",
    "scopes": ["다상품일 때 page_no/card_no별 선택된 템플릿과 선택 근거"]
  },
  "reading_evidence_contract": {
    "version": "nh-ad-review-evidence-v6",
    "parser_primary_text": "파서 기본 텍스트 위치 설명",
    "vlm_region_reading_mode": "shadow_observation",
    "parser_mutates_primary_text_from_vlm": false,
    "p2_text_selection": "judge_selected_region_test; whole-region scope only",
    "card_template_selection": "positive card_no가 둘 이상이면 per_card",
    "table_structure": "structurev3_bbox + table_vlm_reader_observation",
    "paddlex_table_grid_used": false
  },
  "pages": ["페이지별 근거"],
  "review_targets": ["템플릿 항목별 점검 대상"],
  "completeness": {"...": "..."},
  "notes": ["처리 중 주의사항"]

```

### 페이지·영역·줄 구조

```text
pages[]
 ├─ page_no, canvas_w, canvas_h, dpi, parse_route, parse_status
 ├─ regions[]
 │   ├─ region_id, bbox, layout(label/score), card_no
 │   ├─ visibility
 │   ├─ text_evidence
 │   │   ├─ parser_primary_text   ← 기본 텍스트와 줄 참조
 │   │   ├─ vlm_region_reading    ← 독립 VLM 판독 후보
 │   │   ├─ parser_vlm_comparison ← VLM/파서 불일치 비교 결과
 │   │   └─ p2_text_selection     ← Judge 선택의 P2 시험 사용 후보
 │   ├─ template_labels   ← 이 영역에서 붙은 템플릿 라벨 근거
 │   ├─ lines[]           ← 실제 원자 단위: text, bbox, source, confidence, line_ref
 │   └─ table             ← 표일 때 StructureV3 bbox + VLM 표 관측
 ├─ unassigned_lines[]    ← 영역에는 못 붙였으나 버리지 않은 줄
 └─ recovery_candidates[] ← 페이지 탐색으로 회수한 미검증 후보
```

#### 꼭 봐야 할 필드

| 필드 | 의미 | 주의점 |
|---|---|---|
| `lines[].parser_text` | 파서 기본 텍스트의 가장 작은 단위 | 심의·검색의 기본 텍스트는 여기서 시작한다. |
| `lines[].bbox` | 문구의 원본 위치 | 화면 하이라이트·시인성 계산·다상품 혼입 조사에 사용한다. |
| `lines[].source` / `confidence` | 디지털/OCR 출처와 OCR 신뢰도 | OCR 신뢰도가 낮다고 자동 오류는 아니다. 검수 우선순위 신호다. |
| `region.card_no` | 공간상 카드/공통 영역 | 상품 의미 확정값이 아니다. 다른 카드 문구를 섞지 않기 위한 경계다. |
| `template.selection_mode/scopes` | 다상품 문서의 카드별 템플릿 선택 | `selection_mode=per_card`이면 각 `scope`의 `page_no/card_no`와 `template.template_id`를 사용한다. 카드별 템플릿 선택은 해당 카드 문구·이미지를 한 번 판독한 결과와 선택 근거를 남긴다. |
| `visibility` | 글자 높이·영역 대비 등 관측 가능한 시인성 정보 | 시인성 위반 판정이 아니라, 후속 규칙/사람 검토에 줄 원시 측정값을 준다. |
| `text_evidence.parser_primary_text` | 영역 안 `lines[].parser_text`를 순서대로 합친 편의 문자열 | 줄 배열과 별개 정답이 아니다. 원자 단위는 여전히 `lines[]`다. |
| `text_evidence.vlm_region_reading` | 동일 영역의 독립 VLM 판독 | 파서 기본 텍스트를 대체하지 않는다. |
| `text_evidence.parser_vlm_comparison` | 파서 기본 텍스트·VLM 판독 비교 상태 | Judge 기록도 자동 수정 지시가 아니다. |
| `text_evidence.p2_text_selection` | Judge가 선택한 영역 단위 P2 후보 | P2 view가 영역 전체 줄을 포함할 때만 사용한다. 부분 라벨에는 절대 사용하지 않는다. |
| `table.vlm_table_reading.rows` | VLM이 관측한 표 행 배열 | 표 구조가 불명확하면 빈 배열 또는 낮은 구조 신뢰도로 남는다. 사람이 확정한 셀 그리드가 아니다. |
| `recovery_candidates` | 누락 가능 문구 후보 | 정본·템플릿 필드에 자동 포함하지 않는다. |

### 표는 어떻게 표현되는가

표는 더 이상 PaddleX가 만든 HTML·셀 격자를 정답처럼 내보내지 않는다. 현재 약속은 다음이다.

```json
{
  "table": {
    "detected_by": "structurev3",
    "paddlex_grid_used": false,
    "parser_primary_line_refs": ["p1/r015/L00", "p1/r015/L01"],
    "vlm_table_reading": {
      "source": "table_region_reader",
      "status": "observed",
      "text": "표에서 읽힌 문구",
      "rows": [["항목", "내용"], ["일반가구주", "수도권 외 지역: 8천만원 이내"]],
      "confidence": 0.0,
      "structure_confidence": 0.0
    }
  }
}
```

즉, StructureV3는 “여기가 표다”라는 경계를 제공하고, VLM은 그 영역에서 읽은 행 관측을 제공한다. 표 Reader가 행/열을 확실히 구분하지 못하면 억지로 셀을 채우지 않고 `rows`를 비우거나 낮은 `structure_confidence`를 남겨 검수 대상으로 보낸다.

과거 `out_0831_region_reader_judge_v2`를 변환한 시험 파일은 이 표 Reader 실행 전 결과다. 따라서 그 안의 표 관측은 `legacy_text_only`이며 `rows=[]`가 정상이다. 새 원본 파싱을 실행한 뒤에만 VLM 표 Reader의 `rows`가 채워진다.

## 6. 최종 산출물 2: ad-review-input-v6(P2) 심의 전달 JSON

P2는 P1을 다시 복사하는 파일이 아니다. 심의 엔진이 읽을 **라벨별 문구**, **미배정 문구**, 그리고 P1으로 돌아갈 **줄 참조**만 전달한다. requirement·writing rules는 구성된 템플릿 팩에서 `document.template`과 `label`로 조회하고, 정형문구 매칭·좌표·VLM/Judge 상세은 P1에서만 확인한다.

P2는 새 OCR/VLM 호출을 하지 않는 결정론적 투영이다. `review_targets[].evidence.line_refs`로 라벨 범위를 정한다. Judge가 VLM 문구를 선택한 경우에도 그 범위가 해당 StructureV3 영역 전체와 일치할 때만 그 문구를 사용한다.

```json
{
  "contract": {
    "version": "nh-ad-review-input-v6",
    "source_evidence_contract": "nh-ad-review-evidence-v6",
    "text_partition": "labelled_ad_copy + unmapped_ad_copy",
    "p1_reference": "every transmitted text keeps P1 line_refs"
  },
  "document": {"문서 메타데이터와 선택된 템플릿"},
  "labelled_ad_copy": ["라벨별 심의 문구"],
  "unmapped_ad_copy": ["라벨 밖 광고 문구"],
  "unverified_recovery_candidates": ["미검증 회수 후보"],
  "summary": {"문구 분할 집계"}
}
```

### A. `labelled_ad_copy[]`: 라벨별 심의 문구

```json
{
  "label_id": "P1 review target의 안정 식별자",
  "label": "예: 대출한도",
  "template_scope": {"scope_id": "p1:card2", "scope": {"page_no": 1, "card_no": 2}},
  "text_views": [
    {
      "scope": {"page_no": 1, "card_no": 2},
      "review_text": "심의/RAG가 읽을 문구",
      "text_source": "parser_primary_text | vlm_judge_selected_region_test | mixed",
      "line_refs": ["p1/p1_r015/L00"]
    }
  ]
}
```

다상품 문서는 `template_scope`가 상품 카드 경계를 고정한다. 따라서 `p1:card1` 라벨은 card 1 문구만, `p1:card2` 라벨은 card 2 문구만 참조한다. 같은 카드의 여러 영역 문구는 하나의 `review_text`로 합치며 `line_refs`로 P1 bbox를 다시 찾는다.

### B. `unmapped_ad_copy[]`: 라벨 밖의 광고 문구

```json
{
  "scope": {"page_no": 1, "card_no": 2},
  "review_text": "광고 문구",
  "text_source": "parser_primary_text | vlm_judge_selected_region_test | mixed",
  "line_refs": ["p1/p1_r020/L00"]
}
```

이 목록은 중요하지 않은 문구 목록이 아니다. 템플릿이 포착하지 못한 광고 주장·혜택·오인 가능 문구를 심의가 탐색하는 입력이다.

### C. 분할 보장과 심의 사용

모든 P1 parser-primary 줄은 `labelled_ad_copy` 또는 `unmapped_ad_copy`에 들어간다. 한 줄이 여러 라벨에 관련될 수는 있지만 미배정과 라벨 목록에 동시에 들어가지는 않도록 검사한다.

```text
1. document.template의 카드별 scope를 독립 상품으로 순회
2. labelled_ad_copy의 label + review_text로 템플릿 팩·규정 RAG 조회
3. unmapped_ad_copy에서 별도 광고 주장·혜택·주의 문구 탐색
4. 심의 결과에 line_refs → P1 bbox → 적용 규정 근거를 연결
```

## 7. 최종 산출물 3: ad-review-region-input-v1(P3 후보)

P2는 같은 라벨의 여러 영역 문구를 페이지·카드 단위로 합친다. 이 구조는 기존 심의 입력과 호환하기 쉽지만, 서로 떨어진 영역이 한 `review_text`에 합쳐지고 한 영역이 여러 라벨에 해당하면 전문을 어느 라벨에 붙여야 하는지가 애매하다.

P3 후보는 반대로 **영역을 심의의 기본 단위**로 둔다.

```json
{
  "contract": {
    "version": "nh-ad-review-region-input-v1",
    "review_unit": "region",
    "region_cardinality": "one region carries zero, one, or multiple label spans",
    "label_overlap": "allowed"
  },
  "pages": [{
    "page_no": 1,
    "regions": [{
      "region_id": "p1_r019",
      "scope": {"page_no": 1, "card_no": null},
      "review_text": "영역 전체 문구 전문",
      "text_source": "parser_primary_text | vlm_judge_selected_region_test",
      "line_refs": ["p1/p1_r019/L00", "p1/p1_r019/L01"],
      "labels": [{
        "label_id": "template:대출금리",
        "label": "대출금리",
        "spans": [{
          "line_from": 0,
          "line_to": 55,
          "line_refs": ["P1의 해당 줄 참조"],
          "sources": ["semantic_vlm"]
        }]
      }],
      "table": {"P1 table 값을 그대로 보존": true}
    }],
    "unassigned_text": ["어느 영역에도 속하지 않은 P1 줄"]
  }],
  "label_index": ["본문을 복사하지 않고 라벨 → 영역/범위만 가리키는 역색인"],
  "unverified_recovery_candidates": ["페이지 sweep의 미검증 후보"]
}
```

핵심 규칙은 다음과 같다.

- 영역의 `review_text`와 `line_refs`는 정확히 한 번만 존재한다.
- 같은 영역의 `labels[]`는 비어 있거나 여러 개일 수 있다.
- 한 줄을 여러 라벨 span이 가리킬 수 있다. 이는 허용된 의미 중복이며 텍스트 복제나 소유권 중복이 아니다.
- `table`은 P1 표 값을 형제 필드로 그대로 복사한다. `review_text`는 검색·심의용 평면 문구이고 `table.vlm_table_reading.rows`는 행·열 관계를 보존하는 보조 관측이다. 둘 중 하나가 다른 하나를 대체하지 않는다.
- bbox, OCR 신뢰도, VLM/Judge 상세, 시인성 원시값은 P3에 반복 복사하지 않는다. `region_id`와 `line_refs`로 P1에서 확인한다.
- `label_index`는 라벨별 빠른 탐색을 위한 역색인일 뿐 본문을 다시 싣지 않는다.
- 페이지 sweep 후보는 여전히 `unverified_recovery_candidates`에 분리한다.

P3의 텍스트 소유권 검사는 `regions[].line_refs + unassigned_text[].line_ref`가 P1 parser-primary 줄을 정확히 한 번씩 포함하는지 확인한다. 라벨 span과 표의 참조는 소유권 검산에서 제외하므로 정상적인 라벨 중복이 분할 오류로 취급되지 않는다.

현재 P3는 비교용 후보이며 P2를 즉시 폐기하지 않는다. 같은 5문서의 P2/P3를 골드셋과 대조해 라벨 정확도, 문맥 보존, 심의 입력 길이, 중복 처리 난이도를 비교한 뒤 하류 기본 계약을 정한다.

## 9. HyundaiHS는 파싱 다음에 무엇을 하는가

`C:\Users\cccjj\cginside\repo-analysis\paddle-gemma-orchestrator\HyundaiHS`의 실제 코드와 문서를 확인했다. 그 프로젝트는 식품·축산물 표시/성적서 검증 도메인이므로 NH 광고 심의와 입력 문서·규칙 내용은 다르다. 그러나 **파싱 결과와 판정 엔진의 경계를 나누는 방식**은 좋은 참고가 된다.


파싱 후 코드 경로의 핵심은 다음과 같다.

| HyundaiHS 단계 | 실제 책임 | NH에서 가져올 원칙 |
|---|---|---|
| 페이지 추출 결과 확정 | VLM 추출 결과에 OCR 근거를 붙이고, 필수 필드를 복구·정합성 검사한 뒤 `structured`와 평면 `fields`를 함께 보관 | NH도 evidence 원장과 업무용 투영을 분리한다. VLM 후보를 원문처럼 덮어쓰지 않는다. |
| logical document 구성 | 여러 페이지/파일을 같은 실제 문서로 묶고, 문서 역할을 판별 | NH에서는 다상품 한 페이지의 `card_no`와 문서/상품 단위 선택이 대응 지점이다. 카드 경계만으로 상품 사실을 확정하지 않는다. |
| 문서 선택 | 검증 대상 문서가 여러 개거나 모호하면 자동 판정을 멈추고 검토자 선택을 요구 | NH도 상품 카드·템플릿 선택이 모호하면 `needs_review`로 보내야 한다. |
| `ValidationBundle` | 역할별로 선택된 논리 문서를 검증 단위로 고정 | NH에서는 “광고물 근거 + 선택된 템플릿 + 상품 조건 + 적용 규정 묶음”이 이 역할을 한다. |
| 별도 규칙 엔진 | WF1/WF2 규칙팩, 상품 사실, 참조 데이터를 사용해 검증하고 `decision_summary` 생성 | NH도 파서 바깥에 심의 규칙 엔진을 둔다. 템플릿 위치 발견과 위반 판정을 한 함수에 섞지 않는다. |
| 저장·검수 | Run, 페이지, 영역, 검수 작업·주석, 검증 결과를 RDB/아티팩트 저장소에 남김 | NH도 원본 evidence 버전, 심의 실행 버전, 사람 확정 결과를 분리 저장해야 재현 가능하다. |

HyundaiHS의 `judge_output__structured`는 파싱/추출 결과를 구조화한 중간 산출물에 가깝다. 그 뒤에도 문서 선택, 규칙팩, 상품 사실·참조 데이터, 검증 응답이 이어진다. 즉 HyundaiHS도 “VLM이 필드를 채운 JSON”을 곧바로 최종 합격/불합격으로 보지 않는다.

또한 이번 확인 범위에서는 HyundaiHS에 범용 VectorDB/RAG 파이프라인 구현은 보이지 않았다. 규정·필수항목은 버전 관리되는 rule pack과 외부 참조 데이터(HMall QA 등)로 해소한다. 설계 문서도 일반 지식이나 LLM/RAG 응답으로 누락 사실을 추론하지 않는 방향을 명시한다. NH는 농협 규정 문서가 별도 지식 원천이므로 RAG가 필요할 수 있지만, **RAG 검색 결과만으로 광고 문구나 위반을 확정하지 말고, 항상 템플릿·광고 bbox 근거·조건 규칙과 함께 판정**하는 편이 안전하다.

## 10. NH에서 다음으로 진행할 일

### 지금까지 준비된 것

- 광고 전문을 좌표와 함께 보존하는 `P1/evidence-v6` 계약
- 카드별 라벨 심의 문구와 비배정 광고 문구, P1 줄 참조만 전달하는 `P2/ad-review-input-v6` 계약
- 영역 전문 1회, 영역당 0..N 라벨 범위, 표 형제값을 전달하는 `P3/ad-review-region-input-v1` 후보 계약
- 파서 기본 텍스트를 덮지 않는 VLM 비교 shadow 관측
- 다상품/이벤트 페이지의 최소 카드·공통영역 경계
- StructureV3 표 bbox + VLM 표 관측이라는 표 처리 방향
- CLI/배치 실행에서 P1/P2/P3를 함께 생성하는 연결(KL Parser는 현재 P1+P2 호환 유지)

### 권장 구현 순서

| 우선순위 | 다음 작업 | 완료 기준 |
|---|---|---|
| F0 | P1/P2/P3 계약을 대표 5파일 원본 재실행으로 확인 | P2 분할식과 P3 영역+미배정 소유권이 각각 P1 전체 줄과 일치하고, 모든 `line_ref`가 원본 bbox로 이동 가능 |
| F1 | 사람 검수 기준과 골드셋 만들기 | 영역별 OCR 정확성, Reader 오염률, 템플릿 라벨 정확성, 표 행 정확성, 카드 혼입률을 표본에서 수치화 |
| F2 | 심의 입력 묶음 설계 | `review_input + 상품 조건 + 적용 템플릿 + 규정 검색 결과`를 한 실행 단위로 만들고, 모호하면 `needs_review`로 멈춤 |
| F3 | 규정 RAG/VectorDB 구축 | 규정문서를 조항 단위로 버전·출처와 함께 색인하고, 심의 항목별로 검색한다. 광고 evidence 자체는 RDB/원장 중심으로 유지 |
| F4 | 좁은 범위의 심의 엔진 PoC | 예금성 또는 대출성 한 유형에서 3~5개 항목만 골라 `pass / fail / needs_review / not_applicable`과 근거 line_ref·규정 조항을 출력 |
| F5 | 운영 저장소·검수 화면 | 원본 파일 해시, 파싱 실행 버전, evidence, 심의 실행, 사람 수정 이력을 RDB에 분리 저장 |

### 지금 하지 않는 편이 좋은 일

- 94건 전체를 먼저 재실행해 결과만 쌓는 일: 표본 골드셋과 Reader 선택 기준이 없으면 비용만 커진다.
- VLM 판독/Judge 결과로 `parser_primary_text` 자동 덮어쓰기: 이웃 영역 혼입 사례가 이미 있어 오염률을 측정하기 전에는 위험하다.
- 모든 광고 문구를 VectorDB에만 넣는 설계: bbox·카드·시인성·Reader 상태 같은 구조 근거가 약해진다. 광고는 RDB/evidence 원장을 기준으로 두는 편이 맞다.
- 템플릿 `located/not_located`를 즉시 법적 위반으로 바꾸는 일: 상품 조건, 조건부 적용, 최신 규정 근거가 아직 합쳐지지 않았다.

## 11. 최종 책임 경계

```text
파싱 파이프라인
  책임: 광고에 보인 텍스트·위치·판독 후보·템플릿 연결을 보존
  산출: P1/evidence-v6 + P2/ad-review-input-v6 + P3/ad-review-region-input-v1 후보

규정 RAG / 참조 데이터
  책임: 어떤 규정·조항·조건이 현재 상품/광고에 적용되는지 근거를 제공
  산출: 버전 있는 규정 근거와 적용 조건

심의 엔진
  책임: 광고 근거 + 템플릿 + 적용 규정 + 상품 조건을 비교해 상태를 결정
  산출: pass / fail / needs_review / not_applicable, 그리고 근거 링크

사람 검수
  책임: OCR/VLM 불일치, 표 구조, 상품 귀속, 규칙의 애매한 적용을 확정
  산출: 골드 데이터와 변경 이력
```

이 경계를 지키면 파싱은 특정 샘플에 과적합하지 않고, 규정이 바뀌거나 심의 기준이 보강되어도 파서를 처음부터 다시 설계하지 않아도 된다.
