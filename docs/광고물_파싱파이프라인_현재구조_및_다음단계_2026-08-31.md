# NH 광고물 파싱 파이프라인: 현재 구조, 산출물, 다음 단계

> 기준일: 2026-08-31
> 기준 브랜치: `codex/region-reader-judge-pipeline`
> 대상 독자: 이 프로젝트를 처음 보는 기획·심의·개발 담당자
> 범위: 현재 광고물 파서의 실제 코드와 새 JSON 계약(`evidence-v4`, `ad-review-input-v2`) 기준. 이 브랜치의 일부 변경은 아직 커밋 전이므로 `main`의 과거 결과와 혼동하지 않는다.

## 1. 먼저 한 문장으로

이 파이프라인은 **광고 이미지에서 글자를 읽어, “어떤 문구가 어느 페이지의 어디에 있었는지”와 “농협 광고 템플릿의 어느 항목과 연결되는지”를 근거와 함께 넘기는 파서**다.

파서가 하지 않는 일도 분명하다.

- 파서는 “위반”을 확정하지 않는다.
- OCR과 VLM의 읽기가 다르다고 VLM 문구로 원문을 자동 교체하지 않는다.
- 템플릿 항목을 찾지 못했다고 곧바로 “미준수”라고 결론 내리지 않는다.

그 판단은 다음 심의 단계가 규정, 상품 조건, 사람 검수 결과를 함께 보고 한다. 파서는 그 판단에 필요한 **광고물 근거 원장**을 만든다.

## 2. 전체 그림

```text
광고 PDF / PNG / JPG / HWP
        │
        ▼
① 입력 판별·렌더·전처리
        │
        ▼
② PaddleX StructureV3: 화면 영역 + OCR 줄 + 좌표 추출
        │
        ▼
③ 좌표 복원·중복 제거·디지털 PDF 텍스트 병합
        │
        ▼
④ 영역별 읽기 순서 + 다상품 카드/공통영역 경계
        │
        ├───────────────► ⑤ 누락 문구 탐색 후보(별도 보관)
        │
        ▼
⑥ 영역 Reader / 불일치 시 Judge  ──► 관측값만 기록, 정본은 유지
        │
        ▼
⑦ 상품군·광고유형 분류 → 농협 제공 광고 템플릿 선택
        │
        ▼
⑧ 템플릿 라벨과 광고 문구의 줄 단위 연결
        │
        ├─────────────────────────────────────┐
        ▼                                     ▼
evidence-v4 (근거 원장·감사용)      ad-review-input-v2 (다음 단계용)
좌표·전문·VLM 판독/비교·표 관측      템플릿 배정 문구 / 비배정 광고 문구
```

파싱 산출물은 두 개이지만, 서로 다른 내용을 중복 생산하는 것이 아니다. 하나의 동일한 광고물을 다음 두 관점으로 제공한다.

| 파일 | 주 사용자 | 목적 |
|---|---|---|
| `json/<문서>.json` | 검수 화면, 운영 감사, 오류 재조사, RDB 저장 | 원문 줄·좌표·영역·VLM 관측을 잃지 않는 근거 원장 |
| `review_input/<문서>.json` | RAG/규정 조회/심의 엔진 | 템플릿에 배정된 문구와 그 밖의 광고 문구를 바로 소비할 수 있는 업무용 투영 |

`review_input`의 모든 값은 `evidence`의 줄(`line_ref`)을 다시 가리킨다. 따라서 심의 엔진이 의심스러운 결론을 내리면 언제든 `evidence`와 원본 이미지의 bbox로 되돌아갈 수 있다.

## 3. 먼저 알아둘 용어

| 용어 | 쉬운 설명 | 이 파이프라인에서의 의미 |
|---|---|---|
| OCR | 이미지 속 글자를 문자열로 읽는 기술 | PaddleX가 광고 이미지에서 줄 단위 텍스트와 좌표를 만든다. |
| StructureV3 | 페이지의 배치를 찾는 PaddleX 모델 | 제목·본문·표·이미지 같은 **사각형 영역**과 OCR 결과를 찾는다. 이 영역은 최종 의미 판단이 아니라 화면상의 경계다. |
| 영역(region) | 화면에서 StructureV3가 잡은 하나의 사각형 | `region_id`, `bbox`, 레이아웃 라벨, 그 안의 OCR 줄을 가진다. |
| bbox | 사각형 위치 | `[왼쪽 x, 위 y, 오른쪽 x, 아래 y]` 픽셀 좌표. 문구가 원본의 어디에 있는지 보여 준다. |
| 디지털 텍스트 | PDF 안에 이미 들어 있는 문자 레이어 | 이미지 OCR보다 우선할 수 있는 텍스트 출처다. 그림으로 만든 글자는 여기 없을 수 있다. |
| 파서 기본 텍스트(parser primary text) | 현재 파서가 기본값으로 보존하는 원문 텍스트 | 각 `lines[].parser_text`와 이를 합친 영역 문자열이다. OCR만 뜻하지 않으며 `text_source`가 `ocr`인지 `digital`인지 함께 밝힌다. 법적 정답이나 사람 검수 완료본이라는 뜻은 아니다. |
| VLM | 이미지를 보고 질문에 답하는 Vision Language Model | 이미지 crop을 보고 독립적으로 문구를 읽거나, 후보 두 개를 비교한다. |
| VLM 영역 판독 | 영역 이미지를 파서 기본 텍스트와 독립적으로 읽는 VLM | OCR·디지털 PDF 텍스트를 교체하는 모델이 아니라, 파서 기본 텍스트를 점검하기 위한 두 번째 판독이다. |
| VLM Judge | 파서 기본 텍스트와 VLM 영역 판독이 다를 때만 둘을 비교하는 VLM | 어느 후보가 화면에 더 가까워 보이는지 의견을 남긴다. 아직 자동 수정 권한은 없다. |
| shadow(섀도우) | 실제로 실행·기록하지만 운영 기준값은 바꾸지 않는 시험 방식 | VLM이 틀려도 `parser_primary_text`는 유지한다. 성능·오염률을 측정한 뒤에만 정책 변경을 검토한다. |
| 카드(card) | 한 페이지에 나란히 있는 여러 상품/이벤트의 공간 묶음 | `card_no=1,2,...`는 같은 카드 안 문구가 섞이지 않도록 돕는다. `0`은 공통 제목·공통 고지처럼 공유 영역, `null`은 공간상 확정하지 못한 영역이다. 상품 의미를 확정하는 라벨은 아니다. |
| 템플릿 | 농협이 제공한 “광고에 어떤 항목을 표시해야 하는지” 목록 | 예: 회사명, 상품명, 금리, 대출한도, 유의사항. 규정 위반 판정 규칙 그 자체가 아니다. |
| 템플릿 라벨 | 광고 문구가 템플릿의 어느 항목과 관련되는지 붙이는 이름 | `template_fields`의 `label`이다. 위치를 찾았다는 뜻이지, 필수조건 충족·위반 결론은 아니다. |
| 회수 후보(recovery candidate) | StructureV3/OCR가 놓쳤을 수 있어 페이지 전체를 훑어 찾은 문구 후보 | 정본·템플릿 값에 자동 합치지 않고 `unverified_recovery_candidates`로 별도 보관한다. |

## 4. 파싱 단계별 설명

### 0) 호출 진입점과 입력

광고물 처리의 공통 진입점은 `src/nh_parsing/pipeline.py`의 `process_file()`이다. CLI는 `tools/run_ad_label.py`, 농협 KL 연동은 `kl_parser/app_custom_parser/service/parsing_service.py`가 이 공통 경로를 호출한다.

입력으로 PDF, PNG/JPG 계열 이미지, HWP를 받는다. 지원하지 않는 확장자는 파싱 불가 상태와 사유를 남긴다.

### 1) 입력 판별, 렌더, 이미지 전처리

PDF는 먼저 페이지가 다음 중 어디에 가까운지 살핀다.

- `structured`: PDF 문자 레이어가 비교적 정상인 문서
- `scan_like`: 스캔 이미지처럼 문자 레이어를 신뢰하기 어려운 문서
- `hybrid`: 문자 레이어와 이미지 기반 텍스트가 함께 있는 문서

그 뒤 PDF를 이미지 캔버스에 렌더하고, 흰 배경 RGB 이미지로 정규화한다. 긴 페이지는 글자가 잘리는 일을 줄이기 위해 겹침(overlap)을 둔 타일로 나누어 처리한다. 스캔형·혼합형은 원본 내장 이미지 해상도를 고려해 불필요한 확대를 피한다.

`structured` PDF도 레이아웃을 잃지 않도록 StructureV3를 호출한다. 다만 같은 글자가 PDF 문자 레이어와 OCR에 동시에 있을 수 있으므로, 다음 단계에서 디지털 텍스트를 우선해 병합한다.

### 2) StructureV3와 OCR: 화면을 영역과 줄로 분해

각 타일을 PaddleX PP-StructureV3에 보낸다. 여기서 얻는 것은 크게 두 가지다.

- **레이아웃 영역**: text, table, image 등 화면의 사각형과 점수
- **OCR 줄**: 실제로 읽힌 글자, 줄 bbox, OCR 신뢰도

중요한 구분은 StructureV3의 `text`/`table`이 화면 배치 모델의 분류라는 점이다. 이것은 아직 “이 문구가 상품명인지, 유의사항인지”를 뜻하지 않는다. 그 업무 의미는 뒤의 템플릿 라벨링 단계에서 붙인다.

### 3) 좌표 복원, 중복 제거, PDF 텍스트 병합

타일 안에서 얻은 좌표는 페이지 전체 좌표로 되돌린다. 겹치는 타일에서 같은 글자가 두 번 읽히면 중복을 제거한다.

디지털 PDF에서는 PDF 문자 레이어와 OCR이 겹치는 경우가 많다. 이때 디지털 텍스트와 겹친 OCR은 제거하거나 보조로 두어, 안정적인 PDF 문자 레이어를 기본 텍스트 출처로 쓴다. 결과 줄에는 `source`가 `digital`, `ocr`, `hybrid` 등으로 남는다.

### 4) 영역에 줄을 붙이고 읽기 순서를 정리

OCR 줄을 가장 알맞은 StructureV3 영역에 붙인다. 어느 영역에도 안전하게 붙일 수 없는 줄은 `unassigned_lines`로 남겨 버리지 않는다.

그 다음 각 영역 안의 줄 순서와 영역 간 순서를 좌표 기반으로 정리한다. 이 단계의 목표는 사람이 페이지를 읽는 순서에 가까운 텍스트 나열을 만드는 것이지, 특정 상품 디자인에 맞춘 “완벽한 의미 순서”를 억지로 확정하는 것이 아니다.

### 5) 여러 상품·이벤트가 한 페이지에 있을 때 카드 경계 보존

한 페이지에 `EVENT 1`과 `EVENT 2`, 또는 두 상품 카드가 나란히 있으면 y좌표만으로 정렬할 때 두 카드의 문장이 교차할 수 있다. 그래서 VLM 보조 판정을 사용해 공간상의 카드 경계를 보존한다.

- `card_no=1,2,...`: 각 상품/이벤트 카드의 공간 묶음
- `card_no=0`: 카드 공통 제목, 공통 심의번호, 공통 하단 고지처럼 공유하는 영역
- `card_no=null`: 좌표상 어느 카드로도 단정하지 않은 영역

이는 “이 카드는 반드시 A 상품”이라고 결정하는 기능이 아니다. 하류 단계가 상품 귀속을 판단할 때 문구 혼입을 막을 최소 공간 정보다.

### 6) 누락 문구 탐색은 보조 후보로만 보관

StructureV3가 아예 영역을 만들지 못한 장식 문구·벡터 텍스트를 찾기 위해 페이지 전체를 한 번 추가로 훑는다. 이를 **페이지 sweep**이라고 한다.

이 결과는 OCR 줄에 섞지 않는다. bbox가 넓은 밴드 단위라 정확한 영역 귀속을 보장하기 어렵기 때문이다. 따라서 `recovery_candidates` / `unverified_recovery_candidates`에만 넣고, 사람 또는 후속 검증이 채택할 때까지 정본과 템플릿 필드에서는 제외한다.

이 방식은 “새로운 문구를 놓치지 않으려는 탐색”과 “기존 정본을 조용히 오염시키지 않는 보수성”을 함께 지킨다.

### 7) 영역 Reader: 같은 StructureV3 영역을 VLM이 독립 판독

현재 시험 파이프라인에서는 StructureV3가 만든 텍스트·표 영역을 대상으로 VLM Reader를 실행한다. Reader 입력은 OCR 문자열이 아니라 **해당 영역의 이미지 crop**이다.

이웃 문구 혼입을 줄이기 위해 crop에서 다음을 적용한다.

- 목표 bbox를 파란 테두리로 표시한다.
- bbox 바깥은 마스킹한다.
- 목표 영역 안에 다른 StructureV3 텍스트 영역이 완전히 포함되어 있으면 그 하위 영역도 마스킹한다.

표 영역에는 일반 Reader와 별도로 표 Reader를 요청할 수 있다. 표 Reader는 `text`, `rows`, `confidence`, `structure_confidence` 관측을 남긴다. **PaddleX의 HTML/셀 격자는 현재 최종 계약에서 사용하지 않는다.** StructureV3의 “표 영역 bbox”만 경계로 사용하고, 표 내부 행 관계는 VLM 관측으로 따로 둔다.

`REGION_READING_MODE=shadow`이고 기본 범위 `REGION_READING_SCOPE=all`일 때 이 단계가 켜진다. 기본 운영 설정은 `off`라서 외부 VLM 호출·비용 없이 일반 파싱만 실행한다.

### 8) Judge: 서로 다르게 읽힌 영역만 비교

OCR 정본과 Reader 텍스트가 글자와 숫자 기준으로 같으면 Judge를 부르지 않는다. 다를 때만 OCR과 Reader를 A/B 후보로 익명화해 Judge에게 같은 crop과 함께 비교시킨다.

Judge 결과는 다음과 같은 상태와 근거로 남긴다.

- `agreed`: OCR 정본과 Reader가 실질적으로 일치
- `judge_selected` 등: Judge가 한 후보를 더 선호
- `uncertain`: 어느 쪽도 안전하게 채택하기 어렵거나 차이가 큼
- `reader_failed` / `judge_failed`: 외부 모델 호출 실패

하지만 shadow 모드에서는 Judge가 VLM 판독을 선호해도 `lines[].parser_text`를 바꾸지 않는다. 즉, **파서 기본 텍스트·VLM 후보·Judge 의견은 함께 보이되 한 값으로 뭉개지지 않는다.** 이것이 세 값이 공존하는 이유다.

### 9) 문서 분류와 광고 템플릿 선택

문서의 텍스트·이미지 문맥으로 상품군, 광고유형, 노출 상품명을 분류한다. 이 결과와 파일명 등을 근거로 농협 제공 템플릿 중 하나를 선택한다. 결정할 수 없으면 VLM 결선 판단을 한 번 보조로 사용하며, 그래도 불확실하면 불확실성을 남긴다.

템플릿은 예금성·대출성 등 유형별로 “회사명, 상품명, 금리, 대출한도, 유의사항…”처럼 광고에서 점검할 항목을 정의한다. 이는 다음 단계가 무엇을 확인해야 하는지 알려 주는 기준표다.

### 10) 템플릿 라벨링: 광고 문구와 템플릿 항목 연결

템플릿을 고른 뒤 광고 문구의 줄 범위를 템플릿 항목과 연결한다. 두 신호를 함께 쓴다.

1. **정형 문구 완전 일치**: 템플릿이 지정한 고정 문구와 문자열이 정확히 맞는지 확인
2. **영역 단위 VLM 라벨링**: 제목/본문 같은 9종 범용 역할이 아니라, 선택한 템플릿의 실제 항목명으로 줄 범위를 판단

여기서 `review_targets`는 “이번 템플릿에서 확인할 항목”과 “현재 광고에서 연결된 줄의 `line_ref`”를 묶은 작업 목록이다.

- `located`는 해당 항목의 문구 위치를 찾았다는 뜻이다.
- `not_located`는 파서가 연결된 줄을 찾지 못했다는 뜻이다.
- 둘 다 최종 심의 결론은 아니다. 조건부 필수 여부, 표현 적정성, 숫자 정확성은 다음 단계에서 판정한다.

과거의 제목/본문/각주 등 9종 role은 전체 문서 읽기 보조로는 쓸 수 있지만, 현재 핵심 출력에서는 템플릿 항목 라벨보다 우선하지 않는다. 광고 심의에 필요한 질문이 “이것이 본문인가?”보다 “이 문구가 금리·대출한도·유의사항과 관련되는가?”인 경우가 많기 때문이다.

### 11) 두 JSON으로 내보내기

마지막으로 동일한 파싱 결과를 두 계약으로 만든다.

- `evidence-v4`: 세부 근거를 빠뜨리지 않는 원장
- `ad-review-input-v2`: 하류 심의 엔진이 바로 순회할 수 있는 업무용 목록

KL Parser 경로로도 두 파일이 함께 반환·압축되도록 연결되어 있다.

## 5. 최종 산출물 1: evidence-v4 근거 원장

### 무엇을 위한 파일인가

`json/<문서>.json`은 “이 문구를 왜 이렇게 판단했는가?”를 다시 확인하기 위한 원본 근거 파일이다. 화면 검수, 오류 분석, RDB 보관, 후속 엔진의 근거 링크에 사용한다.

### 최상위 구조

```json
{
  "doc_id": "문서 식별자",
  "source_file": "원본 파일명.pdf",
  "file_type": "pdf",
  "classification": {
    "product_group": "대출성",
    "ad_type": "...",
    "product_name_shown": "...",
    "source": "...",
    "confidence": 0.0
  },
  "template": {
    "template_id": "...",
    "status": "resolved 또는 unresolved",
    "basis": ["템플릿 선택 근거"]
  },
  "reading_evidence_contract": {
    "version": "nh-ad-review-evidence-v4",
    "parser_primary_text": "파서 기본 텍스트 위치 설명",
    "vlm_region_reading_mode": "shadow_observation",
    "parser_mutates_primary_text_from_vlm": false,
    "final_text_selection": "deferred_to_review",
    "table_structure": "structurev3_bbox + table_vlm_reader_observation",
    "paddlex_table_grid_used": false
  },
  "pages": ["페이지별 근거"],
  "review_targets": ["템플릿 항목별 점검 대상"],
  "completeness": {"...": "..."},
  "notes": ["처리 중 주의사항"]
}
```

### 페이지·영역·줄 구조

```text
pages[]
 ├─ page_no, canvas_w, canvas_h, dpi, parse_route, parse_status
 ├─ regions[]
 │   ├─ region_id, bbox, layout(label/score), card_no
 │   ├─ visibility
 │   ├─ text_evidence
 │   │   ├─ parser_primary_text   ← 기본 텍스트와 줄 참조
 │   │   ├─ vlm_region_reading    ← 독립 VLM 판독 후보
 │   │   └─ parser_vlm_comparison ← VLM/파서 불일치 비교 결과
 │   ├─ template_labels   ← 이 영역에서 붙은 템플릿 라벨 근거
 │   ├─ lines[]           ← 실제 원자 단위: text, bbox, source, confidence, line_ref
 │   └─ table             ← 표일 때 StructureV3 bbox + VLM 표 관측
 ├─ unassigned_lines[]    ← 영역에는 못 붙였으나 버리지 않은 줄
 └─ recovery_candidates[] ← 페이지 탐색으로 회수한 미검증 후보
```

#### 꼭 봐야 할 필드

| 필드 | 의미 | 주의점 |
|---|---|---|
| `lines[].parser_text` | 파서 기본 텍스트의 가장 작은 단위 | 심의·검색의 기본 텍스트는 여기서 시작한다. |
| `lines[].bbox` | 문구의 원본 위치 | 화면 하이라이트·시인성 계산·다상품 혼입 조사에 사용한다. |
| `lines[].source` / `confidence` | 디지털/OCR 출처와 OCR 신뢰도 | OCR 신뢰도가 낮다고 자동 오류는 아니다. 검수 우선순위 신호다. |
| `region.card_no` | 공간상 카드/공통 영역 | 상품 의미 확정값이 아니다. 다른 카드 문구를 섞지 않기 위한 경계다. |
| `visibility` | 글자 높이·영역 대비 등 관측 가능한 시인성 정보 | 시인성 위반 판정이 아니라, 후속 규칙/사람 검토에 줄 원시 측정값을 준다. |
| `text_evidence.parser_primary_text` | 영역 안 `lines[].parser_text`를 순서대로 합친 편의 문자열 | 줄 배열과 별개 정답이 아니다. 원자 단위는 여전히 `lines[]`다. |
| `text_evidence.vlm_region_reading` | 동일 영역의 독립 VLM 판독 | 파서 기본 텍스트를 대체하지 않는다. |
| `text_evidence.parser_vlm_comparison` | 파서 기본 텍스트·VLM 판독 비교 상태 | Judge 기록도 자동 수정 지시가 아니다. |
| `table.reader.rows` | VLM이 관측한 표 행 배열 | 표 구조가 불명확하면 빈 배열 또는 낮은 구조 신뢰도로 남는다. 사람이 확정한 셀 그리드가 아니다. |
| `recovery_candidates` | 누락 가능 문구 후보 | 정본·템플릿 필드에 자동 포함하지 않는다. |

### 표는 어떻게 표현되는가

표는 더 이상 PaddleX가 만든 HTML·셀 격자를 정답처럼 내보내지 않는다. 현재 약속은 다음이다.

```json
{
  "table": {
    "detected_by": "structurev3",
    "paddlex_grid_used": false,
    "parser_primary_line_refs": ["p1/r015/L00", "p1/r015/L01"],
    "vlm_table_reading": {
      "source": "table_region_reader",
      "status": "observed",
      "text": "표에서 읽힌 문구",
      "rows": [["항목", "내용"], ["일반가구주", "수도권 외 지역: 8천만원 이내"]],
      "confidence": 0.0,
      "structure_confidence": 0.0
    }
  }
}
```

즉, StructureV3는 “여기가 표다”라는 경계를 제공하고, VLM은 그 영역에서 읽은 행 관측을 제공한다. 표 Reader가 행/열을 확실히 구분하지 못하면 억지로 셀을 채우지 않고 `rows`를 비우거나 낮은 `structure_confidence`를 남겨 검수 대상으로 보낸다.

과거 `out_0831_region_reader_judge_v2`를 변환한 시험 파일은 이 표 Reader 실행 전 결과다. 따라서 그 안의 표 관측은 `legacy_text_only`이며 `rows=[]`가 정상이다. 새 원본 파싱을 실행한 뒤에만 VLM 표 Reader의 `rows`가 채워진다.

## 6. 최종 산출물 2: ad-review-input-v2 다음 단계용 JSON

### 왜 별도 파일이 필요한가

심의 엔진이 매번 `pages → regions → lines` 전체를 훑어서 “금리 항목 문구만 모아 달라”고 하면 구현이 복잡하고 누락 위험도 높다. 그래서 evidence의 줄을 새로 해석하지 않고, **템플릿 배정 문구와 비배정 광고 문구를 분리한 보기**를 만든다.

이 파일은 새로운 OCR이나 VLM 호출을 하지 않는 결정론적 투영이다. `review_targets[].evidence.line_refs`만 사용하므로, 이 파일을 만드는 과정에서 문구 의미가 바뀌지 않는다.

### 최상위 구조

```json
{
  "contract": {
    "version": "nh-ad-review-input-v2",
    "source_evidence_contract": "nh-ad-review-evidence-v4",
    "parser_primary_text_policy": "template_fields + unmapped_ad_copy partition parser primary lines",
    "vlm_observation_policy": "observation_only; never replaces parser primary text",
    "table_policy": "structurev3 region bbox + table VLM observation; PaddleX grid excluded"
  },
  "document": {"문서 메타데이터와 선택된 템플릿"},
  "template_fields": ["템플릿 항목에 배정된 문구"],
  "unmapped_ad_copy": ["템플릿에 배정되지 않은 광고 문구"],
  "unverified_recovery_candidates": ["미검증 회수 후보"],
  "summary": {"분할 개수와 표·후보 집계"}
}
```

### A. `template_fields[]`: 템플릿 항목별 문구

각 원소는 하나의 템플릿 점검 항목이다.

```json
{
  "target_id": "템플릿 항목의 안정 식별자",
  "field_key": "현재는 target_id와 동일",
  "label": "예: 대출한도",
  "requirement": "템플릿의 필수/조건 정보",
  "writing_rules": ["템플릿 작성 기준"],
  "evidence_status": "located 또는 not_located",
  "fixed_phrase_checks": ["고정 문구 대조 결과"],
  "values": [
    {
      "value_id": "...",
      "value": "연결된 정본 줄을 순서대로 합친 문자열",
      "value_source": "parser_primary_text",
      "page_no": 1,
      "region_id": "p1_r015",
      "region_bbox": [0, 0, 0, 0],
      "card_no": 1,
      "lines": ["line_ref, text, bbox, source, confidence"],
      "vlm_region_reading": {"text": "...", "comparison_status": "..."},
      "table": {"표일 때의 관측"}
    }
  ]
}
```

한 템플릿 항목이 여러 카드·페이지에 반복될 수 있으므로 `values[]`를 하나로 합치지 않는다. 심의 엔진은 `card_no`, `page_no`, `bbox`를 유지한 채 비교해야 한다.

`evidence_status=located`는 “항목에 연결된 광고 문구가 발견됨”일 뿐이다. 예를 들어 금리 문구가 `located`여도 상품 조건에 맞는지, 필수 고지가 모두 충족됐는지는 규정과 상품 사실을 더 확인해야 한다.

### B. `unmapped_ad_copy[]`: 템플릿 밖의 광고 문구

템플릿 라벨에 배정되지 않은 모든 정본 줄은 이 목록으로 간다. 헤드라인, 혜택 문구, 이벤트 안내, 브랜드 문구, 아직 의미를 정할 수 없는 문구를 포함한다.

```json
{
  "copy_id": "copy:p1_r020:1",
  "assignment_status": "unmapped_to_template",
  "ad_copy_text": "광고 문구",
  "page_no": 1,
  "region_id": "p1_r020",
  "region_bbox": [0, 0, 0, 0],
  "card_no": 2,
  "layout": {"label": "text", "score": 0.0},
  "visibility": {"...": "..."},
  "lines": ["원자 줄 근거"],
  "vlm_region_reading": {"...": "..."},
  "table": null
}
```

이 목록은 “중요하지 않은 문구” 목록이 아니다. 오히려 템플릿이 아직 포착하지 못한 광고 주장·혜택·오인 가능 문구를 다음 심의 단계가 찾는 출발점이다.

### C. 분할 보장

한 정본 줄은 다음 둘 중 정확히 하나에 속한다.

```text
모든 parser primary lines
  = 템플릿 항목에 한 번 이상 배정된 줄
  + 어느 템플릿 항목에도 배정되지 않은 줄(unmapped_ad_copy)
```

하나의 줄이 관련 있는 여러 템플릿 항목에 중복 참조될 수는 있다. 하지만 `unmapped_ad_copy`와 `template_fields`에 동시에 들어가지는 않도록 검사한다. 이 성질 때문에 “광고 전문이 다음 단계에 다 넘어갔는가?”를 `summary.parser_primary_line_total`로 점검할 수 있다.

### D. 다음 단계가 이 파일을 쓰는 예

```text
1. document.template으로 현재 상품 유형 템플릿 확인
2. template_fields에서 필수/조건부 점검 항목과 광고 근거 수집
3. 규정 RAG에서 해당 항목·상품 조건에 맞는 근거 조항 검색
4. unmapped_ad_copy에서 별도 광고 주장·혜택·주의 문구 탐색
5. bbox·시인성·VLM 비교 상태로 검수 우선순위 결정
6. 심의 결과에는 반드시 line_ref / bbox / 규정 근거를 다시 연결
```

## 7. 지금 결과를 볼 수 있는 위치와 실행 방법

새 파이프라인을 원본부터 실행할 때는 다음과 같은 구조가 생긴다.

```text
<출력 폴더>/
 ├─ json/<문서>.json                 # evidence-v4
 ├─ review_input/<문서>.json         # ad-review-input-v2
 ├─ parsed/<문서>.json               # 옵션/실행 흐름에 따라 중간 파싱 결과
 ├─ summary.json                     # 문서별 수량 집계
 └─ explorer.html                    # 검수용 화면(생성했을 때)
```

```powershell
# 일반 파싱 + 두 JSON 출력
uv run python tools/run_ad_label.py --input <광고 파일 또는 폴더> --out <출력 폴더>

# 이미 있는 evidence JSON(v2/v3)에서 review_input만 시험 생성
uv run python tools/build_ad_review_input.py out_0831_region_reader_judge_v2

# VLM 판독/Judge shadow까지 켜는 원본 실행
$env:REGION_READING_MODE = "shadow"
$env:REGION_READING_SCOPE = "all"
uv run python tools/run_ad_label.py --input <광고 파일> --out <새 출력 폴더>
```

`out_0831_region_reader_judge_v2`는 과거 3개 대표 파일의 VLM 비교 시험 결과다. 이 폴더에 `build_ad_review_input.py`를 실행하면 기존 근거는 바꾸지 않고 `review_input/`만 추가 생성해 다음 단계 JSON 모양을 검토할 수 있다. 단, 원본을 새로 읽는 실행이 아니므로 v2의 과거 표 관측을 새 VLM 표 행 구조로 바꾸지는 않는다.

외부 호출을 켜는 원본 실행에서는 광고 원본 이미지/페이지 crop이 다음 사내 서비스로 전송된다.

- `PADDLEX_URL`: 페이지 또는 타일 이미지. 레이아웃과 OCR을 얻기 위한 호출이다.
- `GEMMA_URL`: 문서 분류, 카드 경계, 페이지 sweep, 템플릿 라벨링, VLM 영역 판독/Judge 및 표 VLM 판독용 원본/영역 crop과 프롬프트.

`build_ad_review_input.py`는 이미 생성된 로컬 JSON만 읽으므로 외부 서비스 호출이 없다.

## 8. HyundaiHS는 파싱 다음에 무엇을 하는가

`C:\Users\cccjj\cginside\repo-analysis\paddle-gemma-orchestrator\HyundaiHS`의 실제 코드와 문서를 확인했다. 그 프로젝트는 식품·축산물 표시/성적서 검증 도메인이므로 NH 광고 심의와 입력 문서·규칙 내용은 다르다. 그러나 **파싱 결과와 판정 엔진의 경계를 나누는 방식**은 좋은 참고가 된다.

### HyundaiHS의 큰 흐름

```text
업로드 파일 묶음
  → 비동기 Job / Run 생성
  → 페이지 렌더·방향/문서유형 분류
  → PaddleX StructureV3 + OCR
  → VLM crop 추출 + 페이지 Judge + OCR 대조
  → 페이지별 structured fields / fields / 원본 근거 저장
  → 같은 실제 문서의 여러 페이지·파일을 logical document로 묶음
  → 검증에 쓸 문서 역할을 선택 (불확실하면 사람 선택 요청)
  → ValidationBundle 생성
  → WF1/WF2 규칙 엔진 호출
  → checks / notices / evidence / decision_summary 저장·화면 제공
  → 필요 시 Label Studio 검수·정답 수집
```

파싱 후 코드 경로의 핵심은 다음과 같다.

| HyundaiHS 단계 | 실제 책임 | NH에서 가져올 원칙 |
|---|---|---|
| 페이지 추출 결과 확정 | VLM 추출 결과에 OCR 근거를 붙이고, 필수 필드를 복구·정합성 검사한 뒤 `structured`와 평면 `fields`를 함께 보관 | NH도 evidence 원장과 업무용 투영을 분리한다. VLM 후보를 원문처럼 덮어쓰지 않는다. |
| logical document 구성 | 여러 페이지/파일을 같은 실제 문서로 묶고, 문서 역할을 판별 | NH에서는 다상품 한 페이지의 `card_no`와 문서/상품 단위 선택이 대응 지점이다. 카드 경계만으로 상품 사실을 확정하지 않는다. |
| 문서 선택 | 검증 대상 문서가 여러 개거나 모호하면 자동 판정을 멈추고 검토자 선택을 요구 | NH도 상품 카드·템플릿 선택이 모호하면 `needs_review`로 보내야 한다. |
| `ValidationBundle` | 역할별로 선택된 논리 문서를 검증 단위로 고정 | NH에서는 “광고물 근거 + 선택된 템플릿 + 상품 조건 + 적용 규정 묶음”이 이 역할을 한다. |
| 별도 규칙 엔진 | WF1/WF2 규칙팩, 상품 사실, 참조 데이터를 사용해 검증하고 `decision_summary` 생성 | NH도 파서 바깥에 심의 규칙 엔진을 둔다. 템플릿 위치 발견과 위반 판정을 한 함수에 섞지 않는다. |
| 저장·검수 | Run, 페이지, 영역, 검수 작업·주석, 검증 결과를 RDB/아티팩트 저장소에 남김 | NH도 원본 evidence 버전, 심의 실행 버전, 사람 확정 결과를 분리 저장해야 재현 가능하다. |

HyundaiHS의 `judge_output__structured`는 파싱/추출 결과를 구조화한 중간 산출물에 가깝다. 그 뒤에도 문서 선택, 규칙팩, 상품 사실·참조 데이터, 검증 응답이 이어진다. 즉 HyundaiHS도 “VLM이 필드를 채운 JSON”을 곧바로 최종 합격/불합격으로 보지 않는다.

또한 이번 확인 범위에서는 HyundaiHS에 범용 VectorDB/RAG 파이프라인 구현은 보이지 않았다. 규정·필수항목은 버전 관리되는 rule pack과 외부 참조 데이터(HMall QA 등)로 해소한다. 설계 문서도 일반 지식이나 LLM/RAG 응답으로 누락 사실을 추론하지 않는 방향을 명시한다. NH는 농협 규정 문서가 별도 지식 원천이므로 RAG가 필요할 수 있지만, **RAG 검색 결과만으로 광고 문구나 위반을 확정하지 말고, 항상 템플릿·광고 bbox 근거·조건 규칙과 함께 판정**하는 편이 안전하다.

## 9. NH에서 다음으로 진행할 일

### 지금까지 준비된 것

- 광고 전문을 좌표와 함께 보존하는 `evidence-v4` 계약
- 템플릿 배정 문구와 비배정 광고 문구를 빠짐없이 나누는 `ad-review-input-v2` 계약
- 파서 기본 텍스트를 덮지 않는 VLM 비교 shadow 관측
- 다상품/이벤트 페이지의 최소 카드·공통영역 경계
- StructureV3 표 bbox + VLM 표 관측이라는 표 처리 방향
- KL Parser에서 두 JSON을 함께 반환하는 연결

### 권장 구현 순서

| 우선순위 | 다음 작업 | 완료 기준 |
|---|---|---|
| P0 | 두 JSON 계약을 대표 3파일 원본 재실행으로 확인 | 각 문서에서 `parser_primary_line_total = template_assigned_parser_primary_line_count + unmapped_ad_copy_parser_primary_line_count`, 모든 `line_ref`가 원본 bbox로 이동 가능 |
| P1 | 사람 검수 기준과 골드셋 만들기 | 영역별 OCR 정확성, Reader 오염률, 템플릿 라벨 정확성, 표 행 정확성, 카드 혼입률을 표본에서 수치화 |
| P2 | 심의 입력 묶음 설계 | `review_input + 상품 조건 + 적용 템플릿 + 규정 검색 결과`를 한 실행 단위로 만들고, 모호하면 `needs_review`로 멈춤 |
| P3 | 규정 RAG/VectorDB 구축 | 규정문서를 조항 단위로 버전·출처와 함께 색인하고, 심의 항목별로 검색한다. 광고 evidence 자체는 RDB/원장 중심으로 유지 |
| P4 | 좁은 범위의 심의 엔진 PoC | 예금성 또는 대출성 한 유형에서 3~5개 항목만 골라 `pass / fail / needs_review / not_applicable`과 근거 line_ref·규정 조항을 출력 |
| P5 | 운영 저장소·검수 화면 | 원본 파일 해시, 파싱 실행 버전, evidence, 심의 실행, 사람 수정 이력을 RDB에 분리 저장 |

### 지금 하지 않는 편이 좋은 일

- 94건 전체를 먼저 재실행해 결과만 쌓는 일: 표본 골드셋과 Reader 선택 기준이 없으면 비용만 커진다.
- VLM 판독/Judge 결과로 `parser_primary_text` 자동 덮어쓰기: 이웃 영역 혼입 사례가 이미 있어 오염률을 측정하기 전에는 위험하다.
- 모든 광고 문구를 VectorDB에만 넣는 설계: bbox·카드·시인성·Reader 상태 같은 구조 근거가 약해진다. 광고는 RDB/evidence 원장을 기준으로 두는 편이 맞다.
- 템플릿 `located/not_located`를 즉시 법적 위반으로 바꾸는 일: 상품 조건, 조건부 적용, 최신 규정 근거가 아직 합쳐지지 않았다.

## 10. 최종 책임 경계

```text
파싱 파이프라인
  책임: 광고에 보인 텍스트·위치·판독 후보·템플릿 연결을 보존
  산출: evidence-v4 + ad-review-input-v2

규정 RAG / 참조 데이터
  책임: 어떤 규정·조항·조건이 현재 상품/광고에 적용되는지 근거를 제공
  산출: 버전 있는 규정 근거와 적용 조건

심의 엔진
  책임: 광고 근거 + 템플릿 + 적용 규정 + 상품 조건을 비교해 상태를 결정
  산출: pass / fail / needs_review / not_applicable, 그리고 근거 링크

사람 검수
  책임: OCR/VLM 불일치, 표 구조, 상품 귀속, 규칙의 애매한 적용을 확정
  산출: 골드 데이터와 변경 이력
```

이 경계를 지키면 파싱은 특정 샘플에 과적합하지 않고, 규정이 바뀌거나 심의 기준이 보강되어도 파서를 처음부터 다시 설계하지 않아도 된다.
