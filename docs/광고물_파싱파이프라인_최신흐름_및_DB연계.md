# 광고물 파싱 파이프라인 최신 흐름 및 VectorDB·RDB 연계 안내

> 기준일: 2026-08-27  
> 대상 독자: 광고 심의 VectorDB/RDB 엔진 설계·개발 담당자  
> 기준 코드: 현재 작업 폴더의 `src/nh_parsing`, `kl_parser` 및 미커밋 고도화 내용 포함  
> 문서 목적: 광고 파일에서 최종 통합 JSON이 만들어지는 과정과, 후속 엔진이 어떤 값을 어떻게 읽어야 하는지를 한 문서로 설명한다.

---

## 1. 지금 파싱 단계가 책임지는 범위

현재 광고물 파싱의 가장 중요한 목표는 다음 한 문장이다.

> 광고에 보이는 텍스트를 가능한 한 전량 보존하고, 각 텍스트의 원본 위치와 판독 근거를 함께 남긴 뒤, 농협 제공 템플릿의 항목명을 라벨로 덧붙인다.

따라서 파싱 단계는 다음을 한다.

- PDF·PNG·JPG·HWP/HWPX에서 텍스트를 읽는다.
- 텍스트의 페이지, 좌표, 출처, OCR 신뢰도와 레이아웃 관계를 보존한다.
- 표가 검출되면 행·열·셀 관계를 보조 정보로 남긴다.
- 제목·본문·유의사항·고지문구 등의 범용 역할을 붙인다.
- 농협 제공 광고 템플릿을 선택하고 `회사명`, `상품명`, `대출한도`, `우대금리`, `유의사항` 같은 `구분` 라벨을 붙인다.
- 템플릿에 해당하지 않는 홍보 문구와 일반 광고 문구도 라벨 없이 그대로 남긴다.

파싱 단계는 다음을 하지 않는다.

- 규정 위반 여부를 확정하지 않는다.
- `필수여부=O`인데 문구가 없다는 이유만으로 위반이라고 판정하지 않는다.
- OCR과 VLM이 다르게 읽었다고 VLM 결과로 원문을 자동 덮어쓰지 않는다.
- 예금·대출 등 상품별 고정 스키마에 값을 억지로 채우지 않는다.
- 광고물을 농협 KL VectorDB에 직접 색인하지 않는다.

위반 여부, 조건부 필수사항 적용 여부, 규정 근거 검색과 최종 심의 판단은 후속 VectorDB/RDB·심의 엔진의 책임이다.

### 현재 구현·검증 상태

| 항목 | 상태 |
|---|---|
| 규정문서·광고물 로컬 비동기 API 왕복 | 완료 |
| 광고물 통합 JSON과 템플릿 라벨 | 구현 완료 |
| 줄 범위별 `gubun` | 3건 부분 재실행 검증, 전체 재검증 대기 |
| PDF 공백 보존·레이아웃 정보 전달·표 품질 경고 | 미커밋, 전체 재검증 대기 |
| 기존 89건+이전 샘플 전체 재파싱 | 아직 수행 전 |
| Python 3.11 호환 | 예정 |
| 농협 폐쇄망 실제 배포·GPU 연동 | 미검증 |

따라서 현재 `out_ad_full` 결과는 최신 미커밋 고도화를 모두 반영한 결과가 아니다. 코드 변경과 기존 결과를 혼동하지 않도록 새 전체 실행은 별도 결과 폴더에 만들어 비교해야 한다.

## 2. 예전 흐름과 현재 흐름의 차이

예전 [out_new/review.html](../out_new/review.html)은 다음 구조를 설명한다.

```text
파싱 → out/json → out/llm_view → Stage 3 상품별 스키마 추출 → out/extracted
```

당시에는 `대출대상`, `대출한도`, `금리` 같은 필드를 상품군별 스키마에 직접 채우고, 값이 없으면 `미표시·해당없음·확인필요` 등으로 분류하려 했다.

현재 광고물 트랙은 다음과 같이 바뀌었다.

```text
파싱 원장
  + 농협 광고 템플릿 라벨
  + VLM 보조 판독 후보
  + 표 관계 및 진단 정보
  = 광고물 통합 JSON 한 파일
```

변경 이유는 명확하다.

1. 상품별 스키마를 파싱 단계에서 완성하면 파서가 심의 의미까지 과도하게 결정하게 된다.
2. 광고에는 템플릿 항목에 속하지 않는 헤드라인, 혜택 문구, 이벤트 설명, 버튼, 브랜드 문구가 많다.
3. 스키마에 들어가지 않는 텍스트도 심의에는 필요하므로, 먼저 모든 텍스트를 보존해야 한다.
4. 농협이 직접 제공한 템플릿의 `구분`을 라벨 어휘로 사용하면 우리 임의 스키마보다 근거가 분명하다.

따라서 `out_new/review.html`의 파일 라우팅, OCR, 좌표, 영역, VLM 후보 설명은 여전히 참고할 수 있지만, **Stage 3 상품별 스키마가 광고물의 최종 산출물이라는 설명은 현재 구조와 다르다.**

## 3. 규정문서와 광고물은 서로 다른 두 트랙이다

```text
규정문서                                      광고물
HWP/HWPX/PDF                                 PDF/PNG/JPG/HWPX
   │                                             │
POST /parsing                                POST /ad/parsing
   │                                             │
규정 청크 + 표 + 이미지 설명                    텍스트 + 좌표 + 영역 + 표 + 템플릿 라벨
   │                                             │
*_hrc.jsonl                                    *_parsed.json
   │                                             │
농협 KL VectorDB 색인                           RDB/심의 엔진 저장·조회
```

규정문서는 검색되는 지식이다. 농협 제공 Custom Parser 규격에 맞춰 `_hrc.jsonl`로 만들고 KL VectorDB에 넣는다.

광고물은 심의 대상이다. “어떤 문구가 원본 어디에 있었는가”가 중요하므로 좌표를 포함한 `_parsed.json`으로 만들고 RDB 또는 JSON 원장에 저장하는 것이 적합하다. 광고물 자체를 VectorDB에 넣는 것은 현재 필수 요구가 아니다.

두 API는 모두 농협 예제와 같은 비동기 통신 방식을 쓴다.

```text
파일 업로드 → 202 + UUID → 백그라운드 파싱
           → GET /parsing/result/{uuid} 폴링
           → 완료 시 kl-core-s2-output.zip 반환
```

`POST /ad/parsing`은 농협 예제에 원래 있던 광고 전용 규격이 아니라, 규정문서 API의 접수·상태조회·ZIP 반환 방식을 그대로 따라 우리가 제안·구현한 광고물 입력 경로다.

## 4. 광고물 한 건의 최신 처리 흐름

### 4-1. 전체 흐름

```text
① /ad/parsing으로 광고 파일 접수
        ↓
② 파일 형식별 라우팅·페이지 캔버스 생성
        ↓
③ PDF 텍스트 레이어 판독 + OCR 필요성 진단
        ↓
④ 긴 페이지 타일 분할
        ↓
⑤ PaddleX PP-StructureV3
   OCR 줄 + 레이아웃 블록 + 표 격자
        ↓
⑥ 좌표 복원·중복 제거·디지털/OCR 병합
        ↓
⑦ 영역 생성·줄 배정·미배정 줄 보존
        ↓
⑧ 범용 역할 판정 + VLM 보조 재판독
        ↓
⑨ 읽기순서 확정 + 문서 분류
        ↓
⑩ 농협 템플릿 선택
        ↓
⑪ 정형 문구 일치 + VLM 줄 범위 라벨링
        ↓
⑫ 통합 JSON 생성·텍스트 보존 검산
        ↓
⑬ _parsed.json + ad_summary.json + 페이지 이미지 ZIP 반환
```

### 4-2. 파일 형식별 시작점

| 입력 | 처리 방식 | 좌표 |
|---|---|---|
| PNG/JPG | 원본 이미지를 그대로 캔버스로 사용하고 OCR·레이아웃 분석 | 있음 |
| PDF | 페이지를 이미지로 렌더하고 PDF 텍스트 레이어와 OCR을 함께 사용 | 있음 |
| HWP/HWPX | 사내 `document-processor`가 본문·표를 디지털 추출하고 내장 이미지는 OCR | 본문 좌표는 현재 제한적 또는 없음 |

광고 심의 결과에서 원본 위치 하이라이트가 중요하므로, HWP/HWPX 광고 입력은 파싱 자체는 가능해도 좌표 요구를 완전히 만족하지 못할 수 있다. 현재 광고 API의 실검증 중심은 PDF·PNG·JPG다.

### 4-3. PDF 처리

PDF는 `pypdfium2`, 즉 PDFium의 Python 바인딩으로 처리한다.

페이지마다 텍스트 수, 깨진 문자 비율, 이미지 면적 등을 확인해 `structured`, `hybrid`, `scan_like` 진단값을 만든다.

- `structured` 또는 `hybrid`: PDF 텍스트 레이어를 읽고 PaddleX OCR·레이아웃 결과와 병합한다. 최종 `parse_route`는 실제로 두 출처를 사용하므로 `hybrid`다.
- `scan_like`: 신뢰할 텍스트 레이어가 없다고 보고 렌더링 이미지 OCR을 중심으로 처리한다.

디지털 텍스트와 OCR이 같은 위치에서 겹치면 일반적으로 디지털 텍스트를 우선한다. 디지털 텍스트는 원래 문자 정보를 직접 읽는 것이고 OCR은 픽셀을 보고 추정한 값이기 때문이다.

최근 발견한 `공무원연금공단에서확인된…` 띄어쓰기 문제는 PDFium이 공백을 못 읽은 것이 아니라 우리 코드가 PDFium이 준 공백을 제거하던 결함이었다. 현재 미커밋 변경에서는 줄바꿈만 제외하고 일반 공백을 보존하도록 고쳤다.

### 4-4. 타일 분할과 PaddleX

세로로 긴 모바일 광고는 그대로 축소해 OCR하면 작은 유의사항이 사라질 수 있다. 그래서 글자 밀도를 참고해 여러 타일로 나누고 경계에는 겹침 구간을 둔다.

각 타일은 PaddleX PP-StructureV3로 보내 다음 정보를 받는다.

- OCR 텍스트, 좌표, 인식 신뢰도
- `text`, `title`, `table`, `image` 등의 레이아웃 종류
- 레이아웃 검출 점수
- 표로 검출된 경우 HTML, 행·열, 셀 좌표

타일 좌표는 다시 원본 페이지 좌표로 복원한다. 겹침 구간에서 중복된 OCR 줄은 위치 기준으로 제거한다. 현재 백로그에는 OCR 줄이 아니라 **레이아웃 블록 자체가 타일 경계에서 중복되는 문제**가 남아 있다.

### 4-5. 영역과 줄

최종 구조의 핵심 단위는 `region`과 `line`이다.

- `line`: OCR 또는 디지털 추출이 읽은 텍스트 조각 하나
- `region`: PaddleX 레이아웃 블록 하나와 그 안에 배정된 줄들의 묶음
- `unassigned_lines`: 어느 영역에도 안전하게 배정하지 못했지만 버리지 않고 남긴 줄

줄은 자신의 bbox가 영역 bbox와 겹치는 비율을 기준으로 한 영역에 배정한다. 여러 영역이 겹치면 더 구체적인 작은 영역을 우선한다. 이후에도 배정되지 않은 디지털/OCR 줄은 같은 가로 구간에 있는 가까운 영역으로 한 차례 재배정하며, 안전하게 붙일 수 없으면 `unassigned_lines`에 그대로 남긴다.

영역 bbox는 검수 화면에서 원본 위 하이라이트 상자로 사용할 수 있다. 다만 미배정 줄을 흡수하면서 영역 bbox가 넓어지거나 PaddleX가 중첩 영역을 낸 경우에는 실제 사용자가 보는 의미 범위보다 크게 표시될 수 있어 검수 대상이다.

### 4-6. 범용 역할과 VLM 보조 판독

각 영역에는 템플릿 라벨과 별개로 다음 범용 역할이 붙는다.

```text
제목 · 본문 · 유의사항 · 각주 · 버튼 · 고지문구 · 표 · 이미지 · 기타
```

PaddleX 레이아웃 종류를 초기값으로 사용하고, VLM이 텍스트와 전체 페이지를 보고 최종 역할을 판정한다. VLM 실패 시 초기 규칙 값을 유지하고 실패 사실을 `notes`에 남긴다.

현재 미커밋 고도화에서는 VLM에 다음 보조 정보도 함께 준다.

- PaddleX `layout_label`, `layout_score`
- 화면 내 `x/y` 위치와 영역의 폭·높이 비율
- 검출된 표 행×열 수
- 디지털 텍스트에서 얻은 평균 글자 크기

이 값들은 참고 신호일 뿐 정답으로 강제하지 않는다.

OCR이 틀리거나 놓친 문구는 VLM이 같은 화면을 다시 읽어 후보를 만든다. 후보는 다음처럼 별도 필드에 남는다.

- 영역 후보: `region.vlm_reading`
- 줄 후보: `line.vlm_reading`
- OCR이 놓친 별도 문구: `source="vlm_sweep"`

VLM 후보는 실행마다 일부 달라질 수 있으므로 `digital`·`ocr` 정본을 자동으로 덮어쓰지 않는다. 후속 엔진 또는 검수자가 원본 이미지와 비교해 채택 여부를 정해야 한다.

### 4-7. 읽기순서와 문서 분류

PaddleX가 준 영역 순서를 기본으로 유지하면서, 명백히 앞뒤가 뒤집힌 인접 영역만 최소한으로 교정한다. 전체를 단순 `y→x` 정렬하지 않는 이유는 2단 문서가 좌우를 번갈아 읽는 형태로 망가질 수 있기 때문이다.

PDF·이미지 입력은 문서 첫 페이지 이미지와 파일명 힌트를 함께 사용해 다음을 분류한다. 캔버스가 없는 HWP/HWPX 본문은 파일명 힌트를 사용하며 그 사실을 분류 출처에 남긴다.

- `product_group`: 예금성·대출성·카드·기타
- `ad_type`: 상세페이지·안내장·배너·이벤트페이지·기타
- `product_name_shown`: 상품명 노출·미노출·판단불가

파일명은 일반적인 상품군 키워드 힌트로만 사용하고, VLM 판단과 다르면 그 경로를 `classification.source`에 기록한다.

## 5. 농협 원본 광고 템플릿을 반영하는 방법

### 5-1. 원본 검증 결과

원본은 농협이 제공한 다음 파일이다.

```text
광고 템플릿(근거규정x, 필수 여부).hwpx
```

실행용 변환본은 다음 파일이다.

```text
nh-data/pilot-data-set/광고 템플릿(근거규정x, 필수 여부).md
```

원본 HWPX 내부 XML과 Markdown 변환본을 대조한 결과:

- HWPX와 Markdown 모두 템플릿 19종을 같은 순서로 포함한다.
- HWPX의 예금자보호 관련 로고 이미지 2개가 Markdown에서 이미지 자리로 보존된다.
- 현재 실행용 JSON 사전을 Markdown에서 다시 생성하면 저장된 `ad_templates.json`과 완전히 일치한다.

현재 범위는 다음과 같다.

| 구분 | 수 | 상태 |
|---|---:|---|
| HWPX 전체 템플릿 | 19종 | 농협 원본 |
| 예금성·대출성·카드 | 12종 | 현재 파싱 라벨링에 사용 |
| 투자성 | 7종 | 실데이터 샘플이 없어 현재 제외 |
| 고유 `구분` | 29종 | 라벨 후보 |
| 공용 정형 문구 | 49개 | 완전일치 탐색 대상 |
| 전체 예시문구 엔트리 | 198개 | O 144개, △ 54개 |

투자성 7종을 삭제한 것은 아니다. 생성 사전의 `scope.excluded`에 이름과 제외 사유를 남겨 두었다. 실제 투자성 광고 샘플과 검증 기준이 생기면 같은 생성 도구로 범위에 포함할 수 있다.

### 5-2. 템플릿 사전 생성

```text
농협 HWPX
   ↓ 내용 보존용 Markdown 변환
광고 템플릿(...).md
   ↓ tools/build_ad_templates.py
src/nh_parsing/templates/ad_templates.json
```

템플릿 표의 네 열을 다음과 같이 사용한다.

| 원본 열 | 현재 사용 방식 |
|---|---|
| `구분` | 광고 텍스트에 붙일 항목 라벨 |
| `예시문구` | 정형 문구 완전일치 또는 VLM 의미 판정의 예시 |
| `필수여부` | 템플릿 정적 메타데이터로 보존. 파싱 단계에서 위반 판정에는 사용하지 않음 |
| `기재요령` | 사전에는 보존하지만 광고 결과마다 반복 복사하지 않음. 후속 심의 규칙에서 조회할 정보 |

숫자 자리가 `0000`, `0.00%`, `0만원` 등으로 되어 있으면 변수형 예시로 보고, 실제 문장이 고정된 경우 정형 문구로 본다.

### 5-3. 어떤 템플릿을 적용할지 선택

1. 앞 단계의 `product_group`과 `product_name_shown`을 확인한다.
2. 예금성 노출 광고처럼 세부유형이 더 필요하면 파일명에서 `입출식·거치식·적립식·지수연동` 힌트를 찾는다.
3. 규칙만으로 못 정하는 예금 세부유형이나 카드 개인·법인 구분은 후보 목록 안에서만 VLM 결선 판정을 한다.
4. VLM도 확신하지 못하면 `template.status="판단불가"`로 두고 라벨 없이 모든 텍스트를 보존한다.

잘못된 템플릿을 억지로 선택하면 존재하지 않는 필수항목을 만들 수 있으므로, 판단불가를 정상 상태로 허용한다.

### 5-4. 라벨은 두 층으로 붙는다

```text
1층: 정형 문구 완전일치
     "NH농협은행"이 실제 텍스트에 있는가?
     → 결정론적 결과, lines[].labels

2층: VLM 의미 판정
     이 줄 범위는 대출한도인가, 대출기간인가, 해당없음인가?
     → 의미 기반 결과, lines[].vlm_gubun 및 region.gubun_breakdown
```

공백·글머리표·유니코드 표기 차이는 정규화한 뒤 비교하지만, 유사도 임계값으로 “비슷하면 일치”시키지는 않는다. 정형 문구는 완전히 포함될 때만 일치로 처리하고, 뜻이 같은 변형 문구는 VLM 층에 맡긴다.

한 영역 안에 항목이 여러 개 섞일 수 있으므로, 현재 VLM은 줄에 `[00]`, `[01]` 번호를 붙인 목록을 보고 줄 범위별로 라벨을 반환한다.

```json
{
  "gubun_breakdown": [
    {"gubun":"회사명", "line_from":0, "line_to":0, "confidence":0.98},
    {"gubun":"심의번호", "line_from":1, "line_to":2, "confidence":0.97}
  ]
}
```

`region.gubun`은 하위호환을 위한 대표 라벨 하나일 뿐이다. 정확한 다중 항목 관계는 `gubun_breakdown`과 각 줄의 `vlm_gubun`을 사용해야 한다.

템플릿에 해당하지 않는 광고 문구는 `해당없음`으로 판정되어 라벨만 비게 된다. 텍스트·좌표는 그대로 남는다. **라벨 없음은 파싱 실패나 문구 누락을 뜻하지 않는다.**

## 6. 최종 광고물 JSON 구조

아래 예시는 구조를 이해하기 위한 축약본이다.

```json
{
  "doc_id": "12. 대출성상품",
  "source_file": "12. 대출성상품.pdf",
  "file_type": "pdf",
  "classification": {
    "product_group": "대출성",
    "ad_type": "안내장",
    "product_name_shown": "노출",
    "source": "filename_and_vlm",
    "confidence": 0.98
  },
  "template": {
    "template_id": "대출성상품-상품명 노출",
    "status": "확정",
    "basis": ["product_group=대출성", "product_name_shown=노출"]
  },
  "pages": [
    {
      "page_no": 1,
      "canvas_w": 1654,
      "canvas_h": 2339,
      "parse_route": "hybrid",
      "parse_status": "ok",
      "regions": [
        {
          "region_id": "p1_r007",
          "bbox": [120, 420, 1490, 510],
          "layout_label": "text",
          "layout_score": 0.91,
          "role": "본문",
          "role_confidence": 0.94,
          "role_source": "vlm",
          "gubun": "대출대상",
          "gubun_breakdown": [
            {"gubun":"대출대상", "line_from":0, "line_to":0, "confidence":0.96}

          "lines": [
            {
              "line_ref": "p1/p1_r007/L00",
              "text": "● 공무원연금공단에서 확인된 재직기간이 3개월 이상인 공무원",
              "bbox": [130, 432, 1450, 472],
              "source": "digital",

      "unassigned_lines": []
    }

  "template_items": [],
  "completeness": {
    "lines_total": 72,
    "labeled": 14,
    "lines_covered": 61
  },
  "notes": []

```

### 주요 필드의 의미

| 필드 | 의미 | 후속 엔진 사용법 |
|---|---|---|
| `lines[].text` | 파싱이 보존한 텍스트 | 기본 텍스트 원장 |
| `lines[].source` | `digital`, `ocr`, `vlm_sweep` | 출처별 신뢰·재현성 구분 |
| `lines[].bbox` | 원본 캔버스상의 줄 위치 | 하이라이트·근거 위치 |
| `region.bbox` | 영역 전체 위치 | 문단/영역 하이라이트 |
| `layout_label/score` | PaddleX의 최초 구조 판단 | 진단·교차검증 신호 |
| `role` | 제목·본문·유의사항 등의 범용 역할 | UI 표시·후속 필터 |
| `gubun` | 영역 대표 템플릿 항목 | 간단 조회용 |
| `gubun_breakdown` | 영역 안 모든 항목과 줄 범위 | 정확한 다중 항목 관계 |
| `line.vlm_gubun` | 줄 단위 템플릿 항목 | RDB 라인 라벨 인덱스 |
| `phrase_hits/labels` | 템플릿 정형 문구 완전일치 | 결정론적 문구 존재 증거 |
| `vlm_reading` | VLM이 다시 읽은 후보 | 원본과 비교 후 선택 가능 |
| `table` | PaddleX 표 구조와 정본 줄 연결 | 표 관계 보조 정보 |
| `unassigned_lines` | 영역에는 못 붙었지만 보존된 텍스트 | 절대 삭제하지 말고 별도 표시 |
| `notes` | 부분 실패·무응답·후보 범람 등 진단 | 재처리·검수 우선순위 |

### `completeness`는 성능 점수가 아니다

`completeness`는 “문서가 정확히 파싱되었다”는 확률이나 필수문구 충족률이 아니다.

- `lines_total`: 통합 JSON에 실린 전체 줄 수
- `labeled`: 정형 문구 완전일치 라벨이 붙은 줄 수
- `lines_covered`: 정형 문구 또는 영역 템플릿 라벨이 닿은 줄 수

광고 헤드라인과 이벤트 문구는 원래 템플릿 라벨이 없을 수 있으므로 `lines_covered < lines_total`은 정상일 수 있다. 이 값은 텍스트 전달과 라벨 적용 현황을 세는 보조 통계로만 사용해야 한다.

### 표 구조를 읽는 규약

표 영역에는 PaddleX HTML과 셀 관계가 들어간다.

```json
{
  "table": {
    "n_rows": 3,
    "n_cols": 2,
    "html": "<table>...</table>",
    "cells": [
      {
        "row": 0,
        "col": 0,
        "text": "대출한도",
        "bbox": [100, 300, 300, 350],
        "line_refs": ["p1/p1_r008/L00"]
      }
    ],
    "lines_outside_cells": [],
    "quality": {
      "status": "trusted",
      "issues": []
    }
  }
}
```

후속 엔진은 다음 원칙을 지켜야 한다.

1. `cells[].text`나 `html`을 텍스트 정본으로 단독 사용하지 않는다.
2. 셀 값은 `cells[].line_refs`로 `lines[].text`를 찾아 함께 확인한다.
3. `quality.status != "trusted"`이면 행·열 관계를 확정값으로 사용하지 않는다.
4. `lines_outside_cells`가 있으면 표 영역 안의 일부 줄이 격자에 연결되지 않았다는 뜻이므로 별도 검토한다.

`table.quality`는 현재 미커밋 고도화 필드다. 기존 표를 수정하거나 삭제하지 않고 위험 신호만 덧붙인다.

## 7. VectorDB/RDB 엔진에 넘길 때의 권장 계약

### 7-1. VectorDB

VectorDB의 주 입력은 규정문서 `_hrc.jsonl`이다.

- 조문·제목·본문·표·이미지 설명을 검색 가능한 청크로 저장한다.
- 광고 심의 엔진은 광고 문구 또는 라벨을 검색 질의로 사용해 관련 규정을 찾는다.
- 검색 결과에는 규정 출처 문서와 조항을 함께 반환한다.

광고물 전체를 별도 VectorDB에 넣는 것은 현재 필수 설계가 아니다. 광고 이력 유사검색 같은 별도 요구가 생길 때만 2차 인덱스로 검토한다.

### 7-2. RDB

광고 결과는 다음 구조가 안전하다.

```text
정본: ad_document.unified JSONB
         ↓ JSONB에서 다시 만들 수 있는 파생 색인
      ad_page
      ad_region
      ad_line
      ad_line_label
      ad_table_cell
      ad_table_cell_line
```

통합 JSON 전체를 한 번 보존하고, 조회가 자주 필요한 문서·페이지·영역·줄·라벨·셀만 관계형 테이블로 펼친다. 파생 테이블이 잘못되면 JSONB에서 다시 만들 수 있어야 한다.

문서 행에는 최소한 다음을 함께 저장하는 것이 좋다.

- 원본 파일명과 원본 SHA-256
- 파이프라인 버전 또는 Git 커밋 해시
- 파싱 실행 시각
- 분류값과 적용 템플릿
- `parse_status`
- 통합 JSONB

같은 원본도 파이프라인 버전이 바뀌면 결과가 달라질 수 있으므로 `source_sha256 + pipeline_version`을 함께 관리해야 한다.

### 7-3. 후속 엔진이 정본으로 봐야 할 것

| 질문 | 우선 사용할 값 |
|---|---|
| 광고에 어떤 글자가 있었나 | `lines[].text`, 단 `source`를 함께 확인 |
| 그 문구가 어디에 있었나 | `line.bbox` + `canvas_w/h` |
| 문단 단위 위치는 어디인가 | `region.bbox` |
| 어떤 템플릿 항목인가 | `line.vlm_gubun` 또는 `gubun_breakdown` |
| 표의 어느 셀인가 | `cells[].line_refs` + `table.quality` |
| VLM이 다르게 읽었나 | `vlm_reading`과 원문을 나란히 비교 |
| 라벨 없는 문구는 버려도 되나 | 안 된다. 일반 광고 문구일 수 있음 |

`digital`과 `ocr`은 기본 정본층이다. `vlm_sweep`과 `vlm_reading`은 누락 회수·교정 후보층이므로 별도 출처로 표시해야 한다.

## 8. 최근 고도화 내용과 과적합 위험

현재 고도화 변경은 커밋하지 않은 상태이며, 전체 문서 재파싱 후 채택 여부를 정한다.

| 변경 | 특정 샘플 과적합 위험 | 판단 |
|---|---|---|
| PDF 일반 공백 보존 | 낮음 | PDFium이 실제 제공한 공백을 버리지 않는 원문 보존 수정. 임계값 없음 |
| VLM에 PaddleX label·score·좌표비·표·글자크기 전달 | 낮음 | 이미 보유한 정보를 참고로 전달할 뿐 텍스트를 수정하지 않음 |
| 최종 JSON에 layout/role 진단값 노출 | 낮음 | 기존 값을 누락 없이 전달하는 가산적 변경 |
| 표 `quality` 경고 | 중간 | `0.65`, `50%`, `80%` 기준은 현재 관측에서 출발한 휴리스틱. 단 표를 수정하지 않고 경고만 추가 |
| 영역 안 줄 범위별 `gubun` | 중간 | 파일별 규칙은 없지만 VLM 입력 상한 40줄·600자는 전수 검증 필요 |

생산 코드에는 `12. 대출성상품이면 이렇게 처리` 같은 파일별 예외 분기가 없다. 특정 샘플명은 대부분 결함의 근거를 남긴 주석이나 회귀 테스트에만 등장한다.

다만 파이프라인 전체에는 OCR·좌표 처리상 필요한 임계값이 존재한다.

- OCR 저신뢰 기준
- 타일 크기와 오버랩
- bbox 겹침 비율
- PDF 텍스트 신뢰 진단
- 카드/스크롤 종횡비
- 표 품질 경고 기준

이 값들은 “임계값이 있으므로 곧 과적합”인 것은 아니지만, 같은 샘플에서 기준을 만들고 같은 샘플만으로 성공을 선언하면 과적합이 된다. 따라서 전체 89건과 기존 샘플을 모두 새 결과 폴더에 재실행하고, 문서 유형별 분포와 오탐을 함께 확인해야 한다.

특히 표 품질 기준은 다음 조건을 충족하기 전에는 확정값으로 커밋하지 않는 편이 안전하다.

1. 알려진 오류 표에서 모두 경고가 발생한다.
2. 원본 대조로 정상 확인한 표에서는 `invalid` 오탐이 발생하지 않는다.
3. 특정 상품군·파일명·해상도에 경고가 편중되지 않는다.
4. 임계값을 조금 바꿔도 결과가 급격히 뒤집히지 않는다.

## 9. 큰 JSON을 사람이 검수하는 방법

JSON 전체를 직접 읽는 방식은 권장하지 않는다. 검수는 `요약 → 원본 대조 화면 → 이상 영역 상세`의 세 단계로 진행한다.

### 9-1. 1단계: 문서 요약으로 실패 문서 먼저 찾기

광고 API 결과의 `ad_summary.json` 또는 통합 JSON 상단에서 다음을 본다.

- `classification`과 실제 상품군이 맞는가
- `template.status`가 확정인지 판단불가인지
- `template.template_id`가 실제 광고 유형과 맞는가
- 페이지별 `parse_status`가 `ok`인지
- `notes`에 OCR 타일 실패, VLM 무응답, 후보 범람이 있는가
- 전체 줄 수가 비슷한 형식의 문서보다 비정상적으로 적거나 많은가

### 9-2. 2단계: 원본과 영역을 나란히 비교

현재 도구는 [tools/make_parse_explorer.py](../tools/make_parse_explorer.py)다.

```powershell
uv run python tools/make_parse_explorer.py
```

생성되는 `out_ad_full/explorer.html`에서는 다음을 볼 수 있다.

- 왼쪽: 원본 페이지 이미지와 영역 bbox
- 오른쪽: 실제 JSON 순서의 영역 목록
- 영역 토글: 정본 줄, 출처, OCR 신뢰도, 글자 크기, bbox
- 정본과 VLM 통독 후보 비교
- 표 HTML과 셀 밖 줄
- 정형 문구 완전일치 결과

영역 토글을 열면 왼쪽 원본에서 같은 bbox가 강조되므로 JSON을 직접 찾는 것보다 빠르다.

최신 고도화 검수 때는 화면에 다음 항목도 표시하도록 열람 도구를 갱신하는 것이 좋다.

- `layout_label`, `layout_score`
- `role_confidence`, `role_source`
- `gubun_breakdown`, 줄별 `vlm_gubun`
- `table.quality.status`, `issues`

### 9-3. 3단계: 무엇을 합격으로 볼지

문서별로 아래 여섯 축을 따로 판정한다. 하나의 “파싱 성공/실패” 숫자로 합치지 않는다.

| 검수 축 | 확인 질문 |
|---|---|
| 텍스트 보존 | 원본의 주요 문구와 유의사항이 결과 어딘가에 모두 있는가 |
| 텍스트 정확도 | 숫자·금리·기간·심의번호·특수기호가 맞는가 |
| 좌표 | 토글한 bbox가 실제 문구 위치를 가리키는가 |
| 읽기순서 | 영역 배열을 순서대로 읽었을 때 문맥이 자연스러운가 |
| 템플릿 라벨 | 항목명과 내용이 맞게 연결됐으며 일반 광고 문구는 억지 라벨이 없는가 |
| 표 관계 | 행·열·셀 연결이 맞고 품질 경고가 실제 상태와 맞는가 |

각 축을 `통과 / 일부 오류 / 실패 / 해당없음`으로 기록하면 “텍스트는 잘 읽었지만 표 관계는 실패” 같은 상태를 정확히 남길 수 있다.

### 9-4. 89건 재검증 권장 절차

1. 기존 `out_ad_full`을 기준선으로 보존한다.
2. 새 결과는 별도 폴더에 생성해 이전 결과를 덮어쓰지 않는다.
3. 전체 문서를 재파싱한다.
4. `tools/measure_parse_defects.py`로 빈 영역·중복·순서 역행·깊은 gubun·표 문제를 전후 비교한다.
5. 새 결과용 `explorer.html`을 생성한다.
6. 다음 고위험 문서를 먼저 본다.
   - `scan_like` PDF
   - 세로가 길어 다중 타일로 처리된 이미지
   - 표가 있는 문서
   - 좌우 2단 또는 3단 카드형 문서
   - `notes`가 있는 문서
   - `vlm_reading_relation=diverged/tail_cut/overflow`가 많은 문서
   - `table.quality != trusted`인 문서
7. 고위험군 뒤에는 각 파일 유형과 상품군에서 정상 문서를 무작위로 뽑아 오탐을 확인한다.
8. 개선 지표와 회귀 결과를 함께 기록한 뒤 커밋한다.

기존 `gold`의 `must_contain`은 처음 받은 약 5개 샘플의 텍스트 회귀 검사용으로 계속 유용하다. 다만 89개 전체 문서를 사람이 모두 전사하기보다는, 고위험 문구·숫자·표·순서 관계를 중심으로 점진적으로 검증 항목을 늘리는 방식이 현실적이다.

## 10. 후속 엔진 담당자와 먼저 합의할 항목

1. 광고 통합 JSON 전체를 RDB JSONB 원장으로 저장할지
2. `page/region/line/label/table_cell` 파생 테이블을 어디까지 만들지
3. 원본 파일과 페이지 이미지의 보관 위치 및 보존 기간
4. bbox를 화면에 표시할 때 `canvas_w/h` 기준 비율로 환산하는 규칙
5. `digital/ocr/vlm_sweep/vlm_reading` 출처별 채택·검수 정책
6. `table.quality != trusted`일 때 표 관계를 사용하지 않는 정책
7. `template.status=판단불가`와 라벨 없는 텍스트를 정상 데이터로 다루는 정책
8. 파이프라인 버전 변경 시 재파싱 결과를 새 버전으로 보관하는 정책
9. 규정 검색 결과와 광고 `line_ref/bbox`를 최종 심의 결과에서 어떻게 연결할지

## 11. 팀원에게 1분 안에 설명하는 문장

> 규정문서는 농협 KL VectorDB에 넣을 검색 지식으로 변환하고, 광고물은 별도의 `/ad/parsing` API에서 텍스트·좌표·영역·표 관계를 보존한 통합 JSON으로 반환합니다. 광고 라벨은 우리가 임의로 만든 상품별 스키마가 아니라 농협이 제공한 광고 템플릿의 `구분`을 사용합니다. 정형 문구는 코드로 완전일치시키고, 표현이 달라지는 항목은 VLM이 줄 범위별로 라벨링합니다. 템플릿에 없는 광고 문구도 삭제하지 않고 라벨 없이 그대로 남깁니다. 후속 RDB는 이 JSON을 원장으로 저장하고, VectorDB에서 검색한 규정 근거와 광고의 `line_ref/bbox`를 연결해 심의 결과를 만들면 됩니다. OCR·VLM 후보와 표 격자는 오류 가능성이 있으므로 출처와 품질 상태를 함께 보고 사용해야 합니다.
