# 파싱 결과 인계 — 스키마 구성과 산출물

> **이 문서 하나만 읽으면 됩니다.** 파싱 단계가 무엇을 만들어 내는지, 스키마를 왜
> 이렇게 짰는지, 다음 단계(RAG 인덱싱·DB 적재)로 넘길 때 무엇을 정해야 하는지.
>
> 기준일 2026-07-29 · 측정값은 전부 골드셋 5문서 실측
> 파이프라인 내부 동작은 [architecture/pipeline-map.md](architecture/pipeline-map.md) 참조

## 0. 회의에서 정할 것 (이게 본론)

아래 5개가 **우리 둘이 합의해야 넘어갈 수 있는 것**들입니다. 각 항목에 제 제안을
같이 적었습니다 — 반박용 초안으로 쓰시면 됩니다.

| # | 정할 것 | 제 제안 | 왜 지금 정해야 하나 |
|---|---|---|---|
| **1** | 세 산출물 중 **뭘 넘길지** | 셋 다. RAG=`llm_view`, DB=`extracted`, 화면=`json` | 뭘 받을지 모르면 인덱싱 설계를 못 시작 |
| **2** | 산출물끼리 **연결 키** | `region_id` + **문서 처리 버전**을 묶어서 | `region_id` 단독은 재처리하면 깨짐 (§5-①) |
| **3** | **값이 없을 때** DB에 어떻게 | `status` + `absence.kind` **두 컬럼** | `null` 하나로 뭉치면 "위반"과 "해당없음"이 같아짐 (§4) |
| **4** | **재처리 정책** | 버전 누적 (덮어쓰기 금지) | 출력이 결정론적이지 않음 — 멱등 전제가 깨짐 (§5-②) |
| **5** | **심의 판정 단계**를 어디서 | 미정 — 논의 필요 | 이게 정해져야 우리 산출물의 끝이 확정됨 (§6) |

**1번부터 순서대로** 보시는 걸 권합니다. 1·2번이 정해져야 3·4번이 의미가 생기고,
5번은 범위 문제라 마지막이 자연스럽습니다.

## 1. 지금 무엇이 되고, 무엇이 안 되나

**되는 것** — 광고 파일(PDF/PNG/HWP)을 넣으면 화면의 글자를 좌표와 함께 뽑고,
심의 스키마에 맞춰 구조화된 값으로 만듭니다. 값이 없으면 **왜 없는지**까지 분류합니다.

**안 되는 것** — "그래서 이 광고가 규정 위반인가"는 **판정하지 않습니다.** 위험도 산정,
수정안 제시, 리포트 생성이 아직 없습니다.

| 지표 | 값 | 재는 도구 |
|---|---|---|
| 분류 (상품군·광고유형) | 9/9 (100%) | `evaluate.py` |
| 섹션 검출 | 37/44 (84%) | `evaluate.py` |
| 문장 회수 | 237/242 (98%) | `evaluate.py` |
| **필드 회수** | **44/44 (100%)** | `verify_extract.py` |

처리 시간은 **문서당 3~7분**이고, 그 시간의 **96~98%가 AI 모델 응답 대기**입니다
(무캐시 5문서 실측: 파싱 10.5~16분 + 추출 5분).

## 2. 스키마를 어떻게 짰나

### 축 1 — 상품군이 스키마 파일을 가른다

**"이벤트성"은 별도 상품군이 아닙니다.** 처음엔 그렇게 보이는데, 실제 샘플
(002 "행운의777", 003 "올원모임")은 둘 다 `product_group=예금성` +
`ad_type=이벤트페이지`입니다. 이벤트는 예금성 **위에 얹히는 광고 유형**이지 새
상품군이 아닙니다. 이 판정이 구조 전체를 결정했습니다:

```
schemas/예금성.json           상품군 스키마      46필드 / 4그룹
schemas/_overlay_이벤트.json  광고유형 오버레이  11필드 / 1그룹
                              └ ad_type=이벤트페이지일 때만 합류
```

**PoC 범위는 예금성 하나뿐입니다.** 대출·카드·투자성은 확장 대상입니다. 004(대출성
HWP)가 파싱은 되는데 추출을 건너뛰는 이유가 이것 — 스키마 파일이 아직 없습니다.

### 축 2 — 호출그룹이 "한 번에 몇 개를 묻는지"를 가른다

46필드를 한 번에 다 물으면 응답이 길어지고, 실제로 **배열이 스키마 앞에 있으면 응답이
중간에 끊기는 현상**이 재현됐습니다(vLLM guided decoding 특성). 그래서 쪼갰습니다:

| 그룹 | 내용 | 필드 |
|---|---|---|
| G1_상품기본 | 상품명·가입대상·가입기간·적립방식 | 8 |
| G2_금리 | 기본/우대금리·중도해지이율·이자계산방식 | 14 |
| G3_의무고지 | 심의필번호·예금자보호·설명받을권리 등 법정 문구 | 15 |
| G4_위험표현 | 단정적 표현·최상급·조건일반화 등 **관측**(판정 아님) | 9 |
| G5_이벤트 (오버레이) | 이벤트명·기간·경품·참여방법 | 11 |

모든 그룹에 `analysis`(분석 서술)를 **첫 필드로** 강제합니다 — 문자열이 앞에 오면
위의 끊김 현상이 안 납니다.

### 필드는 어디서 왔나 — 근거 우선순위

"이런 게 있으면 좋겠다"로 만들지 않았습니다. 순서대로 깔았습니다:

1. **NH 광고심의 체크리스트 v12** (씨지인사이드 규제정책연구소) — 1차 근거.
   6개 시트가 이미 `체크질문 · 근거법령 · 근거조문 · 필수/권장` 구조라 거의 완성형
2. **은행연합회·금융위 규정 원문 9종** — 체크리스트가 안 다루는 세부 보강
3. **실제 광고 샘플 실측** — 근거 문서에 없는데 광고에 반복되는 것은 **필드가 아니라
   파싱 결함**으로 분류해 코드 쪽에서 처리

지킨 원칙: **"샘플에만 있는 표현을 일반 규칙으로 승격하지 않는다."** 근거가 약하거나
문서끼리 충돌하면 억지로 필드를 만들지 않고 `확인 필요`로 분리했습니다.

### 규정이 바뀌면 코드는 안 바꾼다

```
out/schema_source/_product_group_fields.json   근거 대장 (조문·출처·필수여부 원본)
schemas/예금성.json                             런타임 스키마 (LLM 이 읽을 지시문만)
```

규정 개정 시 대장을 먼저 고치고 `schemas/*.json`을 갱신합니다. **파이프라인 코드는
건드리지 않습니다.**

## 3. 무엇이 나오나 — 산출물 3층

한 문서를 처리하면 세 개가 나옵니다. **합치지 않은 이유가 있습니다.**

| 산출물 | 내용 | 문서당 | 용도 |
|---|---|---|---|
| `out/json` | 전체 IR — 영역·라인·bbox·신뢰도·출처·VLM후보 | 60~85 KB | 감사, 화면 하이라이트 |
| `out/llm_view` | 정제본 — 섹션→영역→텍스트 (좌표 제거) | 17~27 KB | **RAG 인덱싱** |
| `out/extracted` | 구조화 필드 — 스키마 기반 값 + 근거 | 18~32 KB | **DB 적재** |

**왜 셋인가.** 목적이 서로 충돌하기 때문입니다. 감사에는 *틀린 판독도 남아 있어야*
합니다("OCR은 `10.1%p`, VLM은 `① 0.1%p`로 읽었다"를 둘 다 보관해야 추적됨). 반대로
LLM 입력에 그 둘을 다 넣으면 판단이 흐려집니다. DB에 넣을 것은 라인이 아니라 **필드**
단위여야 하고요.

### 최종 output(`out/extracted`) 실제 모양

```jsonc
{
  "doc_id": "…", "product_group": "예금성", "ad_type": "이벤트페이지",
  "schema_id": "예금성", "schema_version": "v1",
  "overlays_applied": ["_overlay_이벤트"],

  "fields": {
    "product_name": {
      "value": "NH올원e적금",
      "evidence": ["p1_r001", "p1_r004"],   // 근거 영역 ID
      "status": "found",
      "evidence_score": 1.0,
      "evidence_backed": true                // 값이 원문에 실재하는가
    }
  },
  "events":       [ /* 이벤트별 배열 (오버레이) */ ],
  "observations": { /* 과장 표현 의심 9종 — 판정 아님 */ },
  "unmapped":     [ /* 스키마에 못 담은 심의 관련 문구 */ ],
  "coverage":     { /* 자기 진단 17지표 */ }
}
```

- **`evidence_backed`** — LLM이 그럴듯한 값을 지어낼 수 있어서, 값의 토큰이 실제 파싱
  텍스트에 있는지 코드로 검산해 표시합니다. 심의가 환각 위에 서면 안 됩니다.
- **`unmapped`** — 46필드 어디에도 안 맞는 심의 관련 문구를 버리면 조용히 사라집니다.
  금융광고 심의에서 가장 위험한 실패라, 못 담은 것도 근거 지목이 되게 남깁니다.

## 4. 값이 없을 때 — 여기가 설계의 핵심 (회의 안건 3번)

`null` 하나로 두지 않고 **왜 없는지를 코드로 4분류**합니다.

```jsonc
"interest_calc_method": {
  "value": "", "status": "not_found",
  "absence": { "kind": "해당없음", "obligation": "필수", "rule": "conditional" }
}
```

| kind | 뜻 | 심의 지적인가 |
|---|---|---|
| **미표시** | 표시 의무가 있는데 광고에 없음 | **예 — 이것만 진짜 지적** |
| 해당없음 | 이 상품 유형엔 그 개념이 없음 (수시입출식의 '만기 후 이율') | 아니오 |
| 확인필요 | 상품 유형을 못 정해 판단 보류 | 아니오 (사람이 봐야 함) |
| 판정제외 | 분류용 필드 등 애초에 심의 대상 아님 | 아니오 |

판정 규칙은 필드 메타데이터에 조건으로 박혀 있고, 4가지 규칙 타입으로 씁니다:

```jsonc
{"rule": "subtype_not_in", "values": ["입출금(통장·MMDA)"],
 "why": "만기 개념이 없는 수시입출식에는 성립하지 않음"}
{"rule": "trigger_any", "fields": ["max_rate"],
 "why": "최고금리를 표시한 경우에만 기본금리 병기 의무가 생김"}
{"rule": "conditional", "why": "세제혜택을 표기한 광고에만 상세 표시 의무"}
{"rule": "subtype_in", "values": ["ELD/주가·환율연동"]}
```

**왜 이렇게까지 나눴나.** 나누기 전엔 값 없는 필드가 전부 `not_found`였고, 실측해보니
그중 대부분이 "이 상품엔 원래 없는 개념"이었습니다. 그대로 심의 화면에 띄우면
**담당자가 가짜 지적 수십 건을 매번 걸러내야 합니다.** 이 판정은 **모델 호출 없이
순수 코드**로 합니다 — 규칙이 이미 메타데이터에 있으니 다시 물어볼 이유가 없습니다.

### `observations`(G4)는 왜 판정을 안 하나

과장·오인 표현 9종을 **후보로만 수집**합니다. 스키마 지시문에 이렇게 적혀 있습니다:

> *"값을 뽑는 그룹이 아니다. … 최종 위반 판정은 이후 심의 단계가 하므로, 여기서는
> 단정하지 말고 해당될 수 있는 문구를 근거와 함께 모은다."*

여기서 위반을 단정하면 ① 규정 해석이 파싱 코드에 박혀 규정이 바뀔 때마다 코드를
고쳐야 하고 ② 판정 근거가 "LLM이 그렇게 말했다" 하나로 줄어듭니다.

## 5. 받는 쪽이 반드시 알아야 할 제약

### ① `region_id`를 영구 키로 쓰면 안 됩니다 ⚠️ (회의 안건 2번)

`region_id`(`p1_r014` 등)는 **생성 순서 라벨**이지 콘텐츠 식별자가 아닙니다.
같은 문서를 두 번 처리한 실측:

```
영역 76개 / 76개
  같은 id · 같은 내용    72개
  같은 id · 다른 내용     4개   ← p1_r018, r019, r022, r026
```

재처리하면 같은 ID가 다른 내용을 가리킬 수 있습니다. **문서 처리 버전과 묶어 저장하고,
버전이 다르면 별개로 취급**해야 합니다.

### ② 재처리하면 결과가 달라집니다 (회의 안건 4번)

VLM 출력이 결정론적이지 않습니다. `temperature=0`으로도 안 잡힙니다(서버측
guided-decoding·배치 비결정성). 실측: 같은 5문서에서 문장 회수가 **235~237 사이로
흔들립니다.** "다시 돌리면 같은 결과"를 전제한 설계(멱등 upsert 등)는 깨집니다.

> 이 제약이 파싱 설계도 규정했습니다 — **OCR을 정본으로 두고 VLM 판독은 후보로만**
> 붙입니다. VLM이 텍스트를 덮어쓰면 실행마다 정본이 흔들려 금융 광고에 쓸 수 없습니다.

### ③ 지금은 예금성만 됩니다

`schemas/`에 예금성 하나뿐입니다. 대출성(004)은 파싱은 되지만 **추출은 건너뜁니다.**

### ④ HWP는 좌표가 없습니다

디지털 텍스트라 정확하지만 `bbox`가 없어 **화면 하이라이트를 못 합니다.**

## 6. 아직 없는 것 / 알려진 결함

### 심의 판정 단계가 없습니다 (회의 안건 5번)

`미표시` 분류와 `observations` 수집까지가 끝입니다. **그 단계를 어디서 돌릴지**에 따라
이 산출물의 경계가 달라집니다.

### 측정된 결함 (추측 아님)

| 결함 | 실측 | 상태 |
|---|---|---|
| **겹친 영역** — 줄바꿈된 문단의 뒷줄이 별도 영역이 되어 두 조각이 다른 섹션으로 갈림 | 4페이지 **37쌍, 그중 32쌍이 섹션 갈라짐**. 조건 문장이 반토막 (`② 0.2%p : … 전체`에서 `동의 시` 분리) | **미해결** — 4문서로 합침 규칙을 만들면 과적합이라 정량화 먼저 |
| **스윕 환각** — 스윕이 기존 줄을 다시 읽어 원본에 없는 문구 생성 | 003 p2에서 원본 3줄 → 6줄 | **절반 해결** — 구조적 원인은 수정, 유사도 임계값은 분리 불가로 보류 |
| **회전 텍스트** | 002 `최고 연 7.1%` → OCR이 `최고연`까지만 | VLM이 후보로 회수. 구조화 필드엔 못 들어감 |
| **장식예시 오분류** | 001 좌측 목업 12영역 + 우측 실제 목록 5영역이 한 섹션 | 격리는 태깅뿐이라 손실 없음. 분류는 부정확 |
| **실행 간 변동** | 문장 235~237, 섹션 37~38 | 구조적 (§5-②) |
