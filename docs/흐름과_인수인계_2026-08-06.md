# 이 저장소는 지금 어떤 상태이고, 어떻게 흐르나

> **PR·인수인계 설명용 문서.** "무엇이 들어가서 무엇이 나오는가", "어디에 붙일 수 있는가"에
> 답한다. 코드를 안 보고도 설명할 수 있게 썼다.
>
> 구조 정리 완료 시점: 2026-08-06 (커밋 `3a6ff7e`)

---

## 1. 한 문장 요약

**광고물 파일 하나를 넣으면, 화면의 글자를 좌표와 함께 뽑고(파싱), 그 글자를 심의 항목별
필드로 채워(추출) JSON 세 개를 내놓는다.** 위반 여부 판정은 하지 않는다 — 사실 관측까지다.

```
광고물 파일                        나오는 것 3개
(PDF · PNG · HWP)   ──►  ① out/json      좌표·신뢰도 포함 전체 (감사·화면용)
                         ② out/llm_view  좌표 뺀 텍스트 (LLM·RAG 입력용)
                         ③ out/extracted 심의 항목별 필드 (DB 적재용)
```

## 3. 흐름 — 파일 하나가 어떻게 변하나

### 3-1. 큰 그림 (2개 프로세스)

```
[프로세스 1: 파싱]   tools/run_nhdata.py       ← 모델 호출 필요
    광고물 파일  →  out/json  +  out/llm_view  +  out/previews  +  out/_timing.json

[프로세스 2: 추출]   tools/run_extract.py      ← 모델 호출 필요
    out/llm_view  →  out/extracted
```

**둘이 분리된 이유**: 파싱은 비싸다(문서당 100~300초, 그중 97%가 모델 대기). 스키마만
바꿔서 추출을 다시 하고 싶을 때 파싱을 재실행하지 않으려고 갈라 두었다.

### 3-2. 파싱 내부 — 자료구조가 다섯 번 바뀐다

단계 15개를 외우는 게 아니라 **자료구조 변환 5번**으로 잡으면 된다.

```
① 파일             [예금성상품-적금] 올원e적금.png
      ↓ 캔버스로 정규화 (PDF 는 렌더, HWP 는 이 단계가 없다)
② 캔버스           1122 × 6429 픽셀   ← 이후 모든 좌표의 기준
      ↓ 글자 밀도로 조각내기 (세로로 길면 통째로 못 읽는다)
③ 조각             9개
      ↓ 조각마다 OCR 서버 1회 호출
④ 라인 + 블록      Line('상품명', bbox=[66,863,200,922], conf=0.99)
                  Line('NH올원e적금', bbox=[410,865,680,920], conf=0.99)
                  LayoutBlock(label='text', bbox=[68,865,677,912])
      ↓ 라인 중심점이 블록 안에 들어가면 그 블록에 넣는다
⑤ 영역             Region(region_id='p1_r004', role='본문',
                         lines=[Line('상품명'), Line('NH올원e적금')])
      ↓ 같은 조각을 VLM 에게도 보여주고 "다시 읽어봐" 
⑥ 후보 부착        Region.vlm_reading = 'NH올원e적금'    ← 원본(lines)은 그대로!
                  Region.vlm_reading_relation = 'head_drop'  ← 둘의 관계 딱지
      ↓ 좌표·신뢰도 버리고 읽는 순서로 평면 나열
⑦ 정제 텍스트      {"region_id":"p1_r004", "role":"본문",
                   "text":"상품명 NH올원e적금", "vlm_reading":"NH올원e적금", ...}
      ↓ 스키마 필드에 값 채우기 (별도 프로세스)
⑧ 필드             "product_name": {"value":"NH올원e적금", "status":"found",
                                    "evidence":["p1_r004"]}
```

**꼭 잡아야 할 4가지**

1. **②가 좌표의 원점이다.** HWP 는 캔버스가 없어 좌표가 없고, 그래서 미리보기·하이라이트를
   못 만든다. 대신 **0.7초**에 끝난다(다른 문서는 100~300초).
2. **⑤에서 `region_id` 가 태어나 ⑧까지 살아간다.** 필드가 `evidence:["p1_r004"]` 로 근거를
   대고, 검수 화면이 그 ID 로 좌표를 되붙여 하이라이트를 그린다.
3. **⑥이 이 파이프라인의 핵심 설계다.** VLM 이 다시 읽은 결과가 원본을 **덮지 않고 옆칸에
   붙는다.** 한 영역에 판독이 둘 공존하고, 코드가 그 관계를 딱지로 판정한다. 최종 값 선택은
   ⑧이 한다. → 실제로 VLM 이 틀린 사례가 여럿 있었다(003 '추첨 15명'을 '10명'으로 씀).
4. **⑦에서 좌표를 일부러 버린다.** LLM 에게 좌표는 노이즈이고, `region_id` 만 있으면 나중에
   되붙일 수 있다.

### 3-3. 입력 형식별로 갈리는 길 3개

| 입력 | 어떻게 다른가 | 실제 사례 |
|---|---|---|
| **PNG/JPG** | ②부터 시작. 전부 OCR | 올원e · 002 |
| **PDF** | 페이지마다 **먼저 판정**한다 — PDF 안에 쓸 만한 글자 데이터가 있나? | 001 · 003 |
| └ `structured` | 있다 → **OCR 을 건너뛴다**(빠르고 정확) | 003 3페이지 |
| └ `scan_like` | 없다(스캔 이미지) → OCR | 001 · 003 1·2페이지 |
| └ `hybrid` | 글자는 있는데 이미지 비중 큼 → 둘 다 | 5문서에서 **한 번도 안 탔음** |
| **HWP** | ②③④를 다 건너뛴다. 사내 파서가 문단·표를 바로 준다 | 004 |

## 4. 나오는 것 3개 — 무엇을 담고 누가 쓰나

### ① `out/json` — 아무것도 안 버린 전체

```
페이지 키: canvas_w, canvas_h, dpi, parse_route, parse_status, triage,
          regions, unassigned_lines, notes
영역 키  : region_id, bbox, label, layout_score, role, role_confidence,
          role_source, role_rule, role_rule_confidence, card_no,
          lines, vlm_reading, vlm_reading_score, vlm_reading_coverage,
          vlm_reading_relation
```

**쓰는 곳**: 감사 추적 · 미리보기 그림 · 검수 화면 왼쪽 · 골드셋 채점.
**`notes` 를 꼭 보라** — 각 단계가 무엇을 했고 무엇이 실패했는지가 여기 남는다.

### ② `out/llm_view` — 좌표 뺀 텍스트

```
최상위: doc_id, document, product_group, ad_type, pages
페이지: page_number, regions
영역  : region_id, role, text, vlm_reading, vlm_reading_relation,
        vlm_reading_score, vlm_reading_coverage
```

**쓰는 곳**: STAGE_3 입력 · RAG 인덱싱 후보.
**모델 호출 0회로 다시 만들 수 있다** — `tools/rebuild_views.py`.

### ③ `out/extracted` — 심의 항목별 필드

```
fields                 항목별 {value, status, evidence, note}
observations           관측 항목 (판정이 아닌 것)
events                 이벤트별 필드 (오버레이)
unmapped               어느 필드에도 안 맞은 문구 — 버리지 않고 남긴다
coverage               found / not_found / 부재 4분류 집계
review_gaps            "미표시" 목록 (표시 의무인데 못 찾은 것)
── 코드 검산 결과 5종 ──
status_corrections     값은 썼는데 "못 찾음"이라 적은 자기모순 보정
evidence_unbacked      근거로 댄 영역에 그 값이 실제로 없는 것
unused_figures         화면엔 있는데 어느 필드에도 안 실린 수치
input_gap              파싱은 됐는데 STAGE_3 입력에서 빠진 영역
events_pruned          내용 없는 유령 이벤트 제거
```

**쓰는 곳**: DB 적재.
**`unmapped` 와 검산 5종이 이 저장소의 차별점이다** — "없는 것"과 "못 찾은 것"과 "해당
없는 것"을 갈라 놓았고, 코드가 모델 답을 검산한 결과를 함께 싣는다.

## 5. 설계 원칙 — PR 리뷰에서 물어볼 것들

### ① 판단은 VLM 이, 검산은 코드가

| 단계 | VLM 이 판정 | 코드가 검산 |
|---|---|---|
| 카드 배정 | 개수·배정 | 픽셀 밀도로 개수 대조 → 불일치 시 `notes` |
| 낱줄 귀속 | (안 씀) | 중심점 포함 + 칼럼 겹침 게이트 |
| 밴드 통독 | 재판독 텍스트 | 관계 딱지로 원본과 교차검증 |
| **역할 판정** | role 9종 | **없음** ← 알려진 공백. 2026-08-06 에 측정 재료를 만들었다 |
| STAGE_3 | 필드 값 | 검산 5종 (위 §4-③) |

### ② 원본을 덮지 않는다

VLM 이 다시 읽은 결과는 **후보**로만 붙는다. 이유는 실측이다 — VLM 이 표기는 더 예쁘게
내면서 **숫자를 바꿔 쓴 사례**가 여럿이었다(003 '추첨 15명'→'10명', 002 '온대!'→'온다!').
원본을 덮었다면 광고에 없는 숫자가 심의 대상 값이 됐을 것이다.

### ③ 조용한 실패 금지

모든 실패는 `notes` 나 종료코드로 올라온다. **2026-08-06 에 이 원칙이 깨진 자리 네 곳을
찾아 고쳤다** — 그중 하나는 VLM 호출 56회가 전부 죽었는데 러너가 `exit 0` 을 찍던 것이다.
지금은 **산출물을 검사해서**(글자가 붙은 페이지에 판독 후보가 0건이면) `exit 1` 로 잡는다.

### ④ 숫자는 손으로 세지 않는다

`tools/verify_numbers.py` 가 `out/` 에서 모든 숫자를 다시 뽑는다(모델 호출 0회). 문서에
적힌 값과 실제 산출물이 어긋난 사고가 반복돼 만든 장치다.

## 7. 다른 저장소에 붙일 때 — 물어볼 것 6개

`nh-ad-compliance`(화면·API·DB·배포까지 있는 저장소)와의 관계는
[compare-nh-ad-compliance.md](compare-nh-ad-compliance.md) 에 실제 코드 대조로 정리돼 있다.
요지는 **기능이 겹치는 게 아니라 그쪽의 빈 자리에 이쪽이 들어간다**는 것이다(그쪽 파서는
현재 "OCR 1회 + 레이아웃 빈 배열" 수준).

붙이기 전에 정할 것 — 자세한 논의는 [handoff.md](handoff.md) §0:

| # | 정할 것 | 왜 지금 |
|---|---|---|
| 1 | 세 산출물 중 **뭘 넘길지** | 뭘 받을지 모르면 인덱싱·적재 설계를 못 시작 |
| 2 | 산출물끼리 **연결 키** | `region_id` 단독은 재처리하면 깨진다 → 처리 버전과 묶어야 |
| 3 | **값이 없을 때** DB 표현 | `null` 하나로 뭉치면 "표시 의무 미발견"과 "해당없음"이 같아진다 |
| 4 | **재처리 정책** | 역할·추출값이 결정론적이지 않다 → 멱등 전제가 깨진다 |
| 5 | **심의 판정을 어디서** | 이게 정해져야 이 저장소의 끝이 확정된다 |
| 6 | 입출금 유형의 **표시 의무 항목** | 지금 5개를 "해당없음"으로 처리 중인데 **조문 근거 없는 우리 해석** |

**⚠️ 3번과 4번이 기술적으로 가장 위험하다.** 3번은 심의 품질에 직결되고(진짜 누락이
묻힌다), 4번은 §6 의 "실행마다 42~43/44" 와 직접 연결된다 — 덮어쓰기를 전제하면 재처리할
때마다 결과가 바뀌어 추적이 안 된다.

## 8. 다시 돌려보는 법

```bash
uv sync                                  # 의존성 (사내 파서 포함, Java 필요)

# ── 모델 호출 필요 (PaddleX + Gemma · WireGuard VPN) ──
uv run python tools/run_nhdata.py        # 파싱 (~8분/5문서)
uv run python tools/run_extract.py       # STAGE_3 (~6분/4문서)

# ── 모델 호출 0회 (out/ 만 있으면 됨) ──
uv run python tools/verify_numbers.py    # 모든 숫자 재계산
uv run python tools/evaluate.py          # 분류·영역·문장 채점
uv run python tools/verify_extract.py    # 필드 회수 채점
uv run python tools/make_review.py       # 육안 검수 화면
uv run python -m pytest tests/ -q        # 159개
```

> ⚠️ **재실행 전에 `.env` 의 `GEMMA_MODEL` 을 확인할 것.** 게이트웨이가 모델 이름을 바꾸면
> 모든 VLM 호출이 400 으로 죽는데 **OCR 은 멀쩡히 돌아 산출물이 그럴듯하게 나온다.**
> ```bash
> curl -s "${GEMMA_URL%/chat/completions}/models"
> ```
