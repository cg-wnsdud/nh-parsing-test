# 파싱 단계 산출물 설계 — 구조와 그렇게 간 이유

> 대상: 이 산출물을 받아 RAG 인덱싱·DB 적재를 맡을 담당자, 그리고 이후 심의 판정 단계를
> 붙일 사람. 스키마 논의용 자료.
> 기준일 2026-07-29 / 측정값은 전부 골드셋 5문서 실측.

---

## 0. 한 줄 요약

이 단계가 답하는 질문은 **"광고에 무엇이 쓰여 있고, 무엇이 빠졌는가"**까지다.
**"그래서 위반인가"는 답하지 않는다** — 그건 다음 단계 몫이고, 산출물은 그 판단에
필요한 근거를 넘기는 것까지가 역할이다.

---

## 1. 무엇을 만들었나 — 산출물 3층

한 문서를 처리하면 세 개가 나온다. **하나로 합치지 않은 데는 이유가 있다.**

| 산출물 | 내용 | 문서당 크기 | 주 용도 |
|---|---|---|---|
| `out/json` | 전체 IR — 영역·라인·bbox·신뢰도·출처·VLM 후보 | 60~85 KB | 감사, 화면 하이라이트 |
| `out/llm_view` | 정제본 — 섹션 → 영역 → 텍스트 (좌표 제거) | 17~27 KB | RAG 인덱싱 |
| `out/extracted` | 구조화 필드 — 스키마 기반 값 + 근거 | 18~32 KB | DB 적재, 심의 판정 입력 |

### 왜 셋으로 나눴나

**하나로 합치면 서로 다른 목적이 충돌하기 때문이다.**

- 감사에는 **틀린 판독도 남아 있어야** 한다. "OCR 은 `10.1%p` 로 읽었고 VLM 은
  `① 0.1%p` 로 읽었다"를 둘 다 보관해야 나중에 왜 그런 값이 나왔는지 추적된다.
- 반대로 LLM 에게 줄 입력에 그 둘을 다 넣으면 **판단이 흐려진다.** 좌표·신뢰도 같은
  기계 정보도 토큰만 먹고 도움이 안 된다.
- DB 에 넣을 것은 또 다르다. 라인 단위가 아니라 **필드 단위**여야 하고, 값마다
  "어디서 나왔나"가 붙어야 한다.

그래서 **같은 내용을 세 번 다른 모양으로 투영**한다. 셋은 `region_id` 로 연결된다
(단, 그 ID 의 안정성에 제약이 있다 — §5 ①).

## 2. 최종 output(`out/extracted`) 구조

```jsonc
{
  "document": "…png", "doc_id": "…",
  "product_group": "예금성",        // 상품군 (스키마 선택 축)
  "ad_type": "이벤트페이지",         // 광고 유형
  "schema_id": "…", "schema_version": "…",
  "overlays_applied": [],           // 적용된 오버레이(이벤트 등)

  "fields":       { /* 스키마 필드별 값 — 아래 참조 */ },
  "observations": { /* 과장·오인 의심 후보. 판정 아님 */ },
  "events":       [ /* 이벤트별 필드 (오버레이) */ ],
  "unmapped":     [ /* 스키마에 못 담은 심의 관련 문구 */ ],

  "coverage":     { /* 자기 진단 17지표 */ },
  "review_gaps":  { }, "input_gap": [], "evidence_unbacked": [],
  "errors":       []
}
```

### 필드 하나

```jsonc
"product_name": {
  "value": "NH올원e적금",
  "evidence": ["p1_r001", "p1_r004"],   // 근거 영역 ID
  "status": "found",
  "group": "G1_상품기본",
  "evidence_score": 1.0,
  "evidence_backed": true                // 값이 원문에 실재하는가
}
```

`evidence_backed` 가 있는 이유: **LLM 이 그럴듯한 값을 지어낼 수 있다.** 값의 토큰이
실제 파싱 텍스트에 있는지 코드로 검산해서 표시한다. 심의 결과가 환각 위에 서면
안 되기 때문이다.

### 값이 없을 때가 이 설계의 핵심

`null` 하나로 두지 않고 **왜 없는지를 4분류**한다.

```jsonc
"interest_calc_method": {
  "value": "", "status": "not_found",
  "absence": {
    "kind": "해당없음",       // 해당없음 | 미표시 | 확인필요 | 판정제외
    "obligation": "필수",
    "rule": "conditional"
  }
}
```

| kind | 뜻 | 심의 지적인가 |
|---|---|---|
| **미표시** | 표시해야 하는데 광고에 없음 | **예 — 이것만 지적이다** |
| 해당없음 | 이 상품 유형에 그 개념이 없음 (수시입출식의 '만기 후 이율' 등) | 아니오 |
| 확인필요 | 상품 유형을 못 정해 판단 보류 | 아니오 (사람이 봐야 함) |
| 판정제외 | 애초에 심의 대상이 아닌 항목 (분류용 필드 등) | 아니오 |

**왜 이렇게까지 나눴나.** 나누기 전에는 값이 없으면 전부 `not_found` 였고, 화면에는
전부 "누락"처럼 보였다. 그런데 실제로는 대부분이 "이 상품엔 원래 없는 항목"이었다.
그대로 두면 심의 담당자가 **가짜 지적 수십 건을 매번 걸러내야 한다.**
분류는 스키마 메타데이터(`obligation`, `applicability.conditions`)를 코드로 평가해서
정한다 — **모델 호출을 늘리지 않는다.**

### `observations` — 판정하지 않는 이유

과장·오인 의심 표현(단정적 표현, 근거 없는 최상급, 조건 일반화 등 9종)을 수집한다.
스키마 지시문에 이렇게 적혀 있다:

> *"값을 뽑는 그룹이 아니다. … 최종 위반 판정은 이후 심의 단계가 하므로, 여기서는
> 단정하지 말고 해당될 수 있는 문구를 근거와 함께 모은다."*

**이 단계에서 위반을 단정하면 두 가지가 망가진다.** 하나는 규정 해석이 파싱 코드에
박혀 규정이 바뀔 때마다 코드를 고쳐야 한다는 것, 다른 하나는 판정 근거가
"LLM 이 그렇게 말했다" 하나로 줄어든다는 것이다. 후보와 근거만 넘기고 판단은
규정 대장을 가진 쪽에서 하게 둔다.

## 3. 이런 구조가 된 이유 — 프로젝트 상황

설계의 상당 부분은 취향이 아니라 **제약에 떠밀린 결과**다. 받는 쪽이 알아야 할
맥락이라 그대로 적는다.

### (A) VLM 출력이 결정론적이지 않다

같은 입력을 두 번 돌려도 결과가 다르다. `temperature=0` 으로도 안 잡힌다
(서버측 guided-decoding·배치 비결정성). 실측: 같은 5문서에서 문장 회수가
**235~237 사이로 흔들린다.**

여기서 나온 설계 원칙 셋:

1. **OCR 을 정본으로 두고 VLM 판독은 후보로만 붙인다.** VLM 이 텍스트를 덮어쓰면
   실행할 때마다 정본이 흔들려 금융 광고에 쓸 수 없다. 그래서 `region.lines`(OCR)는
   그대로 두고 `vlm_reading` 을 나란히 보관한다. 어느 쪽이 맞는지는 스키마를 아는
   최종 단계가 고른다.
2. **조용한 실패 금지.** 어떤 단계가 실패하면 원값을 유지하고 `notes` 에 남긴다.
   실패가 폴백에 먹혀 "정상인데 결과가 나쁨"으로 보이면 원인을 못 찾는다.
3. **판단은 모델, 검산은 코드.** 규칙으로 우열을 정하지 않되, 모델이 낸 값이
   원문에 실재하는지는 코드로 검산한다.

### (B) 폐쇄망 + 사내 파서

- HWP/HWPX 는 사내 파서(`document-processor`)를 쓴다. 이미지 입력은 못 받고,
  스캔형 문서는 조용히 건너뛴다.
- OCR 은 PaddleX(PP-StructureV3), VLM 은 Gemma. 둘 다 사내 엔드포인트.
- **추론 서버를 여러 사람이 공유**해서 응답 시간이 실행마다 2.5~4배 흔들린다.
  그래서 개선 효과를 **시간이 아니라 모델 호출 수로** 판정한다.

### (C) 규정이 코드 밖에 있어야 한다

심의 기준은 은행연합회·금융위 문서에서 오고 개정된다. 그래서 **근거 대장(정적)**과
**런타임 스키마(실행용)**를 2층으로 갈랐다. 규정이 바뀌면 대장을 고치고 스키마 JSON 을
갱신한다 — 파이프라인 코드는 안 건드린다. `schemas/예금성.json` 이 그 파일이다.

### (D) 골드셋이 5문서뿐이다

정답지가 작아서 **통계적 신뢰구간이 없다.** 그래서 규칙을 만들 때 임계값을 데이터에
맞춰 고르는 걸 피했다. 실제로 이번에 스윕 중복 판정 임계값을 정하려다 포기했는데,
4문서 전수 측정에서 진짜 중복과 오탐이 겹쳐 **그을 자리가 없었기 때문**이다.
표본이 늘 때까지 보류한 항목은 §6 에 적었다.

### (E) 성능은 전부 모델 대기 시간이다

무캐시 실측(5문서):

| 문서 | 파싱 | 추출 | 합계 |
|---|---:|---:|---:|
| 올원e | 145~161s | 62s | ~207s |
| 001 | 145~323s | 82s | ~227~404s |
| 002 | 187~258s | 78s | ~265~336s |
| 003 (3p) | 136~248s | 95s | ~231~343s |
| 004 (HWP) | 1.7s | 스킵 | 1.7s |

**시간의 96~98% 가 VLM 대기다.** OCR·좌표계산·규칙판정은 다 합쳐 2~4%.
문서당 3~7분이며, 그중 가장 큰 단일 항목은 밴드 통합판독(전체의 43%)이다.
호출 수를 줄이는 작업이 곧 속도 개선이라, 최근 최적화는 전부 호출 병합이었다
(122회 → 60회).

## 5. 받는 쪽이 반드시 알아야 할 제약 5가지

### ① `region_id` 를 영구 키로 쓰면 안 된다 ⚠️

`region_id`(`p1_r014` 등)는 **생성 순서 라벨**이지 콘텐츠 식별자가 아니다.
같은 문서를 두 번 처리한 실측:

```
영역 76개 / 76개
  같은 id · 같은 내용    72개
  같은 id · 다른 내용     4개   ← p1_r018, r019, r022, r026
```

재처리하면 같은 ID 가 다른 내용을 가리킬 수 있다. **문서 처리 버전과 묶어서 저장하고,
버전이 다르면 별개로 취급**해야 한다.

### ② 재처리하면 결과가 달라진다

§3(A) 대로 출력이 결정론적이지 않다. "다시 돌리면 같은 결과"를 전제한 설계
(멱등 upsert 등)는 깨진다. **덮어쓸지 버전을 쌓을지** 정해야 한다.

### ③ 지금은 예금성만 된다

`schemas/` 에 예금성 하나뿐이다. 대출성(004)은 **파싱은 되지만 추출은 건너뛴다.**
상품군별로 테이블을 나눌지 공통 스키마로 갈지가 논의 대상이다.

### ④ HWP 는 좌표가 없다

디지털 텍스트라 정확하지만 `bbox` 가 없다. **화면 하이라이트(F-010/F-013)를 못 한다.**
렌더링 방안은 미정.

### ⑤ 심의 판정 단계가 아직 없다

`미표시` 분류와 `observations` 수집까지가 끝이다. 위험도 산정·수정안 제시·리포트는
없다. **그 단계를 어디서 돌릴지**에 따라 이 산출물의 경계가 달라진다.

| **장식예시 오분류** — 실제 내용이 목업과 같이 격리됨 | 001 좌측 목업 12영역 + 우측 실제 목록 5영역이 한 섹션 | 격리는 태깅뿐이라 손실 없음. 분류는 부정확 |
| **실행 간 변동** | 문장 235~237, 섹션 37~38 | 구조적 문제(§3 A) |

## 7. 논의에서 정해야 할 것

1. **어느 산출물을 넘기나** — 셋 다인가, 일부인가. 연결 키는 무엇으로 하나(§5 ①)
2. **재처리 정책** — 덮어쓰기 vs 버전 누적 (§5 ②)
3. **부재 4분류를 어떻게 저장하나** — `null` 로 뭉개면 "위반"과 "해당 없음"이 같아진다
4. **상품군 확장 순서** — 대출성 스키마를 언제 만드나 (§5 ③)
5. **심의 판정 단계의 위치** — 이 저장소인가, 통합 레포인가 (§5 ⑤)
6. **근거 추적 범위** — 값 → `region_id` → `bbox` 까지 저장할지, 텍스트만 저장할지
