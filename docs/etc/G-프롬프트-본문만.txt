## 이 프로젝트가 무엇인가

농협은행 광고심의 자동화 PoC. **트랙이 두 개**고 성격이 정반대다.

| | 규정문서 트랙 | 광고물 트랙 |
|---|---|---|
| 입력 | 규정·준수사항 문서 (HWP/PDF) | 광고물 (PDF/PNG/JPG) |
| 역할 | **검색당하는 쪽** = 지식 | **검색하는 쪽** = 심의 대상 |
| 좌표 | 불필요 | **필수** (지적 근거를 원본 위에 표시해야 함) |
| 산출물 | `_hrc.jsonl` (농협 규격) → 농협 KL 벡터DB | 통합 JSON (좌표+라벨) → KL 밖 |
| API | `POST /parsing` | `POST /ad/parsing` |

**목표는 심의 판정이 아니다.** "이 항목이 여기 이렇게 적혀 있다 / 안 보인다"는 **관측**만
내고, "그래서 위반이다"는 결론은 다음 단계가 낸다.

**그리고 지금 단계의 성공 기준은 커버리지가 아니라 텍스트 전량 보존이다.**
라벨이 안 붙은 줄(광고 헤드라인·장식 문구 등)도 좌표와 함께 전부 실려야 한다.
애매한 것에 억지로 라벨을 붙이면 없는 지적을 만든다.

## 처리 흐름 (광고물 트랙)

```
입력 파일
  ↓  ① 파싱                                    → out_ad_full/parse/{이름}.json
     PaddleX(레이아웃+OCR) + 디지털 텍스트 추출
     + VLM: 상품 분류 · 영역 역할 판정 · 카드 분할 · 밴드 통독 · 누락 문구 회수
     + 표 격자 생성 (PaddleX table_res_list)
     + 읽기 순서 보정
  ↓  ② 템플릿 라벨링 + 통합                      → out_ad_full/json/{이름}.json  ★최종
     + VLM: 영역마다 템플릿 항목명(gubun) 붙이기 (12개씩 나눠 호출)
```

**`parse/` 와 `json/` 은 다른 문서가 아니라 같은 파일의 두 단계다.** `parse` 에도 이미
VLM 이 여러 번 들어간다(분류·역할·통독). `json` 에서 새로 생기는 건 `gubun`(템플릿 항목명)
뿐이고, 나머지는 `parse` 것을 그대로 물려받는다 — 영역 순서까지 동일하다.

## 템플릿이 어디서 오나

```
nh-data/pilot-data-set/광고 템플릿(근거규정x, 필수 여부).md     농협 원본 (gitignore)
        ↓ tools/build_ad_templates.py
src/nh_parsing/templates/ad_templates.json                    라벨 사전 (커밋됨)
        ↓ src/nh_parsing/ad_template.py 의 _GUBUN_PROMPT 로 조립
VLM 호출 → 영역마다 gubun 부착
```

md 표의 "구분" 열(회사명·상품명·대출대상·…)이 그대로 항목 목록이 된다.
**판정 도구가 아니라 라벨 사전이다** — `필수여부(O/△)`·`기재요령`은 정적 근거로 담고
실행 결과에는 `template_id` + `gubun` 만 남긴다.

## 이 저장소에서 지켜온 규율

1. **원본으로 검증한다** — JSON·좌표만 보고 결론 내지 말 것. 필요하면 원본 이미지를 눈으로 대조
2. **판단 주체는 VLM** — 정규식은 폴백·보조 신호로만. 과적합 휴리스틱 금지
3. **모든 텍스트 보존** — 라벨이 안 붙어도 좌표와 함께 실린다
4. **조용한 실패 금지** — 못 한 것은 `notes` 에 남긴다
5. **임계값 넣기 전에 왜 안 맞는지부터 측정**
6. **착수 전에 완료 기준을 숫자로 못박고, 안 할 것도 명시**
7. **실행결과에 정적 근거를 복사하지 않는다** — 근거 조문은 스키마 설계 시 1회만
