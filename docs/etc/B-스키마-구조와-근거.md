# B. 스키마 — 어떻게 생겼고 무엇을 근거로 정했나

> 스키마 파일들의 구조와 합쳐지는 방식, 필드 하나의 속성들, 그리고 **무엇을 근거로
> 이 필드들을 정했는지**.
>
> 이 문서 끝에 **중간에 물어본 3가지**에 대한 답이 있다(B-①②③).
>
> **정본 xlsx 를 직접 열어 확인했다.** openpyxl 이 없어 표준 라이브러리로 xlsx 를
> 파싱하는 도구를 만들어 읽었다.

---

## 0. 위치 — 스키마는 파이프라인 **다음** 단계다

[A 문서](A-파이프라인-입력부터-결과까지.md)는 **"무슨 글자가 어디에 있나"** 까지였다.
B는 그 결과를 받아 **"그래서 이 광고가 규정이 요구하는 항목들을 어떻게 표시했나"** 를 채운다.
이 단계를 코드에서 **STAGE_3** 라고 부른다.

```
A 파싱          →  out/llm_view/*.json  (읽기순서 텍스트 + region_id)
                        ↓
B 스키마 추출    →  out/extracted/*.json (필드 48칸이 채워진 것)
                    코드: src/nh_parsing/extract.py
```

## 1. 파일은 4개가 아니라 **5개**다 — 그리고 5번째가 뿌리다

```
src/nh_parsing/schemas/
  _product_group_fields.json   44KB   ← 근거 대장 (사람이 읽는 근거·조문·판단 기록)
  _common.json                 26KB   ← 런타임: 예금성·대출성 공통 31필드
  예금성.json                  28KB   ← 런타임: 예금성 전용 31필드
  대출성.json                  32KB   ← 런타임: 대출성 전용 38필드
  _overlay_이벤트.json         10KB   ← 런타임: 이벤트페이지일 때만 덧붙는 11필드
```

### 2층으로 나눈 이유

| | 근거 대장 | 런타임 스키마 |
|---|---|---|
| 무엇 | "왜 이 필드가 있나" — 조문·출처·확인필요 표시 | "LLM 이 읽을 지시문" |
| 누가 읽나 | 사람 | AI |
| 실행 시 | **안 읽는다**(커버리지 검사에만 씀) | 매 호출마다 읽는다 |

각 런타임 스키마의 `note` 에 그 규약이 못박혀 있다:

> *"런타임 추출 스키마. **근거 조문은 근거대장에 있고 여기엔 LLM 이 읽을 지시문만 둔다.**
> 규정이 바뀌면 대장을 먼저 고치고 이 파일을 갱신한다."*

**왜 이렇게 하나.** 조문을 실행 결과에 매번 복사하면 ① 산출물이 뚱뚱해지고 ② 같은 조문이
여러 곳에 생겨 어느 게 최신인지 모르게 된다. 그래서 실행 결과엔 `field_key` 만 남고
조문은 스키마 설계 시 1회만 기록한다.

> ⚠️ **문서와 코드가 어긋난 지점.** 근거 대장 `_product_group_fields.json` 의 `scope` 는 아직
> ```json
> "in_scope_product_groups": ["예금성"],
> "out_of_scope_future": ["대출성", "투자성", ...]
> ```
> 라고 적혀 있다(`generated: 2026-07-24`). 그런데 **`대출성.json` 은 실제로 존재하고 38필드로
> 돌고 있다.** 대장이 런타임보다 뒤처져 있고, 대장이 "정본"이라는 규약과 어긋난다.
> → [E 문서](E-남은-일과-정리-후보.md) 정리 후보.

두는 이유는 순서 의존성이 아니라 단순히 "이 문서가 뭔지부터 확인하는 게 자연스러워서"다.

```json
{
  "field_key": "fee_and_cost",
  "label": "수수료·부대비용",
  "type": "string",
  "kind": "numeric",
  "catalog_ref": "common/fee_and_cost",
  "checklist_ref": ["DEP-INC-11", "LOAN-INC-10"],
  "prompt": "상품 이용에 따라 발생할 수 있는 수수료·부대비용 표기. 금액·요율·산식이 있으면
             숫자를 한 글자도 바꾸지 않고 담는다. 발생하지 않는다거나 면제된다는 표기도
             담는다. 대출성 광고에서 부대비용이 여러 종류로 나열되면 이 필드에는 요약을

  "obligation": "필수",
  "applicability": {
    "conditions": [
      {"rule": "conditional", "basis": "ledger",
       "why": "수수료·비용이 발생하지 않는 상품에는 표시 대상이 없음"}
    ]
  }
}
```

| 속성 | 뜻 |
|---|---|
| `field_key` | 산출물에서 이 칸의 이름 (실행 결과엔 이것만 남는다) |
| `kind` | **처리 정책** — 아래 4절 |
| `checklist_ref` | **어느 심의 체크리스트 항목에서 왔나** — 아래 5절 / B-② |
| `catalog_ref` | 근거 대장의 어느 항목인가 (조문 추적용) |
| `prompt` | AI 에게 그대로 주는 지시문 — B-② |
| `obligation` | 표시 의무 성격 — B-③ |
| `applicability` | **"이 광고에 이 항목이 애초에 해당되나"** — 아래 6절 |

`obligation` 전수 분포(111필드): `필수 73 · 관측 20 · 수집 11 · 권장 4 · 분류 2 · 절차 1`

## 4. `kind` 5종 — 무엇을 바꾸나

[_common.json 의 `field_kinds`](../../src/nh_parsing/schemas/_common.json) 원문이다.
**각각 "실패하는 방식"이 다르고, 그래서 처리가 다르다.**

| kind | 개수 | 정의 (원문) |
|---|---|---|
| `verbatim` | **43** | *"광고가 스스로 쓴 표현. 정본이 곧 원문이다. **다듬거나 합치면 심의 대상 자체가 사라진다**(표기 불일치가 심의 대상이다)."* |
| `numeric` | **26** | *"수치를 담는 필드. OCR 은 소수점·단위를 잃고 VLM 은 숫자를 바꿔 쓰는 실측이 있어 **실패 방식이 다르다 → 교차검증이 성립한다.** 숫자를 절대 창작하지 않는다."* |
| `template` | **16** | *"규정이 요구하는 정형 문구. 있으면 원문 그대로, 없으면 빈 문자열 + not_found. **없는 문구를 만들어 채우면 심의 결과가 뒤집힌다.**"* |
| `collection` | **9** | *"전수 수집 배열. **같은 값이라도 표기가 다르면 합치지 않고** 각각 담는다."* |
| `enum` | **6** | *"분류값. 광고 문구를 근거로 코드가 쓸 값을 고른다. 근거가 부족하면 '판단불가'."* |

**5종 합계는 100이지 111이 아니다.** 나머지 11개는 `_overlay_이벤트.json`(G5 그룹, `event_name`·
`event_period`·`period_mentions` 등)에 있는데, 이 필드들은 **`kind` 키 자체가 없다** — 이벤트
오버레이 필드는 이 분류 체계 밖에 있다는 뜻이다.

### `verbatim` 이 왜 43개(최다)인가 — 실측 사고가 있다

> 003 문서에서 `1,000명` 과 `1,000팀` 의 **표기 불일치가 심의 대상이었는데**, 정규화 과정에
> 둘이 합쳐지며 **심의 대상이 소멸했다**

광고 심의는 "정확한 정보를 썼나"만 보는 게 아니라 **"표기가 일관되나"** 도 본다. 그래서
다듬으면 안 된다. 이게 규율 4의 근거다.

### `numeric` 의 "교차검증이 성립한다"가 무슨 뜻인가

A 단계의 정본/후보 구조와 연결된다.

```
OCR 정본:      '71%'        ← OCR 은 소수점을 잃는다
VLM 후보:      '7.1%'       ← VLM 은 장식을 읽어내지만 숫자를 바꿔 쓰기도 한다
   ↓
두 실패 방식이 다르므로, 둘이 일치하면 신뢰할 수 있고 갈리면 사람이 봐야 한다는 신호가 된다
```

STAGE_3 이 어느 쪽을 채택했는지 `reading_choice` 로 기록한다 — 값 5종:
`동일 · 정본채택 · 후보채택 · 양쪽보존 · 해당없음`
(⚠️ 단 **응답 필드로는 아직 미구현** — E 문서 참조)

### 그럼 규칙리스트를 뭘로 썼나 — 4가지, 전부 파일에 근거가 남아 있다

**① `category` 축의 어휘를 여기서 가져왔다** — 근거대장에 출처가 명시돼 있다:

```json
// _product_group_fields.json → classification_axes
{"axis": "category",
 "values": ["표시의무", "금지", "양식", "절차"],
 "source": "규칙리스트 category + v12 대분류"}       ← ★ 명시
```

규칙리스트 2,024건의 `카테고리` 칼럼 값이 정확히 이 4종이다(표시의무 953·금지 617·절차 238·
양식 166). **농협 체크리스트의 `구분`(포함사항/금지사항/형식/…)과 다른 어휘 체계**이고, 우리는
둘 다 쓴다 — 자세한 건 [B-③](#b-③-obligation표시-의무-성격은-어떻게-판단하나).

**② `priority`(필수/권장) 어휘도 같은 계열이다.** 규칙리스트 `우선순위` = 필수 1,992 / 권장 32.
근거대장 `field_catalog` 49항목의 `priority` = **필수 46 / 권장 3**. 같은 두 값이다.
`칼럼값_판단기준` 시트가 그 판정 기준까지 적어 놨다:

| 값 | 이 값을 쓰는 기준 |
|---|---|
| 필수 | 매뉴얼 원문에 "하여야 한다", "필수" 등 **강제 표현** |
| 권장 | 매뉴얼 원문에 "원칙", "바람직", "권장" 등 표현 |

**③ 대출성 스키마의 recall 보강에 실제로 썼다.** 예금성과 대출성이 다르다 — 파일에 그대로 적혀 있다:

```json
// 예금성.json:5
"derived_from": "근거대장 _product_group_fields.json
               + NH 준법감시부 체크리스트(DEP-*)
               + (2023년)예금성상품 광고시 준수사항_은행연합회"
                                                        ← 규칙리스트 없음

// 대출성.json:5
"derived_from": "NH 준법감시부 체크리스트(LOAN-*) 36항목
               + (2025년)대출성 상품 광고시 준수사항_은행연합회
               + 규칙리스트 순수 대출 규칙          ← ★ 여기엔 있다
               + 실데이터 004 파싱 결과"
```

**예금성은 규칙리스트를 안 썼고, 대출성은 썼다.** 대출성이 나중에 만들어졌고(8/13),
예금 규칙 73건보다 대출 규칙 202건이 많아 훑을 값이 있었다.

**④ 규정 충돌을 발견하는 데 썼다.** 근거대장 `open_questions` Q1:

```
예금자보호 한도:  규칙리스트/M04 = 5천만원  vs  v12 체크리스트·샘플 = 1억원
→ 스키마에 값을 박지 않고 "부보 문구 존재 + 최신 한도 일치" 로 검사
```

규칙리스트가 없었으면 이 충돌을 못 봤을 것이고, **금액을 하드코딩했을 위험**이 있었다.

### 그래서 "참고용"의 정확한 뜻

| 썼는가 | 무엇에 |
|---|---|
| ✅ 썼다 | `category` 축 어휘 4종 / `priority` 어휘 2종 / 대출성 recall 보강 / 규정 충돌 탐지 |
| ❌ 안 썼다 | **`checklist_ref` 의 ID 체계** — CL### 을 가리키는 필드가 0개 |

근거대장이 이 지위를 문장으로 못박아 뒀다:

> `meta.source_priority`:
> `"recall 보강(보조, status=임시): pilot-data-set/NH_광고심의_규칙리스트_v0.xlsx (1721건)"`
>
> `limitations`:
> *"규칙리스트 v0(1721건)는 status=임시 — 본 카탈로그의 근거는 v12 체크리스트를 우선했고
> 규칙리스트는 recall 보강용."*

`status=임시` 의 근거도 대장 Q5 에 적혀 있다:

> *"status 전부 임시, **원문검증 실패 6.2%**, 중복 미정리"* → *"recall 보강 보조 근거로만,
> 인용 시 `status=임시` 명시"*

**즉 "참고용"은 신뢰도 판정이다.** 규칙 자체가 자동 추출 초안(`칼럼값_판단기준` 시트에도
*"상태=임시: 서브에이전트가 자동 추출한 초안 상태. 사람 검토 전"* 이라고 정의돼 있다)이라,
**조문을 직접 인용하는 근거로는 쓰지 않고 "빠진 게 없나" 훑는 데만 썼다.**

### ⚠️ 확인 중 발견한 문제 2건

**① 인용된 규칙리스트 버전이 3개로 갈린다.**

| 어디 | 인용한 버전 | 건수 |
|---|---|---|
| 근거대장 `meta.source_priority` | `NH_광고심의_규칙리스트_v0.xlsx` | 1,721건 |
| `docs/스키마설계_상품유형_2026-08-13.md` | "규칙리스트 통합 xlsx" | 1,744건 |
| **현재 폴더에 있는 파일** | `NH_광고심의_규칙리스트_최종.xlsx` (8/19) | **2,024건** |

우리 스키마는 **v0(1,721건) 기준으로 만들어졌고**, 그 뒤 최종본이 303건 늘었다. 늘어난
303건에 예금·대출 규칙이 있으면 recall 보강을 다시 한 번 돌려야 한다. **확인 안 된 상태다.**

**② 규칙리스트 `R-0002` 의 인용 조문이 틀렸다.**

```
근거 상세      자본시장과 금융투자업에 관한 법률 제117조의9
인용 조문 원문  "제117조(청산) 제95조는 신탁업을 영위하는 금융투자업자의 청산에 관하여
                준용한다."                          ← 제117조의9 가 아니라 제117조
```

조문 자동 조회가 **"제117조의9"를 "제117조"로 잘라 찾은 것**으로 보인다. 규칙리스트를
근거 원문으로 인용할 때 이런 사례가 더 있는지 봐야 한다 — 대장이 *"원문은 개별 확인 전
인용 자제"* 라고 한 이유가 이것이다.

## 6. `applicability` — "그 항목이 애초에 해당되나"

**왜 필요한가.** 규정 항목은 조건부인 것이 많다. "수수료 표시" 항목은 **수수료가 발생하는
상품에만** 해당된다. 수수료 없는 상품 광고에 수수료 문구가 없는 걸 "누락"으로 지적하면
**허위 지적**이다.

[applicability.py](../../src/nh_parsing/applicability.py) 코드가 **처리할 줄 아는 규칙
문법은 5종**이다. 그중 지금 스키마에 실제로 쓰인 건 4종(전수 분포):

| rule | 건수 | 뜻 |
|---|---|---|
| `conditional` | 24 | 조건에 따라 해당 여부가 갈린다 (근거는 `basis`·`why` 에) |
| `trigger_any` | 6 | 광고에 특정 요소가 있을 때만 해당 |
| `subtype_not_in` | 5 | 상품 하위유형이 이 목록에 **없을 때만** 해당 |
| `subtype_in` | 2 | 이 하위유형일 때만 해당 |
| `ad_type_in` | 0 | 코드는 처리하지만 지금 스키마 어디서도 안 씀 |

> ⚠️ **`subtype_not_in` 에서 실측 사고가 있었다**: enum 에 없는 값이 `not_in` 을 통과해
> **허위 지적을 생성**했다. → 근거 없는 항목에는 판정 등급을 붙이지 않도록 고쳤다.
> [C 문서](C-최종-산출물과-다음-단계.md)의 `absence.kind` 분류가 이 문제의 정면 대응이다.

**`conditional`이 뭔지 감이 안 오면**: 예를 들어 "수수료 조건" 필드는 그 자체가
`conditional` 이다 — 광고에 수수료 관련 문구가 아예 없으면, 그건 "누락"이 아니라 **그
필드 자체가 자동으로 "해당없음" 처리**된다("이 광고가 그 소재를 안 다뤘다"는 뜻). 값이
없다는 것 자체가 판단 근거가 되는 경우다.

## 7. 왜 그룹으로 나눠 AI 를 여러 번 부르나

**단순한 이유부터**: 필드 111개(적용 73~80개)를 한 번에 물으면 **응답이 길어져 중간에
끊긴다.** 끊기면 JSON 이 깨져 그 호출분이 통째로 사라진다.

그래서 그룹 단위로 나눠 부른다 — 예금성 이벤트페이지면 **10회 호출**.

**그런데 여기서 실측으로 배운 것이 있다:**

> **토큰 예산을 필드 개수로만 쟀다.** 배열 필드 길이는 필드 수가 아니라 **문서 크기**에
> 비례한다. `C4_전수수집` 은 필드 3개뿐이라 상한이 2,700토큰이었고, **197영역 문서에서
> 응답이 끊겨 그 그룹 전체가 실패**했다(하필 유실 방지 안전망 그룹).
> 배열 필드에 +1,800 여유 → 근거커버리지 **0.437 → 0.675**

### 그룹 나누기가 단순 분할이 아닌 이유 — 그룹마다 성격이 다르다

| 그룹 | 성격 | 특징 |
|---|---|---|
| `C1_주체와상품` | 식별 정보 | 짧고 확정적 |
| `C2_의무고지문구` | 정형 문구 | **없으면 없다고 해야 함** (생성 절대 금지) |
| `C4_전수수집` | 배열 | **응답 길이가 문서 크기에 비례** — 안전망 |
| `C5_공통표현관측` | 관측만 | `fields` 가 아니라 **`observation_fields`** 를 쓴다 |

**`observation_fields` 가 왜 따로인가.** C5 그룹 instruction 원문:

> *"**값을 뽑는 그룹이 아니다.** 규정이 금지하거나 주의를 요구하는 표현이 광고에 있는지
> '의심 후보'로 수집한다. **최종 위반 판정은 이후 심의 단계가 하므로 단정하지 말고**,
> 해당될 수 있는 문구를 원문 그대로 인용해 근거와 함께 모은다."*

예:

```json
{"field_key": "obs_superlative", "label": "근거 없는 최상급 표현", "kind": "verbatim",
 "obligation": "관측",
 "prompt": "규정이 열거한 최상급 표현(최고·최상·최저·최초·최대·1위·제일·유일)이 다른
            상품이나 다른 기관과 비교해 우위를 주장하는 맥락으로 쓰인 경우.
            주의: 금리 수치에 붙은 '최고'·'최대'·'최저' 는 상품 조건을 나타내는 정상
            표기이므로 여기에 넣지 않는다 — 그건 금리 필드가 담는다."}
```

**"금리에 붙은 '최고'는 정상"** 같은 구분이 프롬프트에 직접 들어 있다. 규칙(정규식)으로
`최고` 를 잡으면 `최고 연 3.5%` 를 전부 위반 후보로 올려 검수자를 파묻는다 — 이게 규율 3
("과적합 휴리스틱 금지, 판단 주체는 AI")이 스키마 안에서 구현된 모습이다.

### 그룹 이름은 무슨 뜻인가 — `C1` · `D2` · `L3` · `G5`

이름 규칙은 단순하다. **앞 글자 = 어느 파일에서 왔나, 숫자 = 읽는 순서.**

| 앞 글자 | 나온 파일 | 뜻 | 그룹 |
|---|---|---|---|
| **C** | `_common.json` | **C**ommon — 예금·대출 공통 | `C1_주체와상품` `C2_의무고지문구` `C3_매체별고지` `C4_전수수집` `C5_공통표현관측` |
| **D** | `예금성.json` | **D**eposit — 예금성 전용 | `D1_상품기본` `D2_금리수치` `D3_예금성고지` `D4_예금성표현관측` |
| **L** | `대출성.json` | **L**oan — 대출성 전용 | `L1_상품기본` `L2_금리수치` `L3_상환과비용` `L4_경고고지` `L5_대출성표현관측` |
| **G** | `_overlay_이벤트.json` | 오버레이로 **붙는** 그룹 | `G5_이벤트` |

같은 자리 숫자가 예금·대출에서 같은 성격을 가리키도록 맞춰 놨다:

```
D1_상품기본  ↔  L1_상품기본       ← 1번은 "이 상품이 무엇인가"
D2_금리수치  ↔  L2_금리수치       ← 2번은 "숫자와 그 부속조건"
D4_..표현관측 ↔ L5_..표현관측      ← 마지막은 항상 관측 그룹
```

대출성만 5개인 이유는 `L3_상환과비용`(중도상환·연체·부대비용) 이 예금성에 대응이 없기 때문이다.

### ⚠️ 그런데 **코드는 이 이름을 읽지 않는다**

이름이 동작을 바꾼다고 오해하기 쉬운데, 확인해 보면 아니다:

```python
# extract.py:278-280 — group_id 는 라벨로만 쓰인다
for group in pack["call_groups"]:
    gid = group["group_id"]
    schema = response_schema(group)
```

`gid` 는 그 뒤 **오류 기록·`group_analysis` 키·캐시 이름**에만 쓰인다. 접두어 `C`/`D`/`L`/`G`
를 파싱하는 코드는 저장소 전체에 없다.

> **문서·주석과 어긋난 점**: [schema_pack.py:137](../../src/nh_parsing/schema_pack.py#L137)
> 의 docstring 이 *"**group_id 로** 세 가지 형태를 만든다"* 라고 적혀 있는데, **실제 분기는
> `group_id` 를 안 본다**:
>
> ```python
> def response_schema(group: dict) -> dict:
>     if group.get("observation_fields"):            # ← 키의 존재로 분기
>         return _observation_schema(group)
>     if group.get("cardinality") == "list_of_events":  # ← 값으로 분기
>         return _event_schema(group)
>     return _fields_schema(group)
> ```
>
> 주석이 낡았다. 그룹 이름을 바꿔도 동작은 안 바뀌고, **키를 바꾸면 바뀐다.**

### 그룹 순서는 결과에 영향을 주지 않는다

호출 순서는 [schema_pack.py:68-90](../../src/nh_parsing/schema_pack.py#L68-L90) 의 병합
순서를 그대로 따른다 — `includes`(=`_common`) → 본체(예금성/대출성) → 오버레이.
그래서 `C* → D* → G*` 순으로 불린다.

하지만 **각 호출은 서로 독립이다.** `_prompt(group, doc_text)` 에 들어가는 건 그 그룹의
지시문과 **문서 전문**뿐이고, 앞 그룹의 결과를 뒤 그룹에 넘기지 않는다. 따라서:

- 순서를 바꿔도 결과는 같다
- 한 그룹이 실패해도 **다른 그룹은 살아남는다** (`result["errors"]` 에 기록하고 `continue`)
- 같은 문서 텍스트를 그룹 수만큼 반복 전송한다 — 토큰을 더 쓰는 대신 **실패 격리**를 얻은 구조다

## 7-A. `observation_fields` 는 왜 따로 있나 — 없어도 되는 것 아닌가

§7 에서 "성격이 다르다"고만 했는데, 실은 **없으면 동작하지 않는다.** 이 키가 vLLM 에 보내는
**JSON 응답 형태 자체를 고르는 스위치**다.

### 응답 형태가 3종인데, 이 키가 그걸 고른다

[schema_pack.py `response_schema()`](../../src/nh_parsing/schema_pack.py#L136-L142):

```python
if group.get("observation_fields"):                 → _observation_schema()
if group.get("cardinality") == "list_of_events":    → _event_schema()
그 외                                                → _fields_schema()
```

세 형태가 실제로 어떻게 다른가:

| | 일반 필드 (`fields`) | 관측 (`observation_fields`) |
|---|---|---|
| 한 항목의 모양 | **객체 1개** | **배열** (0개 이상) |
| 칸 | `value` · `evidence` · `status` · `note` | `quote` · `evidence` · `why` |
| 최상위 키 | `"fields"` | `"observations"` |
| 없을 때 | `value: ""` + `status: "not_found"` | `[]` (빈 배열) |

```jsonc
// _fields_schema — 값을 하나 고르는 형태
"max_rate": { "value": "4.7%", "evidence": ["p1_r009"],
              "status": "found", "note": "" }

// _observation_schema — 후보를 여러 개 모으는 형태
"obs_definitive_expression": [
  { "quote": "#농협은행 최초가입",        // 원문 그대로
    "evidence": ["p1_r003"],
    "why": "비교 대상 없이 '최초가입' 을 사용 … 확인 필요" }
]
```

### 왜 배열이어야 하나 — 개수가 다르다

- 필드는 **답이 하나다.** "최고금리가 뭐냐" → 4.7%. 두 개면 그게 오히려 결함이다.
- 금지표현은 **몇 개가 나올지 모른다.** 최상급 표현이 광고 한 장에 0개일 수도 5개일 수도 있다.

이걸 `fields` 형태로 억지로 담으면 `value` 한 칸에 여러 인용을 이어 붙이게 되고, 그 순간
**`evidence`(어느 영역에서 나왔나)가 인용별로 안 붙는다.** 검수자가 화면에서 하이라이트를
누를 수 없게 된다 — C 문서의 `evidence_backed` 검산도 못 한다.

### `status` 가 없는 이유 — 판정을 안 하기 때문

일반 필드에는 `status: found / not_found / uncertain` 이 붙고, `not_found` 면 `absence.kind`
가 계산돼 **"미표시(지적)"** 가 될 수 있다. 관측에는 그 칸이 아예 없다. 대신 `why` 에
"…의심됨", "확인 필요" 를 적는다.

> 이게 규율 3(**판단 주체는 AI, 최종 판정은 사람**)이 스키마 형태로 굳은 자리다.
> 관측 항목에 `status` 를 주면 **자동으로 위반 판정이 생겨 버린다.** 형태에서 막았다.

### `obligation: "관측"` 과 정확히 같은 집합이다 (실측)

두 장치가 겹쳐 보이는데, 세어 보면 **완전히 1:1** 이다:

| | 개수 |
|---|---|
| `observation_fields` 에 든 항목 | **20** |
| `obligation: "관측"` 인 항목 | **20** |
| 교집합 | **20** (예외 0건) |

역할이 다르다:

- **`observation_fields`(키)** — vLLM 에 보낼 **응답 형태**를 고른다. 기계용.
- **`obligation: "관측"`(값)** — 결과 집계 시 **판정 등급**을 고른다. 이 값이면 `review_gaps`
  의 "미표시" 목록에 절대 안 들어간다. 사람·보고서용.

즉 **하나는 입력 형태, 하나는 출력 취급**이다. 둘 다 있어야 "물어보는 방식"과 "결과를 세는
방식"이 같은 방향으로 정렬된다. 실수로 어긋나면(관측 그룹에 `obligation: 필수` 를 적으면)
**근거 없는 지적이 생긴다** — 그래서 20/20 일치를 확인한 것이다.

## 8. 두 가지 설계 규약 (guided decoding 함정)

> **guided decoding 이란**: AI(VLM)의 응답이 우리가 정한 JSON 형식(스키마)을 반드시
> 지키도록 서버가 강제하는 방식이다. `strict json_schema` 도 같은 뜻으로 쓰인다. 형식은
> 강제되지만, 그 강제 방식 자체가 특정 스키마 모양에서 불안정하게 구는 경우가 있고
> (아래 2번) 그게 이 절의 주제다.

[schema_pack.py 상단](../../src/nh_parsing/schema_pack.py#L11-L16) 의 응답 형태 규약.
둘 다 실측 사고 대응이다.

1. **값 타입은 `string`/`array` 만 쓴다.** `nullable`(비어 있을 수 있음) 표현이 제약
   디코딩에서 불안정해 → **"없으면 빈 문자열 + `status=not_found`"** 규약으로 대체.
   `status` 가 권위 신호다.
2. **`analysis`(문자열)를 항상 첫 필드로 둔다.** 배열이 스키마 선두에 오면 모델이
   **최소 유효 출력(빈 배열)으로 조기 종료하는 퇴행**이 실측됐다(2026-07-16, gemma-4-26b).
3. **`unmapped` 는 모든 호출그룹에 필수다.** 어느 필드에도 안 맞은 텍스트를 여기 남기지
   않으면 조용히 유실된다 — *"금융광고 심의에서 가장 위험한 실패"* 라고 주석에 적혀 있다.

## 9. 마무리 — 근거규정은 전부 법조항인가, 스키마는 준법감시부 자료로만 만들었나

스키마 설명을 마무리하며 짚어야 할 질문 2개다. **추측하지 않고 97개 항목의 `근거규정` 칸을
전부 파싱하고, 연구소 규칙리스트의 조문 시트 300건도 다시 열어 대조했다.**

### 9-1. 정본 체크리스트의 `근거규정` — 전부 법조항이 아니다

97개 항목의 `근거규정` 칼럼을 인용 문자열로 전수 분류했다:

| 근거규정에 인용된 것 | 건수 | 비율 | 정체 |
|---|---|---|---|
| **`기준 §...`만 단독 인용** | **57건** | **59%** | **은행 광고심의 기준** — 은행연합회가 만든 **자율규제**. 국가가 만든 법이 아니다 |
| 금소법·시행령·감독규정·정보통신망법·금융지주회사법·표시광고심사지침 등 **국가 규정 포함** | 37건 | 38% | 법률·시행령(법령 하위규정)·감독규정/심사지침(행정규칙) |
| 근거 없음(`심의의견에 별도로 작성`) | 3건 | 3% | `PLUS` 자유기술 항목 |

**"기준"이 법이 아니라는 근거** — 규칙리스트의 `매뉴얼` 시트에 발행기관이 적혀 있다:

```
M04   은행 광고심의 매뉴얼(기준·세칙)   은행연합회   2023   133쪽
```

**발행기관이 은행연합회다.** 국회·정부가 만든 법령이 아니라 **은행들의 협회가 자체적으로
정한 자율규제 기준**이다. 다만 이 자율규제는 **금소법 §22(광고 규제)가 세부 기준을
협회 자율규제에 위임**한 결과물이라, 법과 무관한 건 아니다 — "법이 위임한 자율규제"다.

**국가 규정을 포함한 37건의 실물**:

```
DEP-INC-11   기준 §16① 5 나 (X) → 금소법 §22③4, 금소법 시행령 §18①1다     ← 법률+시행령
DEP-FMT-01   금소법 §22⑦, 시행령 §19①, 감독규정 §18                      ← 법률+시행령+행정규칙
DEP-ETM-01   정보통신망법 §50④, 시행령 §61③                              ← 다른 법률(광고 아닌 통신망법)
DEP-JNT-01   금융지주회사법 §48④, 시행령 §27⑨, 감독규정 §24               ← 또 다른 법률
```

**즉 정답은 "아니다, 대부분(59%)이 자율규제이고 법 관련은 소수(38%)다."** 다만 그 소수가
가볍지 않다 — 전자적전송매체(ETM) 9건 전부, 공동광고(JNT) 6건 전부가 **순수 법령 근거**다.

### 9-2. 연구소 규칙리스트의 `조문` 시트 — 이것도 법만은 아니다

`조문` 시트(300건)에도 **`근거_구분`** 칼럼이 있다. 전수 집계:

| 근거_구분 | 건수 | 비율 |
|---|---|---|
| 법령 | 147 | 49% |
| **자율규제** | **105** | **35%** |
| 행정규칙 | 47 | 16% |

**"조문"이라는 이름이 오해를 만든다.** 법조문만 있는 게 아니라 **자율규제 문서의 조항도
같이 "조문"으로 저장**했다. 예:

```
LM001   CMA 업무관련 모범규준            자율규제   ← 협회 모범규준, 법 아님
LM002   개별 영업점 자체제작 광고 판단기준  자율규제   ← 우리 내부 판단기준 문서
LM003   개인정보 보호법 제15조           법령       ← 이건 진짜 법
LM211   은행 광고심의 기준               자율규제   ← M04, 위에서 본 그 문서
```

**즉 "조문"은 "조 단위로 쪼갠 근거 원문"이라는 뜻이고, 그 원문의 발행 주체가 국가(법령·
행정규칙)인지 협회(자율규제)인지는 항목마다 다르다.** 두 질문(9-1, 9-2)의 답이 같은
구조다 — **정본 체크리스트도, 연구소 조문 시트도, 둘 다 "법+자율규제"의 혼합이다.**

### 9-3. 그래서 스키마는 준법감시부 자료로만 만들었나 — **아니다, 최소 4개 출처를 교차했다**

**실물로 확인한다.** `interest_rate_range`(이자율 범위·산출기준) 필드 하나를 끝까지 추적하면
네 갈래가 다 나온다.

**① 준법감시부 체크리스트** — "무엇을 점검할지"의 항목·ID·1차 의무축만 준다:

```
DEP-INC-06   점검내용: "이자율·수익률의 범위 및 산출기준을 표시하였는가?"     ← 질문만, 상세 없음
             근거규정: "기준 §16① 5 나"
```

**② 학습자료 원문 15종** — 조문 전체와 세부 요건. 스키마 파일이 직접 인용한다:

```json
// 예금성.json:5
"derived_from": "근거대장 + NH 준법감시부 체크리스트(DEP-*)
               + (2023년)예금성상품 광고시 준수사항_은행연합회"     ← 준법감시부 밖의 원문
```

`은행 광고심의 기준 제16조` 원문(조문 시트 LM222)을 직접 열어보면 "나. 이자율의 범위 및
산출기준"이라고만 돼 있다 — **세전/세후·기준일자 얘기가 조문 자체엔 없다.**

**③ 그 "산출기준"이 뭘 뜻하는지는 다른 문서가 풀어 쓴다.** 같은 매뉴얼(M04) 63쪽(조문
원문)과 27쪽(해설)이 다르다:

```
R-0754  (M04 p.63, 조문)   "이자율·수익률의 범위 및 산출기준을 표시하였는가?"        ← 질문 그대로
R-0689  (M04 p.27, 해설)   "…산출기준(기준일자, 세전/세후, 기간별 이율, 우대금리
                             조건 등)이 표시되어 있는지 확인"                       ← ★ 상세는 여기서
```

**세전/세후·기준일자가 우리 스키마 `prompt` 에 있는 문구와 정확히 일치한다** — 준법감시부의
한 줄짜리 질문에는 없던 상세가 **같은 매뉴얼의 다른 페이지(해설부)에서 나왔다.**

**④ 심지어 하나의 필드가 서로 다른 문서 4개를 동시에 인용하는 경우도 있다.** 근거대장의
`interest_rate_range` 항목 실물:

```json
"review_items": [
  {"check": "이자율의 범위 및 산출기준(기준일·세전/세후)을 표시하였는가?",
   "basis": {"law": "은행 광고심의 기준 §16①5나목 / 감독규정 §17①3호 가목 / 금소법 §22③3호",
             "source_type": "자율규제·행정규칙·법률"}},          ← 3개 문서 동시 인용
  {"check": "이자율·수익률 표기 시 '세전'·'세후' 구분을 표기했는가?",
   "basis": {"law": "금융상품 등의 표시·광고에 관한 심사지침 Ⅴ.1",
             "source_type": "행정규칙"}}                        ← ★ 준법감시부에도 학습자료
]                                                                    15종에도 없는 별도 행정규칙
```

**"금융상품 등의 표시·광고에 관한 심사지침"은 학습자료 폴더 13개 파일에도 없다.** 조문
시트에 `MCP_MST`(법제처 일련번호)·`MCP_URL`(국가법령정보센터 링크)로만 존재한다 — **법제처
행정규칙 DB를 직접 조회해 가져온 근거**라는 뜻이다.

### 실제로 재료가 된 출처 — 최종 정리

| # | 출처 | 무엇을 줬나 |
|---|---|---|
| ① | **NH 준법감시부 체크리스트** (97항목) | 항목 존재 여부·ID 체계(`checklist_ref`)·1차 의무축(`구분`) |
| ② | **학습자료 원문 15종**(M01~M15, HWP/PDF) | 조문 전문, `derived_from` 에 파일명으로 직접 명시 |
| ③ | **연구소 규칙리스트의 "판단 기준" 해설 열** | 조문이 말 안 해주는 실무 상세(세전/세후·기준일자 등), 특히 대출성 recall 보강 |
| ④ | **법제처 법령·행정규칙 DB 직접 조회** | 학습자료에도 없는 개별 조문(표시·광고 심사지침 등), `MCP_URL` 로 추적 가능 |

**"준법감시부 자료로만 작성됐다"는 아니다.** 준법감시부 자료는 **"몇 개 항목이 있고 그중
뭐가 필수인지"의 뼈대**를 줬고, **그 뼈대 각 칸이 구체적으로 뭘 요구하는지는 학습자료
원문·연구소 해설·법제처 원문 조회를 교차해서 채웠다.** 근거대장의 `basis.law` 칸에 여러
문서가 동시에 나열되는 게 바로 이 교차 작업의 흔적이다.

# 중간에 물어본 것 3가지

## B-① 오버레이(overlay)란 무엇인가

### 문제부터 — 이벤트를 "상품군"으로 만들면 안 되는 이유

상품군(`예금성`/`대출성`)은 **배타적**이다. 한 광고가 둘 다일 수 없다.
그런데 **이벤트는 배타적이 아니다** — 예금성 광고에도 붙고 대출성 광고에도 붙는다.

이벤트를 상품군으로 만들면:

```
❌ 예금성 · 대출성 · 예금성이벤트 · 대출성이벤트 · …  → 조합이 곱셈으로 늘어난다
❌ "이 광고는 예금성인가 이벤트인가?"  → 답이 없는 질문이 생긴다
```

**오버레이 = 조건이 맞을 때 기본 스키마 위에 덧붙이는 필드 묶음.** 상품군과 **직교(直交)**
한다 — 서로 간섭하지 않고 곱셈이 아니라 덧셈이 된다.

```
예금성(62필드)  +  이벤트 오버레이(11필드)  =  73필드
대출성(69필드)  +  이벤트 오버레이(11필드)  =  80필드
```

파일의 `note` 에 그 판단이 한 줄로 적혀 있다:

> *"**이벤트는 상품군이 아니라 광고유형 오버레이다.** `ad_type` 이 이벤트페이지일 때 상품군
> 스키마에 이 그룹을 덧붙인다. 한 광고에 이벤트가 여러 개면(카드형) 카드별로 하나씩 담는다."*

### 붙는 조건이 파일 안에 선언돼 있다

```json
// _overlay_이벤트.json
"applies_to": { "ad_type": ["이벤트페이지"] }

// 예금성.json
"applies_to": { "product_group": "예금성" },  "includes": ["_common"]
```

[schema_pack.py:44 `load_pack()`](../../src/nh_parsing/schema_pack.py#L44) 이 오버레이 파일을
**전수 훑어서** `applies_to` 조건을 검사하고 맞는 것만 붙인다. 코드에 `if 이벤트페이지: ...`
같은 분기가 없다 — **파일을 하나 추가하면 코드 변경 없이 새 오버레이가 생긴다.**

### 실물 — 붙었다는 기록이 결과에 남는다

```
003 문서:  ad_type = "이벤트페이지"
           overlays_applied = ["_overlay_이벤트"]     ← 21키 중 하나
           events = 2건
```

`overlays_applied` 가 비어 있으면 "이 문서엔 이벤트 필드를 아예 물어보지 않았다"는 뜻이다.
**"안 물어본 것"과 "물어봤는데 없는 것"** 을 구별하기 위한 기록이다.

### 그리고 이 오버레이가 A 단계의 카드 분할과 이어진다

이벤트 오버레이는 **배열**이다(한 광고에 여러 이벤트). 그 경계를 어디서 가져오나 —
instruction 원문:

> *"광고에 담긴 이벤트를 이벤트 단위로 하나씩 분리해 배열로 담는다. 한 이미지에
> EVENT1/EVENT2 처럼 여러 개가 있으면 각각 별도 항목이고, **서로 내용을 섞지 않는다**
> (기간·경품이 이벤트별로 다르다). **카드 번호(card_no)나 섹션이 이미 나뉘어 있으면 그
> 경계를 따른다.**"*

**A 단계의 `card_no` 가 여기서 쓰인다.** 003 실측 결과:

```
이벤트1: 'EVENT 1. 신규모임개설이벤트'  근거 p3_r004   기간 2025년 10월 1일(수)~10월 31일(금)
이벤트2: 'EVENT 2. 게시물 공유 이벤트'   근거 p3_r008   기간 2025년 10월 20일(월)~10월 31일(금)
```

**두 이벤트의 기간이 다르다**(10/1 vs 10/20). 카드 분할이 없으면 좌표만으로 정렬해 두
이벤트 문장이 섞이고, **기간이 뒤바뀌면 그게 곧 허위 심의 결과**가 된다.

`period_mentions`(전수수집) 실측:

```
이벤트1의 기간 표기 4개:
  '2025년 10월 1일(수)~10월 31일(금)  (p1_r005)'
  '2025.10.01 - 2025.10.31            (p1_r001)'   ← 페이지 상단 배너의 통합 기간
  '2025년 10월 1일~2025년 10월 31일    (p2_r003)'
  '2025.10.01.(수)~10.31.(금)         (p3_r007)'
이벤트2의 기간 표기 2개:
  '2025년10월 20일(월)~10월 31일(금)   (p1_r015)'
  '2025.10.20.(월)~10.31.(금)         (p3_r011)'
```

**배너는 10.01 부터인데 이벤트2는 10.20 부터다.** 프롬프트에 그 이유가 적혀 있다:

> *"③은 이 이벤트만의 기간이 아니지만, **소비자가 이 이벤트의 기간으로 읽을 수 있으므로
> 담는다** — 통합 표기와 개별 기간이 어긋나면(배너는 10.01부터인데 이 이벤트는 10.20부터)
> **그 오인 소지가 바로 심의 대상이다.**"*

### `_common.json` 도 사실은 같은 메커니즘의 다른 얼굴이다

근거 대장의 `field_catalog` 는 4갈래다:

```
common          18항목
deposit         20항목
event_overlay    6항목
media_overlay    5항목   ← 매체 오버레이도 설계됐다
```

**그런데 `_overlay_매체.json` 파일은 없다.** 매체별 고지(SMS 에 `(광고)` 표시, 수신거부 안내
등)는 `_common` 의 **`C3_매체별고지` 그룹 5필드**로 들어갔다. 오버레이로 분리하지 않고
공통부에 넣은 것인데, 대신 각 필드에 `applicability` 조건(`rule: "conditional"`)을 달아
"해당 매체가 아니면 해당없음"으로 떨어지게 했다.

즉 **"오버레이로 분리"와 "공통부 + 적용조건"** 두 방법이 있고, 이벤트는 전자, 매체는 후자를
골랐다.

## B-② `checklist_ref` 와 `prompt` 는 무엇을 보고 정했나

### `checklist_ref` = 정본 xlsx 의 항목 ID 를 그대로 가리킨 것

즉 **우리가 만든 게 아니라 농협 파일의 ID 를 인용한 것**이다. 그래서 검증이 가능하다.

**직접 대조한 결과 — 유령 참조 0건:**

```
스키마 111필드가 가리키는 모든 checklist_ref 를 정본 97항목과 대조
  → 정본에 없는 ID: 0건
```

(문서에 적혀 있던 수치인데, 문서를 믿지 않고 xlsx 를 열어 다시 세었다. 일치한다.)

### `prompt` 는 3겹이다 — 실물 대조

**`prompt` 는 인용이 아니라 우리가 쓴 것**이다. 다만 아무렇게나 쓴 게 아니라 3겹 구조다.

#### 예 1 — 정본 그대로면 짧다

```
정본[DEP-INC-01] (포함사항)  "은행의 명칭을 표시하였는가?"
                근거규정      기준 §16① 1

우리 prompt   "광고 주체인 은행의 명칭 표기. 광고 어디든 한 번이라도 표기돼 있으면 담는다.
               로고 안의 글자도 판독됐다면 포함한다."
                            └────────────────────┘
                            ↑ 우리가 추가한 부분 — A단계 실측에서 로고 글자가 OCR로 잡힌다는 걸 알아서
```

**왜 형태를 바꾸나.** 정본은 **판정 질문**("표시하였는가?")이고 우리가 필요한 건 **추출
지시**("담아라")다. 판정 질문을 그대로 주면 AI 가 `true/false` 를 답하는데, 우리 단계는
**판정하지 않고 값을 뽑는 단계**다.

#### 예 2 — 정본에 없는 실무 규칙을 우리가 추가한 경우

```
정본[DEP-INC-02] (포함사항)  "준법감시인 심의필번호 및 유효기간을 표시하였는가?
                             (라디오방송·휴대전화메시지 등 표시가 곤란한 경우 생략 가능)"
                근거규정      기준 §16① 2, 기준 §16① 8

우리 prompt   "준법감시인 심의필 표기 전체를 담는다 — 심의주체·심의필번호·유효기간이 모두
               들어가야 한다. 번호나 기간 중 일부만 있으면 있는 대로 담는다(무엇이 빠졌는지는
               이후 단계가 판단한다). 번호와 날짜는 한 글자도 바꾸지 않는다.
               자릿수가 가려진 견본 표기(0 이나 O 가 이어진 형태)도 그대로 옮긴다."
               └──────────────────────────────────────────────┘
               ↑ 실측 유래: 004 문서의 '심의필 2026-0000 (2026.00.00.~2027.00.00.)' 견본 표기
```

`'2026-0000'` 은 **실제 광고가 아니라 견본**이다. 이걸 "이상한 값"으로 판단해 버리면 원문이
사라진다. 그래서 "그대로 옮긴다"를 명시했다.

#### 예 3 — 정본이 어휘를 열거하면 그걸 그대로 쓴다 (⭐ 가장 명확)

```
정본[DEP-PRO-05] (금지사항)  "객관적 근거가 있는 사실이나 공인된 자료 없이 최고, 최상, 최저,
                             최초, 최대, 1위, 제일, 유일 등의 최상급 표현을 사용하지 않았는가?"
                근거규정      기준 §17 5

우리 prompt   "규정이 열거한 최상급 표현(최고·최상·최저·최초·최대·1위·제일·유일)이 다른 상품이나
               다른 기관과 비교해 우위를 주장하는 맥락으로 쓰인 경우.
               주의: 금리 수치에 붙은 '최고'·'최대'·'최저' 는 상품 조건을 나타내는 정상 표기이므로
               여기에 넣지 않는다 — 그건 금리 필드가 담는다."
               └──────────────────────────────────────────────────┘
               ↑ 실측 유래: '최고 연 3.5%' 를 전부 위반 후보로 올리면 검수자가 파묻힌다
```

**어휘 8개는 정본에서 한 글자도 안 바꾼 인용**이고, 뒤의 "주의" 문장은 실측에서 나온 우리
추가다.

### 정리 — `prompt` 3겹

| 겹 | 출처 | 예 |
|---|---|---|
| ① **무엇을 뽑나** | 정본 `점검내용` | "은행의 명칭", "최고·최상·최저…" 어휘 8개 |
| ② **어떻게 뽑나** | 정본 → 추출 지시로 형태 변환 | "표시하였는가?" → "담는다" |
| ③ **함정 회피** | **A 단계 실측** | 견본 표기, 로고 글자, '최고 연 3.5%' 오탐 |

③이 이 프로젝트가 규율 3(과적합 휴리스틱 금지)을 지키는 방식이다. **정규식으로 걸러내지
않고, AI 에게 "이 경우는 아니다"를 말로 알려준다.** 정규식이면 새 케이스마다 코드를 고쳐야
하고 그게 곧 샘플 과적합이다.

### 그리고 `catalog_ref` 가 조문까지 이어 준다

```
fee_and_cost
  catalog_ref     "common/fee_and_cost"      → 근거대장의 그 항목 (조문·판단 기록)
  checklist_ref   ["DEP-INC-11","LOAN-INC-10"] → 정본 항목 ID
       ↓ 정본이 들고 있는 근거규정
  DEP-INC-11:  금소법 §22③ 4, 금소법 시행령 §18① 1 다
  LOAN-INC-10: 기준 §16① 6 바
```

**같은 항목인데 근거 조문이 예금성/대출성에서 다르다.** 이걸 필드 안에 복사하지 않고
ID 로만 가리키는 것이 규율("실행결과에 정적근거 복사 금지")이다.

## B-③ `obligation`(표시 의무 성격)은 어떻게 판단하나

### 답: 정본의 `구분` 칼럼이 1차 근거다. 다만 **기계적 1:1 이 아니고, 예외에 사유가 있다.**

### 어휘가 서로 다르다는 것부터 짚어야 한다 — **2축이 합쳐진 값이다**

여기서 가장 많이 막히는 지점이다. **`obligation` 값은 정본 `구분` 칼럼을 그대로 베낀 것이
아니다.** 어휘 자체가 다르다:

```
정본 체크리스트의 '구분'      포함사항 · 금지사항 · 형식 · 전자적전송매체 · 공동광고 · 기타
우리 스키마의 obligation      필수 · 권장 · 관측 · 수집 · 분류 · 절차
                              ↑ 겹치는 단어가 하나도 없다
```

**두 축이 합쳐져서 나온 값이다:**

| 축 | 값 | 어디서 왔나 | 무엇을 말하나 |
|---|---|---|---|
| **A. 무엇을 점검하나** | 포함사항 / 금지사항 / 형식 / … | **정본 `구분` 칼럼** | 있어야 하나, 없어야 하나 |
| **B. 얼마나 강제인가** | **필수 / 권장** | **근거대장 `priority`**<br>(= 규칙리스트 `우선순위` 어휘) | 없으면 지적인가 |

```
A(포함사항) × B(필수)   →  obligation = 필수     "있어야 하는데 없으면 지적"
A(포함사항) × B(권장)   →  obligation = 권장     "있으면 좋지만 없어도 지적 아님"
A(금지사항) × (판정보류) →  obligation = 관측     "후보만 모으고 판정은 사람이"
근거가 정본에 아예 없음   →  obligation = 수집     "빠뜨리지 않는 게 목적, 판정 안 함"
필드가 축 판정용          →  obligation = 분류
광고물 밖의 절차          →  obligation = 절차
```

**B 축의 어휘 출처가 실제로 확인된다:**

| | 필수 | 권장 |
|---|---|---|
| 규칙리스트 `우선순위` (2,024건) | 1,992 | 32 |
| 근거대장 `priority` (49항목) | 46 | 3 |
| 스키마 `obligation` (111항목) | 73 | 4 |

규칙리스트 `칼럼값_판단기준` 시트가 이 두 값의 판정 기준까지 정의해 놨다 —
*필수 = 원문에 "하여야 한다"·"필수" 등 강제 표현 / 권장 = "원칙"·"바람직"·"권장"*.
[§5-A](#5-a-사내-연구소-자료규칙리스트는-무엇이고-참고용이-정확히-무슨-뜻인가) 참조.

**나머지 4종(관측·수집·분류·절차)은 우리가 만든 값이다.** 정본에도 규칙리스트에도 없다.
왜 만들었는지는 아래 예외 3건이 답이다 — 요약하면 **"근거가 없는 항목에 판정 등급을 주면
허위 지적이 생긴다"** 는 실측 사고 대응이다.

### 1차 근거 — 정본의 `구분` + 근거대장의 `category` 축

근거 대장의 `classification_axes` 7축 중 마지막 축이 `구분` 을 4갈래로 추상화한다:

```json
{"axis": "category", "values": ["표시의무", "금지", "양식", "절차"],
 "source": "규칙리스트 category + v12 대분류"}
```

> 참고 — `classification_axes` 는 7개다. 그중 광고를 서술하는 축이 5개
> (`product_group` · `product_subtype` · `ad_type` · `media` · `advertiser`)이고,
> 나머지 2개(`review_gate` · `category`)는 **규칙을 서술하는 축**이다. "5축 분류"라는 말은
> 앞의 5개를 가리킨다.

### 실제 교차표 — xlsx 와 스키마를 직접 대조한 결과

```
우리 obligation      ←  정본 구분
─────────────────────────────────────────────────────────────
필수  (73)   포함사항 47 · 금지사항 7 · 전자적전송매체 3 · 공동광고 2 · [참조없음 14]
관측  (20)   금지사항 15 · 형식 2 · 포함사항 2 · [참조없음 1]
권장  ( 4)   포함사항 2 · 금지사항 1 · [참조없음 1]
수집  (11)   [전부 참조없음 11]
분류  ( 2)   [전부 참조없음 2]
절차  ( 1)   [참조없음 1]
```

**주 흐름은 명확하다.**

| 정본 구분 | → obligation | 왜 |
|---|---|---|
| **포함사항** (표시해야 함) | **필수** | 없으면 지적 대상 → 값을 뽑아야 한다 |
| **금지사항** (하면 안 됨) | **관측** | **뽑을 "값"이 없다.** "이 표현이 있나"만 볼 수 있다 |
| 전자적전송매체·공동광고 | 필수 | 조건부 포함사항 (해당 매체일 때만) |

**"금지사항 → 관측"이 핵심 통찰이다.** 금지사항은 *"쓰지 마라"* 이므로 광고에서 **뽑아낼
값이 존재하지 않는다.** 뽑을 수 있는 건 *"이런 표현이 있는 것 같다"* 는 의심 후보뿐이다.
그래서 `observation_fields` 라는 별도 자리가 있고 `obligation="관측"` 이 붙는다.

### 예외에 사유가 있다 — 실물 4건

#### 예외 ① `필수` 인데 정본은 `금지사항` (7건)

```
rate_reference_date                금리 기준일자              ← DEP-PRO-01 / LOAN-PRO-01
rate_tax_basis                     세전·세후 구분 표기         ← DEP-PRO-01
preferential_rate_payment_condition 우대금리 지급 시점 조건    ← DEP-PRO-01
interest_calc_method               이자 계산방식              ← DEP-PRO-12
loan_restriction                   대출 제한조건              ← LOAN-PRO-11
multi_loan_limit_notice            복수대출·총한도 제한 안내   ← LOAN-PRO-10
```

**왜 금지사항인데 `필수` 인가.** 이 금지사항들은 *"~하지 않았는가"* 형태이지만 **내용상
"빠뜨리면 안 되는 표기"** 를 요구한다:

```
LOAN-PRO-11: "대출가능 대상이나 자격 또는 담보제공 등 일정한 제한이 따를 수 있는 경우에
              이러한 제한조건을 표기하지 않고 표시하지 않았는가?"
                                  └──────────────┘
                                  ↑ 금지의 대상이 '표기 누락' 이다 = 표기가 있어야 한다
DEP-PRO-12: "복리로 계산되는 상품을 … 구분하지 않고 단순히 '복리식'이라고 표시하지 않았는가?"
                                    └──────┘ ↑ 구분 표기가 있어야 한다
```

**부정의 부정이다.** "표기 안 하는 것을 금지" = "표기해야 함". 그래서 뽑을 값이 **존재하고**
(기준일자·세전세후·제한조건), `필수` 로 둔 것이다.

#### 예외 ② `관측` 인데 정본은 `포함사항`/`형식` (4건)

```
obs_max_rate_only_emphasis  최고금리만 강조 의심  [형식]
   정본[DEP-FMT-01] "글자 색깔·크기 또는 음성 속도·크기 등이 혜택과 불이익을
                     균형 있게 전달하는가?"
obs_min_rate_only_emphasis  최저금리만 강조 의심  [형식]  ← LOAN-FMT-01
obs_rate_basis_vague    이자율 산출기준 불충분 의심  [포함사항]  ← LOAN-INC-06
obs_credit_level_vague  신용수준 요건 불충분 의심   [포함사항]  ← LOAN-INC-05
```

**왜 포함사항인데 `관측` 인가.** 이건 **"있나 없나"가 아니라 "충분한가"** 를 묻는다.

```
LOAN-INC-06 이자율 산출기준을 표시하였는가?
   → 있다/없다는 값으로 뽑을 수 있다 → 그건 interest_rate_range 필드가 필수로 담는다
   → 그런데 "표시는 됐지만 산출기준이 불충분하다" 는 값이 아니라 **정도(程度) 판단**이다
   → 값 필드는 값 필드로, 정도 판단은 별도 관측 필드로 분리
```

`DEP-FMT-01`("글자 색깔·크기가 균형 있는가")은 더 분명하다 — **이게 시인성 항목**이고,
A 단계에서 좌표·글자 크기 정보를 안 넘기고 있으니 **지금은 판정 자체가 불가능하다.**
그래서 "최고금리만 강조 의심"이라는 텍스트 기반 의심 후보로만 수집한다.

> [E 문서](E-남은-일과-정리-후보.md)의 보류 항목과 정확히 이어진다 — 시인성(글자 크기·색·굵기)
> 판정 보류. `DEP-FMT-01`·`LOAN-FMT-01` 이 그 조문상 자리다.

#### 예외 ③ `checklist_ref` 가 없는 30필드 — 근거가 정본이 아니다

```
_overlay_이벤트  G5_이벤트        필수 8 · 수집 3   ← 11개 전부 참조 없음
_common         C4_전수수집       수집 3
_common         C1_주체와상품     수집 1 · 절차 1
예금성/대출성    상품기본·금리수치   필수 5 · 수집 4 · 분류 2 · 권장 1
```

**이벤트 오버레이 11필드가 전부 `checklist_ref` 가 없다.** 이유가 명확하다 — **정본 체크리스트
97항목에 이벤트 항목이 없다.** 대신 이벤트 필드는 `catalog_ref: "event_overlay/event_name"`
로 근거 대장을 가리키고, 대장은 `규칙리스트`(1,721건 보조 대장)와 은행연합회 준수사항을
근거로 쓴다. 그리고 `required_by_rule: true` 라는 다른 표식을 쓴다.

**즉 근거 계층이 2개다.**

| 근거 | 표식 | obligation |
|---|---|---|
| 정본 체크리스트 97항목 | `checklist_ref` | 구분에서 파생 (필수/관측) |
| 근거 대장(규칙리스트 등) | `catalog_ref` + `required_by_rule` | 우리 판단 |

`수집`·`분류` 는 **규정 항목이 아니라 우리 파이프라인이 필요해서 만든 것**이다:
- `수집`(11) — `rate_mentions`·`period_mentions` 같은 **전수수집 배열**. 유실 방지 안전망
- `분류`(2) — `deposit_kind`·`loan_subtype`. 다른 필드의 `applicability` 를 결정하는 축
- `절차`(1) — 광고물 밖의 절차(준법감시인 사전심의 실시 여부)

### 그리고 `obligation` 이 실제로 무엇을 바꾸나 — 코드 한 줄

[applicability.py:52-54](../../src/nh_parsing/applicability.py#L52-L54)

```python
# 판정 대상이 아닌 의무등급 — 분류축(product_subtype), 전수수집 배열(rate_mentions),
# 금지표현 관측(G4), 광고물 밖의 절차(준법감시인 사전심의).
_NON_JUDGED_OBLIGATIONS = {"분류", "수집", "관측", "절차"}
```

모듈 docstring 마지막 줄:

> *"의무등급(`obligation`): **필수 / 권장 은 판정 대상, 분류·수집·관측·절차 는 판정 제외.**"*

즉 `obligation` 은 **"이 필드가 비었을 때 지적 대상이 되나"** 를 가른다:

```
fee_and_cost (필수)      가 비었다  →  지적 후보가 될 수 있다 (applicability 통과 시 '미표시')
obs_superlative (관측)   가 비었다  →  아무 일도 안 일어난다 ('판정제외')
rate_mentions (수집)     가 비었다  →  아무 일도 안 일어난다
```

**이게 왜 중요한가.** 이걸 안 가르면 111필드 중 비어 있는 것 전부가 "지적사항"으로 올라간다.
[extract.py:445](../../src/nh_parsing/extract.py#L445) 에 그 실측 사고가 적혀 있다:

> *"필수 항목 전부를 '미표시 = 심의 지적사항' 6건으로 올린다 — **없는 지적을 만들어내는** …"*

```
근거 대장 (_product_group_fields.json)      ← 사람용. 조문·출처·확인필요
      ↓ 파생 (규정 바뀌면 대장 먼저 고침)

      ↓ 그룹 단위 호출 (10~11회) — 한 번에 물으면 응답이 끊긴다
필드가 채워진 결과 (C 문서)

정본: 심의사례 NH농협은행 준법감시부 1.xlsx / 체크리스트 시트 (97항목)

   → 커버리지 71/97 (BIZ 24는 대상 유형 없음), 미커버 2건은 자유기술 항목
   → 실제 심의사례 20건 역매핑: ID 매칭 100%, 스키마 미커버 0개
```

**B 에서 꼭 잡고 갈 세 가지**

1. **`kind` 는 "실패하는 방식"으로 갈린 것이다** — `verbatim` 은 다듬으면 심의 대상이
   소멸하고, `numeric` 은 OCR 과 VLM 의 실패 방식이 달라 교차검증이 성립하고, `template` 은
   없는 걸 만들면 결과가 뒤집힌다.
2. **`checklist_ref` 가 정본과의 연결선이다** — 이 ID 덕분에 "97항목 중 무엇을 커버하는가"를
   코드로 셀 수 있다. 유령 참조 0건이 그 연결이 살아 있다는 증거.
3. **`obligation` 은 정본 `구분` 에서 파생되지만 기계적 1:1 이 아니다** — 부정의 부정
   (금지사항→필수 7건), 정도 판단(포함사항→관측 4건), 우리 파이프라인용(참조없음 30건).
   그리고 이것이 **"비었을 때 지적 대상이 되나"** 를 가른다.
