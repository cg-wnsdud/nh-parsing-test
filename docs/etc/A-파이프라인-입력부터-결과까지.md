# A. 파이프라인 — 파일 하나가 들어와 결과가 나올 때까지

> 광고물 파일(PDF/PNG/JPG/HWP) 하나가 입력으로 들어와 결과가 나올 때까지 **거쳐 가는 단계**.
> 각 단계마다 ① 무엇을 받아 무엇을 내놓나 ② 왜 필요한가(없으면 뭐가 잘못되나)
> ③ 실제 산출물에서 어디에 보이나 를 적었다.
>
> 이 문서 끝에 **중간에 물어본 3가지**에 대한 답이 있다(A-①②③).

## 0. 전체 그림 — 결과물이 3종이다

입구는 [tools/run_nhdata.py](../../tools/run_nhdata.py), 핵심 함수는
[pipeline.py:32 `process_file()`](../../src/nh_parsing/pipeline.py#L32) 하나다.

| 산출물 | 내용 | 위치 |
|---|---|---|
| `out/json/*.json` | 좌표·신뢰도·출처 전부 담긴 **정밀 기록** | [prototype/out/](../../prototype/out/) |
| `out/llm_view/*.json` | 좌표 다 빼고 **읽기순서 텍스트만** — AI 에게 줄 것 | [prototype/llm_view/](../../prototype/llm_view/) |
| `out/previews/*.jpg` | 원본 위에 상자 그린 **눈으로 볼 검수 이미지** | `out/previews/`, `out_new/previews/` |

### 실제 처리량 (캐시 없는 실행, [out/_timing.json](../../out/_timing.json))

```
파일                              형식   쪽   경로        영역  라인   총초   VLM초  VLM호출
올원e적금.png                    image   1    ocr         50    79   107.9  102.0    12
NH농협은행-2026_001-예금성.pdf     pdf    1    ocr         76   192   181.9  177.1    23
NH농협은행-2026_002-예금성.png   image   1    ocr         53    98   113.5  108.1    13
NH농협은행-2026_003-예금성.pdf     pdf    3    hybrid+ocr  61   130   301.1  296.8    18
NH농협은행-2026_004-대출성.hwp     hwp    1    digital      1    12     1.7    0.0     0
```

**여기서 두 가지가 이미 보인다.**
① 시간의 95% 이상이 VLM(AI) 대기다 — 우리 코드가 느린 게 아니다.
② **HWP 는 VLM 을 한 번도 안 부른다**(1.7초). 이유는 1번 항목.

## 1. 갈림길 — 파일 확장자로 세 길이 갈린다

[pipeline.py:32-43](../../src/nh_parsing/pipeline.py#L32-L43)

```
.hwp/.hwpx  → _process_hwp    (사내 파서가 텍스트를 그대로 준다)
.png/.jpg   → _process_image  (그림밖에 없으니 OCR 직행)
.pdf        → _process_pdf    (안을 들여다봐야 안다 → 3번 triage)
그 외        → parse_status="unreadable" 로 기록하고 종료
```

**왜 갈라야 하나.** HWP 는 워드프로세서 파일이라 "이 문자가 여기 있다"는 정보가 파일 안에
이미 들어 있다. PNG 는 픽셀뿐이라 글자를 **다시 알아내야** 한다. 같은 길로 보내면 HWP 에서
이미 정확히 아는 글자를 OCR 로 다시 틀리게 읽는 손해가 난다.

### 실물 — HWP 결과 ([out/json/NH농협은행-2026_004-대출성.json](../../out/json/NH농협은행-2026_004-대출성.json))

```
page: parse_route='digital', canvas_w=0, canvas_h=0, regions=1
region p1_r000: bbox=None, label='hwp_body'
  lines: digital / bbox=None / '준법감시인 심의필 2026-0000 (2026.00.00.~2027.00.00.)'
         digital / bbox=None / '대출금리 | 최저 연 4.45% ~ 최대 연 5.45% ...'
```

**`bbox` 가 `None` 이고 `canvas` 가 0×0 이다.** 그림이 없으니 좌표가 없고, 좌표가 없으니
뒤에 나오는 타일링·카드분할·밴드통독이 **전부 건너뛰어진다**(그 단계들은 모두 이미지를
필요로 한다). 그래서 VLM 호출 0회, 1.7초.
`label='hwp_body'` 는 [hwp_ingest.py:328](../../src/nh_parsing/hwp_ingest.py#L328) 에서
붙인 것 — 페이지 전체가 통짜 영역 1개다.

> ⚠️ **이게 나중에 문제가 된다.** 좌표가 없으면 "이 문구가 화면 어디에 있나"를 못 말한다.
> 농협 심의는 "작은 글씨로 숨겼나"(시인성)를 보는데 HWP 경로는 지금 그 근거를 못 낸다.
> → [E 문서](E-남은-일과-정리-후보.md) 보류 항목.

## 2. 캔버스 — 모든 좌표의 기준자

[canvas.py](../../src/nh_parsing/canvas.py)

**용어**: "캔버스"는 그 페이지를 그림 한 장으로 펼친 것. 이후 모든 `bbox`(상자 좌표)는
**이 그림의 픽셀 좌표** — `[왼쪽x, 위쪽y, 오른쪽x, 아래쪽y]`, 원점은 왼쪽 위.

- PNG/JPG → 파일 그대로가 캔버스
- PDF → 200 DPI 로 그림으로 뽑음 ([config.py:93](../../src/nh_parsing/config.py#L93) `pdf_render_dpi=200`)

**실물**
- `1. 예금성상품(적립식).pdf` → `canvas_w=1654, canvas_h=2339, dpi=200`
- `올원e적금.png` → `canvas_w=1122, canvas_h=6429, dpi=None` (원본 PNG 라 DPI 개념 없음)

**예외 하나** ([pipeline.py:91-94](../../src/nh_parsing/pipeline.py#L91-L94)):

```python
dpi = None
if verdict.verdict in ("scan_like", "hybrid"):
    dpi = native_image_dpi(pdf_page)
```

스캔 문서는 PDF 안에 이미 사진이 박혀 있다. 그걸 200 DPI 로 다시 렌더하면 **없는 해상도를
늘려 뿌옇게 만드는** 셈이라, 박혀 있는 원본 해상도를 찾아 그대로 쓴다.

## 3. `parse_route` — 세 갈래인데 실제로는 두 갈래다

### 3-a. triage(3판정)는 여전히 돈다

[triage.py:101 `triage_page()`](../../src/nh_parsing/triage.py#L101) — PDF 페이지마다 4가지를
재서 판정한다.

| 신호 | 임계 | 뜻 |
|---|---|---|
| 글자수 | ≤20자 → `scan_like` | 텍스트 레이어가 사실상 비었다 |
| U+FFFD(`�`) 비율 | ≥8개 & ≥30% → `scan_like` | 인코딩이 깨졌다 |
| 정상문자 비율 | ≤10% → `scan_like` | PUA(사설영역 — 글꼴이 실제 문자 대신 자기만 아는 임의 코드로 텍스트를 저장해, 다른 프로그램은 깨진 글자로 읽는 경우) 난독 폰트 |
| 이미지 면적비 | ≥50% → `hybrid` | 텍스트는 정상인데 그림이 화면을 덮었다 |

**실측 89문서 PDF 페이지 분포**: `structured 29 · hybrid 11 · scan_like 9`

### 3-b. 그런데 `parse_route` 에는 이제 `digital` 이 안 찍힌다

[pipeline.py:99-128](../../src/nh_parsing/pipeline.py#L99-L128) 에서 `structured` 와
`hybrid` 가 **같은 처리**를 받고, route 는 둘 다 `"hybrid"` 로 통일된다.

**왜 바꿨나** (주석 [pipeline.py:100-114](../../src/nh_parsing/pipeline.py#L100-L114) 의 실측):

예전엔 "디지털 텍스트가 이미 있으면 무거운 레이아웃 검출을 부를 필요 없다"고 건너뛰었다.
그런데 절약분은 **StructureV3 호출 하나(3.67초)** 뿐이었고, 대신 **가로 인식을 통째로
잃었다.** 레이아웃 블록이 없으면 [`_pseudo_regions`](../../src/nh_parsing/pipeline.py#L765)
폴백이 도는데 그건 세로 간격만 본다 → 좌우 2단 페이지가 한 덩어리로 뭉친다.

> 실측 2026-08-14, `6. 대출성상품.pdf` p1: 라벨 5줄(원금및이자상환방법~신청채널)이
> **한 영역 27줄로 뭉쳤다**

**코드로 확인한 `digital` 의 유일한 출처 — HWP 뿐이다**

```
$ grep -rn "parse_route" src/
hwp_ingest.py:300   parse_route="digital"   ← unreadable HWP
hwp_ingest.py:320   parse_route="digital"   ← 정상 HWP
pipeline.py:42      parse_route="ocr"       ← 미지원 확장자
pipeline.py:81      parse_route="ocr"       ← pdfium 실패
pipeline.py:754     parse_route=route       ← "ocr" 또는 "hybrid"
```

**89문서 산출물 전수**: `(pdf, hybrid) 40쪽 · (pdf, ocr) 9쪽 · (image, ocr) 48쪽` —
`digital` 0쪽.

**정리**: `parse_route` 는 "OCR 을 불렀는가 + 디지털 텍스트를 썼는가"만 말하는 3값이고,
진짜 3갈래 판정 근거는 `page.triage` 에 따로 남는다.

```json
"triage": {"verdict": "hybrid", "char_count": 1081, "korean_count": 760,
           "fffd_count": 0, "image_area_ratio": 1.0, "path_count": 108,
           "reasons": ["텍스트 레이어 정상이지만 이미지 면적비 100% — 이미지 영역 OCR 병행"]}
```

### 3-c. 다섯 번째 신호 — 잉크 커버리지

[bands.py:317 `ink_coverage()`](../../src/nh_parsing/bands.py#L317).
이게 왜 필요했는지가 이 프로젝트에서 제일 교훈적인 사례다.

기존 4개 신호는 전부 **"뽑힌 글자가 이상한가"** 만 본다. 글자가 **아예 안 뽑히는** 경우는
글자수 하한(20자)으로 거르는데 — 심의필 도장처럼 몇 줄만 진짜 텍스트면 그 하한을 넘긴다.

> `2. 예금성상품(입출식).pdf` p1: 124자(심의필 문구 + 숫자 파편)로 `structured` 판정 →
> OCR 생략 → **예금자보호법·금융소비자보호법 등 의무고지 14개 문구가 통째로 유실**
> 외부 파서(kordoc 4.7.3)로 돌려도 `totalTextChars: 124, needsOcr: false` 로 **똑같이
> 오판** — 글자 수를 세는 지표로는 구조적으로 못 잡는다

`ink_coverage` 는 "화면에 글자처럼 보이는 픽셀 중 텍스트 레이어가 설명하는 비율"을 잰다.

**임계 30% 가 1건 과적합이 아닌 근거**: structured 29쪽 전부 계산했더니 **2.5%(그 파일)
다음이 56.3%** — 사이 53.8%p 가 비어 있어 5~50% 어디에 그어도 같다.

## 4. 타일링 — 세로로 긴 그림을 자른다

[tiling.py:23 `make_tiles()`](../../src/nh_parsing/tiling.py#L23) → 실제 자르기는
[bands.py:175 `content_bands()`](../../src/nh_parsing/bands.py#L175)

**왜 자르나.** 모바일 상품 상세페이지는 세로로 아주 길다(올원e적금 = 1122×**6429**px).
OCR 검출기는 긴 변을 2500px 로 줄여서 본다 → 6429px 를 통짜로 보내면 **0.39배로 축소**되어
작은 글씨(fine-print)가 사라진다. 유의사항이 전부 fine-print 인데 그게 사라지면 심의를
할 수 없다.

**자를지 말지는 높이가, 어디서 자를지는 글자 밀도가 정한다.**

- 트리거: 높이 4000px 초과 ([config.py:104](../../src/nh_parsing/config.py#L104))
- 조각 높이 상한: 1600px, 오버랩 200px

**"글자 밀도"가 무슨 뜻인가.** 산술로 1600px 마다 자르면 조각마다 담기는 글자량이 2.3~3.4배
차이 나고, 컷이 **글자 한가운데를 지난다**(001 실측: 112px 크기 '20,000원' 이 반토막).
잘린 글자는 양쪽 조각 어디에서도 안 읽혀 사라진다.

그래서 ① 글자량을 n등분하는 지점을 목표로 잡고 ② 그 근처에서 **글자가 없는 행**으로
컷을 옮긴다(스냅, ±160px 안).

**"글자"를 어떻게 재나 — 밝기가 아니라 에지.**
[bands.py 상단 주석](../../src/nh_parsing/bands.py#L6-L9):

> '어두운 픽셀 = 글자'로 재면 색 배경이 깔린 광고에서 전부 잉크로 잡혀 무의미해진다
> (001 실측: 글자 없는 행이 6554행 중 **121행=2%**). 글자의 특징은 어둡다는 게 아니라
> **국소 대비가 크다**는 것이라, 가로 방향 밝기 변화량으로 재면 배경색과 무관해진다
> (같은 001 에서 **31%**)

**조각 높이 상한이 왜 필수인가** — 글자량만 맞추면 성긴 구간이 2000px 넘는 조각이 되고,
레이아웃 검출이 블록을 거칠게 묶는다.

> 상한 없이: 002 레이아웃 블록 84→62 로 줄고, '최고연 7.1%' 를 담던 작은 영역이 큰 영역에
> 흡수돼 통독 후보가 부실해짐
> 상한 걸면: 조각 15→24장으로 늘지만 블록 332→360, 골드 회수 138→139 — **손실 없이 개선**

**실물**
- `올원e적금.png` 노트 → `"타일 9개 처리 (오버랩 200px)"`
- `1. 예금성상품(적립식).pdf`(2339px) → `"타일 1개 처리"` (4000px 미달 → 안 자름)

## 6. 디지털 텍스트 합치기 — 정본의 우선순위

PDF 의 `structured`/`hybrid` 페이지는 **두 출처**가 있다: 파일 안의 디지털 텍스트(정확) +
OCR(추정). [pipeline.py:723 `_merge_digital_ocr()`](../../src/nh_parsing/pipeline.py#L723)
가 **디지털을 먼저 깔고, 그와 겹치는 OCR 라인을 버린다.**

겹침 판정에 두 가지를 쓴다 — IoU(두 상자가 겹치는 정도. `교집합 면적 ÷ 합집합 면적`,
0이면 안 겹침·1이면 완전히 겹침) 0.5 **또는** 포함비 0.5. 왜 IoU 만으론 안 되나:

> 실측 2026-08-13: 표 한 셀을 디지털은 `"가입대상개인"` 하나로, OCR 은 `"가입대상"`+`"개인"`
> 둘로 읽으면, 디지털 상자가 OCR 상자 둘 다를 품는데도 IoU 는 0.48·0.24 — **둘 다 살아남아
> 중복**. 포함비로 재면 0.69·0.58 로 분명하다.
> 165건 전부(크기비 1.0~69.1배) 확인 결과 오탐 0 — 가장 극단(69배)도 OCR 이 `※` 하나만 읽고
> 디지털이 그 문장 전체를 읽은 **진짜 중복**이었다

### 디지털 텍스트 뽑는 법 자체에도 함정이 있었다

> ⚠️ **2026-08-23 갱신**: 이 절이 설명하는 "글꼴칸/잉크칸" 방식은 **지금은 주 경로가 아니라
> 폴백**이다. 이 문서 작성(8/20) 다음 날 커밋 `a74c0e4`가 주 경로를 PDF 자체의 구조(TEXT
> 런의 베이스라인·세로 벡터 구분선)로 줄 소속을 정하는 방식으로 바꿨다 — 그 구조를 못 읽는
> PDF만 아래 방식으로 폴백한다. 새 방식의 상세는 [triage.py:449
> `extract_digital_lines()`](../../src/nh_parsing/triage.py#L449)의 `_text_runs()`·
> `_vertical_dividers()`·`_lines_from_runs()`를 보라. 아래는 **폴백 경로 설명**으로 읽어라.

글자를 줄로 묶을 때 **글꼴칸**(loose)을 쓰고 좌표는 **잉크칸**(tight)을 쓴다.

> 잉크칸은 글자마다 높이가 제각각(같은 줄에서 `ㆍ` 5.3px vs `임` 25.8px) → 키 큰 글자가
> 윗줄에 흡수됨. 실측 `7. 대출성상품.pdf` p1: `필`(28.7)이 윗줄 `임`(25.8)과 51.6% 겹쳐
> 흡수, `류`·`요` 는 46~49%로 탈락해 **`필요서류` → `필서` + `요류`**
> 글꼴칸은 글꼴 메트릭이 정하므로 같은 줄 글자가 전부 같은 상자(`필요서류` 넷 다
> 1916.3~1948.9)

표 칸도 갈라야 한다 — 세로 위치가 같아 한 줄로 합쳐지므로 **평균 글자폭의 4배** 이상
벌어진 자리에서 쪼갠다(실측: 정상 낱말 간격 최대 2.2배 vs 표 칸 경계 5.6~19배 — 사이가
비어 있다). **이 gap_limit 임계값이 지금은 문제의 근원이기도 하다** — 라벨/값 칸이 붙어
있는 경우(간격 26px)는 4배 임계값(약 107px)에 한참 못 미쳐 안 갈린다. 임계값을 낮추면
정상 낱말 사이가 쪼개지므로 단순 조정으로는 못 고친다.

**실물** (`1. 예금성상품(적립식)` p1): 영역 안 라인 **digital 52 · ocr 7**, 미배정 **ocr 3**.
89문서 전수로는 **ocr 4661 · digital 2321 · vlm_sweep 378**.

## 7. 영역(Region)과 줄(Line) — 이 구분이 전부의 기초

- **줄(Line)** = OCR/디지털이 검출한 글자 덩어리 하나. 반드시 한 시각적 줄은 아니다 —
  OCR 은 한 줄을 여러 상자로 쪼갠다.
- **영역(Region)** = 레이아웃 블록 하나에 줄들을 담은 것. **"이 문구가 누구 소속인가"** 를
  정하는 단위이고, **심의 근거를 지목하는 단위**다.

[regions.py:81 `build_regions()`](../../src/nh_parsing/regions.py#L81) 가 배정한다.
**줄 면적의 50% 이상이 영역과 겹쳐야** 그 소속이다
([regions.py:78](../../src/nh_parsing/regions.py#L78)).

**왜 중심점이 아니라 겹침 면적인가:**

> 예전엔 줄 중심점이 영역 안에 있나만 봤다. 표 칸이 한 줄로 합쳐진 경우 중심점이 어느 칸에
> 찍히느냐에 따라 통짜 줄 전체가 엉뚱한 영역에 붙었다 — 올원 p1_r006 실측: 오른쪽 칸
> `'가입금액100만원이상'` 이 왼쪽 영역에 붙음

## 8. 역할 판정 — 규칙이 초기값, VLM 이 결정

**역할(role)** = 이 영역이 화면에서 뭐냐. 9종:
`제목·본문·유의사항·각주·버튼·고지문구·표·이미지·기타`

**2단 구조다.**

1. **규칙** ([regions.py:153 `_apply_role_rules()`](../../src/nh_parsing/regions.py#L153)) —
   레이아웃 라벨 매핑 + 정규식 3개(`유의사항|알아두|꼭확인|주의사항` / `심의필 제0000-000` /
   하단 20% 본문 → 유의사항)
2. **VLM** ([vlm_judge.py:93 `judge_region_roles()`](../../src/nh_parsing/vlm_judge.py#L93)) —
   페이지당 **1회 호출**로 영역 전체를 판정하고 규칙 값을 **덮어씀**

**규칙 판정은 지워지지 않고 `role_rule` 에 스냅샷으로 남는다.** 왜 남기나:

> 지금까지는 VLM 이 성공하면 규칙 판정이 흔적 없이 사라져 **"규칙과 VLM 이 어디서 몇 건
> 갈리는가"를 잴 수가 없었다** (총계 97.3% 일치만 알았다)

**부분 실패를 소리 나게 만든 사례**
([pipeline.py:221-230](../../src/nh_parsing/pipeline.py#L221-L230)): VLM 이 정상 응답하면서
일부 영역을 빠뜨리면 그 영역은 **조용히** 규칙 폴백 값을 유지했고 노트에 아무것도 안 남았다.
이제 `"VLM 역할 판정 부분 응답: N개 중 M개만"` 을 남긴다.

> 실측 2026-08-05, 글자 있는 영역 201개 전수: VLM 적용 199 · 폴백 2. 그 2 중 하나는
> HWP(캔버스 없어 안 부름) → **진짜 부분 응답은 1건**. 규모가 작아 이건 결함 수정이 아니라
> **예방**이다

### 사라진 계층 하나 — 섹션

"섹션"(의미 묶음: 헤드라인/경품안내/참여방법)은 2026-08-03 에 제거했다.
[vlm_judge.py:23-41](../../src/nh_parsing/vlm_judge.py#L23-L41) 의 이유 셋:

> ① **흔들린다** — 같은 입력 2회에 4문서 중 3문서 불일치(001 11↔10, 002 13↔12, 올원e 10↔9).
> 다른 VLM 단계는 다 검산이 있는데(카드=밀도 관측, 낱줄=좌표 게이트, 통독=관계 라벨)
> 여기만 VLM 답을 그대로 썼다
> ② **받는 쪽에 자리가 없다** — 후속 계약이 문서→페이지→블록 3층
> ③ **파싱의 일이 아니다** — 광고의 의미 해석이지 글자를 어떻게 읽었나가 아니다

## 9. 카드 분할 — 개수는 코드, 배정은 VLM

**문제**: 좌우로 나란한 카드(003 의 EVENT1/EVENT2)가 있으면, y좌표만으로 정렬하면
**두 카드 문장이 한 줄씩 번갈아** 나온다. 읽기 순서가 망가진다.

[cards.py](../../src/nh_parsing/cards.py) 의 역할 분담:

| | 담당 | 근거 |
|---|---|---|
| 카드 **개수·경계** | 코드 (픽셀 글자밀도, [bands.py:359](../../src/nh_parsing/bands.py#L359)) | 003 3페이지의 3/2/1 을 **모델 호출 0회**로 정확히 맞힘 |
| **배정**("이 영역이 몇 번 카드냐") | VLM | 전폭 헤드라인은 어느 컬럼에도 안 속해 좌표로 못 정함 |

**"가장 넓은 빈틈이 경계"는 틀렸다** — 003 p2 에서 가장 넓은 566px 빈틈이 카드 경계가
아니었다. 넓이가 아니라 **양쪽 덩어리의 글자량**으로 판단한다:
진짜 카드 28~59% vs 아닌 것 0~4.4%.

**게이트 두 개로 호출 자체를 막는다.**
- 캔버스 종횡비(높이/폭) ≥ 2.0 → **긴 스크롤**이라 카드 아님 (올원e 를 4카드로 쪼갠 실측 있음)
- 밀도로 1덩어리면 안 부름

밀도 관측은 **정답이 아니라 증거로** 프롬프트에 붙는다
([cards.py:64](../../src/nh_parsing/cards.py#L64)):
*"다만 이건 글자가 몰린 자리를 센 것이라 틀릴 수 있습니다 — 화면을 보고 다르다고 판단되면
다른 개수로 답하세요."*

**서로 엇갈리는 관측 둘을 다 적어주는 경우도 있다**
([cards.py:76](../../src/nh_parsing/cards.py#L76)) — 전체 폭으로는 1덩어리인데 일부 구간에서만
좌우 분리가 보일 때. 이 신호는 **'진짜 카드'와 '단일 상품의 2단 표'를 못 가르므로** 둘 다
적어 VLM 이 판단하게 한다.

`card_no` 는 `1..N`=카드(위→아래·좌→우), `0`=페이지 공통(배너/헤더), `null`=미적용.

## 10. 밴드 통독 — 이 프로젝트의 핵심 설계(B안)

[pipeline.py:850 `_merged_band_read()`](../../src/nh_parsing/pipeline.py#L850) +
[vlm_direct.py:549 `read_band_regions()`](../../src/nh_parsing/vlm_direct.py#L549)

**"밴드"** = OCR 에 준 것과 **같은 조각**. 그 조각 이미지 1장 + 그 안 영역 목록을 함께
보내 **두 가지를 한 번에** 묻는다.

1. **regions** — "이 영역들을 다시 읽어 고쳐라" (원문자가 숫자에 붙음 `10.1%p`→`① 0.1%p`,
   소수점 소실 `71%`→`7.1%`)
2. **missing** — "이미지엔 보이는데 목록에 없는 문구를 찾아라"

**호출 절감 실측** (2026-07-28, 5문서): 예전엔 영역별 통독 60회 + 밴드 스윕 15회 = 75회를
서로 다른 크롭으로 두 번 훑었다. 합치니 **VLM 122→65회(-47%), 파싱 37.2→12.2분(-67%)**
이고 골드 문장 234~235→**236/242**, STAGE_3 필드 **44/44 유지**.

### ⭐ 가장 중요한 대목 — 정본과 후보

**VLM 판독은 OCR 정본을 절대 덮지 않는다.** `region.vlm_reading` 에 **후보로만** 붙는다
([ir.py:61-71](../../src/nh_parsing/ir.py#L61-L71)). 이걸 "B안"이라 부른다.

**왜.** 예전엔 대입했는데, VLM 이 실행마다 다른 것을 회수하므로 **정본이 실행마다
흔들렸다**:

> 같은 코드·같은 입력 2회 실측(2026-08-03): 정본 484줄 중 2줄이 갈렸고 그 2줄이 전부 이
> 경로였다 (002 `'이벤트 기간'` ↔ `'이벤트 기간內'`, 올원e `'20.2%p:...'` ↔ `'② 0.2%p : ...'`)

**최종 텍스트 선택은 STAGE_3(스키마 추출)가 한다.** 파싱은 정본과 후보를 **둘 다 남길 뿐**
조용히 대체하지 않는다.

### 후보에 붙는 딱지 3종

[pipeline.py:330 `_score_reading_candidates()`](../../src/nh_parsing/pipeline.py#L330)

| 딱지 | 뜻 |
|---|---|
| `vlm_reading_score` | 후보가 정본 대비 얼마나 정확한가 (정밀도) |
| `vlm_reading_coverage` | 후보가 정본 내용을 얼마나 담았나 (재현율) |
| `vlm_reading_relation` | `same` / `tail_cut`(뒤 잘림) / `head_drop`(앞 생략) / `expanded`(더 읽음) / `diverged`(내용 자체가 다름 — 어느 쪽이 맞는지 여기서 못 정함) / `overflowed`(범람) |

**점수만으론 안 되는 이유**: 토큰 겹침이라 **순서를 못 본다** — 뒤가 잘린 판독이 정밀도
만점을 받는다(실측 5건). 그래서 관계 라벨을 따로 붙인다.

**딱지를 매기는 시점이 중요하다.** 밴드 판독 직후가 아니라 **정본이 확정된 뒤**다.

> 실측 2026-08-06, 5문서 177건 중 7건이 뒤집혔다:
> [밴드 판독 시점] 정본 `'12 개월 가입기간'` → 후보 `'12 개월'` 위치 0 →
> **`tail_cut` "뒷부분 50% 소실"** ← 틀린 딱지
> [최종 정렬 후] 정본 `'가입기간 12 개월'` → 후보 위치 4 →
> **`head_drop` "앞 항목명 생략, 값은 온전"** ← 맞는 답
> 거짓 '잘림 경보'가 위험순 정렬로 "확인 필요" 목록 맨 위에 올라와 검수자가 먼저 보던 자리다

### 범람(overflowed) 탐지

[pipeline.py:286](../../src/nh_parsing/pipeline.py#L286) — VLM 이 분배 지시를 무시하고 밴드
전체 판독문을 **목록 첫 항목에 통째로** 넣는 사고:

> 실측 2026-08-13, 89문서: 범람 13건 중 **12건이 자기 밴드 요청목록의 첫 항목**
> `12. 카드상품` p1_r000 은 121×113px SNS 게시자 표시(자기 3줄 20자)인데 후보에 페이지

## 11. `source` 3종과 스윕 — 실행마다 흔들리는 층

`Line.source` 는 이 줄을 **누가 읽었나**다 ([ir.py:16](../../src/nh_parsing/ir.py#L16)).

| `source` | 누가 | 좌표 정밀도 | 재현성 |
|---|---|---|---|
| `digital` | 파일 안 텍스트 레이어 | 정밀 | **항상 같음** |
| `ocr` | PP-StructureV3 | 정밀 | **항상 같음** |
| `vlm_sweep` | VLM 이 "이미지엔 있는데 목록에 없다"고 회수 | **근사**(밴드 기준 추정) | **실행마다 다름** |

> 주석에 검증 기록이 있다: *"예전에는 `vlm`·`vlm_region` 도 있었는데 B안 전환 이후 대입되는
> 코드가 없어졌다 — **지우기 전 전수 확인함**"*

**스윕이 2종 있다**: ① 밴드 통독의 `missing` ② 통짜 캔버스 1회 — 밴드가 원래 못 잡는
**대형 장식 타이포**용(002 '행운의 777 이벤트').

# 중간에 물어본 것 3가지

## A-① HWP 가 들어올 때 StructureV3 로 레이아웃을 잡나?

### 답: 안 잡는다. `digital` 이 안 찍히는 것은 **PDF 에만** 반영된 변경이다.

**HWP 경로에는 StructureV3 를 부를 지점이 아예 없다.**
[hwp_ingest.py:204-255](../../src/nh_parsing/hwp_ingest.py#L204-L255) 흐름 전체:

```
사내 파서(DocIR.from_file) → docir.paragraphs 순회
    문단 텍스트     → Line(source="digital", bbox 없음)
    TableIR 발견 시 → _tables_to_lines() 로 '라벨 | 값' 평문 줄로 눌러서 Line 추가
        ↓
Region(region_id="p1_r000", label="hwp_body") 하나에 전부 담음
        ↓
내장 이미지만 따로 image_page_processor 로 → PNG 와 같은 OCR/VLM 트랙 (p2, p3…)
```

StructureV3 를 부르려면 이미지가 필요한데 이 경로엔 이미지가 없다. PDF 는
`render_pdf_page()` 로 그림을 만들지만 HWP 는 만드는 코드가 없다. 코드에 그 사실이 노트로
남아 있다 ([hwp_ingest.py:322-325](../../src/nh_parsing/hwp_ingest.py#L322-L325)):

> `"HWP 디지털 추출 — bbox 없음. 시각 검토(F-011/F-013)용 렌더링은 설계서 6.8 옵션
> (R1: LibreOffice 변환 등) 확정 후 별도 처리"`

### "레이아웃 잡고 각 칸에 파서 텍스트 넣기" — 그게 정확히 지금 PDF 가 하는 일이다

`hybrid` route 의 정의다:

```
구조(어디가 표이고 어디가 제목인가) ← StructureV3 레이아웃 블록
값  (그 칸에 무슨 글자가 있나)      ← 디지털 텍스트가 정본, OCR 은 안 겹치는 것만 보충
```

[pipeline.py:115-128](../../src/nh_parsing/pipeline.py#L115-L128)

```python
digital = extract_digital_lines(pdf_page, canvas.px_per_pt)   # 파서가 준 텍스트
...
page = _ocr_canvas_to_page(canvas, page_no, extra_digital=digital, route="hybrid")
                                            # ↑ 이걸 StructureV3 블록 칸에 넣는다
```

**`digital` 이 안 찍히는 이유가 정확히 이 변경이다.** 같은 문서 3페이지 전후 실측:

```
                        003 p3 (structured 판정 페이지)
run1 (08-14 이전)   route=digital   ocr=  0  digital=25   ← StructureV3 안 불렀다
run2 (08-14 이후)   route=hybrid    ocr=  7  digital=25   ← 부르고 칸에 넣었다
현재 out/           route=hybrid    ocr=  7  digital=25
```

### HWP 에도 하려면 — 여기서 목적을 갈라야 한다

**"레이아웃을 잡는다"에 두 목적이 섞여 있다.**

| 목적 | HWP 에 지금 있나 | 필요한 것 |
|---|---|---|
| **구조** (여기가 표, 여기가 제목) | ✅ **이미 있다** — 파서가 문단/`TableIR` 로 정확히 준다 | StructureV3 **불필요**. 지금 코드가 그 구조를 **버리고 있는 것**이 문제 |
| **좌표** (그 문구가 화면 어디에) | ❌ 없다 (`bbox=None`) | HWP → 이미지 렌더러가 있어야 함. 현재 없음 |

**StructureV3 는 "그림에서 구조를 추정하는" 도구다.** HWP 는 추정할 필요가 없다 — 파일 안에
정답이 들어 있다. 그래서 **HWP 를 렌더해서 StructureV3 로 다시 추정하는 것은 정답을 갖고
있으면서 추정으로 바꾸는 셈**이다(더 나빠질 수 있다).

**지금 실제 결함은 이쪽이다** — 004 산출물:

```
regions: 1개  (p1_r000, label='hwp_body')
  lines: 12줄 전부 여기 들어 있음
    'digital / 대출대상 | 공무원(3개월이상 재직 중)'   ← 표가 '라벨 | 값' 평문으로 눌렸다
```

PDF 는 영역 25~76개로 갈라져 **"이 지적은 p1_r018 에 있다"** 고 근거를 지목할 수 있는데,
HWP 는 영역이 1개라 **"이 문서 어딘가"** 밖에 못 말한다. 파서가 준 문단·표 구조를 그대로
영역으로 만들면 StructureV3 없이도 해결된다.

**표를 표로 넘기는 함수는 이미 있다** —
[hwp_ingest.py:369 `table_to_html()`](../../src/nh_parsing/hwp_ingest.py#L369). 다만 농협 KL
출력용으로만 쓰이고 광고물 파싱 경로에서는 안 쓴다. 주석에 그 사실이 적혀 있다:

> *"그런데 우리는 `_tables_to_lines()` 로 표를 행 단위 평문(`'용어 | 설명'`)으로 눌러 왔다.
> **구조를 이미 갖고 있는데 버리고 있었던 것**"*

**좌표(bbox) 복원은 여전히 보류 항목이다** — `region p1_r000: bbox=None` (위 §A-①) 그대로다.
이건 StructureV3 같은 좌표 검출기를 HWP 경로에 붙이는 별개 작업이라 아직 손대지 않았다.

> ⚠️ **2026-08-23 갱신**: 다만 같은 문단에 섞여 있던 **시인성(글자 크기·색·굵기) 쪽은 이미
> 해결됐다.** 이 문서 작성(8/20) 다음 날 커밋 `813027a`가 `RunIR.run_style` 을
> `Line.style` 에 채워 넣었다 — "코드가 버리고 있다"는 더 이상 사실이 아니다. 남은 건
> 좌표 복원뿐이다. (실측: 004 대출성 run 141개 전부 스타일 있음, 크기 19종·색 7종.)

## A-② "좌표 복원·영역 조립" — 무엇이 분해됐고 무엇을 조립하나

### 헷갈리는 이유: **서로 다른 두 가지가 같은 "조립"이라는 말에 묶여 있다.**

| | 무엇이 나뉘었나 | 무엇을 되돌리나 | 함수 |
|---|---|---|---|
| **①좌표 복원** | **이미지**를 조각으로 잘랐다 | 조각 안 좌표 → 원본 캔버스 좌표 | [`restore_coords`](../../src/nh_parsing/tiling.py#L51) |
| **②영역 조립** | 아무것도 안 나뉘었다 | **처음부터 흩어져 있던 줄들**을 묶는다 | [`build_regions`](../../src/nh_parsing/regions.py#L81) |

②는 "분해된 것을 되돌리는" 게 아니다. OCR 은 원래 **줄 단위로 흩어진 결과**를 주고, 그걸
"누구 소속인가"로 묶는 것이 처음 있는 조립이다.

### ① 좌표 복원 — 실제 숫자로

올원e적금 PNG(1122×6429)를 실제로 잘라 본 결과:

```
캔버스 (1122, 6429) → 조각 9개
  조각0: y_offset=    0   높이=1575   원본구간 y    0~1575
  조각1: y_offset= 1375   높이=1333   원본구간 y 1375~2708
  조각2: y_offset= 2508   높이= 632   원본구간 y 2508~3140
  조각3: y_offset= 2940   높이= 638   원본구간 y 2940~3578
  조각4: y_offset= 3378   높이= 949   원본구간 y 3378~4327
  조각5: y_offset= 4127   높이= 750   원본구간 y 4127~4877
  조각6: y_offset= 4677   높이= 555   원본구간 y 4677~5232
  조각7: y_offset= 5032   높이= 617   원본구간 y 5032~5649
  조각8: y_offset= 5449   높이= 980   원본구간 y 5449~6429
```

**여기가 핵심이다.** OCR 서버는 조각 하나를 **독립된 그림 한 장**으로 본다. 조각5를 보낼 때
서버는 그게 원본 y=4127 에서 잘려 나왔다는 걸 **모른다**. 그래서 조각5 맨 위 글자를
`y=16` 이라고 돌려준다.

그대로 쓰면 **원본 맨 위(y=16)에 있는 것으로 오해**된다. 그래서 `y_offset`(4127)을 더해서
되돌린다 — 이게 "복원"이다.

**실물로 확인한 3줄** (오버랩 구간 y 4127~4327):

```
최종 y=4143  (p1_r032)  '중도해지이율 및 만기 후 이율 : NH농협은행 영업점 및'
   → 조각5가 봤을 때는 y=  16  (4143 - 4127)
   → 조각4가 봤을 때는 y= 765  (4143 - 3378)   ← 같은 글자가 다른 숫자!

최종 y=4205  (p1_r030)  '홈페이지에 고시한 이율'
   → 조각5 기준 y= 78 / 조각4 기준 y=827

최종 y=4289  (p1_r033)  '<만기 시 예상 수취이자 예시>'
   → 조각5 기준 y=162 / 조각4 기준 y=911
```

**같은 글자가 조각마다 다른 숫자로 보고된다.** 그걸 하나의 기준자(원본 캔버스)로 통일하는
것이 복원의 전부다.

### ①-b 그리고 복원하면 중복이 생긴다

조각4는 3378~4327, 조각5는 4127~4877 — **4127~4327 의 200px 는 둘 다 봤다.** 그래서 위
3줄은 **두 번 검출된다.**

**왜 일부러 겹치게 자르나.** 안 겹치게 자르면 경계에 걸친 글자가 **양쪽 조각 어디에서도
온전히 안 읽힌다.** 반토막 난 글자는 OCR 이 못 읽고 사라진다. 겹쳐 두면 최소 한 조각에는
온전히 담긴다.

**중복 제거**([tiling.py:113](../../src/nh_parsing/tiling.py#L113))는 **텍스트가 같은지
안 본다.** 위치 겹침만 본다. 경계에서 잘린 텍스트는 같은 자리에 **다른 글자로** 다시
검출되기 때문이다(`'수 있는 권리가 있습니다.'` 0.99 vs `'7리콘극'` 0.6). 텍스트로 비교하면
이 둘은 "다른 줄"로 판정돼 **둘 다 살아남는다.**

### ② 영역 조립 — 흩어진 줄을 묶기

이 시점의 손에 있는 것:

```
줄 목록:  79개   ('중도해지이율 및…' @ [x,4143,x,4167], …)  ← 좌표는 이제 전부 원본 기준
블록 목록: 50여개 ('table' @ [40,4100,1080,4320], 'text' @ …)
```

**둘은 완전히 별개 결과다.** 줄은 "글자 인식"이 준 것, 블록은 "레이아웃 검출"이 준 것 —
같은 서버가 주지만 서로 모른다. `build_regions` 가 **좌표만 보고** 짝지어 준다:

```
각 줄에 대해:
   이 줄 면적의 50% 이상이 어느 블록과 겹치나?
      겹치는 게 있으면 → 그 블록 = 이 줄의 소속 (여럿이면 겹침 큰 쪽, 동률이면 작은 쪽)
      없으면          → unassigned_lines (버리지 않고 따로 보관)
```

**왜 이게 필요한가** — 이걸 안 하면 결과가 **"이 페이지에 79줄이 있다"** 로 끝난다. 심의는
*"유의사항 칸에 이 문구가 있어야 하는데 없다"* 를 말해야 하고, 그건 **줄이 어느 칸 소속인지
알아야** 나온다. 위 실물에서 `p1_r030`·`p1_r032`·`p1_r033` 이 그 결과이고, **이 ID 가 나중에
"지적 근거가 화면 어디인가"의 주소**가 된다.

### 전체 그림

```
그림 1장                                  ← 여기서 나눈다
  ↓ 자르기 (조각 9개, 각각 y_offset 기억)
조각 → OCR → "조각 안 좌표"로 된 줄들      ← 각 조각이 자기가 세상의 전부인 줄 안다
  ↓ ① 좌표 복원 (+y_offset)               ← 기준자를 하나로 통일 = "복원"
원본 좌표로 된 줄들 (오버랩 중복 포함)
  ↓ 중복 제거 (위치 겹침, 신뢰도 높은 쪽)
줄 79개                    블록 50여개     ← 서로 모르는 두 결과
  ↓ ② 영역 조립 (겹침 50% 게이트)          ← 처음 있는 조립 = "묶기"
영역 50개 (각각 줄 몇 개씩) + 미배정 6개
```

## A-③ "지표를 2층으로 가른다" — 실제로 두 번 돌려 본 결과

### 용어

- **지표** = 성적을 매기는 숫자. "줄 몇 개 잡았나", "골드(정답지) 문장 몇 개 회수했나"
- **재현성** = 같은 파일을 두 번 넣으면 같은 숫자가 나오나

### 실제로 같은 파일을 두 번 돌린 결과

같은 3문서, 두 번의 실행 (`archive_session_20260814/`):

```
== 올원e적금.png
   ocr         1차=  73  2차=  73   집합동일=True    ← 텍스트·좌표까지 한 글자도 안 다름
   vlm_sweep   1차=   1  2차=   4   집합동일=False   2차에만=3
        [2차만] '③ 0.2%p : 최근 6개월간 당행 예·적금(주택청약 제외) 미보유 고객 신규 시²'
        [2차만] '금융소비자 보호에 관한 법률 제19조제1항에 따른 설명을 받을 수 있는 권리가 있습니다.'
        [2차만] '중도해지이율 및 만기 후 이율 : NH농협은행 영업점 및 홈페이지에 고시한 이율'

== NH농협은행-2026_002-예금성.png
   ocr         1차=  93  2차=  93   집합동일=True
   vlm_sweep   1차=   4  2차=   5   집합동일=False
        [1차만] 'N pay 20,000원'                    ← 2차에서 사라짐
        [2차만] '이벤트 기간 内'                     ← 2차에서 새로 나옴
```

**`ocr` 은 텍스트와 좌표까지 완전히 동일**하고, **`vlm_sweep` 은 매번 다른 것을 건진다.**
심지어 1차에 있던 `'N pay 20,000원'` 이 2차엔 없어졌다.

### 그래서 무엇이 문제인가 — 이렇게 오판한다

```
어제:  코드 A 로 돌렸다 → 골드 문장 234개 회수
오늘:  코드 B(개선) 로 돌렸다 → 골드 문장 236개 회수
결론:  "개선이 +2 효과!"     ← ❌ 틀릴 수 있다
```

`vlm_sweep` 이 그냥 오늘 운이 좋아 2개를 더 건졌을 수 있다. 위 실측에서 **아무것도 안
고쳤는데 같은 문서에서 3개가 오갔다.** 즉 **±3 수준의 차이는 코드 개선인지 그날의 변동인지
구별이 불가능하다.**

**반대 방향도 위험하다.** 진짜 개선을 했는데 그날 sweep 이 2개를 덜 건지면 **"효과 없음"으로
오판하고 좋은 코드를 되돌린다.**

### 그래서 이렇게 읽는다

| 층 | 무엇 | 어떻게 보고 |
|---|---|---|
| **결정론 층** | `ocr` 4661줄 + `digital` 2321줄 = 6982 | **단일 수치.** 바뀌면 100% 우리가 뭔가 바꿨다는 뜻 |
| **비결정 층** | `vlm_sweep` 378줄 + `vlm_reading` 후보 | **범위로.** "회수 375~382" 처럼. 1회 관측으로 판단 금지 |

### 그리고 결정론 층이 바뀌면 원인을 찾을 수 있다

A-① 의 003 케이스가 정확히 그 사례다:

```
== NH농협은행-2026_003-예금성.pdf
   digital  1차= 25  2차= 25   집합동일=True
   ocr      1차= 97  2차=104   집합동일=False   2차에만=7   ← 결정론 층이 바뀌었다!
```

`ocr` 이 바뀌었으니 **"우연"이 아니라 원인이 있어야 한다.** 그리고 찾았다:

```
003 p3:  run1 route=digital (ocr 0)  →  run2 route=hybrid (ocr 7)
```

structured 페이지도 StructureV3 를 부르게 한 변경(2026-08-14) 때문이고, +7 은 정확히 그
페이지의 것이다. **결정론 층은 이렇게 원인까지 추적된다.** 만약 이 7개가 `vlm_sweep` 층에
있었다면 "변경 때문인지 그날 운인지" 영원히 못 갈랐을 것이다.

> 이게 규율 6("원인을 추측으로 짚지 않는다")과 짝을 이룬다. 어느 층이 흔들렸는지가
> **"원인을 찾아야 하나 / 여러 번 돌려 봐야 하나"** 를 갈라 준다.

## A 요약 — 한 장

```
파일
 └─ 1. 확장자 갈림길 ──── HWP → 사내 파서 → digital 라인(bbox 없음) → 끝 (VLM 0회)
                        PNG/JPG → 캔버스
                        PDF → 2. 렌더(200dpi) → 3. triage(structured/hybrid/scan_like)
                                                    + 잉크커버리지 5번째 신호
                                                    ↓ structured·hybrid 는 route="hybrid"
 ├─ 4. 타일링 (>4000px, 글자밀도로 컷 위치, 1600px 상한, 200px 오버랩)
 ├─ 5. PaddleX → ①OCR 라인 ②레이아웃 블록 → 좌표 복원 → 중복 제거
 ├─ 6. 디지털 우선 병합 (IoU 0.5 또는 포함비 0.5)
 ├─ 7. 영역 구성 (겹침 50% 게이트) → 못 붙은 줄 = unassigned
 ├─ 8. 역할 판정: 규칙 초기값 → VLM 1회 덮어쓰기 (규칙값은 role_rule 에 보존)
 ├─ 9. 카드 분할: 개수=밀도(코드), 배정=VLM (스크롤/1덩어리는 호출 안 함)
 ├─ 10. 밴드 통독: 밴드당 1회로 "고쳐라 + 찾아라"
 │       → vlm_reading 후보 (정본 안 덮음) + 점수·관계 딱지 + 범람 탐지
 ├─ 11. 통짜 스윕 → 중복 심판 → 저신뢰 재판독 → 미배정 귀속 → 읽기순서
 └─ 12. 분류(product_group/ad_type) + category_source
     ↓
  out/json (정밀) · out/llm_view (AI 입력) · out/previews (눈 검수)
```

**A 에서 꼭 잡고 갈 세 가지**

1. **정본 vs 후보(B안)** — OCR/디지털이 정본, VLM 판독은 후보. 파싱은 선택하지 않고 둘 다
   남긴다. 선택은 STAGE_3 가 한다.
2. **`source` 가 지표를 2층으로 가른다** — `ocr`/`digital`(6982줄, 항상 같음) vs
   `vlm_sweep`(378줄, 실행마다 다름). 섞어서 비교하면 오판한다.
3. **조용한 실패 금지** — 실패·부분응답·버린 이유가 전부 `notes` 에 남는다. 코드 곳곳의
   실측 주석은 "조용히 실패했다가 발견된" 사고 기록이다.
