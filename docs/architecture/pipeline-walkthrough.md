## 1. 골격 — 자료구조가 5번 바뀐다

단계 15개를 외우면 안 잡힌다. 실제로는 **자료구조가 다섯 번 바뀌는 것**이고, 단계들은 그
변환을 돕는 부속이다. 올원e적금의 실제 영역 하나를 끝까지 따라간다.

### 1.1 한 영역을 끝까지 따라가기

```
① 파일          [예금성상품-적금] 올원e적금.png
      ↓  canvas.py — 캔버스로 정규화
② 캔버스        Image 1122 × 6429   ← 이후 모든 좌표의 유일한 기준계
      ↓  bands.py + tiling.py — 글자 밀도로 9조각
③ 타일          Tile(y_offset=0) … 9개
      ↓  paddlex_client.py — 조각마다 1회 호출
④ 라인 + 블록   Line(text='상품명',      bbox=[ 66,863,200,922], conf=0.99, source='ocr')
                Line(text='NH올원e적금',  bbox=[410,865,680,920], conf=0.99, source='ocr')
                LayoutBlock(label='text', bbox=[ 68,865,677,912])
      ↓  regions.py — 라인 중심점이 블록 안에 들어가면 넣는다
⑤ 영역          Region(region_id='p1_r004', bbox=[68,865,677,912],
                       label='text',        ← StructureV3 가 준 것
                       role='본문',          ← 우리가 만든 9종 중 하나
                       lines=[Line('상품명'), Line('NH올원e적금')])
      ↓  vlm_judge.py — 역할을 VLM 이 다시 정함 (페이지당 1회)
                       role='본문', role_source='vlm'
      ↓  pipeline.py::_merged_band_read — 같은 조각을 VLM 에 다시 줌
⑥ 후보 부착      Region.vlm_reading          = 'NH올원e적금'      ← 정본은 그대로!
                Region.vlm_reading_score    = 1.0
                Region.vlm_reading_coverage = 0.5
                Region.vlm_reading_relation = 'head_drop'
      ↓  llm_view.py — 좌표·신뢰도를 버리고 읽기순서로 평면 나열
⑦ 정제 텍스트    {"region_id": "p1_r004", "role": "본문",
                 "text": "상품명 NH올원e적금",
                 "vlm_reading": "NH올원e적금",
                 "vlm_reading_relation": "head_drop"}
      ↓  extract.py — 스키마 필드에 값 채우기 (별도 프로세스)
⑧ 필드          "product_name": {"value": "NH올원e적금",
                                 "status": "found",
                                 "evidence": ["p1_r004"]}
```

### 1.2 반드시 잡아야 할 4가지

**(1) ②가 좌표의 원점이다.** 캔버스가 만들어진 뒤로 모든 `bbox` 는 이 좌표계다. 타일 좌표는
즉시 `restore_coords` 로 되돌아오므로 ④부터 이미 캔버스 좌표다. HWP 는 캔버스가 없어
`bbox=None` 이고, 그래서 미리보기도 근거 하이라이트도 만들 수 없다.

**(2) ⑤가 화면의 굵은 박스이고 근거 지목의 단위다.** `region_id` 가 여기서 태어나 ⑧까지
그대로 살아간다. STAGE_3 가 `evidence: ["p1_r004"]` 로 근거를 대고, 검수 화면이 그 ID 로
bbox 를 되붙여 hover 하이라이트를 그린다. **⑤에서 영역에 못 들어간 라인은 이 ID 를 못 받는다** —
그게 미배정이고, 텍스트는 전달되지만 근거를 영역 단위로 지목할 수 없다.

**(3) ⑥이 이 파이프라인의 핵심 설계다.** VLM 이 다시 읽은 결과가 `lines` 를 덮지 않고
옆칸(`vlm_reading`)에 붙는다. 한 영역에 판독이 둘 공존하고, 코드가 그 관계를 딱지로 판정한다.
최종 값 선택은 ⑧이 한다. 근거는 §5.2.

**(4) ⑦에서 정보를 일부러 버린다.** 좌표·신뢰도·출처를 다 뺀다. 남기는 건 `region_id` 뿐 —
나중에 좌표를 되붙이려고. 그리고 **라인 단위 후보는 ⑦로 넘어가지 않는다**(§9-①).

<a id="산출물-3개가-골격의-어느-지점인가"></a>

**산출물 3개가 골격의 어느 지점인가**

```
out/json      = ②③④⑤⑥ 전부 (아무것도 안 버림)   → 감사 · 미리보기 · 화면 왼쪽
out/llm_view  = ⑦                                → RAG · STAGE_3 입력
out/extracted = ⑧                                → DB
```

### 1.3 분기 3개

| 분기 | 무엇을 건너뛰나 | 실제 사례 |
|---|---|---|
| PDF `structured` | ③④(타일·OCR)를 건너뛰고 PDF 내부 텍스트가 ④로 직행. 블록이 없으니 ⑤는 `_pseudo_regions`(수직 갭 군집)가 대신 | **003 p3** — 영역 2개·라인 25개 |
| HWP | ②③④를 다 건너뜀. 사내 파서가 문단·표를 바로 ④로. 캔버스가 없어 ⑤는 영역 1개 고정 | **004** — 영역 1개·라인 12줄 |
| ⑤로 되돌아오는 경로 | ⑤에서 남은 미배정 낱줄을 좌표만 보고 영역에 다시 붙임 (VLM 없음) | **001** — 58줄이 이 경로로 붙음 |

## 2. 단계 0 — 라우팅

[pipeline.py::process_file](../../src/nh_parsing/pipeline.py) 이 확장자만 보고 세 갈래로 보낸다.
핵심은 **PDF 에만 판정이 있고 HWP 엔 없다**는 것.

<a id="21-pdf--렌더링-전에-파일-내부를-읽는다"></a>

### 2.1 PDF — 렌더링 전에 파일 내부를 읽는다

`_process_pdf` 는 페이지 루프 안에서 `triage_page(pdf_page)` 를 **먼저** 부른다. 이때 렌더링을
아직 안 했다. `pypdfium2` 가 하는 일은 둘뿐이다:

- `page.get_textpage().get_text_bounded()` → PDF 안에 **텍스트 오브젝트로 저장된 글자**를 그대로 꺼냄
- `page.get_objects()` 로 훑어 `FPDF_PAGEOBJ_IMAGE` 타입의 면적 합 → 이미지 면적비

즉 **그림으로 찍어서 글자를 찾는 게 아니라 파일 내부 자료구조를 읽는다.** 판정 뒤에
모든 페이지를 **판정과 무관하게 렌더**한다 — `structured` 도 포함이다(미리보기·VLM 크롭에 필요).

**판정 기준 4개** ([triage.py:61-86](../../src/nh_parsing/triage.py#L61-L86), 순서대로 평가하고 먼저 걸리는 것으로 확정)

| # | 조건 | 판정 | 실제 사례 |
|---|---|---|---|
| 1 | 공백 뺀 글자 **20자 이하** | `scan_like` | 001 p1 = **0자** / 003 p1 = 0자 / 003 p2 = 17자 |
| 2 | `U+FFFD(�)` **8개 이상 + 비율 30%↑** | `scan_like` | 이번 샘플엔 없음 |
| 3 | 50자 이상인데 **정상 문자 비율 10% 이하** | `scan_like` | 이번 샘플엔 없음 (PUA 폰트 방어) |
| 4 | 위 셋 통과 + **이미지 면적비 50% 이상** | `hybrid` | **이번 샘플엔 없음** |
| — | 전부 통과 | `structured` | 003 p3 = 503자, 한글 317자, 이미지 0% |

조건 3이 필요한 이유: 어떤 PDF 는 **글자가 있는 척**하지만 폰트가 사설영역(PUA)이라 복사하면
깨진 기호가 나온다. 글자 수만 세면 속는다. 그래서 한글·ASCII·정상 유니코드 카테고리만 세고
`Co`(사설영역)는 제외해 비율을 본다.

판정 근거는 버리지 않는다 — `AdPage.triage` 에 남아 검수화면 머리줄에
`triage=scan_like (텍스트 0자 이하 — 텍스트 레이어 불신)` 으로 찍힌다.

> ⚠️ **`hybrid` 경로는 이번 샘플 5문서에서 한 번도 안 탔다.** 코드는 있지만 실측 검증이 없다.
> `_merge_digital_ocr`(디지털 우선 병합)도 같은 이유로 미검증 상태다.

<a id="22-hwp--판정-자체가-없다"></a>

### 2.2 HWP — 판정 자체가 없다

무조건 `document_processor.DocIR.from_file()` 로 문단·표를 뽑는다. 내장 이미지는 `iter_assets`
로 하나씩 꺼내 크기 필터(`min(w,h) < 32` 또는 `w*h < 20,000`)를 통과한 것만 **PNG 와 똑같은
OCR/VLM 경로**로 p2, p3… 별도 페이지를 만든다. 004 에는 통과한 내장 이미지가 없어 1페이지다.

**표를 어떻게 살리나.** 004 는 라인 12줄인데 그중 8줄이 표이고, 열 구분자 `|` 가 살아 있다:

```
 3  대출대상 | 공무원(3개월이상 재직 중)
 6  대출한도 | 최대 1억원 이내
10  부대비용 | 중도상환해약금 : [중도상환원금 × 적용요율 × (잔여기간 ÷ 대출기간)] … 구분 | 고정금리 | 변동금리 …
```

markdown 문자열 대신 구조 API(`iter_cell_positions()`)를 쓰는 이유가 실측으로 남아 있다.
`markdown()` 은 병합 셀을 걸친 칸 수만큼 반복 출력하는데, 예전에는 "연속으로 같은 값이면
병합셀"이라는 텍스트 규칙으로 접다가 **값이 진짜로 같은 이웃 칸까지 삼켰다**:

```
원본 구조 : (2,2) colspan=1 '0.01%'  /  (2,3) colspan=1 '0.01%'   ← 별개 셀
옛 출력   : '적용요율 0.01%'                                        ← 하나 소실
```

고정금리와 변동금리 중 **어디에 요율이 붙는지 알 수 없게 된다.** 금리·수수료 표에는 같은 값이
나란히 오는 일이 흔해 이 규칙은 계속 값을 잃는다. `iter_cell_positions()` 는 병합 셀을 논리 셀
하나로 한 번만 돌려주므로 추측이 필요 없다 — **규칙을 손본 게 아니라 없앤 수정이다.**

<a id="23-structured-가-건너뛰는-것"></a>

### 2.3 `structured` 가 건너뛰는 것

`_assemble_page(canvas, lines, blocks=[], route="digital", …)` — **PaddleX 를 한 번도 안 부른다.**
블록이 `[]` 이라 `build_regions` 가 영역을 못 만들고 `_pseudo_regions`
([pipeline.py:548](../../src/nh_parsing/pipeline.py#L548))가 대신 돈다: 글자 높이 중앙값의
1.5배를 갭 기준으로 라인을 수직 군집화.

003 p3 결과가 **영역 2개 · 라인 25개**다. `p3_r001` 한 영역에 페이지 전체가 들어 있다:

```
[NHBenefit]모여봐요,올원모임으로!시즌3 / 총1억원모임지원금, / … /
-네이버페이포인트3만원권(추첨15명) / 기간:2025.10.20.(월)~10.31.(금) / …
```

**공백이 전부 사라진 것을 보라.** `extract_digital_lines` 가 `if not ch or ch.isspace(): continue`
로 공백 문자를 버리고 나머지를 이어붙이기 때문이다. 관계 딱지가 `same` 으로 나오는 건
`truncation.norm` 이 글자·숫자만 남겨 공백 차이를 지우기 때문.

그리고 **이 페이지가 p1 의 `추첨 15명` 을 독립적으로 증언한다.** p1 OCR 은 `(추첨15)`,
VLM 후보는 `(추첨 10명)` 인데, p3 의 디지털 텍스트 레이어에 `(추첨15명)` 이 박혀 있다.
원본 미리보기 이미지로도 확인했다.

<a id="24-pdf-는-왜-사내-파서를-안-쓰나"></a>

### 2.4 PDF 는 왜 사내 파서를 안 쓰나

document-processor 는 PDF 도 지원하고 초기 설계는 오히려 그걸 쓰기로 했었다
(`docs/previous/parsing-pipeline-design_v0.1_2026-07-16.md` §11). 안 쓴 이유는
[triage.py:6-7](../../src/nh_parsing/triage.py#L6-L7) 에 적혀 있다 — 어차피 미리보기·VLM 용으로
페이지를 직접 렌더해야 하는데, 사내 파서가 한 번 렌더하고 우리가 또 렌더하면 **이중 렌더 +
좌표계 불일치**가 생긴다. 모든 bbox 가 우리 렌더 좌표계여야 한다. 프로덕션에서는 이 자리를
사내 파서 probe 로 감싸도 된다고 명시돼 있다.

## 3. 단계 1 — 글자 획득 (①~⑤)

<a id="31-왜-자르나-왜-밝기가-아니라-에지인가"></a>

### 3.1 ① 왜 자르나, 왜 밝기가 아니라 에지인가

자를지 말지는 높이만 본다: `if h <= 4000: return [Tile(canvas, 0)]`.
**어디서 자를지가 [bands.py](../../src/nh_parsing/bands.py) 의 전부다.**

"어두운 픽셀 = 글자"로 재면 **색 배경이 깔린 광고에서 배경 전체가 잉크로 잡힌다** — 001 실측으로
글자 없는 행이 6554행 중 121행(2%)뿐이었다. 자를 자리가 없다는 뜻이다. 글자의 특징은 어둡다는
게 아니라 **국소 대비가 크다**는 것이라, 1px 옮긴 이미지와의 차분(`ImageChops.difference`)으로
재면 배경색과 무관해진다. 같은 001 에서 31% 로 올라갔다.

기준 셋이 겹친다:

- **등량(等量)** — 높이로 균등하게 자르면 조각별 글자량이 2.0~2.7배 차이 난다(001: 15/20/18/19/40%).
  VLM 은 크기와 무관하게 같은 토큰 예산을 쓰므로 글자 몰린 조각이 손해를 본다.
- **스냅** — 등량 목표점을 ±160px 안의 "글자 없는 행"으로 옮긴다. 못 찾으면 `snapped=False` 로
  사유를 돌려준다(조용히 실패하지 않게).
- **높이 상한 1600px** — 상한 없이 돌리면 성긴 구간이 2157px 조각이 되고 002 의 레이아웃 블록이
  84→62 로 줄어 `최고연 7.1%` 를 담던 작은 영역이 큰 영역에 흡수됐다. 상한을 걸면 조각이
  15→24장으로 늘지만(PaddleX 호출만 증가) 블록은 332→360 으로 세밀해지고 골드 회수도 138→139.

<a id="32-밴드와-타일은-같은-것이다"></a>

### 3.2 밴드와 타일은 같은 것이다

**지금 코드에서는 완전히 같다.** 둘 다 같은 호출로 만들어진다:

```python
content_bands(canvas, span=1600, max_span=1600)      # tiling.make_tiles:46      (OCR 타일)
content_bands(canvas_img, span=1600, max_span=1600)  # pipeline._merged_band_read:650 (VLM 밴드)
```

증거는 판단 로그다 — 올원e `타일 9개 처리` / `밴드 통합판독: 9회 호출`. 001 은 7/7, 002 는 8/8,
003 p1 은 1/1. **일부러 같게 맞춘 설계다**: OCR 이 본 것과 같은 크롭을 VLM 에 주면 "이 영역이
어느 밴드에 속하나"가 계산 없이 맞아떨어진다.

> ⚠️ `config.vlm_band_ratio = 2.0`("밴드 높이 = 캔버스 폭 × 2.0")과 `vlm_band_min_height_px` 는
> **지금 실행 경로에서 안 쓰인다.** 파이프라인은 `sweep_missing_lines(…, banded=False)` 만
> 호출하므로 `_sweep_bands`/`vlm_band_span` 은 테스트에서만 도달한다. config 주석의 긴 근거는
> 옛 경로에 대한 기록이다.

<a id="33--structurev3-가-돌려주는-것"></a>

### 3.3 ② PP-StructureV3 가 돌려주는 것

한 번의 `request_layout_parsing(tile)` 응답에 **세 덩어리**가 있다
([paddlex_client.py:102-138](../../src/nh_parsing/paddlex_client.py#L102-L138)).
**가는 박스와 굵은 박스가 한 응답에서 같이 온다.**

| 응답 필드 | 내용 | 우리 자료구조 |
|---|---|---|
| `overall_ocr_res.rec_texts / rec_scores / rec_boxes` | 글자 한 조각 + 신뢰도 + 좌표 | `Line(source="ocr")` → **가는 박스** |
| `parsing_res_list[].block_label / block_bbox` | 레이아웃 블록(`doc_title`/`text`/`table`/`figure`…) | `LayoutBlock` → **굵은 박스** |
| `layout_det_res.boxes[]` | 같은 블록의 다른 표현(점수 포함) | 중복이라 `build_regions` 가 `parsing_res_list` 우선으로 버림 |

**우리가 정한 것 / 모델이 준 것**

- **우리가 정한 것 = 요청 파라미터 5개뿐**
  - `textDetLimitSideLen=2500` — 서버 기본 960 이 타일(장변 2000px)을 절반 이하로 축소해
    fine-print 를 깨뜨렸다 (2026-07-17 실측: 올원 유의사항 완전 복구)
  - `layoutMergeBboxesMode="small"` — 기본 `large` 가 겹침 박스를 큰 쪽으로 흡수해
    003 p1 사진형 카드 콜라주가 통짜 1블록이 됐다 (3→20블록)
  - `useTextlineOrientation=False` — 방향 분류기가 얇은 회색 fine-print 를 180도 회전으로
    오판해 거꾸로 인식했다 ('링이어니을용은' 사건)
  - `useFormulaRecognition=False`, `useDocOrientationClassify=False` — 광고물엔 불필요, 속도 절약
- **모델이 준 것 = 텍스트 문자열, 신뢰도, 좌표, 블록 라벨.** 여기엔 손대지 않는다.
- **우리 코드의 변환 = 폴리곤/4점 bbox 정규화(`_norm_bbox`)와 캔버스 범위 클램프뿐.**

### 3.4 ③ 좌표 복원 · 중복 제거

**좌표 복원** — PaddleX 좌표는 보낸 타일 기준이므로 `y_offset` 만 더한다.

**중복 제거 (`dedupe_lines`)** — 타일이 200px 겹치니 경계 글자가 두 번 검출된다. 신뢰도 높은
순으로 정렬해 앞에서부터 채택하고, 뒤에 오는 것이 이미 채택된 것과 **IoU ≥ 0.5 또는
포함비 ≥ 0.7** 이면 버린다.

**텍스트 동일성은 안 본다.** 경계에서 잘린 글자는 같은 자리에 "깨진 텍스트 + 낮은 신뢰도"로
나오기 때문이다 (실측: `수 있는 권리가 있습니다.` 0.99 vs `7리콘극` 0.6). 포함비를 IoU 와 같이
보는 이유는 조각(`1천원 이상3`, `세저`, `기보그리`)이 온전한 라인 안에 들어가면 IoU 가 낮게
나와 통과하기 때문.

### 3.5 ④ 디지털 우선 병합

`hybrid` 페이지에서만 돈다. 디지털 라인을 전부 채택하고, OCR 라인은 디지털과 IoU ≥ 0.5 로
겹치는 것만 버린다. **이번 샘플 5문서에 `hybrid` 가 없어 이 경로는 안 탔다.**

<a id="36--영역-조립--중심점-판정"></a>

### 3.6 ⑤ 영역 조립 — 중심점 판정

여기서 굵은 박스가 생긴다. 순서는 이렇다:

1. 블록 라벨 → 역할 초기값 매핑 (dict 27줄)
2. 라인의 **중심점**이 블록 안에 들어가면 그 블록에 넣음. `for region in regions` 순서대로
   **첫 매칭에서 멈춤**(`break`)
3. 어디에도 안 들어간 라인 → `unassigned_lines`
4. 영역마다 `_refine_role` 로 규칙 보정

**중심점 판정을 좌표로 풀면** ([regions.py:60-63](../../src/nh_parsing/regions.py#L60-L63)):

```
블록          bbox = [ 68, 865, 677, 912]
라인 '상품명'  bbox = [ 66, 863, 200, 922]

중심 = ( (66+200)/2 , (863+922)/2 ) = (133, 892)
   68 ≤ 133 ≤ 677  ✓ 가로
  865 ≤ 892 ≤ 912  ✓ 세로   → 넣는다
```

**왜 '완전히 들어가면'이 아니라 '중심점'인가.** 위 예의 라인은 블록 밖으로 삐져나와 있다 —
왼쪽 2px, 아래 10px:

```
        x=66  68                      677  680
 y=863 ──┼────┼── 라인 시작 (블록보다 2px 왼쪽·2px 위)
 y=865   │ ┌──┴────────────────────────┐   │  ← 블록 시작
 y=912   │ └───────────────────────────┘   │  ← 블록 끝
 y=922 ──┴─── 라인 끝 (블록보다 10px 아래)
```

완전 포함을 요구했다면 이 라인은 버려졌을 것이다. OCR 박스와 레이아웃 박스는 **서로 다른
모델이 그린 사각형**이라 몇 px 씩 안 맞는 게 정상이다. 그래서 점 하나만 보는 관대한 판정을 쓴다.

<a id="41-⑥⑦-카드-게이트와-배정"></a>

### 4.1 ⑥⑦ 카드 게이트와 배정

**게이트(⑥)는 순수 코드다.** 모델 호출 0회로 재현한 결과
(`uv run python tools/verify_numbers.py --section card`):

```
올원e적금   1122×6429  종횡비 5.73  →  스크롤 (≥2)     →  VLM 호출 안 함
001 p1      720×6554  종횡비 9.10  →  스크롤           →  VLM 호출 안 함
002         720×6111  종횡비 8.49  →  스크롤           →  VLM 호출 안 함
003 p1     1990×1120  종횡비 0.56  →  슬라이드 · 덩어리 3개  →  VLM 호출
                1번 x_ratio 0.04~0.33  글자량 33%
                2번 x_ratio 0.36~0.64  글자량 34%
                3번 x_ratio 0.68~0.96  글자량 28%
003 p2     1990×1120  종횡비 0.56  →  슬라이드 · 덩어리 2개  →  VLM 호출  (58% / 38%)
003 p3     2000×1125  종횡비 0.56  →  슬라이드 · 덩어리 1개  →  단일패널, 호출 안 함
```

**7페이지 중 2페이지만 VLM 을 부른다.** 나머지 5페이지는 좌표 계산으로 걸러낸다.

**덩어리를 세는 방법**: 세로 방향 글자 프로파일에서 **20px 이상 글자가 없는 구간(거터)**으로
자르고, **글자량이 10% 미만인 조각은 버린다.** 넓이가 아니라 글자량인 이유 — 003 p2 의 가장
넓은 빈틈(566px)이 카드 경계가 아니었다. 실측 마진이 넉넉하다: **진짜 카드 28~58% vs
카드 아닌 덩어리 0~4.4%.**

**개수는 코드가 세는데 왜 배정은 VLM 인가.** 전폭 헤드라인처럼 **어느 컬럼에도 안 속하는
요소**가 있다. 003 p1 의 `10/20 인스타그램 / 올원모임 소문내기 이벤트 시안` 은 x=95~515 라
좌표로는 표지 카드 소속으로 보이지만 실제로는 3장 전체를 설명하는 안내문이다. 그래서
개수(결정론)를 **증거로 프롬프트에 실어** 배정만 VLM 에게 묻는다.

**번호를 매기는 방법 — 순열 문제를 피한다.** 관측을 여러 번 하면 "run A 의 1번 = run B 의 2번"
일 수 있어 번호를 직접 투표할 수 없다. 그래서 **"두 영역이 같은 카드에 묶였나"를 투표**하고
(union-find), 묶음이 정해진 뒤 **시각 순서(위→아래, 좌→우)로 1..N 을 재부여**한다.
밀도 증거가 있으면 관측은 1회만 한다.

**003 p1 에서 밀도 3장 vs VLM 2장이 어긋났고 코드는 VLM 을 채택하고 로그에 남겼다** —
`카드 개수 불일치(VLM 판단 채택): 밀도 3장 vs VLM 2장`. 밀도가 맞았을 가능성이 높지만 근거가
문서 1건뿐이라 밀도를 절대 권한으로 올리지 않았다.

<a id="42-⑧-역할-3층"></a>

### 4.2 ⑧ 역할 3층

3층이 순서대로 다 실행되고 **뒤 층이 앞 층 값을 덮어쓴다.**
(`uv run python tools/verify_numbers.py --section role`)

| 층 | 무엇을 보고 정하나 | 실측 (225개 중) |
|---|---|---|
| **1층** `_LABEL_TO_ROLE` | StructureV3 가 준 `label` 하나. dict 조회 27줄 | 시작값 |
| **2층** `_refine_role` | 그 영역의 **텍스트 문자열** + **화면상 세로 위치** | **54개를 바꿈** |
| **3층** `judge_region_roles` | 텍스트 발췌 + y_ratio + **페이지 전체 이미지** | **94개를 바꿈** |

3층 다 거쳐도 값이 안 바뀐 영역이 88개.

**`label` 과 `role` 은 완전히 다른 것이다.**

| | 값 | 누가 만들었나 |
|---|---|---|
| `label` | `"text"` | **StructureV3 모델 출력.** `doc_title`, `paragraph_title`, `text`, `table`, `figure`, `footnote`, `header`, `seal` … 모델에 고정된 영어 어휘 |
| `role` | `"본문"` | **우리가 만든 9종.** 제목·본문·유의사항·각주·버튼·고지문구·표·이미지·기타 |

StructureV3 는 "유의사항"이나 "고지문구"라는 개념을 모른다. 그건 금융광고 심의에서만 쓰는
말이고 우리가 정한 것이다. 그래서 번역표가 필요하고 그게
[regions.py:22-48](../../src/nh_parsing/regions.py#L22-L48) 의 dict 27줄이다.

**2층은 정규식 3개가 전부다** ([regions.py:113-130](../../src/nh_parsing/regions.py#L113-L130)):

```
① text 에 '유의사항|알아두|꼭 확인|주의사항' 이 있으면   → 유의사항 (확신도 0.9)
② text 에 '심의필 제2025-0000' 패턴이 있으면            → 고지문구 (확신도 0.9)
③ 1층 결과가 '본문' 이고 bbox 상단이 캔버스 높이 80% 아래 → 유의사항 (확신도 0.5)
```

③에는 조건이 하나 더 붙는다 — **1층이 '본문'일 때만**. StructureV3 가 `doc_title`(→제목)이라
한 블록은 페이지 맨 아래에 있어도 유의사항으로 안 바뀐다.

**3층 VLM 에게 주는 것 / 안 주는 것** (페이지당 딱 1번 호출):

```
[텍스트] 영역 목록 — 영역마다 한 줄
  - region_id=p1_r004 y_ratio=0.13 텍스트: "상품명 / NH올원e적금"
        └ 앞 4줄만, 160자로 자름     └ bbox 상단 ÷ 캔버스 높이
[이미지] 페이지 전체 축소본 1장 (최대 896×2400)
[지시] 역할 9종 정의. 핵심: "'유의사항'이라는 단어가 없어도 내용이 고지·제한·경고
       성격이면 유의사항입니다" / "특정 키워드 유무가 아니라 내용의 성격으로 판단하세요"
```

**못 보는 것**: bbox 좌표 상세, OCR 신뢰도, 5줄째 이후 텍스트, 다른 페이지,
VLM 후보(그 시점에 아직 없음).

**2층과 3층이 갈리는 실제 예 — "왜 규칙이 판단 주체가 아닌가"의 답:**

```
올원e p1_r035   label=paragraph_title   텍스트가 딱 '유의사항' 한 낱말
  1층 : paragraph_title → 제목
  2층 : 정규식 ①이 '유의사항' 글자를 발견 → 유의사항     ← 규칙이 틀렸다
  3층 : VLM → 제목                                    ← 이게 맞다
```

이 영역은 유의사항 문단이 아니라 **유의사항 섹션의 제목**이다. 정규식은 낱말 존재만 보니
제목과 본문을 구분할 수 없다. 반대 방향도 있다:

```
올원e p1_r011   label=text   '농협은행에서 광고하는 상품으로, 토스는 상품 내용과 이벤트에 관여하지 않아요.'
  1·2층 : 본문     (하단 80% 위쪽이라 ③도 안 걸림, '유의사항' 낱말도 없음)
  3층   : 유의사항  ← 내용이 면책 고지라는 걸 VLM 이 알아본 것
```

**"폴백"의 정확한 의미.** 2층 결과는 항상 만들어지고, 3층이 그 영역에 대한 답을 안 주면
2층 값이 살아남는다. 그게 `role_source='rules'` 25건이다. 내막:

- **24건은 빈 박스** — 라인이 없어 `judgeable` 에서 걸러져 **VLM 에게 아예 안 물어봄.** 정상.
- **1건은 진짜 폴백** — 올원e `p1_r016`, 라인 4줄이 있는데 VLM 응답에 이 `region_id` 가 안 왔다.
  하필 `① 0.1%p / ② 0.2%p` 우대금리 영역. role 은 1층의 `text→본문` 이 그대로 남았다.

<a id="43--낱줄-귀속--되돌림-경로"></a>

### 4.3 ⑨ 낱줄 귀속 — 되돌림 경로

**시간 순서로 보면 잡힌다.** 같은 판정을 두 번 하는 게 아니라, **한 번 실패한 것을 나중에
느슨한 규칙으로 다시 시도**한다.

```
시각 1  build_regions        중심점 판정 → 001: 영역 127줄 / 미배정 58줄
시각 2  카드 배정 (VLM)        bbox 안 건드림
시각 3  역할 판정 (VLM)        bbox 안 건드림
시각 4  _absorb_unassigned   미배정 58줄을 다시 시도 → 58줄 전부 붙음
```

시각 4 의 규칙 ([pipeline.py:333-404](../../src/nh_parsing/pipeline.py#L333-L404)):

```
㉠ 포함 : 중심점을 품는 영역 (여럿이면 가장 작은 것)
㉡ 근접 : 품는 영역이 없으면
           · 같은 칼럼에 있는 영역만 후보   ← 가로 구간이 라인 폭의 50% 이상 겹칠 것
           · 그중 세로 간격이 가장 가까운 영역
           · 간격이 max(300px, 캔버스높이 × 15%) 이내일 때만
           · 동률이면 가로 겹침 큰 쪽 → region_id 순 (실행마다 같은 답)
㉢ 둘 다 실패 → 미배정 유지
대상: source 가 'ocr'·'digital' 인 라인만. vlm_sweep 은 근사 좌표라 제외.
```

**주의할 점 — "포함 29 / 근접 29"는 입력의 성질이 아니다.** ㉠은 시각 1 에서 이미 실패한 판정과
**완전히 같은 계산**이다. 그런데 001 로그에 `포함 29 / 근접 29` 라고 나온다. 이유는
[pipeline.py:300-303](../../src/nh_parsing/pipeline.py#L300-L303) — 라인을 붙일 때마다
**영역 사각형이 그 라인을 삼키도록 커진다**:

```python
target.bbox = [min(target.bbox[0], line.bbox[0]),  min(target.bbox[1], line.bbox[1]),
               max(target.bbox[2], line.bbox[2]),  max(target.bbox[3], line.bbox[3])]
```

```
   붙이기 전                     A 를 근접으로 붙인 후
 ┌──────────┐                  ┌──────────┐
 │  영역 R  │                  │  영역 R  │
 └──────────┘                  │          │  ← 박스가 아래로 늘어남
    · 라인 A                    │  라인 A  │
    · 라인 B                    └──────────┘
                                  · 라인 B  ← 이제 늘어난 박스 '안' = "포함"
```

즉 **처리 순서에 따라 포함/근접 비율이 달라진다.** 순서 자체는 결정론적이라 같은 입력이면
같은 답이 나온다.

**이 부수효과가 세 현상의 공통 원인이다:**

1. **"영역 bbox 가 실제 글자보다 넓다"** (200개 중 10개가 상단 20px+ 초과)
2. **003 의 `내지1`·`내지2` 꼬리표가 본문 영역에 붙은 것** — 세로 간격이 가까운 같은 칼럼이라
   ㉡에 걸린다. `p1_r011` 정본이 `지원금10만원 / (선착순1,000팀) / 내지1` 이 됐다.
3. **003 `p1_r011` 의 "뒷부분 잘림 17% 소실" 경보가 오탐인 이유** — 정본에 `내지1` 이 딸려와서
   VLM 이 그걸 안 읽은 게 "잘림"으로 잡혔다.

**가로 게이트가 왜 필요했나.** 예전엔 세로 간격만 봤는데, 003 처럼 좌우 3분할이면 **캔버스
반대편 패널도 세로 간격이 0**이다. 그래서 `내지2` 꼬리표(x≈1587)가 표지 영역(x≈104~491)에
붙고, 박스가 커지는 이 로직 때문에 **영역 사각형이 패널 3개를 관통**했다. 225개 중 17개가
폭이 늘고 12개가 캔버스 절반 이상을 가로질렀다. 가로 게이트로 17→2, 관통 12→0.
남은 2건은 원본 대조 결과 진짜 흡수(같은 문단 이어붙임)였다.

**미배정으로 남아도 글자는 안 사라진다.** `llm_view` 의 `unassigned` 로 STAGE_3 에 전달된다.
근거를 영역 단위로 지목할 수 없을 뿐이다.

## 5. 단계 3 — 통합 판독 (⑩~⑬)

<a id="51-넷의-차이는-보는-그림-크기"></a>

### 5.1 넷의 차이는 '보는 그림 크기'

| | ⑩ 밴드 통독 | ⑪ 통짜 스윕 | ⑫ 중복 심판 | ⑬ 저신뢰 재판독 |
|---|---|---|---|---|
| **VLM 에게 주는 그림** | OCR 타일과 **똑같은 조각** | 페이지 **전체 1장**(896×2400 축소) | **그 줄 하나만** 크롭 → 폭 600px 로 확대 | 같음 |
| **묻는 것** | "이 영역 목록을 고쳐라 **+** 목록에 없는 문구를 찾아라" | "목록에 없는 문구를 찾아라" | "이 줄을 정확히 전사하라" | 같음 |
| **호출 수** | 밴드당 1회 (5문서 **27회**) | 페이지당 1회 (**6회**) | 중복 1건당 1회, 상한 8 (**14회**) | 라인 1건당 1회, 상한 12 (**10회**) |
| **결과가 붙는 곳** | `Region.vlm_reading` | **새 `Line`**(`source='vlm_sweep'`) → 미배정 | `Line.vlm_reading` | `Line.vlm_reading` |
| **트리거** | 항상 | 항상 | ⑪ 회수 문구가 기존 줄의 다른 판독일 때 | OCR `confidence < 0.80` |
| **실측 성과** | 후보 **177건** 부착 | **24줄** 회수 | **5건** 부착 | **5건** 부착 |

**⑩과 ⑬이 왜 둘 다 필요한가 — 배율이다.**

```
⑩ 밴드 : 720×1800 한 장에 영역 5~10개  →  한 영역이 그림의 10~20%
⑬ 크롭 : 그 줄만 잘라 폭 600px 이상으로 확대  →  한 줄이 그림의 100%
```

001 `생학해대`(conf 0.46)가 산증인이다. **⑩도 이 영역을 봤고 고치지 못했다** — 밴드에서는 이
낱말이 너무 작았다. ⑬이 그 줄만 확대해 `생활형태` 로 읽었다. 반대로 ⑬만 있으면 안 된다 —
⑬은 저신뢰 줄만 보니 `1O.1%p` 처럼 **신뢰도 0.99 로 자신 있게 틀린** 판독은 손도 못 댄다.
그건 ⑩이 문맥을 보고 잡는다.

**⑫와 ⑬은 크롭·프롬프트가 완전히 같다.** 다른 건 둘:

- **트리거** — ⑫는 "두 판독이 갈렸다"(⑪이 회수한 문구가 기존 줄과 같은 줄로 보일 때),
  ⑬은 "OCR 이 자신 없다"
- **부착 조건** — ⑫는 재판독 결과가 두 판독 중 하나와 겹쳐야 부착(엉뚱한 크롭 방어),
  ⑬은 VLM 확신도 ≥ 0.60 이어야 부착

**⑩의 밴드 배정 규칙.** 밴드가 200px 겹치므로 "중심이 범위에 들면"으로 고르면 겹침 구간의
영역이 양쪽에 다 들어간다 — 실측(올원e): 50개 중 12개(24%)가 두 밴드에서 각각 판독되고 뒤
밴드 결과가 앞 것을 조용히 덮었다. **겹친 높이가 가장 큰 밴드 하나에만** 준다. 영역이 밴드
경계에 걸치면 컷을 옮기지 않고 **크롭을 넓힌다**(컷을 옮기면 밀도 분할이 연쇄로 깨진다).

**⑪이 왜 통짜인가.** 밴드가 원래 못 잡는 **대형 장식 타이포**용이다. A/B 실측: 001 은 밴드가
4/4 회수(통짜 0/4)로 압승했지만 002 는 통짜가 2/4(밴드 0/4)로 이겼다. 002 가 놓친 것은 화면을
꽉 채우는 `인생 대박적금이 온다!`, `행운의 777 이벤트` 로, 밴드 경계에서 글자가 잘려 못 읽는다.
작은 글씨는 밴드가, 큰 글씨는 통짜가 유리해 두 패스의 합집합을 쓴다.

<a id="52-정본은-안-덮는다--정확한-범위"></a>

### 5.2 "정본은 안 덮는다" — 정확한 범위

정본이란 `Line` 의 네 필드다: `text` · `bbox` · `confidence` · `source`.
**이 넷은 OCR/디지털이 준 값에서 절대 안 바뀐다.** ⑩⑫⑬ 어느 것도 여기 쓰지 않는다.

예외가 하나 있다. ⑬의 **유령 중복 제거**는 라인을 **삭제**한다 — 같은 행에 더 높은 신뢰도
라인이 그 가로 구간을 60% 이상 덮으면 중복 검출로 보고 `region.lines` 에서 뺀다. 텍스트를
바꾸는 게 아니라 목록에서 지우는 것. **이번 5문서에서는 0건 발동**했다.

**왜 이 원칙이 생겼나 — 실측 근거.** 예전에는 ⑫⑬이 `line.text` 에 직접 썼다. 그런데 두 단계
다 비결정적이라(스윕이 회수하는 문구가 실행마다 다름) 정본이 실행마다 흔들렸다. 같은 코드·같은
입력 2회 실측(2026-08-03): **정본 484줄 중 2줄이 갈렸고 그 2줄이 전부 이 경로**였다
(002 `이벤트 기간` ↔ `이벤트 기간內`, 올원e `20.2%p:…` ↔ `② 0.2%p : …`).

**최종 값은 STAGE_3 가 정하고, 실제로 후보를 채택한다:**

```
002   max_rate                    정본 '최고연71%'    → 후보 '최고연 7.1%'   → 필드 '연 7.1%'
003   advertiser_bank_name        정본 'NH놓협은행'    → 후보 'NH농협은행'    → 필드 'NH농협은행'
올원e  preferential_rate_conditions 정본 '1O.1%p…'     → 후보 '① 0.1%p…'      → 필드는 후보 쪽
```

**그리고 정본은 그대로 남는다.** 002 의 `rate_mentions`(전수수집 배열)에
`'최고연71% (p1_r014)'` — OCR 오독이 근거 ID 와 함께 산출물에 실려 있다. 감사할 때 "왜 이
값이 됐나"를 되짚을 수 있다.

<a id="53-관계-딱지--코드가-어떻게-판정하나"></a>

### 5.3 관계 딱지 — 코드가 어떻게 판정하나

[truncation.py](../../src/nh_parsing/truncation.py) 한 파일이 전부이고 **모델 호출 없이
문자열 비교만** 한다.

**1단계 정규화** — 글자·숫자만 남기고 원문자는 숫자로 (`①`→`1`):

```
'상품명 NH올원e적금'  →  '상품명nh올원e적금'   (10자)
'NH올원e적금'         →  'nh올원e적금'         (7자)
```

공백·괄호·낫표를 버리는 이유: OCR 은 `[NH대박7적금]`, VLM 은 `「NH대박7적금」` 으로 쓰는 게
흔해서 그걸 "내용이 다르다"로 세면 안 된다.

**2단계 판정 트리** (실제 계산값 포함):

```
정규화 후 같은가?
  └ 예 → same

후보 ⊂ 정본 ?   ('nh올원e적금' ⊂ '상품명nh올원e적금')
  └ 예 → a.index(b) = 3  → 앞에서 3/10 = 30% 사라짐
          뒤에서는          0% 사라짐
          뒤 ≥ 앞 ?  0% ≥ 30% ?  아니오
          → head_drop  "앞 항목명 생략 — 값 자체는 온전"
          (앞·뒤 둘 다 15% 미만이면 표기 흔들림으로 보고 same)

정본 ⊂ 후보 ?
  └ 예 → expanded  "정본보다 많이 읽음 — 누락 회수 가능"
          실측: 정본 '읽어보시기바랍니다'(9자) ⊂ 후보 33자 → 더읽음 73%

둘 다 아니면 → 글자 단위 유사도(difflib) ≥ 0.92 면 same, 아니면 diverged
          실측: '인생대박적금이온대' vs '인생대박적금이온다' → diverged
```

**왜 점수만으로는 안 되나.** 점수(`정밀도`)는 **토큰이 몇 개 겹치나**를 재는데 토큰 집합은
순서를 버린다. 그래서 **뒤가 잘린 판독이 만점을 받는다**:

```
정본 : 예금잔액증명서 발급 당일 및 계좌에 (가)압류 등 법적 지급제한조치, 질권설정 등이…
후보 : • 예금잔액증명서 발급 당일 및 계좌에 (가)압류 등 법적       ← 문장 중간에서 끊김
정밀도 1.0 (만점!)     커버리지 0.59
```

커버리지로 거르면 될 것 같지만 안 된다 — 같은 커버리지 대역에 **무해한 경우**가 섞인다:

```
정본 : 상품명 NH올원e적금     후보 : NH올원e적금      커버리지 0.50
→ 잘린 게 아니라 항목명만 뺀 것. 값은 온전하다.
```

두 경우의 차이는 **"어느 쪽이 없어졌나(앞 vs 뒤)"** 이고, 그건 순서 정보라 점수에 안 남는다.
그래서 위치를 따로 잰다.

**5문서 관계 분포** (저장값 / 최종순서 재계산):

| | same | head_drop | tail_cut | diverged | expanded |
|---|---:|---:|---:|---:|---:|
| 저장값 | 146 | 5 | 8 | 15 | 3 |
| **재계산** | **150** | **8** | **6** | **10** | **3** |

차이 7건의 원인은 §9-② 참조.

## 6. 단계 4 — 정렬과 분류 (⑭⑮)

<a id="61-⑭-읽기순서-정렬"></a>

### 6.1 ⑭ 읽기순서 정렬

정렬 키는 **카드 → 위→아래 → 좌→우**
([llm_view.py::region_order_key](../../src/nh_parsing/llm_view.py#L55)).

**y·x 는 영역 bbox 가 아니라 그 안 라인들의 최소 좌표를 쓴다** (2026-08-04 수정). 레이아웃 검출
박스는 서로 겹치거나 한쪽이 다른 쪽을 품는 일이 있어서, bbox 상단으로 정렬하면 실제 글자가
아래에 있는 영역이 먼저 나온다:

```
001 p1  r069 bbox=[42,5963,590,6097]  가 r065 bbox=[43,5963,589,6040] 을 감쌈
        r069 의 실제 글자는 y=6047~,  r065 의 실제 글자는 y=5965~
        → bbox 로 정렬하면 우대금리 ③이 ①②보다 먼저 출력됐다 (5문서 중 4페이지에서 어긋남)
        → 라인 좌표로 정렬하면 화면에 보이는 순서와 일치 (역순 쌍 0)
```

부수 효과로 `evaluate.py` 의 **"STAGE_3 입력 제외" 표시가 5건 → 1건**으로 줄었다. 골드 문장이
인접 영역 둘에 걸쳐 있을 때 순서가 어긋나면 이어붙인 텍스트에서 문장이 끊겨 "입력에서 빠졌다"로
잡혔던 것이다.

**⑭′ 진단** — 레이아웃이 통째로 놓친 덩어리가 있으면 노트로 남긴다
([layout_gap.py](../../src/nh_parsing/layout_gap.py)). 미배정 낱줄 숫자만으로는 "레이아웃이
깨진 것"인지 "원래 흩어진 화면"인지 모르므로 **응집한 덩어리만** 골라낸다. **감지만 하고
유사 영역으로 승격하지 않는다** — 승격하면 STAGE_3 입력이 흔들리는데, 지금 상태를 검증 없이
위험에 빠뜨릴 이유가 없다.

### 6.2 ⑮ 문서 분류

파일명에서 키워드로 prior 를 만들고(`예금성`: 예금·적금·입출금 / `대출성`: 대출·신용대출·담보),
VLM 에게 이미지와 함께 **"파일명 힌트는 강한 사전확률이다. 이미지에서 명확히 반대되는 증거가
보일 때만 뒤집어라"** 고 지시한다. 결합 결과를 `category_source` 에 남긴다:

```
올원e / 001 / 002   filename_and_vlm   예금성 / 상세·이벤트페이지     conf 1.0
003                 filename           예금성 / 이벤트페이지          conf 0.9
004                 filename           대출성 / (ad_type 없음)        conf None
```

**003 이 `filename` 인 게 좋은 사례다.** VLM 이 남긴 이유 — *"특정 금융상품의 가입 유도보다는
'올원모임' 서비스 이용 활성화를 위한 경품 증정 이벤트"*. VLM 은 상품군을 `기타`/`판단불가` 로
봤고, 코드가 그걸 `None` 으로 바꿔 파일명 prior(`예금성`)를 채택했다. `ad_type=이벤트페이지` 는
VLM 값이 그대로 쓰였다. **한 호출의 두 답 중 하나만 채택한 것**이고 그 사실이 남는다.

004(HWP)는 캔버스가 없어 `classify` 를 아예 안 부른다 → `ad_type=None`.

## 7. STAGE_3 — 별도 프로세스

입력은 `out/llm_view/*.json` + `schemas/*.json`, 출력은 `out/extracted/*.json`.
`tools/run_extract.py` 로 따로 돌린다.

**설계 원칙 3개** ([extract.py:8-14](../../src/nh_parsing/extract.py#L8-L14)):

- **이미지를 넣지 않는다.** 텍스트 정본 + VLM 후보만. 파싱 단계에서 이미 VLM 이 이미지를
  봤고, 여기서 또 보면 판정이 흔들린다.
- **bbox 를 넣지 않는다.** `region_id` 만 주고 근거로 돌려받아 코드가 나중에 되붙인다.
- **호출을 그룹으로 쪼갠다.** 한 번에 57필드를 물으면 뒤쪽 필드가 뭉개진다.

**호출그룹은 광고유형에 따라 다르다:**

```
상세페이지   G1 상품기본(8) · G2 금리(14) · G3 의무고지(15) · G4 위험표현(9)         = 4그룹 46필드
이벤트페이지  위 4개 + G5 이벤트(11, list_of_events)                                = 5그룹 57필드
```

5문서 중 예금성 4건 → 올원e 4호출 + 나머지 3건 × 5호출 = **19호출**.

### 7.1 정본/후보를 어떻게 고르나

**VLM 에게만 맡기지 않지만, 선택 자체는 VLM 이 한다.** 코드는 관계 딱지를 **지시로 바꿔** 준다.

`_render_doc` 가 프롬프트에 이렇게 쓴다:

```
  p1_r016 (본문): 최고 연0.5%p / 1O.1%p:[NH올원e통장]에서 출금하여 신규 시 / …
      [후보-정본과불일치] ① 0.1%p : 「NH올원e통장」에서 출금하여 신규 시 …
       ↑ 관계 딱지가 그대로 이름이 됨
```

그리고 프롬프트 규칙 5 가 **딱지별로 다른 지시**를 준다:

```
[후보-뒷부분잘림]       → 정본을 값으로 쓰세요. 표기만 빌리려면 잘린 뒤는 정본에서 채워 합치세요
[후보-항목명생략]       → 값만 필요한 칸이면 후보를 그대로 써도 됩니다
[후보-정본보다많이읽음]  → 후보 쪽이 유리합니다
[후보-정본과불일치]     → 어느 쪽도 확신할 수 없으니 필수 항목이면 status="uncertain" + note 에 둘 다
```

> 프롬프트에 **"★ 후보 딱지가 곧 지시입니다"** 라고 쓰여 있다. 코드는 값의 우열을 정하지 않고
> **어느 쪽이 위험한지만 말로 바꿔** 넘긴다.

### 7.2 코드 검산 장치 9개

| 장치 | 무엇을 잡나 | 이번 실행 발동 |
|---|---|---|
| `_validate_group_response` | strict 스키마를 실제로 지켰나 (guided decoding 이 100%는 아님) | 0건 |
| `_normalize_status` | 값은 있는데 `status=not_found`, `value="해당없음"` 같은 자기모순 | **15건** (001 11, 002 4) |
| `prune_empty_events` | 값이 하나도 없는 **유령 이벤트** | **1건** (001) |
| `_verify_evidence` | 값이 자기가 댄 근거 영역에 실재하나 (환각) | **5건** 미검증 표시 |
| `_unused_figures` | 광고엔 있는데 어느 값에도 안 실린 수치 | **4건** |
| `input_gap` | 파싱은 됐는데 STAGE_3 입력에서 빠진 영역 | **0건** |
| `_reclassify_already_handled` | 다른 그룹이 이미 뽑은 문구를 "필드 없음"으로 올린 것 | **15건** 재분류 |
| `classify_absences` | `not_found` 를 4분류 | 57건 전부 |
| `ExtractResult.model_validate` | 최종 출력 계약 (실패하면 **파일 안 쓰고 멈춤**) | 통과 |

**`prune_empty_events` 가 001 에서 실제로 발동한 게 중요하다.** 모델이 `event_count=1` 이라고
답해놓고 `events` 배열에는 2개를 보냈고 두 번째는 전 필드가 빈 값이었다. 안 걸렀다면 그 안의
필수 항목 전부가 "미표시"로 올라가 **없는 지적사항 6건**이 만들어졌을 것이다. 001 의 미표시가
2건인 건 이 장치 덕분이다.

### 7.3 부재 4분류

`not_found` 를 한 통에 두면 심의 지적사항(미표시)을 골라낼 수 없다. **코드가 결정론적으로**
가른다 — 스키마 각 필드의 `applicability`(적용조건) + `obligation`(의무등급)을 평가할 뿐
**VLM 을 부르지 않는다.**

001(입출금 통장) 미발견 19건의 내막:

| 근거 코드 | 건수 | 뜻 |
|---|---:|---|
| `conditional` | **8** | 광고가 그 소재를 안 다룸. 방아쇠가 필드 자신이라 없으면 항상 해당없음 |
| `subtype_not_in` | **5** | 입출금 통장엔 성립 안 함 — `early_termination_rate`, `post_maturity_rate`, `contract_period`, `installment_type`, `maturity_interest_example` |
| `subtype_in` | **3** | 특정 유형에만 의무 — `deposit_kind`, `tax_benefit`, `interest_calc_method` |
| `not_judged` | **1** | 광고물 밖의 절차 — `compliance_procedure_declaration` |
| `applicable` | **2** | 조건 다 통과 → **미표시** — `deposit_amount`(권장), `rate_change_possibility`(필수) |

> ⚠️ **`subtype_not_in` 5건이 준법팀 확인이 필요한 항목들이다.** "수시입출식 통장에는 만기
> 개념이 없어 만기후이율이 성립하지 않는다"는 판단은 **조문에 문장으로 없다.** 스키마에
> `basis="derived"` + `why` 로 표시해 두고 `derived_rules()` 로 뽑아 볼 수 있게 했다.
> **검토 없이 굳으면 지적사항을 조용히 삼키는 규칙이 된다.**

**"미표시"는 판정이 아니라 사실 관측이다.** 우리가 넘기는 것은 "표시 의무가 있는 항목이 광고
텍스트에서 발견되지 않았다"는 사실이고, 위반인지·위험도가 얼마인지는 규정과 대조하는 하류
(RAG/DB 엔진 + 심의 담당자)의 몫이다.

### 코드가 **일부러** 판단하지 않는 자리 — 8곳

대부분 **"임계값을 그을 자리가 없었다"는 실측 결론**이다.

1. **⑫ 두 판독의 우열** — 규칙으로 안 정하고 VLM 에게 그 자리를 다시 읽힌다.
2. **`_find_twin` 의 유사도 임계값** — 4문서 전체 스윕 라인에서 진짜 중복과 오탐이 겹쳐
   선을 그을 자리가 없었다:
   ```
   유사도 0.727  '정년드림정약통상)은 제외'   ← 진짜 중복(OCR 오독)
   유사도 0.700  '[NH저축TEENZ]'             ← 오탐(다른 상품)
   최장공통 0.27 '정년드림정약통상)은 제외'   ← 같은 진짜 중복이 최하위
   ```
   좌표로 가르는 것도 안 된다 — 스윕 bbox 는 y_ratio 추정치라 진짜 중복이 1863px 떨어져
   나온 사례가 있었다. 그래서 포함 관계만 쓴다.
3. **카드 개수** — 밀도 3장 vs VLM 2장에서 **VLM 을 채택**하고 불일치만 로그에 남긴다.
4. **관계 딱지** — 라벨만 붙이고 어느 쪽을 쓸지는 안 정한다.
5. **레이아웃 미검출 진단** — 감지만 하고 유사 영역으로 승격하지 않는다.
6. **`_unused_figures`** — 판정이 아니라 검토 신호.
7. **목업(지폐·앱화면) 격리** — 코드 격리가 **없다.** STAGE_3 프롬프트 규칙 8 이 말로 지시하고
   판단은 VLM 이 한다.
8. **미표시 = "위반" 아님** — 사실 관측까지만.

### ② 관계 딱지가 정렬 전 순서로 계산된다 — **✅ 해결 (2026-08-06, `1aee68c`)**

> **수정 완료.** `classify_reading` 을 `_merged_band_read` 밖으로 빼내
> `_finalize_reading_order` 뒤의 별도 패스(`_score_reading_candidates`)로 옮겼다.
> 재파싱 후 **저장값 vs 재계산 불일치 18건 → 0건**(181건 전체 일치).
> 아래는 무엇이 문제였는지의 기록이다.
>
> 옮기면서 하나 더 찾았다 — 정본을 바꾸는 단계가 정렬 말고 **하나 더** 뒤에 있었다.
> 유령 중복 라인 삭제([vlm_direct.py:413](../../src/nh_parsing/vlm_direct.py#L413))가
> 라인을 빼므로, 밴드 판독 시점의 `region.text` 는 두 가지 이유로 최종본이 아니었다.

`classify_reading` 이 밴드 통독 시점에서 돌았는데, 그건
`_finalize_reading_order`([pipeline.py:271](../../src/nh_parsing/pipeline.py#L271))
보다 앞이다. 표의 `라벨|값` 행이 뒤집힌 상태로 비교돼 딱지가 뒤집혔다:

```
[밴드 판독 시점 — 라인 순서 뒤집힘]
  정본 '12 개월 가입기간' → norm '12개월가입기간'
  후보 '12 개월'          → norm '12개월'  (위치 0)
  → 뒤에서 50% 사라짐 → tail_cut  "뒷부분 잘림(50% 소실)"      ← 저장된 값

[최종 정렬 후 — 화면에 보이는 순서]
  정본 '가입기간 12 개월' → norm '가입기간12개월'
  후보 '12 개월'          → norm '12개월'  (위치 4)
  → 앞에서 50% 사라짐 → head_drop  "앞 항목명 생략 — 값은 온전"  ← 맞는 답
```

**영향 규모** — 측정 시점에 따라 값이 다르므로 원인별로 갈라 적는다:

| 재는 방법 | 값 | 무엇을 재나 |
|---|---|---|
| 옛순서 vs 최종순서 (8/5, 당시 코드) | 7건 | 순서 효과만 |
| 옛순서 vs 최종순서 (8/6, 현행 코드) | **11건** / 라인 2개 이상인 후보 99건 | 순서 효과만 |
| 저장값 vs 재계산 (8/6 재파싱 **전**) | 18건 | 순서 + 8/6 오전 커밋(숫자 게이트·폴백 제거) |
| 저장값 vs 재계산 (8/6 재파싱 **후**) | **0건** | — |

7 → 11 로 늘어난 것은 결함이 커진 게 아니라 **판정 코드가 바뀐 것**이다(`1c86add` 숫자
게이트, `6d860ec` 유사도 폴백 제거). `verify_numbers.py --section relation` 이 이 셋을
따로 찍는다 — 한 숫자에 합치면 어느 쪽이 움직였는지 못 본다.

점수(`vlm_reading_score`/`coverage`)는 토큰 집합이라 순서엔 영향이 없지만, 위에서 말한
유령 라인 삭제에는 영향을 받으므로 같은 패스로 옮겼다.

**무엇이 실무 문제였나**: ③ 대조 패널의 "확인 필요" 개수가 부풀고, 위험한 것부터 정렬하는

**2층 대조는 의견이 갈릴 때만 작동한다.** 심의필 번호는 규정상 필수 표기라 실제로 중요한

**같은 문서 안에서 경로가 갈린 대비 사례.** 003 은 심의필 문구를 p1(표지)과 p3(텍스트 슬라이드)

같은 문서 안에서 그대로 드러난 자리다 — `structured` 판정이 왜 이득인지의 실증.

> 골드 미회수 5건을 전부 대조한 결과 **5건 모두 해당 영역은 정확히 검출됐고 글자 한둘이
> 어긋난 것**이었다. "영역을 못 잡았다"는 한 건도 없다.

### ⑤ 역할 판정이 앞 세 층의 정보를 버린다 — **1단계 ✅ 완료 · 2단계 ✅ 측정됨 · 3단계 착수 가능**

> **2026-08-06 진행.** 아래 "고도화 계획 3단계" 중 1·2단계를 끝냈다.
> - **1단계(재료 만들기)**: `Region.layout_score`(엔진 확신도)와 `Region.role_rule`
>   (VLM 이 덮기 전 규칙 판정)을 저장한다. 판정에는 안 쓴다. `0b13f01`
> - **2단계(측정)**: 규칙 vs VLM 이 **어디서** 갈리는지 처음 셌다 — 아래 표.
> - **3단계(프롬프트·검산 추가)**: ⚠️ 로 막아 두었던 전제(1단계 없이 가지 말 것)가
>   해소됐다. 다만 role 이 하류에서 하는 일이 작다는 판단은 그대로다 — 우선순위 문제.
>
> **`layout_score` 는 처음에 225개 전부 비었다.** 원인이 아래 표의 설명("Region 에 받는
> 칸이 없어서")과 달랐다 — 서버가 레이아웃을 **두 형태로** 주는데 확신도가 한쪽에만 온다:
> `parsing_res_list`(우리가 쓰는 목록, 확신도 **없음**) vs `layout_det_res`(중복이라
> 버리던 목록, 확신도 **있음**). 두 목록을 bbox IoU 로 이어 붙여 해결했다. `5d59b87`

역할은 4단계를 거치는데, 마지막 단계가 앞의 셋을 **하나도 안 본다.**

```
① StructureV3        label(8종) + bbox + score 를 준다
② 코드가 초기값       _LABEL_TO_ROLE 사전으로 label → role 9종   regions.py:90
③ 규칙이 다듬음       _refine_role — 유의사항/고지문구/하단20%     role_source="rules"
④ VLM 이 최종 판정    judge_region_roles — role 을 통째로 덮어씀   role_source="vlm"
```

④ 가 프롬프트에 싣는 것은 이게 전부다([vlm_judge.py:113-115](../../src/nh_parsing/vlm_judge.py#L113-L115)):

```python
f'- region_id={r.region_id} y_ratio={y_ratio} 텍스트: "{excerpt}"'
#    ID          세로위치만        앞 4줄·160자
```
\+ 캔버스 축소 이미지 1장.

**있는데 안 주는 것:**

| 데이터 | 지금 어디 있나 | VLM 에 주나 |
|---|---|---|
| StructureV3 `label` | `Region.label` | ✗ |
| StructureV3 `score` | **`Region.layout_score`** (2026-08-06 추가. 그전에는 `parsing_res_list` 에 아예 안 와서 어디에도 없었다) | ✗ |
| 규칙이 정한 초기 role | **`Region.role_rule`** (2026-08-06 추가. 그전에는 VLM 이 덮어써서 사라졌다) | ✗ |
| 규칙 확신도 | `Region.role_confidence` | ✗ |
| x_ratio (가로 위치) | bbox 에서 계산 가능 | ✗ (카드 배정엔 주는데 — [cards.py:84](../../src/nh_parsing/cards.py#L84)) |
| 글자 크기 (bbox 높이 ÷ 줄 수) | 계산 가능 | ✗ |

**즉 "다시 매핑"이 아니라 "처음부터 독립적으로 다시 판정"이다.**

#### label 을 버리는 게 왜 아쉬운가 — 실측 (2026-08-05, 글자 있는 영역 201개)

```
StructureV3 label          최종 role
  text             164       유의사항  63    이미지  14
  paragraph_title   21       본문     62    고지문구  7
  header             5       제목     46    각주      6
  doc_title          4                      버튼      3
  image · footer     4
  text_cluster       2
  hwp_body           1
```

`text` 164개(82%)가 유의사항·본문·각주·버튼·고지문구로 갈라진다 — **이건 label 이 도움이
안 되고 VLM 이 해야 하는 게 맞다.** 그런데 `paragraph_title` 21 · `doc_title` 4 ·
`header` 5 · `footer` 2 는 다르다. StructureV3 가 레이아웃 구조로 판단한 결과이고,
특히 `footer` 는 "고지문구"의 강한 근거인데 VLM 은 그걸 모른 채 텍스트만 보고 다시 정한다.

#### 글자 크기를 안 주는데, 유의사항 정의가 크기다

프롬프트는 유의사항을 "소비자 보호 고지 … **fine-print**"로 정의한다. fine-print = 작은
글씨인데, VLM 에게 주는 건 텍스트 내용과 y_ratio 뿐이다. bbox 높이 ÷ 줄 수로 쉽게 낼 수 있다.

#### 검산이 없다 — 이 모듈 자신이 지적한 부분

[vlm_judge.py:28-29](../../src/nh_parsing/vlm_judge.py#L28-L29) 주석 그대로:

> "그리고 이 단계에는 **검산이 없었다** — 카드배정은 밀도 관측, 낱줄귀속은 좌표 게이트,
> 밴드통독은 관계 라벨로 교차검증하는데 **여기만 VLM 답을 그대로 썼다.**"

| 단계 | VLM 판정 | 코드 검산 |
|---|---|---|
| 카드 배정 | 개수·배정 | 픽셀 밀도로 개수 대조 → 불일치 시 `notes` |
| 낱줄 귀속 | (없음, 좌표만) | 중심점 포함 + 칼럼 겹침 게이트 |
| 밴드 통독 | 재판독 텍스트 | relation 딱지로 정본과 교차검증 |

VLM 이 "본문"이라 해도 **불일치 자체가 기록되지 않았다** — 2026-08-06 부터 `role_rule` 에
남는다.

#### 2단계 측정 — 규칙과 VLM 이 **어디서** 갈리나 (2026-08-06 재파싱)

`verify_numbers.py --section role`. **VLM 판정 199건 중 95건 불일치(52.3% 일치).**

| **유의사항 → 제목** | **10** | ⚠️ **하단 20% 휴리스틱이 제목을 유의사항으로 오판** — 규칙 쪽 결함 |

> - **97.3%** = 같은 판정자(VLM)를 **두 번 돌렸을 때**의 일치 — *재현성*
> - **52.3%** = **서로 다른 판정자**(규칙 4개짜리 폴백 vs VLM)의 일치 — *일치도*
>
> 규칙은 임시 폴백이라 낮은 게 정상이고, 낮다는 것 자체는 VLM 이 틀렸다는 뜻이 아니다.

**가설 하나가 기각됐다.** "레이아웃 엔진이 헷갈린 자리(낮은 `layout_score`)에서 판정도
갈릴 것"이라고 봤는데 실측은 반대다:

가중치로 쓰는 방향은 근거가 없다.

**바로 손댈 수 있는 것 하나** — `유의사항 → 제목` 10건은 규칙의 하단 20% 휴리스틱
([regions.py](../../src/nh_parsing/regions.py) `_apply_role_rules`)이 페이지 아래쪽
제목까지 유의사항으로 찍는 것이다. VLM 이 덮으므로 최종 결과에는 안 나타나지만,
**VLM 이 실패하면 그대로 폴백된다.** 규칙 자체를 손보는 건 값이 싸다.

#### 목업 격리 — 2026-08-05 판단의 정정

8/5 에는 "STAGE_3 가 코드 게이트 없이도 목업 값을 잘 걸러낸다"고 적었다. 근거는 001 앱

**그 관측 자체는 여전히 맞다.** 그러나 8/6 재실행에서 **반대 방향의 실패**가 나왔다:

```
001 경품안내 영역
  화면에 보이는 것 :  지폐 그림(만원권 목업)  +  그 아래 큰 흰 글씨 '20,000원'
  STAGE_3 결과     :  event_prize = '지원금 만원 (고객 전원)'
                                        ↑ 목업 지폐에 인쇄된 글자
  진짜 경품        :  20,000원   →  _unused_figures 로 밀려남
```

**즉 목업 값이 걸러지지 않은 게 아니라, 목업 값이 진짜 값을 밀어냈다.** 우려는 "목업이
필드에 새어 든다"였는데 실제로는 "목업이 정답을 이겼다"였다. 경위는
[산출물 보고서 §5-1](../parsing-output-report.md).

**그래도 보류 판단은 유지한다.** 이 사고의 직접 원인은 목업 격리의 부재가 아니라 **밴드
통독의 배치 오정렬**(영역 5개 후보가 한 칸씩 밀림)이고, 관계 딱지는 `diverged` 로 정확히
경고했는데 STAGE_3 가 그 딱지를 무시했다. 고칠 곳이 둘 다 격리와 무관하다:

1. 파싱 — 배치 오정렬 재발 방지 (알려진 문제)
2. STAGE_3 프롬프트 — `diverged` 후보를 값으로 쓰지 말라는 규칙 5를 실제로 지키게 하기

목업 격리를 넣더라도 **5문서 목업 영역을 눈으로 세어 정답을 만드는 것이 여전히 선행**이다.
지금 게이트를 넣으면 오판이 진짜 심의 대상을 조용히 뺄 수 있어 현재보다 나빠질 수 있다.

## 12. 숫자를 다시 뽑는 법

이 문서의 모든 숫자는 아래 명령이 낸다. 손으로 센 것은 없다.

```bash
uv run python tools/verify_numbers.py                    # 전체
uv run python tools/verify_numbers.py --section parse     # 페이지별 영역·라인·미배정·저신뢰
uv run python tools/verify_numbers.py --section relation  # 관계 딱지 — 원인별로 3개를 따로 찍는다
uv run python tools/verify_numbers.py --section linecand  # 라인 후보 전달 여부
uv run python tools/verify_numbers.py --section role      # 역할 3층 + 규칙 vs VLM 불일치 전이표
uv run python tools/verify_numbers.py --section card      # 카드 게이트 재현 (모델 0회)
uv run python tools/verify_numbers.py --section stage3    # STAGE_3 집계·검산 장치
uv run python tools/verify_numbers.py --json              # 기계 판독용
```

골드셋 채점은 별개 도구다:

```bash
uv run python tools/evaluate.py         # out/json  → 분류 9/9 · 영역검출 43/44 · 문장 237/242
uv run python tools/verify_extract.py   # out/extracted → 필드 회수 43/44 (실행마다 42~43)
```

**모델 호출이 필요한 재실행** (PaddleX + Gemma · WireGuard VPN):

```bash
uv run python tools/run_nhdata.py     # 파싱. 파일별 소요시간 표 + out/_timing.json
uv run python tools/run_extract.py    # STAGE_3
```

> ⚠️ **재현성 100% 가 정확도 100% 가 아니다.** 같은 오답을 두 번 내면 재현성은 100% 다.
> 실제로 이 방식으로 놓칠 뻔한 것들이 있었다 — 낱줄 귀속 로직 변경 때 재현성 검사는 통과했는데
> 미리보기 그림을 눈으로 보니 영역 박스가 좌우 패널 3개를 관통하고 있었다. 지표를 신뢰하면서도
> **원본 이미지 대조를 병행할 것.** §10 의 10·11·12번, 그리고 2026-08-06 의 20·23번이 전부
> 그렇게 찾은 것이다.

> ⚠️ **`--section relation` 의 숫자를 하나로 합치지 말 것.** 세 값이 원인이 다르다:
> `저장값 vs 재계산`(재파싱 후 0 이어야 함 — 회귀 감시) / `순서 효과만`(현행 코드로 두
> 순서를 비교) / `숫자 게이트만`. 합치면 어느 쪽이 움직였는지 못 본다.

> ⚠️ **재실행 전에 `.env` 의 `GEMMA_MODEL` 을 확인할 것.** 게이트웨이가 이름을 바꾸면
> 모든 VLM 호출이 400 으로 죽는데 OCR 은 멀쩡히 돌아 산출물이 그럴듯하게 나온다
> (2026-08-06 실제 사고 — §10). 지금은 러너가 `exit 1` 로 잡지만, 현재 이름은
> `GEMMA_URL` 의 `/chat/completions` 를 `/models` 로 바꿔 GET 해 대조하는 것이 확실하다.
