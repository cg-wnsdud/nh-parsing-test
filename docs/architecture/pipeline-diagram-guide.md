## 2. ② 라우팅

**무엇을 하나**: 이 페이지를 OCR로 읽을지, 디지털 텍스트를 그대로 쓸지 정한다.

**PDF만 판정이 있다.** 판정은 **렌더링 전에** 이뤄진다 — PDF 파일 내부의 텍스트 오브젝트와
이미지 오브젝트를 직접 읽는다(그림으로 찍어서 글자를 찾는 게 아니다). HWP는 이 판정 자체가
없다 — 무조건 사내 파서가 텍스트·표를 정본으로 준다.

데이터 띠의 `→ route='ocr'` 은 올원e적금(PNG)이 판정 없이 바로 OCR 경로로 간다는 뜻이다.
PNG는 애초에 이 판정 대상이 아니다.

<a id="2-1-분기-scan_like--hybrid--structured--hwp-판정없음"></a>

### 2-1. 분기: `scan_like` / `hybrid ⚠` / `structured` / `HWP·판정없음`

**②에서 아래로 뻗은 이 4갈래는 순서가 아니라 "이 중 하나"다.** 화살표가 팬아웃(부채꼴)로
그려진 이유가 그거다 — 하나로 이어지면 "순서대로 다 거친다"로 잘못 읽힌다.

판정 기준 4개를 **위에서부터 먼저 걸리는 것으로** 확정한다:

| 조건 | 판정 | 실제 사례 |
|---|---|---|
| 공백 뺀 글자 20자 이하 | `scan_like` | **001 p1**(0자) · **003 p1**(0자) · **003 p2**(17자) |
| U+FFFD 8개 이상+비율 30%↑ | `scan_like` | 이번 샘플엔 없음 |
| 50자 이상인데 정상문자 10% 이하 | `scan_like` | 이번 샘플엔 없음 (PUA 폰트 방어용) |
| 위 셋 통과 + 이미지면적 50% 이상 | `hybrid` | ⚠️ **이번 샘플에서 0건 — 미검증 경로** |
| 전부 통과 | `structured` | **003 p3** (503자, 한글 317자, 이미지 0%) |

`structured` 로 판정되면 화살표 하나가 더 있다 — 다음 절을 본다.

> 더 보려면 → [walkthrough §2.1 판정 기준 표](pipeline-walkthrough.md#21-pdf--렌더링-전에-파일-내부를-읽는다)

<a id="2-2-점선-structured-면-structurev3-를-건너뛴다"></a>

### 2-2. 점선: "structured 면 StructureV3 를 건너뛴다"

캔버스 위쪽으로 아치처럼 그려진 보라 점선이다. **②에서 곧바로 ⑤로 건너뛴다** — ③(조각 분할)
④(StructureV3)를 아예 안 거친다.

`structured` 는 "PDF 안에 이미 신뢰할 만한 텍스트가 있다"는 뜻이라 OCR을 부를 이유가 없다.
PaddleX 호출이 **0회**다. 대신 레이아웃 블록도 없으므로 ⑤(영역 조립)는 다른 방법(수직 갭
군집)으로 영역을 만든다 — 그 결과가 **003 p3: 영역 2개 · 라인 25개**다. 데이터 띠에 적힌
`🏷003 p3` 가 이 사례다.

> 더 보려면 → [walkthrough §2.3 structured 가 건너뛰는 것](pipeline-walkthrough.md#23-structured-가-건너뛰는-것)

## 3. ③ 조각 분할

**무엇을 하나**: 캔버스가 세로로 너무 길면(4000px 초과) 한 번에 OCR·VLM에 못 보낸다.
어디서 자를지를 정하는 상자다.

**밝기가 아니라 대비(에지)로 잰다.** 색 배경이 깔린 광고에서 "어두운 픽셀=글자"로 재면 배경
전체가 잉크로 잡힌다. 대신 1px 옮긴 이미지와의 차분으로 재면 배경색과 무관해진다.

데이터 띠 `9조각 (y=0,1400,2800…)` — 올원e적금(1122×6429)이 이렇게 잘린다. 조각 높이
상한이 **1600px**인 이유도 있다 — 상한을 빼면 성긴 구간이 2157px 조각이 되고, 그 결과
레이아웃 검출(다음 상자 ④)이 블록을 거칠게 묶는다(002 실측: 블록 84→62개, 작은 영역이
흡수됨).

<a id="4-structurev3"></a>

## 4. ④ StructureV3

**무엇을 하나**: 조각 하나당 PaddleX 를 1회 호출한다. **한 응답에 가는 박스와 굵은 박스가
같이 온다** — OCR 라인(글자 한 줄)과 레이아웃 블록(문단 단위 사각형)이 별도 필드로 함께
돌아온다.

데이터 띠가 이걸 그대로 보여준다:

```
Line '상품명'      bbox [66,863,200,922]   conf 0.99    ← 가는 박스
Block 'text'       bbox [68,865,677,912]                ← 굵은 박스
```

**우리가 정한 건 요청 파라미터 5개뿐**(검출 크기, 병합 모드, 방향분류기 끔 등). 텍스트·좌표·
신뢰도·블록 라벨은 전부 모델이 준 값이고 손대지 않는다.

> 더 보려면 → [walkthrough §3.3 우리가 정한 것 vs 모델이 준 것](pipeline-walkthrough.md#33--structurev3-가-돌려주는-것)

<a id="5-영역-조립"></a>

## 5. ⑤ 영역 조립

**무엇을 하나**: 라인을 굵은 박스(블록) 안에 배정한다. **여기서 굵은 박스가 화면의 "영역"이
된다.**

**판정은 "중심점"이다.** 라인 사각형 두 모서리 좌표의 가운데 점 하나만 계산해서, 그 점이
블록 사각형 안에 있으면 넣는다.

```
블록          bbox = [68, 865, 677, 912]
라인 '상품명'  bbox = [66, 863, 200, 922]
중심 = ((66+200)/2, (863+922)/2) = (133, 892)
68 ≤ 133 ≤ 677 ✓   865 ≤ 892 ≤ 912 ✓   → 넣는다
```

완전 포함이 아니라 중심점만 보는 이유: OCR 박스와 레이아웃 박스는 서로 다른 모델이 그린
사각형이라 몇 px 씩 안 맞는 게 정상이다(위 예시도 라인이 블록 밖으로 2~10px 삐져나와 있다).

데이터 띠 `Region p1_r004 role=본문` — 여기서 태어난 **`region_id`가 ⑨(STAGE_3)까지 그대로
살아간다.** 근거 지목의 단위다.

**중심점을 품는 블록이 하나도 없는 라인은 "미배정"이 된다.** 그게 아래 점선 경로가 존재하는
이유다.

> 더 보려면 → [walkthrough §3.6 중심점 판정](pipeline-walkthrough.md#36--영역-조립--중심점-판정)

<a id="5-1-점선-미배정-낱줄--좌표만-보고-다시-붙인다"></a>

### 5-1. 점선: "미배정 낱줄 — 좌표만 보고 다시 붙인다"

⑤ 박스 아래로 다시 ⑤ 박스로 돌아오는 **자기 루프**다. 순서가 아니라 **시간이 지난 뒤 같은
단계로 되돌아온다**는 뜻이라 이렇게 그렸다.

⑤에서 실패한 라인(중심점을 품는 블록이 없던 것)을 나중에 **더 느슨한 규칙**으로 다시
시도한다: 포함(중심점) 실패 → 같은 칼럼에 있는 가장 가까운 영역에 근접 배정. **VLM 호출
없이 좌표 계산만으로.**

데이터 띠 `🏷001: 58줄 붙음 (포함29/근접29)`. 여기서 "포함 29"가 이상해 보일 수 있다 — ⑤가
이미 실패한 판정인데 왜 되돌림에서는 성공하나? 답은 부수효과다 — 라인을 붙일 때마다 **영역
사각형이 그 라인을 삼키도록 커지기** 때문에, 처리 순서에 따라 나중 라인이 커진 박스 안에
"포함"된 것으로 잡힌다. 이 부수효과가 "영역 bbox가 실제 글자보다 넓다"는 알려진 한계의
원인이다.

> 더 보려면 → [walkthrough §4.3 낱줄 귀속 — 되돌림 경로](pipeline-walkthrough.md#43--낱줄-귀속--되돌림-경로) (박스가 커지는 이유까지 전부)

## 6. ⑥ 구조 판정

**무엇을 하나**: 두 가지를 페이지당 1회로 정한다 — 영역이 몇 번 카드에 속하는지, 영역의
역할이 무엇인지.

**카드**: 좌우로 나란한 패널이 있는지. **개수는 코드**(픽셀 글자밀도)가 세고, **배정은
VLM**이 한다 — 전폭 헤드라인처럼 어느 컬럼에도 안 속하는 요소는 좌표로 못 정하기 때문.

**역할**: 제목·본문·유의사항·고지문구 등 9종. **3층을 거친다** — ① StructureV3 라벨을 역할로
번역(dict 조회) → ② 정규식 3개로 보정 → ③ **VLM 이 페이지 이미지를 보고 최종 판정.** 실측
225개 중 **VLM 199개 · 규칙 폴백 25개**.

데이터 띠 `role: 본문 (VLM 판정)` — 3층까지 갔다는 뜻.

<a id="7-통합-재판독"></a>

## 7. ⑦ 통합 재판독

**무엇을 하나**: VLM 이 OCR/디지털이 읽은 것과 **같은 자리를 다시 읽는다.** 4가지 방식이
있고(아래 분기), **결과는 항상 후보(`vlm_reading`)로만 붙는다 — 정본(`text`)은 절대 안
바뀐다.**

데이터 띠:
```
+ vlm_reading 'NH올원e적금'
+ relation 'head_drop'
```
정본은 `상품명 / NH올원e적금` 그대로 남아 있고, 옆에 후보가 나란히 붙었다. `relation` 은
코드가 둘의 관계를 문자열 비교로 판정한 딱지다(뒷부분 잘림·앞항목 생략·더 읽음·불일치·표기차이
5종).

> 더 보려면 → [walkthrough §5.3 관계 딱지 판정](pipeline-walkthrough.md#53-관계-딱지--코드가-어떻게-판정하나) (판정 트리 전체)

<a id="7-1-분기-밴드통독--통짜스윕--중복심판--저신뢰재판독"></a>

### 7-1. 분기: 밴드통독 · 통짜스윕 · 중복심판 · 저신뢰재판독

넷 다 "VLM에게 다시 읽힌다"인데, **VLM에게 보여주는 그림의 크기**만 다르다.

| | ⑩ 밴드 통독 | ⑪ 통짜 스윕 | ⑫ 중복 심판 | ⑬ 저신뢰 재판독 |
|---|---|---|---|---|
| 보여주는 그림 | OCR 조각과 **똑같은 크롭** | 페이지 **전체 1장** | **그 줄 하나만** 확대 | 같음 |
| 호출 (5문서) | 27회 | 6회 | 14회 | 10회 |
| 성과 | 후보 177건 부착 | 24줄 회수 | 5건 부착 | 5건 부착 |

`⑩`은 문맥(영역 5~10개가 같은 그림)을 보고 고치는 데 강하고, `⑬`은 그 줄 하나를 화면 전체로
확대해서 보므로 작은 글자 오독을 잡는 데 강하다. 001의 `생학해대`→`생활형태`가 그 증거다 —
⑩도 이 영역을 봤지만 못 고쳤고 ⑬이 고쳤다.

⚠️ **`⑬` 데이터 띠의 "3건 유실"**: `⑬`이 만드는 후보(`Line.vlm_reading`, 라인 단위)는
지금 다음 단계(⑧ 읽기순서 → 정제 텍스트)로 안 넘어간다. `⑩`의 후보(`Region.vlm_reading`,
영역 단위)만 넘어간다. 실측 10건 중 3건이 이 경로로 사라진다 — 골드 44필드엔 영향 없지만
설계 의도(하류가 선택한다)와 어긋난 결함이다.

<a id="7-2-빨간상자-정본은-안-덮는다"></a>

### 7-2. 빨간상자: "정본은 안 덮는다"

이 캔버스에서 **가장 중요한 설계 결정**이다. 정본이란 `Line`의 네 필드 — `text`·`bbox`·
`confidence`·`source`. **⑩⑫⑬ 어느 것도 이 넷을 바꾸지 않는다.**

**왜.** VLM 출력은 실행마다 미세하게 달라진다. 정본을 덮으면 같은 광고를 두 번 돌렸을 때
심의 대상 문구가 바뀐다 — 금융광고 심의에 쓸 수 없는 성질이다. 실측(2026-08-03, 같은
코드·같은 입력 2회): 정본 484줄 중 **2줄만 갈렸고, 그 2줄이 전부 옛 방식(정본을 직접 덮던
경로)이었다.**

빨간상자 아래 데이터 띠는 002 의 실제 사례다:

```
정본 '최고연71%'   ← OCR 이 소수점을 잃음
후보 '최고연 7.1%' ← VLM 이 바로잡음
필드 '연 7.1%'     ← STAGE_3 가 후보를 채택
```

**정본은 그대로 남는다.** `rate_mentions`(전수수집 배열)에 `'최고연71% (p1_r014)'` 로 OCR
오독이 근거 ID와 함께 남아 있다 — 감사할 때 "왜 이 값이 됐나"를 되짚을 수 있다. **최종
선택은 다음 상자(⑨의 STAGE_3)가 한다.**

## 8. ⑧ 읽기순서

**무엇을 하나**: 영역을 **카드 → 위→아래 → 좌→우** 순서로 정렬하고, 좌표·신뢰도를 버리고
`region_id`만 남긴다.

데이터 띠 `→ llm_view 투영` — 이 상자를 지나면 자료구조가 바뀐다(다음 상자 ⑨의 첫 산출물).

**정렬 기준이 영역 bbox가 아니라 "그 안 라인들의 최소 좌표"인 이유**: 레이아웃 검출 박스는
서로 겹치거나 한쪽이 다른 쪽을 품는 일이 있다. bbox 상단으로 정렬했을 때 001에서 우대금리
③이 ①②보다 먼저 출력되는 결함이 실측됐고(5문서 중 4페이지 어긋남), 라인 좌표로 바꿔 역순
쌍 0으로 고쳤다.

## 9. ⑨ 산출물

**무엇을 하나**: 여기까지 만든 것을 목적에 맞게 3개 파일로 나눠 쓴다. **합치지 않는 이유가
있다** — 감사에는 틀린 판독도 남아 있어야 하고(그래서 out/json은 정본·후보를 다 담음), LLM

### 9-1. 분기: out/json · out/llm_view · out/extracted

| 파일 | 담긴 것 | 받는 쪽 |
|---|---|---|

좌표를 되붙인다.
